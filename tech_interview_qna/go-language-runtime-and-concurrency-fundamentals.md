# Go Language Runtime and Concurrency Fundamentals

本文对应《AegisMesh 技术面试问题库》里“Go 语言、Go Runtime 与高并发服务问题 / Go 基础和 Runtime”这一大类。这个主题在 `tech_interview_qna` 中没有独立的 Go 专属文件，所以本文件从题号 1 开始；后续同类问题继续沿着本文件编号往下接。内容按面试口述来组织，先给可以直接回答的主线，再补 runtime 边界、工程误区和排查落点。写作参考 Go 官方文档、标准库文档和 runtime 源码，但文件内不单列参考资料。

## 1. Goroutine 和线程有什么区别？

可以先这样答：线程是操作系统内核调度的执行流，goroutine 是 Go runtime 调度的轻量级执行单元。goroutine 最终仍然要跑在真实 OS 线程上，但程序员看到的是 `go f()` 这种语言级并发抽象，而不是直接创建和管理 pthread。Go runtime 会把大量 goroutine 复用到一组 OS 线程上，这就是它能承载很多并发任务的核心原因。

资源成本差别很明显。传统线程通常有较大的固定栈，创建和销毁都要经过内核，线程数量上来后会吃掉内存和调度资源。goroutine 初始栈很小，栈可以按需增长和收缩，所以启动几十万 goroutine 在很多 I/O 型场景下是可行的。注意这里说的是“可行”，不是“没有成本”。goroutine 也要占栈、调度元数据、队列位置和 GC 扫描成本。

调度方式也不同。线程由内核调度，内核负责抢占、阻塞、唤醒和 CPU 分配。goroutine 由 Go scheduler 调度，scheduler 再通过 M 也就是 OS 线程去执行。goroutine 在 channel、mutex、network poller、timer、GC safepoint、系统调用等位置可能让出执行权；长时间运行的 Go 代码也可以被 runtime 抢占，避免一个 goroutine 长期霸占 P。

阻塞行为是面试里要讲清楚的点。goroutine 阻塞在 Go 能识别的同步原语或网络 I/O 上时，通常只会挂起这个 G，承载它的线程可以去执行别的 G。线程阻塞在内核调用上时，内核会换别的线程运行；Go runtime 也会在系统调用路径上尽量释放 P，让其他 goroutine 继续跑。但如果你在 cgo 或不可被 runtime 管理的阻塞调用里卡住，仍然可能占住真实 OS 线程，线程数会被迫增长。

所以二者不是“goroutine 比线程高级”这么简单。线程是操作系统资源和调度对象；goroutine 是 Go 为高并发服务提供的语言级任务对象。goroutine 的优势在轻量、栈可增长、调度和网络轮询集成好；线程的边界在于它是真正被内核调度的执行实体。面试时最好补一句：goroutine 适合大量并发 I/O 和请求编排，但 CPU 密集任务仍然受 `GOMAXPROCS` 和核心数限制。

## 2. Go 的 GMP 模型中 G、M、P 分别是什么？

可以先这样答：G 是 goroutine，表示一段待执行或正在执行的 Go 代码及其栈、状态和调度信息；M 是 machine，可以理解为 OS thread，是实际执行代码的线程；P 是 processor，是执行 Go 代码所需的一组 runtime 资源和调度许可。一个 G 真正运行时，需要一个 M 持有一个 P，然后由这个 M 执行这个 G。

G 不是函数本身，而是 runtime 里的 goroutine 描述对象。它记录 goroutine 的栈边界、当前状态、调度上下文、等待原因等信息。G 的状态可能是 runnable、running、waiting、syscall、dead 等。`go f()` 会创建一个新的 G，把它放入某个运行队列，等待某个 P 上的 M 来取走执行。

M 是 OS 线程。它可以执行用户 Go 代码，也可以执行 runtime 代码、系统调用，或者处于空闲状态。M 的数量不是固定等于 CPU 核数，因为可能有很多线程阻塞在系统调用、cgo 或 runtime 需要的辅助工作里。真正能同时执行用户 Go 代码的 M 数量，主要受 P 的数量限制。

P 是很多人回答时最容易说虚的部分。P 不是 CPU 核心本身，而是 runtime 里的“执行 Go 代码的许可和资源包”。P 持有本地 run queue、部分调度状态、内存分配缓存、timer 等资源。`GOMAXPROCS` 决定 P 的数量，也就决定同一时刻最多有多少个 M 能执行用户 Go 代码。

这三个对象的关系可以这样记：G 是任务，M 是干活的线程，P 是让 M 执行 Go 任务所需的令牌和本地资源。M 没有 P 时不能执行普通 Go 代码；G 没有 M 时只是 runnable 队列里的任务；P 没有 M 时资源空着，runtime 会尽量找或创建 M 来接手。

## 3. Go 调度器为什么需要 P？

可以先这样答：P 的作用是把“有多少任务要调度”和“有多少 OS 线程存在”解耦，同时限制 Go 代码的并行度，并把调度和分配的热点状态分片。没有 P，所有 runnable goroutine 可能都要争一个全局队列，所有线程也更难在系统调用、阻塞和恢复时高效协作。

第一，P 限制并行度。Go 程序里可以有很多 M，因为系统调用和 cgo 可能阻塞线程；也可以有海量 G，因为业务请求会创建 goroutine。但同一时刻真正并行执行 Go 用户代码的数量不应该无限增长。`GOMAXPROCS` 个 P 就像 runtime 的并行执行配额，最多只有这么多个 M 能持有 P 并跑 Go 代码。

第二，P 提供本地队列。每个 P 有自己的 runnable G 队列，新建 goroutine、唤醒 goroutine、继续执行局部任务时，很多操作都可以先落到本地 P，减少对全局调度锁的争用。只有本地队列满、负载不均、需要全局公平性或找不到活干时，才更多依赖全局队列和工作窃取。

第三，P 承载本地资源。内存分配器需要 per-P cache，timer 和调度状态也适合按 P 分片。这样大量 goroutine 并发分配小对象时，不必每次都去抢全局锁。对高并发服务来说，这种分片很关键，因为调度器和分配器本身如果变成热点，业务再怎么优化也会被 runtime 开销拖住。

第四，P 让系统调用路径更稳。一个 M 进入阻塞系统调用时，可以把 P 交出来，runtime 再让别的 M 绑定这个 P 去跑其他 G。等系统调用返回，原来的 M 再尝试拿回 P；拿不到就把自己的 G 放回队列。这套机制让一个线程阻塞不至于把一个并行执行名额长期浪费掉。

所以 P 不是多余的一层抽象。它让 Go scheduler 可以在 M:N 调度里控制并行度、降低全局锁竞争、保存本地缓存，并处理阻塞系统调用带来的线程变化。回答这题时，不要只说“P 是处理器”，要讲出 P 解决了全局队列争用、资源分片和 syscall 释放执行权这几个具体问题。

## 4. Go 的工作窃取是如何提升调度效率的？

可以先这样答：Go scheduler 主要靠每个 P 的本地运行队列降低争用，再用工作窃取解决负载不均。一个 P 本地没有 runnable G 时，不是马上睡眠，而是先查全局队列、network poller、timer，再尝试从其他 P 的本地队列偷一部分 G 过来执行。这样既减少全局锁，又避免某些 P 很忙、某些 P 空闲。

本地队列的好处是快。一个 goroutine 创建另一个 goroutine，通常会把新 G 放到当前 P 附近；当前 P 继续处理相关任务，缓存局部性也可能更好。高并发服务里，所有请求都去抢一个全局 runnable 队列会很糟，队列锁、cache line bouncing 和调度延迟都会上升。

工作窃取补上了本地队列的缺点。只用本地队列会出现不均衡：一个 P 上堆了很多 runnable G，另一个 P 没活干。偷取时，空闲 P 会从别的 P 队列里拿走一批任务，而不是只拿一个。拿一批能摊薄偷取成本，也能让被偷的 P 继续有活干。

这套设计还会控制自旋线程数量。空闲 M 如果一直忙等偷任务，会浪费 CPU；如果太早睡眠，又会增加唤醒延迟。Go runtime 会限制 spinning M，避免在程序并行度很低但 `GOMAXPROCS` 很大时烧掉大量 CPU。调度器的难点就在这里：既要让 runnable G 尽快被执行，又不能为了找活干把 CPU 全花在调度上。

面试里可以把工作窃取和局部性一起讲。它提升效率不是因为“偷”这个动作便宜，而是因为大多数调度先在本地完成，只有不均衡时才跨 P 转移任务。工程上如果你看到大量 goroutine 频繁创建、阻塞、唤醒，或者任务特别碎，调度开销和工作窃取本身也会变成成本，需要用 trace、scheduler latency、goroutine profile 和 CPU profile 去看。

## 5. Go 什么时候会发生协作式或抢占式调度？

可以先这样答：Go 调度既有协作式的一面，也有抢占式的一面。协作式调度发生在 goroutine 主动进入 runtime 可管理的阻塞点或安全点，比如 channel 收发、mutex 等待、timer、网络 I/O、`runtime.Gosched`、GC safepoint、函数调用栈检查等。抢占式调度则是 runtime 发现某个 goroutine 跑太久时，主动要求它停在安全位置，让其他 goroutine 有机会运行。

早期 Go 更依赖协作式调度。如果一个 goroutine 长时间跑纯 CPU 循环，又没有函数调用、没有 channel、没有阻塞点，它可能让同一个 P 上的其他 goroutine 等很久。后来 Go 引入了更强的异步抢占能力，runtime 的 sysmon 可以发现长时间运行的 G，并通过抢占请求让它在合适位置停下来。这样死循环或大循环对调度公平性的伤害小了很多。

但抢占不是任意指令都能打断。runtime 必须保证栈、寄存器、GC root、写屏障和调用状态能被正确理解。运行在系统栈、某些 `nosplit` 函数、cgo、信号处理、关键 runtime 路径里，都可能暂时不可抢占。系统调用里的 goroutine也不是靠普通 Go 抢占来停止，因为它不在执行 Go 代码；runtime 更多是把 P 拿回来，让别的 M 继续执行 Go 任务。

协作式调度在日常代码里仍然很重要。`<-ch`、`select`、`time.Sleep`、网络读写、锁等待都会让 G park，M/P 去执行别的 G。一个健康的高并发 Go 服务，绝大部分等待都应该落在这些 runtime 知道的点上，而不是卡在不可观测的阻塞 C 调用、同步文件 I/O 或自旋循环里。

回答时要避免两个极端：不能说 Go 完全协作式，因为现代 Go 能抢占长时间运行的 goroutine；也不能说 Go 像 OS 线程那样在任意机器指令上随便抢占，因为 runtime 仍然需要安全点和状态约束。更稳的说法是：Go 用协作式阻塞点处理大多数调度，用抢占机制兜住长时间运行的 Go 代码，系统调用和 cgo 则通过释放 P、补充 M 和 sysmon 监控来处理。

## 6. Go 的栈为什么可以动态增长？

可以先这样答：Go goroutine 的栈不是像很多传统线程那样一开始就预留很大的固定栈。goroutine 初始栈很小，函数调用前会检查当前栈空间是否足够；不够时 runtime 会分配更大的栈，把旧栈内容复制过去，并更新相关指针。这样大多数 goroutine 只为自己实际用到的栈付费。

这个设计直接服务于高并发。一个服务如果为每个请求、每个连接、每个异步任务都创建 goroutine，而每个 goroutine 都绑定几 MB 栈，很快就会被虚拟内存和实际内存拖垮。小初始栈加按需增长，让 goroutine 可以承担大量 I/O 等待型任务。

Go 现在使用的是连续栈增长思路。早期 Go 曾使用 segmented stack，后来转向复制式增长的连续栈。连续栈的好处是普通函数调用和栈访问更接近传统模型，不会在每个栈段之间频繁跳转；扩容成本集中发生在栈不够的时候。runtime 也可以在合适时机收缩栈，避免短暂深调用后长期占住大栈。

能动态增长，前提是编译器和 runtime 配合得很紧。编译器会在函数入口生成栈检查，runtime 能识别栈上的指针并在复制栈后修正它们。GC 也要知道每个栈帧里哪些位置是指针，哪些只是普通数据。Go 禁止普通代码把任意地址当成长期稳定的裸指针来玩，这也是为了让栈移动和 GC 精确扫描成立。

所以这题的重点不是“Go 栈会自动扩容”一句话，而是要讲出取舍：小栈让 goroutine 数量可以很大，复制扩容让普通执行路径保持简单，但扩容时需要暂停当前 goroutine、复制栈、修正指针，深递归和大栈对象仍然会带来成本。写高并发服务时，goroutine 很轻，但不是没有内存和 GC 代价。

## 7. Goroutine 栈扩容时需要注意什么？

可以先这样答：普通 Go 代码通常不需要手动关心栈扩容，因为 runtime 会复制栈并修正栈上的 Go 指针。但一旦代码涉及 `unsafe`、`uintptr`、cgo、汇编、`//go:nosplit`、把 Go 指针交给外部系统长期保存，就必须理解栈可能移动。正常的 Go 指针会被 runtime 更新，裸整数形式的地址不会。

第一个风险是把指针转成 `uintptr` 后跨越安全点使用。`uintptr` 只是整数，不是 GC 能跟踪的指针。栈扩容、栈收缩或 GC 发生后，原来的地址可能不再有效。短时间在同一表达式里做 `unsafe.Pointer` 和 `uintptr` 转换有一些允许模式，但把地址存到变量里、放到结构体里、传给异步回调，风险就很高。

第二个风险是 cgo。把 Go 栈上的指针交给 C，如果 C 只在调用期间同步使用，runtime 可以按规则处理；如果 C 把这个指针保存起来，Go 栈移动后它就可能指向旧地址。更麻烦的是，C 代码不受 Go GC 指针规则管理，里面保存的 Go 指针可能让 GC 无法正确判断对象存活。高并发服务里接本地库时，这类问题比普通 Go 代码更难排查。

第三个风险是大栈帧和深递归。栈可以增长，不代表递归可以无限深，也不代表在栈上放巨大数组一定没事。栈扩容要复制已有栈内容；如果每个 goroutine 都经历大栈增长，内存、复制时间和 GC 扫描都会上来。热点路径里最好避免无界递归，避免在函数栈上放很大的临时对象。

第四个风险是 runtime 和汇编里的 `nosplit`。普通函数有栈检查，不够就可以扩容；`nosplit` 函数没有这个入口检查，常用于 runtime 底层、信号处理、早期启动或不能安全扩栈的路径。业务代码很少需要它。乱用 `nosplit` 会把栈空间检查责任转移给作者，出错就是很底层的崩溃。

面试可以这样收束：对普通业务代码，栈扩容是透明能力；对 `unsafe`、cgo、汇编和底层库，栈移动是必须尊重的约束。不要长期保存栈地址，不要把 Go 指针藏进整数，不要让 C 异步持有 Go 栈指针，热点路径也要避免大量 goroutine 同时触发深栈增长。

## 8. Go channel 的基本语义是什么？

可以先这样答：channel 是 Go 里用于 goroutine 之间通信和同步的类型化通道。它有元素类型、方向、容量和关闭状态。发送 `ch <- v` 把值送入 channel，接收 `<-ch` 从 channel 取值，`close(ch)` 表示不会再有新的发送。channel 既是数据传递工具，也是内存同步工具。

channel 是引用类型，零值是 `nil`。对 nil channel 发送或接收会永久阻塞，关闭 nil channel 会 panic。这个特性常被用在 `select` 里动态禁用某个 case：把某个 channel 变量设成 nil，对应 case 就永远不会 ready。但如果不是有意这么做，nil channel 阻塞通常就是 bug。

发送和接收的阻塞规则取决于容量。无缓冲 channel 需要发送方和接收方同时 rendezvous；发送方没有接收者会阻塞，接收者没有发送者也会阻塞。有缓冲 channel 在缓冲区没满时发送可以完成，在缓冲区非空时接收可以完成。缓冲满了发送阻塞，缓冲空了接收阻塞。

channel 还有 happens-before 语义。一次发送会同步到对应接收完成；关闭 channel 会同步到因为关闭而收到零值的接收；无缓冲 channel 的接收也会同步到对应发送完成。也就是说，channel 不只是队列，它能让发送前的写入对接收后的代码可见。很多 Go 代码用 channel 发布结果、传递所有权、通知退出，靠的就是这层内存语义。

但 channel 不是所有并发问题的默认答案。它适合传递消息、所有权、信号和背压；不适合保护复杂共享结构的任意读写。比如一个 map 的多个字段不变量，通常 mutex 更直接；一个高频计数器，atomic 可能更合适；一个单次取消信号，关闭 channel 或 context 更清晰。面试里可以用一句话讲清楚：channel 擅长表达“谁把什么交给谁，以及什么时候可以继续”。

## 9. 无缓冲 channel 和有缓冲 channel 有什么区别？

可以先这样答：无缓冲 channel 的容量是 0，发送和接收必须同时配对；有缓冲 channel 的容量大于 0，可以在缓冲区里暂存值，让发送方和接收方在一定范围内解耦。区别不只是性能，还有同步语义、背压位置和系统行为。

无缓冲 channel 是强同步。发送方直到接收方准备好才完成，接收方直到发送方准备好才完成。它很适合表达交接和确认，例如把任务交给 worker、等待另一个 goroutine 到达某个点、把错误或结果同步返回。因为双方必须 rendezvous，它天然提供背压，生产者不会无限领先消费者。

有缓冲 channel 是有限队列。生产者可以先写入缓冲区，只要缓冲没满就不阻塞；消费者可以稍后读取，只要缓冲不空就不阻塞。它适合削峰、批量生产消费、限制并发数、让短时间抖动不直接传导到上游。容量越大，生产者和消费者解耦越强，但延迟和内存占用也可能更难控制。

内存同步上也有差别。无缓冲 channel 的发送和接收互相卡住，所以很容易用它建立明确的先后关系。有缓冲 channel 的发送完成只说明值进入了缓冲区，不说明接收方已经处理。Go 内存模型对有缓冲 channel 有专门规则：容量为 C 的 channel，第 k 次接收同步到第 k+C 次发送完成。这使得有缓冲 channel 可以表达信号量，但不能把它误当成“发送完成就代表对方已经看见”。

工程里最常见的错误是随手给 channel 加一个很大的 buffer，试图“提高性能”。buffer 可能让压测均值好看一点，但也可能把下游慢的问题藏起来，让请求在队列里排很久，最终超时更晚、内存更高、取消更难传播。容量应该来自业务约束：最多允许多少并发、最多接受多少排队、取消后能否及时清理，而不是凭感觉填一个数字。

## 10. channel close 后读写分别会发生什么？

可以先这样答：`close(ch)` 表示不会再有新的值发送到这个 channel。close 之后，接收方可以继续把缓冲区里已有的值读完；缓冲耗尽后，再接收会立即返回元素类型的零值，并且双返回形式里的 `ok` 为 `false`。发送到已经关闭的 channel 会 panic；重复关闭已经关闭的 channel 也会 panic；关闭 nil channel 同样会 panic。

接收侧要重点看双返回值：

```go
v, ok := <-ch
```

`ok == true` 表示拿到的是发送方真正发送的值；`ok == false` 表示 channel 已经关闭且缓冲也读空了。这对元素类型本身可能有零值的 channel 很重要。只看 `v == 0`、`v == nil` 不能判断是不是关闭，因为发送方也可能真的发送了零值。

`for v := range ch` 会一直接收，直到 channel 关闭并且缓冲被读空。这个模式适合由生产者关闭 channel，消费者 range 退出。注意 close 不是“清空 channel”，也不是“取消所有发送者”。已经在缓冲区里的值仍然会被读到；正在或未来尝试发送的 goroutine 会 panic，所以必须设计清楚谁拥有关闭权。

关闭权通常应该属于发送方，或者属于唯一能确认“所有发送都结束”的协调者。多个发送者都去 close 同一个 channel 是高危模式，因为任何一个发送者提前 close，其他发送者都会 panic。多生产者场景更常见的做法是用 `sync.WaitGroup` 等待所有生产者退出，再由一个单独 goroutine close 输出 channel。

close 也常被用作广播信号，因为从关闭 channel 接收会立即返回。比如 `done := make(chan struct{})`，关闭 `done` 后，所有 `<-done` 或 select 中监听 done 的 goroutine 都能被唤醒。这个模式适合一次性通知，不适合反复开关；需要携带错误原因、deadline 和跨 API 传播时，`context.Context` 往往更合适。

## 11. select 的语义是什么？它如何处理多个 ready case？

可以先这样答：`select` 是 Go 对多个 channel 操作进行等待和选择的语句。每个 case 必须是一次 channel send 或 receive，`select` 会先评估所有 channel 表达式和发送值表达式，然后找出当前可以立即执行的 case。如果没有 case ready，并且有 `default`，就执行 `default`；如果没有 `default`，当前 goroutine 阻塞，直到某个 case ready。

多个 case 同时 ready 时，Go 规范要求从这些可执行 case 中做伪随机选择。这个设计避免总是选择源码顺序里靠前的 case，降低固定优先级带来的饥饿风险。但它不等于严格公平，不保证每个 case 在长期运行中按比例执行，也不保证某个 case 等待若干次后一定被选中。需要强公平或优先级时，要自己在业务层建队列或调度策略。

`default` 会把 `select` 变成非阻塞检查。比如尝试发送失败就走降级路径，尝试接收失败就继续做别的事。它也很容易写出忙等：`for { select { case <-ch: ... default: } }` 如果 default 里没有阻塞、休眠或其他实际工作，就会空转烧 CPU。高并发服务里看到这种代码，要特别警惕。

nil channel 在 select 里很有用。对 nil channel 的收发永远不会 ready，所以把某个 channel 变量设成 nil，就相当于动态关闭对应 case。比如一个输入 channel 已经关闭后，把它设成 nil，避免 select 反复读到零值；或者某个输出暂时不能发送时，把输出 channel 设成 nil，直到条件满足再启用。

面试里还可以补一个细节：select 只解决 channel 多路等待，不自动解决业务原子性。比如从两个 channel 里选一个请求处理，处理过程中仍然可能需要锁、context、幂等控制和错误恢复。select 是调度控制流的工具，不是通用事务机制。

## 12. context.Context 解决什么问题？

可以先这样答：`context.Context` 解决的是跨函数、跨 goroutine、跨进程调用链里的取消、超时、deadline 和请求作用域数据传播问题。它让一次请求的生命周期有一个可以传下去的控制信号：上游取消了、超时了、客户端断开了，下游正在做的数据库查询、RPC、后台 goroutine 都应该知道并尽快停下来。

最典型的场景是服务端请求处理。入口收到 HTTP 或 RPC 请求后拿到一个 ctx，往下调用缓存、数据库、另一个 RPC 服务时都传同一个 ctx 或派生 ctx。调用链上任何一层发现 ctx done，都可以停止等待、释放资源并返回。没有 context，常见问题是调用方已经超时返回，下游还在工作，连接、goroutine、timer 和锁都被白白占着。

context 还统一表达 deadline。超时不是每层自己拍脑袋加一个固定值，而是从入口预算里逐层扣。比如入口剩 200ms，下游就不应该再创建一个 2s 的超时去慢慢等。好的 RPC、数据库和队列客户端都会接受 ctx，利用其中的 deadline 和 cancellation 做及时退出。

`Context.Value` 只适合传请求作用域的元数据，比如 trace id、认证主体、租户、语言区域这类会跨 API 边界传播的信息。它不适合传可选参数、业务配置或大对象。把所有东西塞进 context，会让函数签名看起来简单，实际依赖变得隐蔽，测试和维护都会变差。

使用习惯上，ctx 应该作为第一个参数，通常命名为 `ctx`；不要把 context 存到结构体里长期持有；不要传 nil context，不确定就用 `context.TODO()`；创建带 cancel、timeout 或 deadline 的子 context 后，要在合适位置调用 cancel，释放 timer 和父子引用。context 本身并不杀掉 goroutine，它只是发出信号；你的代码要在 select、I/O 调用或循环里主动观察这个信号。

## 13. context 的取消应该如何在调用链中传播？

可以先这样答：取消应该从入口向下游单向传播。上游创建或接收 ctx，下游函数接受 ctx，并把它继续传给自己调用的 RPC、数据库、缓存、worker 或 goroutine。任何一层不要随便用 `context.Background()` 切断链路，除非它明确要启动一个脱离当前请求生命周期的后台任务，而且这个任务有自己的生命周期管理。

常见写法是入口创建子 context：

```go
ctx, cancel := context.WithTimeout(parent, 200*time.Millisecond)
defer cancel()
```

`defer cancel()` 不只是取消工作，它还释放 timer 和父 context 对子 context 的引用。如果函数提前返回而没有 cancel，子 context 可能一直挂到 deadline 或父 context 取消，短请求量很大时会累积成 timer 和内存压力。

下游循环或阻塞等待要监听 `ctx.Done()`。例如 worker 从队列拿任务时，可以用 `select` 同时等任务和 ctx；调用外部客户端时，优先选择支持 context 的 API；自己封装阻塞库时，要设计退出通道或把阻塞操作放到可控制的边界上。只把 ctx 传进函数，但函数内部从不检查，取消就只是摆设。

错误传播也要清楚。ctx 取消后，`ctx.Err()` 通常是 `context.Canceled` 或 `context.DeadlineExceeded`；如果使用带 cause 的 API，还可以记录更具体的取消原因。业务代码不应该把所有取消都包装成内部错误报警。客户端主动断开、上游超时、服务关闭，处理策略不一样，日志和指标也应该能区分。

还有一个边界：取消是“请求停止等待”的信号，不保证已经发出去的副作用自动回滚。下游服务可能已经写了数据库，只是响应没回来。RPC 重试、事务、幂等键和补偿逻辑仍然要单独设计。面试里说 context 时，最好补上这句，避免把取消传播讲成分布式事务。

## 14. defer 的执行时机是什么？它有什么性能影响？

可以先这样答：`defer` 在执行到 defer 语句时注册一个函数调用，等当前函数返回时执行。这里的“返回”包括正常 return、执行到函数末尾，也包括 panic 导致当前 goroutine 栈展开。多个 defer 按后进先出顺序执行。defer 语句里的函数值和参数会在注册 defer 时求值，不是等到最后执行时才求值。

这个参数求值规则很容易出错：

```go
x := 1
defer fmt.Println(x)
x = 2
```

最后打印的是 1，因为参数在 defer 那一行已经算好了。如果 defer 使用闭包并在闭包里读取外部变量，那读到的可能是函数返回前变量的最终值。面试里如果能主动说出这个差别，说明不是只背“defer 后执行”。

defer 可以修改命名返回值。函数执行 return 语句时，会先给返回值赋值，然后执行 defer，最后真正返回。所以常见模式是 defer 里记录耗时、关闭资源、recover 后把错误写进命名返回值。这个能力有用，但也容易让控制流变隐蔽，尤其是 defer 里改 error 时要写得非常清楚。

性能上，现代 Go 对很多 defer 做了优化，简单 defer 的成本已经比早期低很多。但 defer 仍然不是零成本：它要注册调用、保存参数和状态；在循环里每次 defer 都要等函数返回才执行，不会在每轮循环末尾执行。热点循环里 `defer f.Close()` 可能导致资源释放延后，也可能带来额外开销。这时应该把循环体拆成小函数，或者在确认安全的情况下手动释放。

工程上，defer 最适合资源释放和成对操作：`mu.Lock(); defer mu.Unlock()`、`file.Close()`、`cancel()`、`span.End()`、`recover` 边界。对低频控制路径，defer 提高正确性通常比省那点开销更重要；对纳秒级热路径或高频循环，要用 benchmark 看真实成本，不要凭印象优化。

## 15. panic 和 recover 的边界是什么？

可以先这样答：`panic` 会让当前 goroutine 开始栈展开，沿途执行已经注册的 defer；`recover` 只有在 panic 展开过程中、并且直接在某个 deferred function 里调用时才有效。recover 成功后，当前 goroutine 停止继续 panic，函数按 recover 后的逻辑返回。普通函数里直接调用 recover，或者 defer 调用的函数再间接调用 recover，通常都拿不到正在发生的 panic。

panic 的边界是 goroutine。一个 goroutine 里发生的 panic，不能被另一个 goroutine 的 defer recover 捕获。父 goroutine 启动子 goroutine 后，在父函数里 defer recover，拦不住子 goroutine 的 panic。高并发服务里，如果 worker goroutine 可能 panic，要在 worker 函数最外层自己 defer recover，并把错误转成日志、指标或任务失败结果。

recover 不应该当成普通错误处理机制。Go 的常规错误应该用 error 返回值表达；panic 更适合不可恢复的程序错误、违反内部不变量、初始化失败或框架边界的保护。比如 HTTP server 可以在每个请求 goroutine 外层 recover，避免单个 handler panic 杀掉整个进程；但业务校验失败、数据库错误、下游超时，不应该用 panic 来走正常流程。

recover 后也要小心状态一致性。panic 可能发生在持锁、修改共享结构或写一半响应时。defer 可以释放锁，但不一定能恢复业务不变量；HTTP 响应头可能已经发出，数据库事务可能已经写了一半。框架层 recover 最多把进程保护住，不能自动保证请求语义正确。

面试时可以这样总结：panic 是当前 goroutine 的异常退出路径，defer 会按栈展开执行；recover 只能在同一 goroutine 的 defer 中截获正在展开的 panic。服务端应在 goroutine 边界设置 recover 防护，但业务逻辑仍然应该优先返回 error，并把 panic 看成需要定位的程序缺陷。

## 16. Go interface 的底层结构是什么？

可以先这样答：从语言语义看，interface 表示一组方法约束，某个具体类型只要实现了这组方法，就可以赋给对应接口变量。从 runtime 实现看，一个 interface 值通常可以理解成两个字：动态类型信息和动态值数据。空接口和非空接口的结构略有不同，但核心都是“类型 + 数据”。

空接口也就是 `any`，runtime 里常用 `_type` 指针加 data 指针表示。`_type` 描述动态具体类型，data 指向具体值或保存值的存储位置。非空接口还需要方法集匹配信息，所以通常用 itab 加 data：itab 里关联接口类型、具体类型和方法表，data 指向动态值。方法调用时，可以通过 itab 找到具体方法实现。

这解释了几个常见现象。第一，接口变量可以保存任意实现该接口的具体类型，但调用接口方法时有动态分发成本。第二，接口赋值可能导致装箱，具体值需要放到一个接口表示里；是否逃逸到堆，要看编译器分析。第三，interface 的相等性要看动态类型和值是否可比较，不是所有 interface 值都能比较成功。

还要强调一个边界：runtime 表示是实现细节，不是 Go 规范承诺的 ABI。面试中用“两字结构”解释 nil interface、typed nil、动态分发和逃逸，很有帮助；但写业务代码不能依赖某个版本的内部结构布局。涉及 `unsafe` 操作 interface 内部字段，基本就是和实现细节绑定。

一个好的回答应该把语义和实现分开：语义上，interface 是隐式实现的方法集合；实现上，它通常携带动态类型和动态值，非空接口还带方法表。正是因为 interface 里有动态类型信息，才会出现 `var err error = (*MyErr)(nil)` 这种“看起来是 nil，接口本身却不是 nil”的问题。

## 17. nil interface 和 typed nil 有什么区别？

可以先这样答：nil interface 是接口的动态类型和动态值都为空；typed nil 是接口里已经有了一个动态类型，只是动态值部分是 nil。接口值和 nil 比较时，只有动态类型和值都为空才等于 nil。因此 `var x any = nil` 等于 nil，但 `var x any = (*T)(nil)` 不等于 nil。

最常见的坑发生在 error 上：

```go
type MyErr struct{}
func (*MyErr) Error() string { return "bad" }

func f() error {
    var e *MyErr = nil
    return e
}
```

`f()` 返回的不是 nil error。因为返回时，`*MyErr` 这个动态类型被装进了 error 接口，data 是 nil，但接口的 type 不为空。调用方写 `if err != nil` 会进入错误分支。这是 Go 面试里非常高频的 typed nil 问题。

解决方式是不要把 typed nil 装进接口。函数要返回 error 时，如果没有错误就直接 `return nil`。如果内部拿到的是某个指针类型错误，返回前要判断指针是否为 nil。对其他接口也一样：把 `(*bytes.Buffer)(nil)` 赋给 `io.Reader` 后，接口不等于 nil，后续调用方法是否 panic 取决于该方法能不能处理 nil receiver。

这个问题不是“Go 的 nil 很怪”，而是接口值本来就有两部分。只看 data 是否 nil 不够，还要看动态类型是否存在。反射里也类似，`reflect.ValueOf(x).IsNil()` 只能用于某些 kind，并且 `ValueOf(nil)` 本身是零 Value，处理不当还会 panic。

面试里可以用一句话收束：nil interface 是“没有类型也没有值”，typed nil 是“有类型但值是 nil”。凡是接口比较 nil，都比较的是整个接口值；凡是返回 interface 或 error，都要避免把有类型的 nil 指针包装进去。

## 18. Go map 为什么不是并发安全的？

可以先这样答：Go 内置 map 的设计目标是普通场景下快速、轻量、易用，而不是每次访问都内置同步。map 的桶、溢出桶、哈希种子、扩容和迁移状态都可能在写入时改变；如果另一个 goroutine 同时读或写，就可能看到不一致的内部状态，轻则读到错误结果，重则 runtime 直接报 fatal error。

map 写入不是单个不可分割动作。插入一个 key 可能要算 hash、定位 bucket、写 key/value、更新计数；如果负载因子高，还可能触发扩容或渐进式迁移。删除也会改 bucket 状态。另一个 goroutine 如果同时遍历、查找或写入，可能正好撞到结构变化中间态。这不是给单个字段加原子读写就能解决的。

Go 官方 FAQ 对这个选择讲得很直：大多数 map 不需要多 goroutine 同时修改；如果给所有 map 操作默认加锁，会让普通使用变慢，而且很多需要并发访问的 map 往往只是更大数据结构的一部分，本来就需要外层同步。Go 选择让内置 map 保持快，把同步责任交给使用者。

只读并发是可以的，前提是没有任何 goroutine 修改 map。初始化完成后不再写的 map，可以被多个 goroutine 同时查找和遍历。只要还有写入，包括新增、删除、更新、扩容，所有读写都必须用同一套同步保护。常见做法是 `sync.RWMutex` 保护 map，或者分片 map 降低锁竞争。

`sync.Map` 也不是普通 map 的直接替代品。它适合特定访问模式，比如写一次读很多次的缓存，或者多个 goroutine 操作不相交的 key。需要维护多个 key 之间的不变量、需要类型安全、需要复杂批量操作时，`map + mutex` 往往更清楚。

## 19. sync.Map 适合什么场景？

可以先这样答：`sync.Map` 是为特定并发访问模式优化的并发 map，不是所有 `map + mutex` 的替代品。官方文档里明确说它主要适合两类场景：一个 key 写一次后被读很多次，比如只增长的缓存；或者多个 goroutine 读写、覆盖的是不相交的 key 集合。它的目标是在这些模式下降低锁竞争。

`sync.Map` 内部不是简单地给 map 套一把大锁。它会把读多的部分放在可无锁读取的 read map 里，把新写入或 miss 相关内容放到 dirty map，并在 miss 累积到一定程度时提升。这样读路径常常可以不抢互斥锁，写路径和 miss 路径再走较重逻辑。读多写少、key 稳定时，它能减少热点锁。

但它有几个代价。第一，类型是 `any`，调用方需要类型断言，泛型业务代码里可读性和类型安全不如普通 map。第二，跨多个 key 的复合不变量不好维护，比如“先查 A 再改 B”“批量删除一组 key”“map 大小和另一个字段必须一致”。第三，频繁写同一批 key、频繁删除再插入时，`sync.Map` 未必比分片锁或普通锁更快。

使用 `sync.Map` 也要理解语义边界。`LoadOrStore` 可以解决“没有就初始化”的并发竞争；`CompareAndSwap`、`CompareAndDelete` 适合一些条件更新。但这些操作只对单个 key 提供原子语义，不会让多个 key 的业务操作自动变成事务。Range 也不保证得到某个瞬间的一致快照，不能拿它做严格一致的全量视图。

工程选择可以这样判断：如果是配置快照、只增长缓存、按连接或 endpoint 独立更新状态，`sync.Map` 可能合适；如果是小 map、高频整体更新、需要类型安全、需要维护 size/列表/索引之间的关系，先用 `map + sync.RWMutex` 或分片 map。面试里不要说 `sync.Map` 更高级，要说它是为特定读写模式换取更低争用的工具。

## 20. Go race detector 的原理是什么？

可以先这样答：Go race detector 是动态检测工具。编译或测试时加 `-race`，编译器会在内存读写和同步操作附近插入检测代码，运行时记录访问历史和 happens-before 关系。如果两个 goroutine 并发访问同一内存位置，至少一个是写，并且没有同步关系把它们排序，race detector 就报告数据竞争。

它的思想来自 ThreadSanitizer 一类工具：不靠静态分析穷举所有路径，而是在程序真实运行时观察发生过的内存访问。锁、channel、atomic、goroutine 创建等同步操作会在检测器里建立顺序关系；普通读写会被记录。如果后续出现未同步的冲突访问，就能给出两个访问栈、goroutine 创建栈等信息。

动态检测的边界很重要。race detector 只能发现实际执行到的路径里的 race。测试没覆盖的分支、线上才有的流量组合、某些特定时序，没有运行就不会被发现。所以官方也建议，除了 `go test -race`，还可以把 `-race` 构建出来的程序放到接近真实的负载下跑一段时间。

`-race` 也有成本。它会显著增加 CPU、内存和运行时间，改变调度时序，所以一般不在正式生产主路径长期打开。它可能让某些超时测试变慢，也可能因为检测开销改变并发交错。这个成本不是缺陷，是动态插桩工具的正常代价。

面试里还要区分数据竞争和业务竞态。race detector 找的是未同步内存访问；它找不到所有“时序导致业务错”的问题。两个请求都通过事务合法地扣库存，但业务上还是超卖，这可能没有 Go data race。并发正确性仍然需要事务、幂等、锁顺序、状态机测试和压测来一起保证。

## 21. Go GC 的基本流程是什么？

可以先这样答：Go GC 是并发标记清扫式 GC，目标是尽量缩短 stop-the-world 时间，同时把 GC CPU 和内存增长控制在可预测范围内。一次 GC 周期大体包括：触发和准备、短暂 STW 启用标记、并发标记、标记终止的短暂 STW、并发清扫，以及后台 scavenger 视情况把内存还给操作系统。

触发时机主要由 heap target 和 pacer 控制。`GOGC` 决定下一次 GC 的目标堆大小，粗略理解就是在上次存活堆的基础上允许新分配多少。`GOGC=100` 常被理解为目标堆约为 live heap 的两倍再触发下一轮。Go 还支持软内存限制，runtime 会在吞吐和内存之间调整。高并发服务里，调 `GOGC` 本质是在换 CPU、内存和延迟。

标记开始时，runtime 会短暂 STW，切换到标记状态，打开写屏障，准备扫描 root。root 包括全局变量、各 goroutine 栈、寄存器里可见的指针等。随后进入并发标记，GC worker 和 mutator assist 一起追踪从 root 可达的对象。mutator 也就是业务 goroutine 仍然运行，但分配太快时可能被要求 assist，帮 GC 做一部分标记工作。

并发标记结束前需要 mark termination。runtime 会再次短暂 STW，确认标记队列清空，处理剩余工作，关闭本轮标记相关状态。之后进入清扫阶段，把未标记的对象所在 span 回收到分配器可复用的空闲空间里。清扫通常是并发和按需推进的，不是一次性长时间停顿。

要回答得像做过线上服务，还要补上观测点。GC 对延迟的影响不只来自 STW，也来自并发标记占 CPU、mutator assist、写屏障开销、栈扫描、堆变大导致 cache 局部性变差。排查时看 `gctrace`、runtime/metrics、pprof heap/allocs、trace 里的 GC assist 和 STW，而不是只盯着“STW 几毫秒”。

## 22. 三色标记法是什么？

可以先这样答：三色标记法是描述可达对象标记过程的一种模型。白色表示还没发现的对象，灰色表示已经发现但它引用的对象还没扫描完，黑色表示对象本身和它指向的对象都已经处理过。GC 从 root 开始，把可达对象逐步从白变灰、从灰变黑；标记结束时仍然白色的对象，就认为不可达，可以在清扫阶段回收。

这个模型的关键不是颜色本身，而是不变量。标记过程中要避免“一个黑色对象直接指向白色对象，而 GC 又不知道这个白色对象”的情况。因为黑色对象已经不会再被扫描，如果它新指向一个白对象且没有被记录，这个白对象可能明明可达却被回收。并发 GC 最大的麻烦就在这里：业务 goroutine 一边改指针，GC 一边标记。

灰色集合可以理解成待办队列。GC 每次取一个灰对象，扫描它的指针字段，把发现的白对象变成灰，然后把自己变成黑。队列为空时，说明从 root 可达的对象都扫描过了。这个过程在单线程 stop-the-world GC 里相对简单；在 Go 这种并发 GC 里，mutator 会不断新增、删除、覆盖指针，所以需要写屏障维持正确性。

三色标记还能解释为什么 GC 不等于“按引用计数减到零”。GC 关心的是从 root 可达性，不是某个对象有几个引用。两个对象互相引用，但从任何 root 都到不了，它们最终仍然是白色，会被清扫。反过来，一个对象只有一条引用，只要这条引用在 root 可达路径上，它就不能被回收。

面试里可以用一句话收束：三色标记把对象分成未发现、已发现待扫描、已扫描三类；并发环境下，为了不漏标，需要写屏障维护“黑对象不能静默指向白对象”这类不变量。讲到这里再引出 Go 的混合写屏障，就比较自然。

## 23. 写屏障解决什么问题？

可以先这样答：写屏障解决的是并发 GC 期间 mutator 修改指针导致 GC 漏标的问题。GC 在标记时，业务 goroutine 还在运行，可能把一个已经扫描完的黑对象指向一个白对象，也可能删除某条还没被 GC 看到的引用。如果没有屏障记录这些变化，GC 可能把仍然可达的对象当垃圾回收。

写屏障不是硬件内存屏障，也不是 Go 内存模型里的 acquire/release。它是编译器和 runtime 在写指针时插入的一段逻辑，用来通知 GC：这里有一个指针关系发生了变化，需要把相关对象标记或放进队列。普通整数写入不需要 GC 写屏障，只有可能影响堆对象可达性的指针写入才相关。

Go 使用过不同的写屏障策略，现代实现可以概括为混合写屏障。它结合了插入屏障和删除屏障的思路：写入新指针时关注新对象，覆盖旧指针时也关注旧对象，避免并发标记中某条可达路径被 mutator 改掉后 GC 再也追不上。这样 Go 可以把大部分标记工作和业务 goroutine 并发执行，减少长时间 STW。

写屏障有成本。GC 标记期每次堆指针写入都可能多做一点工作，所以指针密集的数据结构、频繁更新的大对象图、很多短命指针关系，都会增加 GC 压力。很多 Go 性能优化会关注减少不必要的堆对象、减少指针字段、用值类型或索引替代指针链，本质上也在降低 GC 和写屏障负担。

回答这题时要避免把写屏障说成“保证多线程可见性”。它保证的是 GC 正确追踪对象引用，不是业务 goroutine 之间的同步。两个 goroutine 共享变量仍然需要 mutex、channel 或 atomic。写屏障属于内存管理机制，内存模型同步属于并发正确性机制，名字都叫 barrier，但问题完全不同。

## 24. 逃逸分析是什么？

可以先这样答：逃逸分析是 Go 编译器判断一个变量能不能安全放在栈上的过程。如果一个值的生命周期不会超过当前函数调用，且不会被未知位置长期引用，编译器可以把它放在栈上；如果它可能在函数返回后仍然被访问，或者编译器无法证明安全，就必须放到堆上，让 GC 管理它的生命周期。

逃逸和写法不总是直觉一致。`new(T)` 不一定分配到堆上，局部变量取地址也不一定逃逸；关键看这个地址有没有离开当前函数的可证明范围。比如返回局部变量指针通常会逃逸，把局部变量地址存进全局变量会逃逸，把变量捕获到可能比当前函数活得更久的闭包里会逃逸，传给接口或未知函数也可能因为编译器看不透而逃逸。

goroutine 是逃逸分析里的高频触发点。把局部变量传给新 goroutine，当前函数可能已经返回，而 goroutine 还在使用它，变量就不能简单放在当前栈帧里。闭包捕获循环变量也经常引出问题：不仅可能逃逸，还可能因为捕获的是同一个变量而造成逻辑错误。现代 Go 已经修正了一些循环变量捕获语义，但理解生命周期仍然重要。

逃逸的代价主要是分配和 GC。堆分配比栈分配更贵，堆对象还会增加 GC 扫描、标记、清扫和 cache 压力。对高并发服务来说，每个请求多几个小对象分配，QPS 上来后就是明显的 CPU 和尾延迟成本。很多热路径优化不是为了“少用指针”，而是为了让对象生命周期更短、更局部，减少堆逃逸。

但不要为了逃逸分析把代码写得很别扭。编译器会随版本、内联结果、泛型实例化和调用图变化做不同判断。正确做法是用 `-gcflags=-m`、benchmark 的 `allocs/op`、pprof allocs 来验证热点路径，再做局部调整。逃逸分析是性能工具，不应该凌驾于清晰的所有权和接口设计之上。

## 25. 如何判断变量分配在栈上还是堆上？

可以先这样答：最直接的办法是看编译器逃逸分析输出。常用命令是 `go build -gcflags="-m=2"`，或者跑测试时用 `go test -gcflags=all=-m`。输出里会出现 `escapes to heap`、`moved to heap`、`does not escape` 之类的信息，告诉你编译器为什么把某个值放到堆上或保留在栈上。

不过 `-m` 输出要结合上下文看。它会受到内联影响：函数被内联后，调用边界消失，原本看起来会逃逸的对象可能不逃逸；没有内联时，编译器看不到被调用函数内部行为，就可能保守地让参数逃逸。泛型、接口调用、反射、闭包和方法值也会让输出变得复杂。不要只截一行 `escapes to heap` 就下结论，要看原因链。

第二个办法是用 benchmark 验证分配。`go test -bench=. -benchmem` 能看到 `B/op` 和 `allocs/op`。如果你改了一段代码，逃逸输出说少了堆分配，benchmem 也显示每次操作分配次数下降，这个证据就比较强。反过来，逃逸输出很多但不在热点路径上，可能没必要动。

第三个办法是看线上或压测的 allocation profile。pprof 的 `alloc_space` 看累计分配量，`alloc_objects` 看对象数量，`inuse_space` 看当前存活堆。高 QPS 服务里，短命小对象会在 `alloc_objects` 里很明显；长寿命缓存对象会在 `inuse_space` 里更明显。逃逸分析告诉你编译期原因，pprof 告诉你运行期影响。

经验判断也有帮助，但只能当线索。返回局部变量地址、把值存到 interface、闭包捕获、启动 goroutine、把指针放进堆对象、反射调用、不可内联的大接口边界，都可能让变量逃逸；纯局部计算、固定大小临时值、没有被外部保存的对象，通常可以在栈上。但最终还是以编译器输出和基准测试为准。

## 26. Go 的 netpoller 解决什么问题？

可以先这样答：netpoller 解决的是大量网络 I/O 等待不能占住大量 OS 线程的问题。Go 的网络连接通常被设置为非阻塞 fd；当 goroutine 执行网络读写但当前不可完成时，runtime 会把这个 goroutine park，把 fd 注册到平台 poller。等 epoll、kqueue、IOCP 等机制通知 fd 可读可写，runtime 再把对应 goroutine 放回 runnable 队列。

没有 netpoller，大量连接等待网络数据时可能需要大量阻塞线程。每个线程都有栈、调度和内核资源成本，几十万连接会很难承受。有了 netpoller，等待 I/O 的单位变成 goroutine，而不是 OS 线程；少量线程就可以承载大量连接的等待和唤醒。

netpoller 和 Go scheduler 是集成的。调度器找不到本地 runnable G 时，会检查网络轮询结果；timer 到期、deadline 触发、fd ready 都可能唤醒对应 goroutine。网络 I/O 对业务代码看起来像阻塞调用：`conn.Read` 没数据就等；但底层不是让 OS 线程傻等，而是把 G 挂起，让 M/P 去跑别的任务。

边界也要说清楚。netpoller主要覆盖 Go runtime 管理的网络 fd，不代表所有阻塞操作都能被它处理。普通磁盘文件 I/O、某些系统调用、cgo 调用、本地库阻塞，可能仍然占住线程。不同平台的底层机制也不同，Linux 是 epoll，BSD/macOS 是 kqueue，Windows 是 IOCP，语义和实现细节会有差异。

排查高并发网络服务时，netpoller 相关问题通常表现为 goroutine 大量停在网络读写、deadline 设置不合理、连接泄漏、fd 数耗尽、poller 唤醒延迟、或者业务层没有及时消费连接。看 goroutine dump、runtime trace、网络指标、fd 数和 pprof，比单纯看线程数更有用。

## 27. Go 中 blocking syscall 对调度器有什么影响？

可以先这样答：Go runtime 会尽量把 blocking syscall 对调度器的影响限制在当前 M 上。当一个 goroutine 进入系统调用时，承载它的 M 可能会释放 P，P 被其他 M 接手继续运行别的 goroutine。这样一个线程卡在内核里，不会直接浪费一个 Go 并行执行名额。系统调用返回后，原 M 再尝试重新获得 P；拿不到就把 G 放回可运行队列等待调度。

这就是 GMP 里 P 的价值之一。没有释放 P 的机制，一个长时间阻塞的 syscall 会让对应 OS 线程和执行 Go 代码的许可一起卡住，其他 runnable goroutine 即使很多也没法用这个并行名额。释放 P 后，runtime 可以创建或唤醒别的 M 来绑定 P，继续跑 Go 代码。

但 blocking syscall 不是完全免费。首先，阻塞线程本身还在，占用内核线程资源和栈。大量 goroutine 同时进入长阻塞 syscall，runtime 可能创建很多 M，线程数会上升。线程多了以后，内核调度、栈内存、cgo 交互和排查复杂度都会增加。

其次，不是所有阻塞都能被 runtime 优雅处理。Go 标准网络 I/O 通常走 netpoller，不需要每个连接占一个线程；但 cgo 调用、某些文件系统调用、第三方 C 库、`LockOSThread` 后的调用，会让调度行为更复杂。特别是 cgo 长时间阻塞时，Go 可以补充线程跑其他 G，但被 C 卡住的线程还是被占着。

面试里可以这样回答边界：Go 对 blocking syscall 的基本策略是“G 进入 syscall，M 可能失去 P，P 被拿去执行别的 G；syscall 返回后再抢 P 或重新入队”。这让系统调用不会轻易阻塞整个调度器，但大量长阻塞 syscall 仍然会增加 OS 线程数和资源压力。设计服务时要优先使用 runtime 支持的非阻塞网络 API，给外部调用加 timeout，并监控线程数和 syscall 阻塞。

## 28. Go 的 sync.Mutex 有哪些状态？

可以先这样答：从公开 API 看，`sync.Mutex` 只有锁定和未锁定两种可观察状态；它不是可重入锁，也不和某个 goroutine 绑定，谁 Lock 谁 Unlock 不是 runtime 强制的所有权模型。但从内部实现看，Mutex 的 state 里编码了多个 bit：locked、woken、starving，以及 waiter count。它还分 normal mode 和 starvation mode。

无竞争时路径很短，Mutex 通过 CAS 把 state 从 0 改成 locked 就成功，通常不进入内核。竞争出现后，等待者数量会增加；goroutine 可能先自旋一小段时间，希望持锁者很快释放。如果不适合自旋，或者自旋失败，就通过 semaphore 机制阻塞，等待 unlock 唤醒。

normal mode 追求吞吐。等待者大体按 FIFO 排队，但被唤醒的 goroutine 并不直接拥有锁，还要和新来的 goroutine 竞争。新来的 goroutine 已经在 CPU 上运行，可能更容易抢到锁，所以 normal mode 吞吐较好，但极端竞争下老等待者可能一直输。

starvation mode 用来限制尾部等待。Go 的内部实现里，如果某个等待者等锁超过大约 1ms，就可能把 Mutex 切到 starvation mode。在这个模式下，unlock 会把锁的所有权直接交给队列前面的等待者，新来的 goroutine 不再抢锁也不自旋，而是排队。这样能避免病态饥饿，但吞吐会下降，所以当等待情况缓解后会切回 normal mode。

面试里不要只背 bit 名。最好说清楚这几个状态服务于什么目标：locked 表示锁被持有，woken 避免重复唤醒，waiter count 记录等待者，starving 在高竞争下牺牲吞吐换公平性。工程上如果 mutex profile 显示锁竞争严重，解决办法通常不是研究这些 bit，而是缩短临界区、降低共享写、分片、copy-on-write 或改队列模型。

## 29. Go 的 RWMutex 如何处理写者饥饿？

可以先这样答：Go 的 `sync.RWMutex` 允许多个读者同时持有读锁，或者一个写者独占持有写锁。为了避免写者一直被源源不断的新读者挡住，当有 goroutine 调用 `Lock` 等写锁时，后续新的 `RLock` 会被阻塞，直到等待的写者获得并释放写锁。也就是说，Go 的 RWMutex 在写者等待时会挡住新读者，让已有读者退场后给写者机会。

如果不这么做，读多写少场景可能出现写者饥饿：读者不断进来，每个读者都很短，但总有读者持锁，写者永远等不到所有读者清空。RWMutex 的策略是，写者到来后关上“新读者入口”，只等当前已经持有读锁的读者释放。等 active readers 归零，写者获得锁。

这个策略降低了写者饥饿风险，但也有代价。只要有写者在等，新读者会被挡住，即使当前系统读请求很多、写者还没真正执行。写操作如果很慢，会让后续读请求排队，读延迟抖动明显。读多写少不代表 RWMutex 一定比 Mutex 快；如果读临界区很短、写者频繁、CPU 核数不多，RWMutex 的计数和唤醒成本可能抵消收益。

RWMutex 还有几个边界。它不能从 RLock 升级到 Lock，否则很容易死锁；也不能把写锁降级成读锁作为一个原子动作。递归读锁也要小心：当有写者等待时，新的读锁会被阻塞，如果同一个 goroutine 已经拿着读锁又试图再次 RLock，可能把自己卡住。官方文档明确提醒了这些限制。

回答这题可以这样收束：Go RWMutex 用“写者等待时阻止新读者进入”的方式避免写者被读流量无限饿死。它适合读临界区相对长、读多写少、共享状态清晰的场景；不适合写操作慢、读写都很短、需要锁升级或维护复杂跨字段不变量的场景。

## 30. Go atomic 包的使用场景是什么？

可以先这样答：`sync/atomic` 提供的是低层原子内存原语，适合实现单变量或少量变量的同步算法，比如计数器、状态标志、一次性发布指针、引用 copy-on-write 快照、无锁数据结构里的 CAS。它不是 mutex 的全面替代品；如果要保护多个字段之间的不变量，通常应该先用 mutex、channel 或更清晰的所有权设计。

Go atomic 的一个重要特点是内存语义相对简单。标准库文档说明，Go 的原子操作表现得像有一个全局顺序一致的原子序；如果一个原子操作的效果被另一个原子操作观察到，前者 synchronizes-before 后者。这比 C++ 那种可选 relaxed/acquire/release/seq_cst 的模型更少选择，也更不容易写错，但仍然需要谨慎。

典型场景一是计数和指标。例如请求数、错误数、inflight 数，可以用 `atomic.Int64.Add` 或 `atomic.Uint64.Add` 更新，用 `Load` 读取。但高竞争计数器也可能因为 cache line bouncing 成为热点，必要时要做分片计数，按 P、按 shard 或按 worker 聚合。

典型场景二是状态发布。比如用 `atomic.Bool` 表示关闭状态，用 `atomic.Pointer[T]` 发布不可变配置快照，写线程构造完整新对象后原子替换指针，读线程原子 Load 后只读快照。这类 copy-on-write 模式读路径很轻，但要求被发布对象后续不再原地修改，否则读写又回到数据竞争。

典型场景三是实现并发原语或无锁结构。CAS、Swap、Load、Store 可以实现自旋锁、once-like 状态、无锁栈队列等。但这类代码难点不在“会调用 CAS”，而在 ABA、内存回收、线性化点、退避、false sharing 和证明正确性。业务代码除非真的在热点路径并且有测试和压测支撑，否则不要轻易手写无锁算法。

最后要强调使用规则：同一个变量一旦用 atomic 并发访问，所有并发访问都应该走 atomic 或同一把锁保护，不要一边普通读写一边 atomic；atomic 只保证单次原子操作和相关内存顺序，不保证一组业务步骤原子；不要为了省一把锁把代码写到没人能证明。Go 内存模型那句建议很实用：不要太聪明。
