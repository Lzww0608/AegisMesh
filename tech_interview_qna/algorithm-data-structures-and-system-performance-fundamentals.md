## 1. 哈希表的平均复杂度和最坏复杂度分别是什么？

可以先这样答：哈希表查找、插入、删除的平均复杂度通常说是 `O(1)`，但这个 `O(1)` 有前提：哈希函数要把 key 分散得足够均匀，装载因子要控制在合理范围内，冲突链或探测序列不能太长。最坏情况下，如果大量 key 都落到同一个桶，普通哈希表的查找和插入会退化到 `O(n)`。

平均 `O(1)` 更准确地说是摊还意义上的平均成本。哈希表扩容时要重新分配桶、搬迁元素、重新建立索引，这一次操作可能是 `O(n)`；但扩容不是每次操作都发生，把扩容成本摊到多次插入上，单次插入仍然可以近似看成常数。面试里如果只说“哈希表就是 `O(1)`”，容易被追问扩容、冲突和恶意输入。

最坏复杂度还取决于实现。传统拉链法里，一个桶后面挂链表，所有 key 都冲到同一个桶时就是线性扫描。开放寻址里，如果表接近满、探测序列很长，也会退化得很明显。一些实现会做额外保护，比如当桶内元素很多时改成树结构，或者对字符串哈希加随机种子来缓解 hash flooding，但这些是具体实现的防御手段，不是哈希表这个抽象天然保证的复杂度。

工程上更应该关注四个指标：哈希函数质量、装载因子、冲突处理方式和扩容策略。内存型缓存、路由表、连接表、去重集合都常用哈希表，因为大部分时候它用一点额外空间换来了非常短的访问路径。但在高并发服务里，还要考虑锁分片、CPU cache、对象分配、rehash 暂停和热点 key。哈希表快，不代表它没有尾延迟。

如果面试官继续追问，可以这样补：平均复杂度是理想分布和受控装载因子下的摊还 `O(1)`；最坏复杂度可以到 `O(n)`，有些工程实现会把桶内结构树化把单桶查找控制到 `O(log n)`，但这不是所有哈希表都有的保证。

## 2. 哈希冲突有哪些解决方式？

哈希冲突就是不同 key 算出了相同桶位置。解决冲突的第一类方法是拉链法，也叫 separate chaining：桶里不直接放单个值，而是放链表、数组、小型树或其他容器。查找时先定位桶，再在桶内比较原始 key。它的优点是删除简单，对装载因子比较宽容；缺点是指针跳转多，cache locality 较差，桶太长时会拖慢尾延迟。

第二类是开放寻址。所有元素都放在同一个数组里，冲突后按规则找下一个位置。线性探测实现简单、局部性好，但容易出现连续堆积；二次探测能缓解一部分聚集；双重哈希用第二个哈希函数决定步长，分布更灵活。开放寻址对装载因子更敏感，删除也麻烦，通常要引入 tombstone，否则会断掉探测链。

第三类是更偏工程优化的开放寻址变体。Robin Hood hashing 会让探测距离长的元素“抢”探测距离短的位置，目标是降低最大探测长度，让查询尾延迟更稳定。Cuckoo hashing 用多个候选位置，插入时可能把已有元素踢到它的另一个候选位置；查询路径短，但插入可能触发连锁搬迁，失败时需要扩容或重哈希。这些方法都在吞吐、尾延迟、内存占用和实现复杂度之间取舍。

第四类是从源头减少冲突。选择更好的哈希函数，使用随机化 seed，控制装载因子，提前按容量初始化，分批或渐进式 rehash，都能降低冲突带来的抖动。对不可信输入，比如外部请求参数、HTTP header、JSON 字段名，哈希表还要考虑 hash flooding 攻击：攻击者故意构造大量冲突 key，让服务 CPU 被桶内比较耗尽。

所以这题不要只背“链地址法和开放地址法”。更稳的答法是：拉链法简单稳，开放寻址局部性好但更怕高装载，Robin Hood 和 Cuckoo 关注探测长度和查询路径，树化、随机哈希、扩容和限流是工程保护。具体选哪种，看 workload 是读多写少、写多读少、内存紧张、key 是否可信、是否要求稳定尾延迟。

## 3. 一致性哈希为什么适合分布式缓存？

一致性哈希适合分布式缓存，核心原因是节点变化时 key 的映射不会大面积重排。普通取模分片通常写成 `hash(key) % N`。一旦缓存节点数从 `N` 变成 `N+1`，大部分 key 的目标节点都会变化，结果就是大量缓存同时 miss，后端数据库或服务会被回源流量打穿。

一致性哈希把哈希空间看成一个环。节点和 key 都落到环上，key 顺时针找到的第一个节点就是负责节点。新增节点时，新节点只接管自己和前驱之间的一段 key；删除节点时，这段 key 转给后继节点。这样受影响的是局部 key，而不是全量 key。对缓存来说，这一点很重要，因为缓存最怕扩容、缩容、故障恢复时突然制造大面积冷启动。

真实系统通常不会只给每台机器一个点，而是使用虚拟节点。虚拟节点把一台物理机映射到环上的多个 token，可以让数据和流量更均匀，也能按机器容量分配不同数量的 token。大机器多放一些虚拟节点，小机器少放一些，负载就更接近容量比例。没有虚拟节点时，随机落点可能导致某些节点负责很大的区间，缓存命中率和内存压力都会不均衡。

一致性哈希解决的是“key 到节点的稳定映射”，不是缓存系统的所有问题。它不能自动解决热点 key、缓存击穿、数据复制、节点健康检查、客户端 ring 版本不一致、迁移期间双读双写、跨机房容灾这些问题。比如一个超级热门商品详情 key，无论哈希到哪台机器，都会把那台机器打热；这时需要副本、热点拆分、本地缓存、请求合并或专门的热点保护。

面试里可以这样收束：一致性哈希让缓存集群在节点增删时只丢失局部命中率，避免取模分片造成全量重映射；虚拟节点进一步改善均衡和异构容量；但它只是分片算法，不能替代副本、一致性、健康检查和热点治理。

## 4. 布隆过滤器解决什么问题？误判和漏判分别如何理解？

布隆过滤器解决的是低成本存在性判断问题：给定一个元素，快速判断它“一定不存在”还是“可能存在”。它不存原始元素，只维护一个位数组和多个哈希函数。插入元素时，把多个哈希位置置为 1；查询元素时，再算这些位置。如果任意位置是 0，就说明这个元素一定没插入过；如果所有位置都是 1，只能说明它可能插入过。

误判通常指 false positive，也就是元素实际上不存在，但布隆过滤器返回“可能存在”。原因是不同元素的哈希位置会重叠。随着插入元素越来越多，位数组里 1 的比例升高，误判率也会上升。误判不是 bug，而是布隆过滤器用空间换速度的代价。创建过滤器时一般要根据预计元素数量和目标误判率计算位数组大小和哈希函数个数。

漏判通常指 false negative，也就是元素实际上存在，但过滤器返回“不存在”。标准布隆过滤器在“只新增、不删除、同一个过滤器正确查询”的条件下不会漏判，因为插入时置过的位不会自动变回 0。漏判一般来自工程问题：删除时错误清位、多个过滤器版本切换不一致、并发写还没完成就查询、数据没有完全灌入过滤器、过滤器过期轮转、或者用 counting Bloom filter 时计数器被错误递减。

典型用法是挡住昂贵的无效查询。比如缓存穿透场景，请求一个根本不存在的 user_id，如果每次都查数据库，攻击者可以构造大量不存在 key 打穿后端。布隆过滤器放在前面后，返回“一定不存在”的请求可以直接拒绝；返回“可能存在”的请求再去查缓存和数据库。它牺牲的是一小部分误判带来的额外后端访问，换来大部分无效请求的快速过滤。

边界也要说清楚。布隆过滤器不能返回元素本身，不能精确计数，不适合必须零误判的权限判断或资金判断。误判率会随着实际插入量超过设计容量而变差。需要删除时要用 counting Bloom filter、cuckoo filter 或分代过滤器，但实现复杂度和内存都会上升。

## 5. 堆适合解决什么问题？

堆适合解决“每次都要快速拿到最大或最小元素”的问题。最常见的是二叉堆：最小堆的根节点是全局最小值，最大堆的根节点是全局最大值。它不保证整个数组有序，只保证父子之间满足堆序。因此堆的 `peek` 通常是 `O(1)`，插入和弹出堆顶是 `O(log n)`。

系统里最典型的用法是优先队列。任务调度器要找最早到期的定时器，延迟队列要找最早可执行的消息，重试系统要找下一次 retry_at 最小的任务，top K 统计要保留最大的 K 个元素，日志或搜索结果合并要做 k 路归并。这些场景不需要每次都维护全量排序，只需要不断取出当前优先级最高的元素。

堆还有一个优点是实现简单、内存紧凑。二叉堆通常用数组存，父子下标可以通过计算得到，不需要每个节点额外存指针。相比红黑树，它的范围查询和任意元素查找弱很多，但如果业务只关心堆顶，堆的常数成本通常更低。

限制也很明显。第一，堆不是有序列表，遍历堆数组得不到排序结果。第二，删除任意元素或更新任意元素优先级，需要知道它在堆里的下标，否则要先线性查找。工程实现里常配一个 `id -> index` 的哈希表，再用 `fix` 或上浮/下沉调整堆。第三，堆只按一个比较函数排序，如果优先级相同，还要补时间戳或序号保证公平性和稳定性。

面试里可以这样答：堆适合优先级驱动的问题，例如调度、定时器、延迟队列、top K、k 路归并和限流事件；它用 `O(log n)` 的更新换取 `O(1)` 看堆顶。只要需求变成范围扫描、按 key 精确查找、顺序遍历，堆就不是最合适的结构。

## 6. 跳表和红黑树有什么区别？

跳表和红黑树都能做有序集合或有序 map，查找、插入、删除的目标都是对数级。区别在于它们维持有序性的方式不同。红黑树是自平衡二叉搜索树，通过颜色、旋转和约束保证树高受控；跳表是多层有序链表，通过随机层高让查找像“高速路”一样先从高层跳，再逐层下降。

红黑树的优势是最坏情况更明确。它有严格平衡约束，查找、插入、删除都是 `O(log n)` 最坏界。很多内核和运行时喜欢红黑树，因为它能提供稳定的有序性和可预测的复杂度。代价是实现细节更复杂，插入删除要旋转和染色，迭代时也要按树结构找前驱后继。

跳表的优势是实现直观，范围扫描很自然，很多并发实现也更容易拆分锁或做 lock-free 设计。它的平均复杂度是 `O(log n)`，但依赖随机层高，严格最坏情况可以退化。实际工程里，只要随机源和层数限制合理，跳表表现很稳定。Redis Sorted Set 的工程直觉就很典型：字典负责按 member 查 score，跳表负责按 score 排序、排名和范围扫描。

从内存和 cache 看，两者都不是完美答案。红黑树每个节点有父子指针和颜色信息，跳表每个节点有多级 forward 指针。跳表层数随机，平均指针数可控，但内存形态更分散；红黑树节点结构固定，但旋转和比较路径也有指针跳转。真正性能要看 key 大小、比较成本、分配器、CPU cache 和访问模式。

面试里可以这样比较：要严格最坏界、成熟库、通用有序 map，红黑树稳；要实现简单、范围扫描方便、并发友好，跳表常见。不要把跳表说成“比红黑树快”，也不要把红黑树说成“永远更稳定”。它们解决的是同一类有序访问问题，只是工程取舍不同。

## 7. LRU、LFU、FIFO、ARC 缓存淘汰策略有什么区别？

FIFO 按进入缓存的时间淘汰，最早进来的先出去。它实现最简单，通常只需要队列，但不看访问行为。一个刚被频繁访问的老 key，也可能因为进来得早被淘汰。FIFO 适合非常简单、访问局部性不强或只需要粗略容量控制的场景，命中率通常不是最优。

LRU 按最近使用时间淘汰，最近没被访问的 key 先出去。它利用的是时间局部性：刚访问过的数据很可能马上还会访问。典型实现是哈希表加双向链表，查找 `O(1)`，命中后把节点移到链表头，淘汰从尾部删。LRU 的问题是容易被一次性扫描污染。比如批量导出扫过大量冷数据，可能把真正热点挤出去。

LFU 按访问频率淘汰，访问次数低的 key 先出去。它适合长期热点明显的场景，比如少量配置、商品、用户画像持续被访问。问题是旧热点会“赖着不走”：某个 key 过去很热，后来不热了，如果频率不衰减，它仍然占着缓存。工程实现通常会做近似计数、衰减、分桶或采样，否则精确 LFU 成本很高。

ARC 是 Adaptive Replacement Cache。它同时考虑 recency 和 frequency，并根据 workload 自动调整两者的比例。可以粗略理解为：它既记住最近访问过的对象，也记住曾经频繁访问过的对象，还会保留被淘汰对象的“影子记录”来判断当前负载更偏向最近性还是频率性。相比固定 LRU 或 LFU，ARC 对扫描污染和访问模式变化更敏感，但实现复杂度也更高。

实际系统还会用近似算法。比如 Redis 的 LRU/LFU 并不是全局精确链表和精确频率表，而是为了内存和 CPU 成本做采样近似。面试里要把“策略思想”和“工程实现”分开：LRU 看最近，LFU 看频率，FIFO 看进入顺序，ARC 自适应平衡最近性和频率性；真正落地时还要考虑元数据开销、锁竞争、采样误差、频率衰减和热点变化。

## 8. 滑动窗口常用于哪些系统问题？

滑动窗口适合处理“只关心最近一段时间或最近 N 个事件”的问题。系统里最常见的是限流：统计某个用户、IP、租户或接口在最近 1 秒、1 分钟、5 分钟内来了多少请求，超过阈值就拒绝或降级。相比固定窗口，滑动窗口能减少边界抖动，比如 00:59 和 01:00 各打一波请求不会轻易绕过限制。

监控和稳定性也大量用滑动窗口。错误率、P99 延迟、慢请求比例、熔断器失败计数、健康检查成功率、重试预算、连接失败率，都不会只看全历史。全历史会太钝，单个点又太敏感。滑动窗口让系统只用最近数据做判断，既能反映当前状态，又能过滤少量偶发噪声。

滑动窗口的实现有几种。最精确的是滑动日志，保存每个事件时间戳，查询时删掉窗口外数据，再看剩余数量。这很准确，但高 QPS 下内存和清理成本高。更常见的是时间桶，把 1 分钟切成 60 个 1 秒桶或 12 个 5 秒桶，用环形数组滚动覆盖旧桶。它不是完全精确，但成本稳定。还有滑动计数器，用当前窗口和前一个窗口按时间比例加权，进一步降低内存。

数据结构选择取决于问题。限流可以用 Redis ZSet 保存时间戳，也可以用本地环形桶；熔断器常用固定数量桶保存成功、失败和慢调用；流式指标可以用 ring buffer、直方图、DDSketch 或 t-digest 的窗口化版本。窗口越小越敏感，越大越平滑；桶越细越准确，元数据和更新成本越高。

边界问题也不少。时钟回拨会让时间窗口错乱，分布式节点各自统计会出现全局超发，热点 key 会让 Redis 窗口结构变慢，窗口清理如果放在请求路径上会制造尾延迟。面试里可以说：滑动窗口解决近期统计和近期控制问题，但要同时设计时间源、桶粒度、清理策略、分布式合并和降级行为。

## 9. 令牌桶和漏桶可以如何用数据结构实现？

令牌桶的实现可以很简单：保存 `capacity`、当前 `tokens`、`fill_rate`、`last_refill_time`。每次请求到来时，先根据当前时间和上次补充时间计算应该补多少 token，令牌数最多不超过容量；然后看请求需要几个 token，够就扣掉并放行，不够就拒绝或等待。单机里这几个字段可以放在内存对象里，用锁或原子操作保护。

令牌桶允许突发。只要桶里攒了 token，短时间内可以连续放行多个请求；长期平均速率由补充速度限制。这适合 API 网关、客户端 SDK、消息发送、后台任务调度这类既要限制平均速率，又要允许短暂突发的场景。Envoy 这类系统的 token bucket 配置也基本围绕最大 token、每次填充 token 数和填充周期展开。

漏桶有两种常见理解。第一种是队列模型：请求进桶，桶按固定速率漏出，队列满了就拒绝。这时数据结构就是 FIFO 队列加最大容量，再配一个定时出队或虚拟出队时间。NGINX 的请求限流就接近这种思路：超出速率的请求可以在 burst 容量内排队或占用槽位，超过容量就拒绝。第二种是 meter 模型，只判断请求是否符合速率，不一定真的排队。

如果不想维护真实队列，可以用“下一次允许时间”实现漏桶。保存 `next_allowed_at` 和固定间隔 `interval`。请求到来时，如果当前时间已经超过 `next_allowed_at`，就把 `next_allowed_at` 推进一个间隔并放行；如果太早到来，就根据是否允许排队计算等待时间，等待超过最大 burst 就拒绝。这种写法状态少，但表达复杂策略时要小心。

分布式实现要更谨慎。把每个请求都打到 Redis 做扣减，语义清楚但会增加网络开销和热点；每个实例本地各自限流，延迟低但全局会超发；折中做法是全局配额按实例预分配，本地桶先执行，后台再校准。面试里最好把结论说清楚：令牌桶更适合允许突发的平均速率限制，漏桶更适合平滑输出或排队整形；数据结构本质上就是计数状态、时间戳、队列或虚拟调度时间。

## 10. 优先队列在调度和限流中有什么作用？

优先队列的作用是让系统每次都能快速找到“下一件最该处理的事”。在调度里，优先级可以是 deadline、retry_at、任务权重、用户等级、资源成本、SLA 等。定时器系统用最早到期时间做优先级，重试队列用下一次重试时间做优先级，任务调度器可以用优先级和提交时间组合，避免高优先级任务一直插队导致低优先级饿死。

限流里优先队列也很常见。比如请求不直接拒绝，而是进入等待队列，队列按到期时间或令牌可用时间排序；当 token refill 后，调度器从队头取可以执行的请求。对多租户系统，还可以按租户权重、套餐等级或剩余额度决定谁先拿到资源。这样限流就不只是“放行/拒绝”，还能做排队、公平和削峰。

实现上通常用堆。堆顶是最早 deadline 或最高优先级，插入和弹出是 `O(log n)`。如果任务需要取消、优先级调整或去重，单纯堆不够，还要配一个哈希表保存任务 id 到堆下标的映射。否则取消一个任务可能要线性扫描整个堆。

风险也要讲。第一是饥饿，高优先级任务源源不断时，低优先级任务永远得不到执行。可以用 aging，让等待越久的任务优先级逐步提高。第二是优先级反转，低优先级任务持有资源，高优先级任务卡住。第三是队列膨胀，如果限流只排队不拒绝，内存、等待时间和客户端超时都会恶化。第四是时间精度，定时堆过大时，频繁调整和锁竞争会成为瓶颈。

所以这题的核心回答是：优先队列把调度问题从“遍历所有候选任务”变成“维护一个可快速取出最重要元素的数据结构”。它适合定时器、延迟队列、重试、限流排队、任务优先级和 top K；但要配合取消索引、公平策略、队列长度上限和超时处理，否则会把系统问题藏进一个越来越大的队列里。

## 11. 环形缓冲区适合什么场景？

环形缓冲区适合固定容量、顺序写入、顺序读取的场景。它通常用一个数组加 `head`、`tail` 两个下标实现；写到数组末尾后再绕回开头。这样可以复用同一块内存，避免频繁分配和释放。日志采样、指标窗口、网络收发缓冲、音视频帧、生产者消费者队列、最近 N 条事件记录，都很适合这种结构。

它的第一类价值是稳定内存。容量固定以后，内存上限明确，不会因为突发流量无限增长。比如保存最近 60 秒的 QPS 桶、最近 1024 条错误、最近 N 个延迟样本，都不需要链表或动态数组反复扩容。对热路径来说，少分配就意味着少 GC、少碎片、少锁竞争。

第二类价值是顺序访问和 cache locality。环形数组在内存里连续，读写下一个槽位很容易被 CPU cache 命中。如果容量设成 2 的幂，取模还可以用位运算优化成 `index & (size - 1)`。Linux 内核文档也专门提到，2 的幂大小的 circular buffer 能用更便宜的按位运算计算空间和占用。

但环形缓冲区必须定义满了怎么办。覆盖旧数据适合日志和近似统计，但不适合任务队列；阻塞生产者适合不能丢的消息，但可能把上游拖慢；直接丢弃适合保护系统，但要记录丢弃数。多生产者、多消费者下，还要处理并发写、内存屏障、伪共享和 ABA 问题。单生产者单消费者最容易做得又快又正确，多生产者多消费者就复杂很多。

面试里可以这样答：环形缓冲区适合固定窗口、流式数据、生产者消费者和最近 N 条记录；它用容量上限和连续内存换稳定延迟。真正落地时要说清楚覆盖、阻塞、丢弃三种满载策略，以及并发模型是一写一读还是多写多读。

## 12. Trie 树适合什么场景？

Trie 树适合按前缀组织字符串或序列。每条边表示一个字符、字节、路径片段或 bit，根到某个节点的路径就是一个前缀。它的查找复杂度主要和 key 的长度有关，而不是和集合里有多少个 key 直接相关。自动补全、词典匹配、敏感词过滤、URL 路由、命令解析、配置前缀匹配、IP 最长前缀匹配，都可以用 Trie 或它的变体。

它的优势是前缀查询自然。哈希表能很快判断完整 key 是否存在，但不擅长找“所有以 `/api/v1/users` 开头的路径”或“用户输入 `che` 后有哪些候选词”。平衡树可以按字典序范围扫描，但需要构造上下界；Trie 则走到前缀节点后，下面的子树就是所有候选。路由系统里，按路径片段建 Trie，也能很快匹配静态路径、参数路径和通配路径。

Trie 的代价是内存。普通 Trie 每个节点可能有很多子指针，稀疏时浪费明显。工程上常用压缩 Trie、radix tree、Patricia trie，把只有一个孩子的链压成一段字符串或一串 bit；也可以用紧凑数组、bitmap 加 child array、双数组 Trie、FST 等方式降低内存。不同实现会在插入成本、查询速度、内存占用和构建复杂度之间取舍。

并发和更新也要考虑。如果词典基本静态，比如搜索补全词库，可以离线构建一个紧凑结构，查询时只读，速度很快。如果路由表或配置规则频繁变化，可以用 copy-on-write 或版本化快照，让请求路径读取稳定结构，后台构建新 Trie 后原子替换。不要在每个请求上临时解析规则并重建 Trie，那会把数据结构优势抵消掉。

所以这题的结论是：Trie 适合前缀匹配、最长前缀匹配和按字符/片段逐步匹配的问题；它用空间换查询路径稳定。完整 key 点查优先想哈希表，区间和排序优先想树，前缀和路径匹配才是 Trie 的主场。

## 13. 位图适合什么场景？

位图适合表示“整数 ID 到布尔状态”的集合。一个 bit 就能表示一个状态：是否签到、是否在线、是否有权限、是否参加活动、某天是否活跃、某个 feature flag 是否打开。相比用 Set 存每个整数，位图的空间非常紧凑。比如 1 亿个用户的单个布尔状态，理论上只需要约 12.5 MB bit 空间，不考虑实现额外开销。

它还适合做集合运算。多个位图按位与可以求交集，按位或可以求并集，异或可以找差异，popcount 可以统计 1 的数量。用户增长分析里，昨天活跃和今天活跃做 AND 得到留存；多个活动人群做 OR 得到总覆盖；权限系统里每个 bit 代表一个权限位，也能快速判断某个权限是否存在。

Redis 的 bitmap 本质上是在 String 上提供 bit 操作，不是独立数据类型。`SETBIT`、`GETBIT` 可以设置和读取某个 offset，`BITCOUNT` 可以做人群数量统计，`BITOP` 可以做集合运算。这类命令适合状态密集、ID 范围可控的场景。

位图不适合稀疏且最大 ID 很大的场景。假设只有 1000 个用户，但最大 user_id 是 10 亿，直接按 user_id 做 offset 会浪费大量空间。此时可以考虑 Roaring Bitmap、分段 bitmap、哈希集合或压缩结构。位图也只能表达简单状态，如果要存时间、次数、金额或对象属性，就需要别的数据结构。

面试里可以这样答：位图适合大规模、稠密、整数编号、布尔状态和集合位运算；优点是省空间、CPU 位运算快、统计方便；缺点是依赖 ID 范围，稀疏数据浪费，表达能力有限。

## 14. HyperLogLog 解决什么问题？

HyperLogLog 解决的是大规模去重计数，也叫基数估算。典型问题是：一天内有多少独立访客、一个接口有多少不同调用方、一个广告有多少不同曝光用户、一个日志流里有多少不同 trace id。精确做法要保存所有已见元素，内存随唯一元素数量增长；HyperLogLog 用固定或近似固定的空间给出一个带误差的估计值。

它的直觉来自哈希的随机性。把元素哈希成二进制串后，观察某些 bit 模式出现的极端程度。越多不同元素进入，越可能看到“前导零很多”的哈希值。HyperLogLog 把哈希空间分成多个寄存器，每个寄存器记录自己见过的最大前导零长度，最后通过调和平均和修正公式估算基数。

它的工程价值是空间稳定、可合并。多个服务实例、多个分片、多个小时窗口各自维护 HLL，最终可以合并成全局估计，合并时通常对同位置寄存器取最大值。这使它很适合分布式统计。Redis 的 HyperLogLog 命令就是 `PFADD` 添加元素，`PFCOUNT` 估算基数，`PFMERGE` 合并多个结构；Redis 文档给出的实现上限内存约 12 KB，标准误差约 0.81%，这是具体实现的参数，不是所有 HLL 都一样。

限制也要讲清楚。HyperLogLog 不能告诉你某个元素是否出现过，不能列出元素，不能做精确去重，也不适合小集合必须完全准确的计费或权限场景。它通常也不支持自然删除，因为一个寄存器只保存最大观测值，你不知道这个最大值来自哪个元素。需要滑动窗口时，常按时间分片维护多个 HLL，再按窗口合并，但过期粒度会受分片大小影响。

所以这题的结论是：HyperLogLog 用可控误差换极低内存，适合 UV、独立 IP、唯一设备数这类大规模基数估算；它不是 Set 的替代品，而是“只要近似数量，不需要成员列表”的统计结构。

## 15. Count-Min Sketch 解决什么问题？

Count-Min Sketch 解决的是数据流里的频率估计问题。比如哪些商品被点击最多，哪些 IP 请求最多，哪些接口错误最多，哪些搜索词出现频率高。精确计数需要为每个 key 保存一个 counter，key 空间很大时内存会增长得很快。Count-Min Sketch 用一个二维计数数组和多组哈希函数，用小得多的空间估算每个 key 的出现次数。

更新时，一个元素会被多组哈希函数映射到多行里的不同列，对这些计数器都加一或加权增加。查询时，再算同样的位置，取这些计数器里的最小值作为估计频率。为什么取最小值？因为冲突只会让计数器被别的 key 额外加大，不会让它变小。对只做正向增加的流来说，Count-Min Sketch 的估计通常是偏大的，不会低估真实频率。

它适合找重频项，但不适合追求低频精确值。Redis 的 Count-Min Sketch 文档也强调，低于误差阈值的结果应当当作噪声看待。实际系统里常把 CMS 和一个小堆或候选表配合：CMS 负责估算频率，堆负责保留当前 top K 候选。这样不用保存所有 key，也能近似发现热点。

Count-Min Sketch 可合并，但前提是结构参数一致，比如宽度、深度和哈希方式相同。多个分片各自统计后，可以把对应计数器相加，得到全局估计。这很适合日志流、指标流和边缘节点汇总。它还支持加权增加，比如一次购买金额或一次批量事件可以加不同权重。

边界同样重要。CMS 不能列出所有 key；如果没有候选集，你只能查询已知 key 的估计值。删除和负数更新会破坏“不低估”的简单性质，除非使用更复杂的变体。恶意 key 分布、哈希函数选择、计数器溢出、窗口过期和参数配置都会影响结果。面试里可以这样收束：Count-Min Sketch 用可控误差估算流式频率，适合热点发现、近似 top K 和大规模计数；它不是精确 map，低频结果和删除语义要谨慎。
## 16. 哈希表的核心思想是什么？

哈希表的核心思想是把 key 通过哈希函数转换成一个近似均匀分布的整数，再映射到数组桶位上。数组提供按下标访问的能力，哈希函数把“按内容查找”变成“按位置访问”，所以它能把很多查找、插入、删除操作压到接近常数时间。

这个结构真正要解决的不是排序，而是快速定位。它通常不关心 key 的顺序，只关心同一个 key 是否总能落到同一个位置附近。由于不同 key 可能算出同一个桶位，所以哈希表必须配套冲突处理，例如拉链法、开放寻址、桶内树化或重新扩容。好的哈希表实现，本质上是在哈希函数质量、装载因子、冲突处理和扩容成本之间取平衡。

面试里可以这样收束：哈希表用空间换时间，用散列把 key 分散到桶里，再用冲突处理保证语义正确。它适合等值查询和成员判断，不适合天然有序遍历、范围查询或前缀匹配。只说“数组加哈希函数”不够，还要补一句：工程效果取决于分布是否均匀、冲突是否可控、扩容是否平滑。

## 17. 哈希表的时间复杂度、空间复杂度和适用场景是什么？

平均情况下，哈希表的 `get`、`put`、`delete` 通常是 `O(1)`；最坏情况下，如果大量 key 冲到同一个桶，可能退化到 `O(n)`。如果实现把长链桶转成平衡树，单桶最坏查找可以降到 `O(log n)`，但这是实现层面的防护，不是所有哈希表都天然具备。扩容本身可能是 `O(n)`，摊还到多次插入后才接近常数。

空间复杂度一般是 `O(n + m)`，`n` 是元素数量，`m` 是桶数组大小。为了保持低冲突，哈希表不会等到数组完全装满才扩容，所以它经常牺牲一部分空桶。拉链法还需要额外节点或小数组，开放寻址则把元素直接放在主数组里，但对装载因子更敏感。

适用场景是等值查找、去重、索引、计数、映射、缓存和状态表。例如 `user_id -> session`、`request_id -> trace context`、`ip -> rate limit state`、`service -> endpoint list` 都是典型哈希表问题。不适合的场景也要说清楚：按范围扫描、按顺序输出、找前缀、找最大最小、需要稳定排序时，应优先考虑树、跳表、堆、Trie 或有序数组。

## 18. 哈希表在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

后端系统里，哈希表最常见的角色是内存索引。服务注册表可以用 `serviceName -> instances`，连接池可以用 `addr -> connection`，幂等控制可以用 `requestId -> result`，会话管理可以用 `token -> user`。这些场景的共同点是按完整 key 精确定位，读写路径希望尽量短。

负载均衡里，哈希表既能存节点元数据，也能做连接保持状态。例如四层负载均衡常维护五元组到后端连接的映射，避免同一条连接的后续包被转到不同后端。缓存里，哈希表通常和双向链表、频率计数、过期索引组合，实现 LRU、LFU、TTL Map、本地对象缓存和去重缓存。限流里，哈希表用来保存每个用户、IP、租户、接口的计数器、窗口桶或令牌桶状态。

调度系统也离不开哈希表。任务 ID 到任务状态、worker ID 到负载、队列名到优先级队列、定时器 ID 到堆下标，都可以用它减少查找成本。真正落地时要注意容量上限和过期清理，否则“每个 key 一个状态”的设计会被高基数输入打爆内存。

## 19. 哈希表在并发场景下需要考虑哪些线程安全问题？

第一件事是结构性修改。插入、删除、扩容、桶链表调整、开放寻址探测状态改变，都会修改内部结构。普通哈希表如果在并发读写下没有同步，可能读到中间状态，轻则返回错误，重则破坏结构。Java `HashMap` 文档也明确说它不是同步结构，多线程结构性修改需要外部同步。

第二件事是复合操作的原子性。`if not exists then put`、读取计数后再加一、先查 key 再延长过期时间，这些操作即使单次 `get` 和 `put` 是线程安全的，也不代表组合语义安全。需要用 `computeIfAbsent`、`putIfAbsent`、CAS、锁或事务脚本把复合逻辑合起来。

第三件事是扩容和热点。全表锁实现简单但高并发下会抖动；分段锁、桶锁、读写锁、无锁读加锁写、copy-on-write 快照各有取舍。热点 key 会让分片锁失效，计数型场景可以用 LongAdder、分片计数、批量聚合来减少争用。还要注意迭代语义：并发遍历通常只能保证弱一致快照，不能把 `size()`、遍历结果或聚合结果当作严格控制逻辑。

## 20. 一致性哈希的核心思想是什么？

一致性哈希的核心思想是把 key 和节点都映射到同一个哈希空间里，通常想象成一个环。key 落到环上的某个位置后，顺时针遇到的第一个节点就是它的归属节点。节点增删时，只影响环上一小段 key 的归属，不会像 `hash(key) % N` 那样因为节点数变化导致大范围重映射。

这个思想解决的是分布式系统里“成员变化时映射尽量稳定”的问题。缓存、分片存储、服务端粘滞路由都怕大量 key 同时迁移，因为迁移会造成缓存失效、后端回源、数据搬迁和连接抖动。一致性哈希把变化局部化，牺牲一点元数据和查找成本，换来更小的扰动面。

工程实现通常会引入虚拟节点。一个物理节点映射成多个 token，能让 key 分布更均匀，也能表达节点容量差异。面试里要把边界讲清楚：一致性哈希只负责 key 到节点的稳定映射，不自动解决热点 key、副本一致性、节点健康探测、迁移期间双写、客户端 ring 版本不一致这些问题。

## 21. 一致性哈希的时间复杂度、空间复杂度和适用场景是什么？

典型 ring 实现会把所有虚拟节点 token 排序。查找一个 key 时先计算哈希，再在有序 token 数组或树里找第一个大于等于它的位置，所以复杂度通常是 `O(log V)`，`V` 是虚拟节点总数。如果用数组加二分，查找局部性好；如果用平衡树，增删 token 更方便。

空间复杂度是 `O(V)`，因为要保存虚拟节点 token、物理节点引用和可能的权重信息。`V` 越大，负载越均匀，但 ring 构建、内存占用、配置分发和二分查找常数也会上升。节点数少时虚拟节点不足会导致倾斜；节点数很多时要关注 ring 更新频率和客户端同步成本。

适用场景是分布式缓存分片、对象存储分片、日志分区、租户路由、服务端连接粘滞、边缘节点选择等。它适合成员会增删、希望减少迁移的系统；不适合强顺序扫描，不适合精确容量调度，也不适合节点集合每毫秒都变化的场景。频繁变化时，ring 分发本身可能变成控制面压力。

## 22. 一致性哈希在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

在缓存里，一致性哈希可以把对象 key 映射到缓存节点。节点扩容时，只把一部分 key 迁到新节点；节点故障时，只由后继节点接管相关区间。这样能减少雪崩式缓存 miss。对分布式 KV 或对象存储来说，它还能决定主副本位置，再叠加副本因子、机架感知和故障域约束。

在负载均衡里，一致性哈希常用于会话粘滞和连接保持。例如按用户 ID、cookie、源地址或请求中的业务 key 映射到后端实例，让同一用户尽量落到同一个后端，减少本地缓存失效或会话迁移。限流里，可以把同一个租户或用户的限流状态路由到同一个限流节点，避免每个节点都维护一份不完整状态。

在调度里，它可以把任务分片、定时任务、采集目标或 shard leadership 分给 worker。worker 增删时，只重新分配局部任务，降低抖动。需要注意的是，一致性哈希不等于负载均衡闭环：如果某个 key 本身流量很大，稳定映射反而会稳定地制造热点，还需要热点拆分、二级调度或动态权重。

## 23. 一致性哈希在并发场景下需要考虑哪些线程安全问题？

一致性哈希的并发问题主要在 ring 更新和读路径一致性。请求线程需要稳定地读取 ring；控制面可能同时新增节点、删除节点、调整权重或标记故障。如果边读边改同一个可变数组或树，可能出现查找越界、读到半更新 token、同一请求两次查找结果不一致等问题。

常见做法是 copy-on-write。控制面在后台构建新的不可变 ring，校验完成后用原子指针替换；数据面每次请求只读当前快照。这样读路径无锁或低锁，更新路径也不会破坏正在使用的旧 ring。代价是 ring 较大时构建和替换会占用内存，旧快照还要等读者退出后再释放。

还要处理版本一致性。多客户端各自持有 ring 时，配置传播存在窗口期，同一个 key 可能被不同客户端打到不同节点。缓存场景通常可接受短暂 miss；存储场景就要配合副本、重试、重定向或元数据版本。节点健康状态也要防抖，避免节点反复上下线导致 key 来回迁移。

## 24. Rendezvous Hash 的核心思想是什么？

Rendezvous Hash 也叫 Highest Random Weight Hash。它的核心思想是：对一个 key，把它分别和每个候选节点组合计算一个分数，选择分数最高的节点。所有客户端只要使用同一份节点列表和同一个哈希函数，就会对同一个 key 得出同一个 winner。

它和 ring 型一致性哈希的区别在于，Rendezvous 不需要把节点放到环上，也不需要维护虚拟节点排序表。基本版本就是遍历候选节点，计算 `score = hash(key, node)`，取最大值。节点下线时，原来落在该节点上的 key 会自动选择第二高分节点；其他 key 的 winner 不变，因此扰动也是局部的。

这个算法的直觉很简单：每个节点都参加一次公平抽签，key 选择得分最高者。权重版可以把节点容量引入分数计算，让高容量节点更容易胜出。面试里可以把它概括成“无需 ring 的一致映射算法”，优点是概念简单、天然支持 top N 副本选择，缺点是基础版本每次要扫描所有候选节点。

## 25. Rendezvous Hash 的时间复杂度、空间复杂度和适用场景是什么？

基础 Rendezvous Hash 的查找复杂度是 `O(N)`，`N` 是候选节点数，因为要给每个节点算一次分数。空间复杂度是 `O(N)` 保存节点列表，不需要保存大量 token。对于几十到几百个节点的服务端负载均衡或缓存路由，这个成本通常可以接受；如果节点数量非常大，直接全量扫描就会变贵。

优化方向有几类。可以先按 shard、机房、机架、区域缩小候选集合，再做 Rendezvous；也可以用层次化 Rendezvous，把 `O(N)` 降成按层选择；还可以预计算部分节点信息。权重版需要小心数学公式，不能简单把哈希值乘权重就认为比例一定正确。

适用场景包括缓存节点选择、分片 owner 选择、副本 top K 选择、消费者分摊分区、任务到 worker 的稳定分配。它尤其适合需要“同一个 key 得到一组稳定候选节点”的场景。与一致性哈希 ring 相比，它少了虚拟节点表和二分查找，多了每次遍历候选的 CPU 成本。

## 26. Rendezvous Hash 在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

在缓存系统里，Rendezvous 可以用来为每个对象选择主缓存节点，或者选择 top K 个备份节点。节点故障时直接选下一个高分节点，不需要沿环找后继，也不需要为每个物理节点配置很多虚拟节点。对于多副本读，top K 列表还能作为候选顺序。

在负载均衡里，它适合按请求 key 做稳定路由，例如用户 ID、租户 ID、房间 ID、文件 ID。后端集合变化时，只有 winner 受影响的 key 会迁移。限流里，可以把某个 key 的状态稳定落到一个限流节点；如果要容灾，可以同时选择多个节点做主备或写入副本。

调度系统里，Rendezvous 很适合做任务分片和消费者分配。每个任务对所有 worker 打分，最高分 worker 拥有任务；worker 加入或退出时，只需重算映射，不需要维护复杂的迁移表。缺点是任务量和 worker 数都大时，重算成本会变成 `tasks * workers`，需要批量化、分层或增量计算。

## 27. Rendezvous Hash 在并发场景下需要考虑哪些线程安全问题？

核心问题仍然是候选节点列表的一致性。请求线程遍历节点列表时，控制面如果同时修改列表，可能出现漏算、重复算、读到已释放节点或同一个 key 在一次决策中使用混合版本。最稳的做法是把节点列表做成不可变快照，更新时整体替换。

还要注意哈希函数和权重配置的确定性。不同语言、不同版本、不同字节序、不同浮点计算方式可能让客户端算出不同 winner。跨语言系统应固定编码、哈希算法、种子、权重公式和 tie-break 规则。分数相等虽然概率低，但仍要定义稳定的节点 ID 次序，否则边界情况下会出现不一致。

并发故障处理也要谨慎。某个节点被标记为 unhealthy 后，是否立刻从候选集移除，会影响大量 key 的归属。直接删除能快速止血，但会触发迁移；保留但降权可以平滑，但故障节点可能仍收到流量。实际系统通常把健康状态、熔断、连接池和哈希选择分开处理，用版本化配置让行为可追踪。

## 28. Maglev Hash 的核心思想是什么？

Maglev Hash 来自 Google 的软件负载均衡实践。它的核心思想是为每个服务后端集合生成一张固定大小的查找表，请求的 flow hash 对表大小取模，表里的值就是后端。数据面转发时只做一次哈希、一次取模、一次数组访问，路径非常短，适合高吞吐负载均衡。

表的构建方式是关键。每个后端根据自己的名字生成一条排列序列，控制面轮流把后端填进查找表的空槽，直到表满。这样不同 Maglev 实例只要看到同一份后端列表，就能构建出同一张表；后端变化时，大部分表项保持不变，从而减少连接迁移。

它本质上是把较复杂的一致性选择提前编译成数组。与 Rendezvous 每次遍历节点不同，Maglev 把计算成本移到后端集合变更时；与普通取模不同，它在后端变化时尽量保持映射稳定。代价是每个服务或后端集合要保存查找表，而且表大小、后端数量和权重表达会影响均匀性。

## 29. Maglev Hash 的时间复杂度、空间复杂度和适用场景是什么？

数据面查找是 `O(1)`：计算 flow hash 后访问 lookup table。空间复杂度是 `O(M)`，`M` 是表大小。构建表的成本与后端数量和表大小有关，粗略可以理解为 `O(N + M)` 到 `O(N * M)` 之间取决于实现和冲突跳过情况，但它发生在配置变化时，不在每个包的热路径上。

表越大，分布越平滑，后端变更时扰动越接近理想；表越小，内存和构建成本低，但负载偏差更明显。Google 论文里的重点不是“哈希函数更神奇”，而是把一致映射做成适合软件负载均衡器的固定表，配合连接跟踪和 ECMP 承接很高的包处理量。

适用场景是四层负载均衡、服务 VIP 到后端 endpoints 的稳定映射、连接保持、网关数据面快速转发。它不适合后端集合每个请求都变化的场景，也不适合需要复杂业务策略逐请求计算的场景。Maglev Hash 更像数据面加速结构，不是完整的调度系统。

## 30. Maglev Hash 在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

在负载均衡里，Maglev Hash 的典型应用是把同一个连接或五元组稳定映射到同一个后端。多台负载均衡器部署在同一个 VIP 前面时，只要它们构建的表一致，任何一台收到同一条 flow 的包，都能算到同一个后端，从而减少跨实例状态同步压力。

缓存和网关也可以借鉴这个思路：对某个后端集合预生成查找表，请求路径只做数组访问。比如边缘网关按租户、对象 ID 或连接 ID 选择后端池，配置更新时后台重建表并原子替换。限流系统如果追求极短路径，也可以用类似表把限流 key 路由到状态节点。

调度场景要谨慎使用。Maglev 表适合稳定映射，不适合实时感知队列长度、CPU、水位和排队时间。如果要动态负载均衡，通常把 Maglev 作为第一层稳定选择，再叠加连接跟踪、健康检查、熔断和局部负载反馈，而不是用它直接替代调度器。

## 31. Maglev Hash 在并发场景下需要考虑哪些线程安全问题？

Maglev 的并发关键是查找表的发布。数据面线程不能读到构建一半的表。常见做法是后台构建完整新表，校验后通过原子指针替换；旧表等所有读者退出后再释放。这样每个请求只读不可变表，避免在热路径加锁。

多实例一致性也很重要。不同负载均衡器如果看到的后端列表顺序、权重、健康状态或表大小不同，同一个 flow 就可能被算到不同后端。配置发布要带版本，后端列表要排序，哈希种子和表大小要固定，健康检查状态也要定义传播策略。

还要处理连接跟踪和表更新的关系。已有连接通常希望继续打到原后端，新连接才按新表选择；否则后端列表变化会让长连接断流。实现上经常是先查 conntrack，命中则复用旧后端；未命中才走 Maglev 表。并发删除后端时，还要决定是保留已有连接到自然结束，还是强制迁移或重置。
## 32. 布隆过滤器的核心思想是什么？

布隆过滤器的核心思想是用多个哈希函数和一个 bit 数组做低成本存在性判断。插入一个元素时，把它映射到多个 bit 位置并置为 1；查询时再计算这些位置，只要有一个是 0，就能确定元素不存在。如果所有位置都是 1，只能说元素可能存在。

它的关键取舍是允许误判，不允许标准语义下的漏判。误判是元素没插入过，但相关 bit 被别的元素碰巧置成 1；漏判是在只插入不删除且查询同一个过滤器的条件下不应发生。如果发生漏判，通常是实现问题，例如并发写未完成、版本切换错误、删除时清错 bit、数据灌入不完整。

所以布隆过滤器不是 Set，也不是缓存本体。它不保存元素，不返回元素数量，不支持精确删除。它适合放在昂贵查询前面，用很小内存挡掉一批“一定不存在”的请求，把后端访问留给“可能存在”的请求。

## 33. 布隆过滤器的时间复杂度、空间复杂度和适用场景是什么？

插入和查询复杂度都是 `O(k)`，`k` 是哈希函数个数。由于 `k` 通常是小常数，所以工程上常近似看成常数时间。空间复杂度是 `O(m)`，`m` 是 bit 数组大小，和目标误判率、预计元素数量有关。误判率越低，或者预计元素越多，需要的 bit 越多。

参数配置很关键。容量估小了，bit 数组很快变满，误判率会上升；容量估大了，内存浪费。哈希函数个数也不是越多越好，太少误判高，太多 CPU 成本高，还会让 bit 更快被置满。很多实现用双哈希派生多个位置，减少真正哈希计算次数。

适用场景包括缓存穿透保护、爬虫 URL 去重、黑名单预过滤、数据库查询前置过滤、日志流中判断“是否可能见过”。不适合权限判断、资金判断、库存扣减这种不能接受误判的场景，也不适合需要列出成员或删除成员的集合语义。

## 34. 布隆过滤器在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

缓存系统里最典型的是防缓存穿透。把数据库里存在的 key 预先加入布隆过滤器，请求到来时先查过滤器。如果返回“一定不存在”，直接拒绝或返回空；如果返回“可能存在”，再查缓存和数据库。这样攻击者大量请求不存在 ID 时，不会每次打到数据库。

后端系统也常用它做预过滤。比如接口只允许已注册设备 ID、合法订单号、已发布商品 ID，可以用布隆过滤器先挡掉大部分非法输入。负载均衡或网关可以用它判断某个租户、路由、灰度名单是否可能存在，再决定是否走较重的配置查询。

限流和调度里，布隆过滤器可以帮助减少状态创建。例如只对“已知用户”创建令牌桶，对明显不存在的用户直接拒绝；任务调度里用它避免重复提交明显已见过的任务 ID。要注意它只能做前置判断，不能作为最终依据。误判只会让一部分请求继续走后端，不应让合法请求被错误拒绝。

## 35. 布隆过滤器在并发场景下需要考虑哪些线程安全问题？

并发写入时，bit 置位必须是线程安全的。多个线程同时对同一个机器字做按位 OR，如果不是原子操作，可能丢失其中一个线程设置的 bit，导致标准布隆过滤器出现漏判。高性能实现通常按 word 做原子 OR，或者对分片 bitset 加锁。

版本切换也很容易出错。布隆过滤器通常由离线任务构建，然后在线服务原子替换。替换过程中，如果请求线程混用新旧过滤器和新旧数据库快照，可能出现数据已经写入数据库但还没进入过滤器的短暂漏判。工程上常用双缓冲、增量过滤器、延迟切换或“布隆说不存在时再做低频兜底查询”来降低风险。

如果需要删除，普通布隆过滤器不能直接清 bit，因为同一个 bit 可能由多个元素共享。Counting Bloom Filter 用计数器替代 bit，删除时递减，但并发下会引入计数器溢出、递减丢失和错误删除问题。面试里可以强调：布隆过滤器的并发正确性不只在哈希函数，还在原子置位、发布顺序和数据源同步。

## 36. 跳表的核心思想是什么？

跳表的核心思想是在有序链表上增加多层“快速通道”。底层保存所有元素，上层只保存一部分元素。查找时从最高层开始向右走，发现再走会越过目标，就下降一层，最后在底层定位目标。它用随机层高来近似平衡树的高度控制。

跳表和红黑树都能实现有序集合，但跳表不靠旋转维护平衡，而是靠概率分布。插入元素时随机决定它出现在多少层，常见做法是每升一层概率减半。这样大多数节点只在底层，少数节点出现在高层，形成稀疏索引。

它的工程优点是实现直观，范围扫描自然。找到起点后沿底层链表往后走就能输出有序区间。Redis Sorted Set 使用跳表加字典组合，就是典型例子：字典负责按 member 找 score，跳表负责按 score 排序、排名和范围查询。

## 37. 跳表的时间复杂度、空间复杂度和适用场景是什么？

跳表查找、插入、删除的期望复杂度是 `O(log n)`，空间复杂度是 `O(n)` 的期望级别，因为每个节点平均只会有常数个 forward 指针。严格最坏情况下，如果随机层高很差，操作可能退化到 `O(n)`，但合理随机源和最大层限制下，这种情况概率很低。

插入和删除都要先搜索路径，并记录每一层上最后一个小于目标的位置，然后改指针。相比平衡树，跳表没有复杂旋转，局部修改更容易理解。范围查询通常是 `O(log n + k)`，先定位起点，再连续读出 `k` 个元素。

适用场景是有序 map、有序 set、排行榜、延迟队列、时间线、范围查询和需要较简单并发设计的索引结构。如果只做等值查找，哈希表更直接；如果必须提供严格最坏 `O(log n)`，红黑树或其他平衡树更合适；如果数据主要在磁盘页上，B+Tree 更适合。

## 38. 跳表在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

后端系统里，跳表常用于需要按分数或时间排序的内存索引。排行榜可以按 score 排序，延迟消息可以按触发时间排序，限流审计可以按时间戳保留事件，任务调度可以按下一次执行时间维护集合。它比单纯哈希表多了有序能力。

在缓存里，跳表可以维护过期时间索引：key 到 value 用哈希表查，过期时间到 key 用跳表扫。这样定期清理时可以从最早过期项开始，不必全表扫描。负载均衡或调度里，也可以按节点负载、权重、健康分、最近失败时间维护有序候选，不过这类动态排序要注意更新频率。

跳表适合“查一个点后继续顺序扫一段”的任务。例如找未来 1 秒内要执行的定时任务，或者找 score 在某个区间的用户。它不适合作为每个请求都全局重排的负载均衡核心，因为频繁更新分数会带来锁争用和内存分配成本。

## 39. 跳表在并发场景下需要考虑哪些线程安全问题？

跳表的并发难点在于一次插入或删除会改多层指针。读线程如果在更新中间看到部分层已更新、部分层未更新，就可能跳过节点、重复节点或读到已删除节点。最简单方案是全局锁，复杂一点可以按节点或区间加锁，再复杂就是 lock-free 跳表。

并发跳表还要处理内存回收。删除节点后，不能立刻释放给内存分配器，因为其他读线程可能还持有指针。无锁实现需要 hazard pointer、epoch、RCU 或语言运行时 GC 来避免 use-after-free。Java 这类托管环境相对轻松，但仍要保证指针发布和可见性。

随机层高也要考虑并发安全。随机数生成器不能成为全局锁热点；层高上限、比较器和 tie-break 规则要稳定。范围遍历时，要明确它是强一致快照还是弱一致遍历。很多系统接受弱一致，因为强一致范围扫描会显著增加锁范围。

## 40. 红黑树的核心思想是什么？

红黑树是一种自平衡二叉搜索树。它给每个节点加一个颜色位，通过“红节点不能连续”“从任意节点到叶子路径上的黑节点数一致”等约束，把树高控制在对数级。查找仍按二叉搜索树规则走左或右；插入删除后通过变色和旋转恢复约束。

它追求的是稳定的最坏情况。普通二叉搜索树如果按有序 key 插入，会退化成链表；红黑树用较弱但便宜的平衡约束避免这种退化。相比 AVL 树，红黑树不追求极致平衡，插入删除旋转次数通常更少，更适合更新频繁的场景。

面试里可以这样讲：红黑树的核心不是“红色和黑色”，而是用颜色规则编码平衡信息，让查找、插入、删除都保持 `O(log n)`。它适合做通用有序 map/set、内核时间器、区间索引、调度器中的有序集合。

## 41. 红黑树的时间复杂度、空间复杂度和适用场景是什么？

红黑树查找、插入、删除的最坏复杂度都是 `O(log n)`。空间复杂度是 `O(n)`，每个节点额外保存左右孩子、父指针和颜色信息。相比哈希表，它的常数通常更高，但能保持有序，并且不依赖哈希分布。

范围查询一般是 `O(log n + k)`：先找到范围起点，再按中序后继遍历 `k` 个节点。找最小、最大也是沿左或右一路走，若实现缓存最左节点，可以把取最小值优化到 `O(1)`。Linux rbtree 文档也提到 cached rbtree 用额外指针缓存最左节点，适合频繁取最小的场景。

适用场景包括有序 map、定时器、区间树、内存区域管理、I/O 调度、需要稳定最坏时间的索引。它不适合只做无序等值查询的热路径，那里哈希表通常更快；也不适合磁盘大页索引，那里 B+Tree 的扇出和顺序扫描更有优势。

## 42. 红黑树在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

后端系统里，红黑树适合管理有序资源。定时器可以按到期时间排序，内存区间可以按起始地址排序，连接超时可以按 deadline 排序。需要找最早到期项时，红黑树能稳定给出最小节点；需要范围查找时，也能沿中序遍历。

缓存系统可以用红黑树维护过期时间索引，哈希表负责 key 查找，红黑树负责过期清理。限流系统可以按窗口结束时间或状态过期时间管理大量 key，避免扫描全表。调度系统里，可以按优先级、deadline、虚拟运行时间维护任务集合，这也是很多内核调度结构喜欢平衡树的原因。

负载均衡里，红黑树不是最常见的请求级选择算法，但可以用于控制面或元数据层。例如按权重区间维护节点、按连接数排序候选、按健康检查失败时间重试节点。若每个请求都要改树，锁和旋转会成为成本；如果更新频率低、查询需要有序性，它就很合适。

## 43. 红黑树在并发场景下需要考虑哪些线程安全问题？

红黑树插入删除会旋转和变色，可能影响祖先、叔父、兄弟等多个节点。并发读写如果没有同步，读线程可能看到不满足树约束的中间状态。最简单做法是用一把锁保护整棵树；读多写少可以用读写锁；更新很频繁时可以考虑分区树或其他结构。

迭代时也要小心。中序遍历依赖父子指针和后继关系，删除当前节点或相邻节点可能让迭代器失效。内核或系统代码通常把“锁由调用者负责”写得很明确，因为通用红黑树库不知道业务的生命周期和锁粒度。

如果要做无锁或 RCU 读路径，更新端要保证新节点内容先初始化，再发布指针；删除端要等读者退出后才能释放节点。增强红黑树还要维护子树统计、最大区间端点等派生信息，这些信息必须和旋转一起更新，否则查找结果会错。

## 44. B+Tree 的核心思想是什么？

B+Tree 的核心思想是面向块设备和页缓存，把树的高度压得很低。它不是每个节点只放一个 key，而是在一个页里放很多 key 和指针，形成高扇出多路搜索树。内部节点只负责导航，数据记录或记录指针主要在叶子节点，叶子节点之间通常按顺序相连。

这样设计特别适合磁盘和 SSD。一次 I/O 读一个页，页里能装很多 key，树高通常很小。查找从根页一路走到叶子页；范围扫描找到第一个叶子位置后，可以沿叶子链表顺序读下去，不需要每条记录都从根开始。

B+Tree 和普通二叉树的核心区别在于“页友好”。红黑树适合内存指针跳转，B+Tree 适合块读写和范围扫描。数据库索引、文件系统目录、LSM 里的某些辅助结构、嵌入式 KV 存储都大量使用 B/B+Tree 思想。

## 45. B+Tree 的时间复杂度、空间复杂度和适用场景是什么？

B+Tree 查找、插入、删除通常是 `O(log_B n)`，`B` 可以理解为节点扇出。因为扇出很大，树高远小于二叉树。空间复杂度是 `O(n)`，但页分裂、填充因子、内部碎片、页头和指针都会带来额外开销。

插入时如果叶子页满了，需要页分裂，并把分裂信息向父节点传播；删除后如果页太空，可能合并或重分布。范围查询是 B+Tree 的强项，复杂度可以看作 `O(log_B n + k/page)`，定位起点后顺序扫描叶子页。PostgreSQL 文档也把 B-tree 索引用于等值、范围和排序检索列为常见能力。

适用场景是数据库索引、文件系统索引、持久化 KV、按主键和二级索引访问、范围扫描、分页查询和有序输出。它不适合纯内存极低延迟的简单等值查找，也不适合没有排序关系的数据类型。比较函数必须定义稳定全序，否则 B+Tree 不知道如何安排 key。

## 46. B+Tree 在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

在后端系统里，B+Tree 最典型的应用是数据库索引。主键查询、范围查询、按时间分页、按状态加时间过滤，都可以落到 B+Tree 或类似结构上。MySQL InnoDB 的索引页、PostgreSQL 的 B-tree 索引，都是后端工程师最常接触到的实现。

缓存系统如果需要持久化本地索引，例如磁盘缓存、对象缓存元数据、边缘节点内容索引，也可以使用 B+Tree。它能按 key 查对象，也能按过期时间或大小范围扫描要清理的对象。限流系统如果把历史计数落盘，按租户和时间范围查询，B+Tree 也很合适。

负载均衡和调度的在线请求路径不常直接使用 B+Tree，因为它偏存储索引，不是每请求调度结构。但控制面可以用它存配置、路由规则版本、审计记录和历史指标。只要需求是“持久化、有序、范围查询”，B+Tree 就比哈希文件更自然。

## 47. B+Tree 在并发场景下需要考虑哪些线程安全问题？

B+Tree 的并发难点在页级修改。插入可能导致叶子页分裂，分裂可能向父节点传播；删除可能合并页。这些操作跨多个页，必须保证读者不会看到断裂的父子关系或错误的叶子链表。数据库通常用页锁、闩锁、锁耦合、B-link tree 右兄弟指针、WAL 和恢复机制来保证安全。

读写隔离也要和事务语义配合。一个索引页结构安全，不代表业务读到了正确版本；MVCC、行锁、间隙锁、next-key lock、谓词锁等机制会参与处理幻读和并发写。面试时不要把“B+Tree 线程安全”只理解成加一把锁，数据库里的结构并发和事务并发是两层问题。

工程上还要关注页分裂热点。单调递增主键会集中写最右叶子页，随机主键会制造页分裂和缓存抖动。并发场景下，填充因子、批量建索引、页合并阈值、后台清理、checkpoint 和 redo 日志都会影响吞吐和尾延迟。
## 48. 堆的核心思想是什么？

堆的核心思想是维护一个“局部有序”的完全二叉树。最小堆保证每个父节点都不大于子节点，所以根节点是全局最小值；最大堆相反，根节点是全局最大值。它不保证所有元素全局有序，只保证堆顶可以快速取得。

二叉堆通常用数组存储，不需要显式指针。下标 `i` 的左右孩子是 `2i+1` 和 `2i+2`，父节点是 `(i-1)/2`。插入时把元素放到末尾再上浮，弹出堆顶时把末尾元素放到根再下沉。这个结构简单、内存连续、常数成本低。

堆适合“持续获得当前最大或最小”的问题。它不像红黑树那样支持完整有序遍历，也不像哈希表那样适合按任意 key 查找。面试里可以把它归纳为：堆用弱排序换取便宜的堆顶访问和对数级更新。

## 49. 堆的时间复杂度、空间复杂度和适用场景是什么？

二叉堆查看堆顶是 `O(1)`，插入是 `O(log n)`，弹出堆顶是 `O(log n)`，从无序数组建堆是 `O(n)`。如果知道元素下标，更新优先级后做 `fix` 也是 `O(log n)`；如果不知道下标，要先线性查找，整体会变成 `O(n)`。

空间复杂度是 `O(n)`。数组堆很紧凑，但如果业务需要按任务 ID 删除或更新堆中任意元素，通常还要配一个 `id -> index` 哈希表，这会增加内存和维护成本。每次交换堆元素时，也要同步更新 index，否则后续 `remove` 或 `fix` 会错。

适用场景包括 top K、定时器、延迟队列、重试队列、k 路归并、最短路径算法、按 deadline 或优先级调度任务。不适合大量范围查询、按 key 点查、顺序遍历和需要稳定全局排序的场景。要输出完整有序结果，就需要不断 `pop`，成本是 `O(n log n)`。

## 50. 堆在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

后端调度里，堆常用来管理定时任务和延迟任务。每个任务带一个 `run_at`，最小堆堆顶就是最早到期任务。调度线程只看堆顶，如果没到时间就睡到堆顶时间；如果到了就弹出执行。重试系统也常用堆保存下一次重试时间。

缓存系统可以用堆辅助过期清理或按成本淘汰。例如按 expire time 建最小堆，后台不断清理过期项。限流中，堆可以保存最早可释放的排队请求、最早过期的窗口状态或最早恢复的熔断资源。负载均衡里，堆可以维护“当前连接数最少”或“负载最低”的后端，但每次请求都更新全局堆会有锁竞争，通常要谨慎。

工程上经常组合使用：哈希表负责按 ID 找任务，堆负责按时间或优先级找下一个任务。单独一个堆很难支持取消任务、更新任务和去重任务；配上哈希索引后，才能做成完整的调度数据结构。

## 51. 堆在并发场景下需要考虑哪些线程安全问题？

堆的并发问题来自数组重排。插入、弹出、删除、更新优先级都会交换元素位置。如果多个线程同时修改同一个堆，没有锁会破坏堆序和 index 映射。最简单方案是一把互斥锁保护整个堆，适合中低并发调度器。

高并发下，全局堆会成为热点。可以按 shard 拆成多个堆，每个 worker 管自己的定时器；也可以用时间轮处理大量近似定时任务，把精度换成吞吐。对于负载均衡这类每请求都可能更新的场景，全局堆通常不如局部采样、P2C 或原子计数稳。

还要处理条件变量和唤醒。调度线程可能正睡到旧堆顶时间，另一个线程插入了更早的任务，此时必须唤醒调度线程重新计算等待时间。取消任务也要同步处理：可以立即从堆中删除，也可以标记取消，等它到堆顶时再跳过。前者复杂，后者简单但可能积累垃圾节点。

## 52. 优先队列的核心思想是什么？

优先队列是一种抽象数据类型：入队时带优先级，出队时总是取当前优先级最高或最低的元素。堆是最常见实现，但优先队列不等于堆；它也可以用有序数组、平衡树、跳表、桶队列、时间轮或多级反馈队列实现。

它的核心是把“先来先服务”变成“按规则服务”。规则可以是优先级、deadline、重试时间、租户权重、任务成本、错误次数或综合评分。调度器、限流器和重试系统都依赖优先队列表达“谁应该先被处理”。

面试里要区分两个层次：优先队列是接口，堆是实现。接口关心 `push`、`pop`、`peek`、`update`；实现才决定复杂度、稳定性、公平性和并发成本。业务里还要定义 tie-break，例如优先级相同时按创建时间或序号保证稳定。

## 53. 优先队列的时间复杂度、空间复杂度和适用场景是什么？

如果用二叉堆实现，`peek` 是 `O(1)`，`push` 和 `pop` 是 `O(log n)`，空间是 `O(n)`。Java `PriorityQueue` 文档也说明，入队和出队是对数时间，查看队首是常数时间，而按对象删除或 contains 是线性时间。这个差异很关键，因为“删除任意任务”不是堆天然擅长的操作。

如果用平衡树实现，插入、删除、取最小通常是 `O(log n)`，但范围能力更好。如果优先级范围很小，可以用桶队列把操作做到接近 `O(1)`。如果优先级是时间且允许精度误差，时间轮可能比堆更适合海量定时器。

适用场景包括任务调度、定时器、延迟消息、重试、限流排队、top K、异步工作队列和资源抢占。它不适合单纯 FIFO，也不适合需要随机访问任意元素的场景。优先级变化很频繁时，要确认实现是否支持高效 `decrease-key` 或 `fix`。

## 54. 优先队列在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

后端调度器用优先队列决定任务执行顺序。例如高优先级告警任务排在普通报表任务前面，deadline 更近的任务先执行，失败重试任务按下次重试时间入队。延迟消息队列也可以把消息按投递时间放入优先队列。

限流里，优先队列可以表达排队策略。被限流但允许等待的请求，按到达时间、用户等级、成本或 deadline 排队；令牌释放时弹出下一批请求。缓存里，优先队列可以维护候选淘汰对象，例如按过期时间、访问频率估计或对象成本排序。

负载均衡里，优先队列可用于控制面选择候选节点，例如健康恢复时间最早的节点、连接数最低的节点、需要探测的节点。请求级负载均衡如果每次都改全局优先队列，可能吞吐不好；更常见的是采样两个或几个节点，用局部信息近似全局最优。

## 55. 优先队列在并发场景下需要考虑哪些线程安全问题？

普通优先队列通常不是线程安全的。多个生产者和消费者同时 `push`、`pop`，必须保护内部结构。可以用互斥锁加条件变量实现阻塞优先队列；也可以用语言库里的线程安全版本，例如 Java 的 `PriorityBlockingQueue`，但仍要理解它的迭代和容量语义。

并发下还要考虑优先级反转和饥饿。高优先级任务源源不断时，低优先级任务可能永远执行不到。调度系统通常需要 aging、配额、租户隔离或多队列加权轮询，不能只靠一个单调优先级。

更新和取消任务尤其麻烦。如果任务已经在队列里，另一个线程要取消或改优先级，需要能定位它，并和消费者弹出动作互斥。常见方案是任务带状态机：queued、running、cancelled、done；消费者弹出后再检查状态。这样可以减少从堆中删除任意元素的复杂度，但会留下惰性垃圾，需要周期清理。

## 56. 环形缓冲区的核心思想是什么？

环形缓冲区的核心思想是用固定大小数组模拟一个首尾相接的队列。生产者在 `head` 写入，消费者在 `tail` 读取，索引到数组末尾后回到开头。这样同一块内存被反复复用，避免动态扩容和频繁分配。

它适合流式数据，因为流式系统关心稳定吞吐和可控内存。日志、指标、网络包、音视频帧、最近 N 条事件、生产者消费者队列，都可以用环形缓冲区。满了之后怎么办必须提前定义：阻塞、覆盖旧数据、丢弃新数据或返回失败。

面试里可以强调两个点：第一，它是固定容量结构，天然提供背压或丢弃边界；第二，它的内存连续，cache locality 好。如果容量是 2 的幂，索引回绕还可以用位与代替取模，降低热路径成本。

## 57. 环形缓冲区的时间复杂度、空间复杂度和适用场景是什么？

在已分配容量内，入队和出队都是 `O(1)`，查看空满也是 `O(1)`。空间复杂度是 `O(C)`，`C` 是固定容量。它不会随流量自动增长，这既是优点也是限制：内存上限明确，但容量估小了会产生阻塞或丢弃。

适用场景包括 SPSC 队列、日志缓冲、指标滑窗、网络收发队列、批处理缓冲、最近事件记录、无锁管道。它不适合需要无限排队、随机删除、按优先级调度或按 key 查找的场景。要做优先级，应该用优先队列；要做等值查找，应该配哈希表。

复杂度之外，还要看并发模型。单生产者单消费者最容易做到无锁；多生产者多消费者需要额外序号、CAS、锁或分段队列。Linux circular buffer 文档也明确把单生产者、单消费者作为使用内存屏障宏的前提之一。

## 58. 环形缓冲区在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

后端系统里，环形缓冲区常用于削峰和批量化。日志线程把事件写入 ring，后台线程批量刷盘；指标采集把最近 N 个样本写入 ring，聚合线程周期读取；网络线程把包描述符放入 ring，worker 线程消费。

负载均衡器可以用环形缓冲区保存最近连接事件、后端健康探测结果或 per-core packet queue。缓存系统可以保存最近访问 key 样本，用于近似 LRU、TinyLFU 采样或热点分析。限流系统可以用固定长度 ring 保存最近若干时间桶的计数，形成滑动窗口。

调度系统也能用它做就绪队列或事件队列，尤其是固定容量、低延迟、可丢弃的内部事件。要注意语义：如果任务不能丢，满了必须阻塞或落盘；如果只是观测数据，覆盖旧样本通常可接受。

## 59. 环形缓冲区在并发场景下需要考虑哪些线程安全问题？

并发环形缓冲区首先要明确生产者和消费者数量。SPSC 可以用两个索引加内存屏障做到很快；MPSC 或 MPMC 需要处理多个线程同时抢同一个槽位的问题。简单地把 `head++` 写成普通加法会丢更新。

还要处理可见性。生产者必须先写入数据，再发布新的 head；消费者必须先看到 head，再读取槽位数据，读完后再发布新的 tail。弱内存模型下，缺少 acquire/release 或锁，可能看到索引更新了但数据还没写完。

空和满的判定也容易出错。常见设计会浪费一个槽位，用 `head == tail` 表示空，用下一个 head 等于 tail 表示满；也可以引入计数或序号，但并发成本会上升。覆盖模式下要特别小心消费者读到正在被覆盖的槽位，必要时用序号校验每个槽位的生命周期。

## 60. 滑动窗口的核心思想是什么？

滑动窗口的核心思想是在连续数据流上维护一个随时间或位置移动的有限区间，只统计窗口内的数据，窗口外的数据过期。它可以按元素个数滑动，也可以按时间滑动。每来一个新事件，把它纳入窗口，同时移除过期事件或过期桶。

它解决的是“最近一段时间”或“最近 N 个元素”的问题。比如最近 1 分钟 QPS、最近 5 分钟错误率、最近 1000 次请求 P99、最近 10 秒每用户请求数。相比全量统计，滑动窗口只保留近期状态，更能反映当前系统压力。

实现上有多种形式。精确窗口可以用队列保存每个事件时间戳；固定桶窗口可以用环形数组保存多个时间桶；滑动日志保存所有请求记录；滑动计数器用当前桶和前一个桶加权估算。不同实现是在精确度、内存、CPU 和并发成本之间取舍。

## 61. 滑动窗口的时间复杂度、空间复杂度和适用场景是什么？

如果用队列保存事件，插入是 `O(1)`，清理过期事件的单次成本可能是 `O(k)`，但每个事件只进出一次，所以摊还是 `O(1)`。空间复杂度取决于窗口内事件数，突发流量下可能很大。精确但成本高。

如果用固定数量时间桶，更新当前桶是 `O(1)`，查询通常是 `O(B)` 或维护滚动总和做到 `O(1)`，`B` 是桶数。空间复杂度是 `O(B)` 或 `O(keys * B)`。桶越细越精确，但内存和清理成本越高；桶越粗越便宜，但边界误差越大。

适用场景包括限流、熔断、错误率统计、SLA 监控、热点检测、滑动 UV、最近延迟分布和异常检测。不适合需要全历史精确统计的场景，也不适合窗口 key 基数无限增长却没有过期清理的设计。每个用户一个窗口时，高基数是主要风险。

## 62. 滑动窗口在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

限流是最直接的应用。对每个用户或 IP 维护最近 60 秒请求数，超过阈值就拒绝或排队。相比固定窗口，滑动窗口减少了边界突刺问题，因为窗口不是按整分钟突然清零，而是随时间推进。

熔断和负载均衡也依赖滑动窗口。服务实例最近一段时间的错误率、超时率、平均延迟、P99 延迟，可以作为摘除、降权或探测恢复的依据。缓存系统可以用滑动窗口发现热点 key：最近几秒访问频率异常高的 key 进入本地缓存、副本扩散或请求合并。

调度系统里，滑动窗口可以统计 worker 最近吞吐、失败数和运行时间，避免只看瞬时值。它的优势是对近期变化敏感，但不会被单个瞬间完全支配。要注意窗口长度：太短会抖，太长会迟钝。

## 63. 滑动窗口在并发场景下需要考虑哪些线程安全问题？

滑动窗口通常是多线程高频更新结构。最简单的全局锁会影响吞吐，尤其是按用户或接口维度更新时。常见优化是按 key 分片、按 CPU 分片、使用原子计数器、LongAdder 或本地累加后周期合并。

时间推进也要一致。多个线程同时发现桶过期并重置，可能把刚写入的新计数清掉。正确做法是每个桶保存时间戳或 epoch，重置时用 CAS 或锁确认它确实属于旧时间片。读取总量时，要决定是否接受弱一致结果；监控和限流通常可接受轻微误差，但计费不行。

分布式场景还要处理时钟和聚合。不同节点本地窗口可能时间不齐，汇总窗口会出现边界偏差。集中式 Redis 计数可以简化一致性，但增加网络开销和热点风险；本地窗口吞吐高，但全局限流不精确。设计时要明确是本地保护还是全局配额。

## 64. 令牌桶的核心思想是什么？

令牌桶的核心思想是系统按固定速率往桶里放令牌，桶有最大容量；请求到来时必须拿到令牌才能通过，拿不到就拒绝、等待或降级。桶容量允许短时间突发，补充速率限制长期平均速率。

它和滑动窗口不同，不直接统计最近多少请求，而是维护一个可消费额度。长时间空闲会积累令牌，直到达到上限；突发请求可以一次性消耗积累的令牌。这样既能保护后端平均负载，又允许真实业务中的短突发。

工程实现通常保存三个字段：当前令牌数、最后补充时间、桶容量和速率。请求到来时先根据时间差补充令牌，再判断是否足够消费。Envoy 的 TokenBucket 配置也体现了这几个要素：最大令牌数、每次补充数量和补充间隔。

## 65. 令牌桶的时间复杂度、空间复杂度和适用场景是什么？

单个令牌桶的请求判断是 `O(1)`，空间也是 `O(1)`。如果按用户、租户、接口维度各维护一个桶，总空间是 `O(K)`，`K` 是活跃 key 数。高基数场景下，真正的成本不是单个桶，而是桶状态的创建、查找、过期和清理。

令牌补充可以惰性计算，不必开定时器每毫秒给每个桶加令牌。请求到来时用 `now - lastRefill` 算应补令牌数，再截断到容量上限。这样空闲桶没有后台成本。需要排队等待时，还要计算下一次可用时间。

适用场景包括 API 限流、网关限速、租户配额、消息发送速率、后台任务提交速率和网络流量整形。它适合允许突发但限制长期平均的系统。不适合严格匀速输出，如果必须平滑发送，就要配合漏桶或队列调度。

## 66. 令牌桶在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

API 网关常按用户、IP、租户、接口维度放一个令牌桶。请求先按维度定位桶，消费成功就放行，失败就返回限流、排队或降级。多级限流也常见：全局桶保护集群，租户桶保护公平性，接口桶保护单个依赖。

负载均衡里，令牌桶可以限制某个后端实例的新连接速率，避免刚恢复的节点被流量打满。缓存系统可以用令牌桶限制回源速率，防止缓存失效时大量请求同时冲击数据库。任务调度器可以按队列或租户发放令牌，控制任务启动速率。

在分布式限流里，令牌桶可以集中在 Redis 或专门限流服务，也可以在每个实例本地维护。集中式更一致，但增加网络延迟和单点热点；本地桶吞吐高，但全局配额只能近似。很多系统会把全局配额拆成本地份额，再周期调整。

## 67. 令牌桶在并发场景下需要考虑哪些线程安全问题？

单机多线程下，令牌数和最后补充时间必须一起更新。否则两个线程可能都看到同一批令牌并同时放行，导致超发。可以用互斥锁保护桶，也可以用 CAS 循环更新一个打包状态。由于每个请求都触碰桶，热点 key 会产生严重争用。

按 key 分桶时，要处理桶对象的并发创建和过期删除。`get or create bucket` 必须是原子的，删除空闲桶时不能删掉正在使用的桶。常见做法是哈希表分片加锁，或者使用并发 map 加引用时间，后台只清理长时间未访问且状态稳定的桶。

分布式并发更难。多个实例本地消费同一个全局配额，会超卖；集中式 Redis 脚本能保证原子性，但网络和 Redis 热点会限制吞吐。要么接受近似，要么用租约、预分配令牌、分层令牌桶或强一致限流服务。面试里要说清楚：令牌桶算法简单，难点在并发状态和全局一致性。
## 68. 漏桶的核心思想是什么？

漏桶的核心思想是请求先进入一个有限队列，系统按固定速率从队列里取出并处理。水倒进桶里可以忽快忽慢，但从桶底漏出的速度稳定；桶满了以后，新来的请求要么被丢弃，要么被拒绝。

它强调平滑输出。令牌桶允许积累令牌后突发放行，漏桶更关注把突发流量整形成稳定速率。对后端依赖来说，漏桶能减少瞬间冲击；对用户来说，它可能增加排队延迟。NGINX `limit_req` 文档就把按 key 限制请求处理速率描述为漏桶方法。

漏桶可以用队列加定时出队实现，也可以用“理论到达时间”或 GCRA 这类方式不显式排队。面试里可以把它和令牌桶对比：令牌桶限制平均速率并允许突发，漏桶限制输出速率并平滑突发。

## 69. 漏桶的时间复杂度、空间复杂度和适用场景是什么？

如果用显式队列实现，入队和出队通常是 `O(1)`，空间复杂度是 `O(C)`，`C` 是队列容量。容量越大，能吸收的突发越多，但最坏排队延迟越高。容量为 0 或很小时，就更接近直接拒绝超速请求。

如果用时间戳算法实现，每个 key 只保存少量状态，例如上次允许时间或理论到达时间，判断是 `O(1)`，空间是 `O(K)`。这种方式不保存请求队列，只决定请求是否可以立即通过或需要等待。它适合网关限流和高吞吐场景。

适用场景包括 API 网关平滑请求、消息发送整形、下游保护、固定速率任务派发和网络流量控制。不适合业务必须快速吸收合法突发的场景，也不适合长时间排队后请求已经失去意义的交互接口。此时要设置最大等待时间或直接失败。

## 70. 漏桶在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

后端系统里，漏桶常用于保护慢依赖。比如数据库写入、短信发送、第三方 API 调用，都可以用漏桶把上游突发请求平滑成固定出流。请求过多时，超过队列容量的部分直接拒绝，避免依赖被打穿。

负载均衡里，漏桶可以按后端实例限制新连接或请求转发速率，尤其适合刚上线、刚恢复、缓存未预热的实例。缓存系统可以用漏桶控制回源速度，让缓存失效后的请求按固定速率访问数据库。调度系统可以用漏桶控制任务启动速率，避免一批任务同时抢 CPU、磁盘或外部配额。

限流策略里，漏桶常和令牌桶组合。令牌桶决定是否允许一定突发，漏桶负责把允许的请求排队平滑输出。组合时要明确拒绝点：是拿不到令牌就拒绝，还是队列满才拒绝；不同选择会影响用户延迟和后端压力。

## 71. 漏桶在并发场景下需要考虑哪些线程安全问题？

显式队列实现时，多生产者入队和消费者定速出队都要同步。队列满的判断、入队、排队长度更新必须是原子的，否则会超容量。阻塞等待时还要防止线程堆积，通常网关不会让业务线程无限等待，而是用异步队列和超时。

时间戳实现时，要原子更新下一次允许时间。多个线程同时判断同一个 key，如果都看到旧时间，就会一起放行，破坏速率。可以用锁、CAS 或 Redis Lua 脚本保证“读取时间、计算、写回”是一个不可分割的步骤。

分布式漏桶还要处理时钟。不同节点的本地时钟不一致，会导致放行速率不稳定。集中式状态可以统一时钟但有网络开销；本地状态吞吐高但只能近似全局速率。高可用设计还要考虑限流服务故障时是 fail-open 还是 fail-closed。

## 72. LRU 的核心思想是什么？

LRU 是 Least Recently Used，核心思想是淘汰最近最少使用的对象。它假设最近访问过的数据在不久后更可能再次被访问。实现上通常用哈希表加双向链表：哈希表负责 `O(1)` 找节点，链表按访问时间排序，最近访问的放到头部，淘汰时从尾部删除。

每次读或写命中后，都要把节点移动到最近端；插入新对象时放到最近端；容量满时淘汰最旧端。这个逻辑直观，适合有明显时间局部性的缓存，例如用户资料、配置、热点商品、模板和连接元数据。

LRU 的弱点是容易被扫描污染。如果一次性顺序读入大量只访问一次的数据，它们会把真正热点挤出去。真实系统常用近似 LRU、分段 LRU、2Q、ARC 或 TinyLFU 来改进，而不是在所有场景坚持严格 LRU。

## 73. LRU 的时间复杂度、空间复杂度和适用场景是什么？

标准哈希表加双向链表实现中，`get`、`put`、移动节点、删除尾节点都是 `O(1)`。空间复杂度是 `O(n)`，每个缓存项除了 key/value，还要存链表前后指针和哈希表条目。严格 LRU 的额外元数据不算小。

适用场景是访问具有时间局部性、对象大小相近、命中后应提升优先级的缓存。比如本地配置缓存、短期会话缓存、小对象缓存。Redis 文档也提到实际系统为了节省内存，可能使用近似 LRU，通过采样选择淘汰候选。

不适合的场景包括大范围顺序扫描、周期性访问集合大于缓存容量、对象大小差异极大、访问频率比最近性更重要的 workload。严格 LRU 还会在每次命中时修改链表，高并发读多场景下可能因为“读也写元数据”产生锁争用。

## 74. LRU 在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

缓存是 LRU 的主场。服务进程可以用 LRU 缓存用户资料、权限、路由配置、模板渲染结果、数据库查询结果。容量满时淘汰最近最久没访问的项，能比较好地保留近期热点。

负载均衡和网关里，LRU 可以管理连接跟踪、会话粘滞表、DNS 解析结果、证书或路由规则缓存。限流系统可以用 LRU 清理长时间不活跃的 key 状态，避免每个曾经访问过的 IP 都永久占用内存。调度系统也可以用它保留最近活跃任务或 worker 的元数据。

需要注意的是，LRU 负责容量管理，不负责正确性。比如限流 key 被 LRU 淘汰后，相当于状态重置，可能让低频攻击者绕过长期限制。连接跟踪被淘汰后，也可能导致后续包重新选择后端。使用 LRU 时要确认状态丢失是否可接受。

## 75. LRU 在并发场景下需要考虑哪些线程安全问题？

LRU 的并发难点是命中也要修改链表。读请求看似只读 value，但为了更新最近性，需要把节点移到链表头。多线程同时移动节点，如果没有锁，会破坏前后指针。全局锁简单但吞吐差，分片 LRU 是常见优化。

还要处理淘汰和读取的生命周期。一个线程拿到 value，另一个线程可能同时淘汰并释放该节点。托管语言依赖 GC 会安全一些；手动内存管理需要引用计数、epoch 或延迟释放。对象有关闭动作时，比如连接或文件句柄，淘汰回调不能在持锁状态下执行太久，否则会拖慢所有缓存访问。

近似 LRU 能减少锁压力。比如只记录访问时间戳，淘汰时采样几个候选；或者每个 shard 一个小 LRU；或者把读命中的移动操作异步批量处理。牺牲一点精确性，常常换来更稳定的并发性能。

## 76. LFU 的核心思想是什么？

LFU 是 Least Frequently Used，核心思想是淘汰访问频率最低的对象。它假设长期高频访问的数据更值得留在缓存里。与 LRU 看“最近一次访问时间”不同，LFU 看“访问次数”或频率估计。

严格 LFU 通常要维护 key 到节点的映射、频率到链表的映射，以及当前最小频率。命中时频率加一，节点从旧频率链移动到新频率链；淘汰时从最小频率链里删除一个对象。为了处理同频对象，常在同一个频率桶内再按 LRU 淘汰。

LFU 的难点是历史污染。一个对象过去很热，现在不热，如果计数永远累加，它会长期占据缓存。所以工程实现通常加入衰减、窗口、近似计数或周期重置。Redis 的 LFU 就是近似频率加衰减，而不是严格保存无限增长的精确计数。

## 77. LFU 的时间复杂度、空间复杂度和适用场景是什么？

严格 LFU 可以做到 `get`、`put`、频率更新和淘汰都是 `O(1)`，但实现比 LRU 复杂，需要多层链表和多个哈希表。空间复杂度是 `O(n)`，常数开销更高。近似 LFU 则用小计数器、采样和衰减减少内存，但结果不再精确。

适用场景是访问频率稳定、热点长期存在、扫描流量不应轻易冲掉热点的缓存。例如热门商品、热门配置、热门模型、热门文章。相比 LRU，LFU 更能抵抗一次性扫描，但对快速变化热点反应慢。

不适合的场景是热点变化很快、对象生命周期短、频率计数成本不能接受的热路径。如果不做衰减，LFU 会记住过期历史；如果衰减太快，又退化得接近 LRU 或随机。参数需要结合实际 workload 调整。

## 78. LFU 在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

缓存里，LFU 用于保留真正高频对象。比如热点商品详情、公共配置、热门搜索结果、常用权限模板，比偶然刚访问过的一次性对象更值得留在内存里。对于读多且热点稳定的系统，LFU 往往比纯 LRU 更抗扫描。

负载均衡和网关可以用 LFU 思路识别热点 key。访问频率高的租户、接口、URL、对象 ID 可以进入特殊保护：本地缓存、副本扩散、请求合并、预热或更严格限流。限流系统本身也可以用近似 LFU 找重频请求源，优先对它们应用更细粒度策略。

调度里，LFU 可以辅助资源分配，但不应直接等同于优先级。频率高的任务源可能只是噪声或攻击源，不一定应该获得更多资源。更常见的用法是观测和保护：识别高频对象，再交给策略层决定缓存、隔离或限流。

## 79. LFU 在并发场景下需要考虑哪些线程安全问题？

LFU 的命中路径会更新频率，比 LRU 更容易产生写热点。每次访问都可能修改计数器、移动链表节点、更新最小频率。如果用全局锁，热点 key 会拖慢整个缓存；如果拆分锁，要保证 key 节点、频率桶和最小频率之间的一致性。

计数器更新可以用原子操作或分片计数降低争用，但节点跨频率桶移动仍然需要同步。近似 LFU 常用小计数器和采样，减少每次访问都调整复杂结构的成本。Redis 这类实现用概率计数和衰减，就是在准确度和并发成本之间取工程平衡。

并发淘汰时还要防止频率信息和缓存项生命周期不同步。一个线程命中并准备提升频率，另一个线程可能已经淘汰该项。需要状态检查、版本号或节点锁。不要在淘汰回调里持有全局结构锁做慢操作。

## 80. TinyLFU 的核心思想是什么？

TinyLFU 的核心思想不是直接替换缓存里的对象，而是做缓存准入。新对象想进入缓存时，TinyLFU 用一个紧凑的频率估计结构判断它是否比当前淘汰候选更值得留下。如果新对象历史频率不高，就算刚被访问，也可能不让它进入主缓存。

它通常用 Count-Min Sketch 一类近似计数结构记录近期访问频率，并配合周期性衰减，让旧历史逐渐失效。这样可以用很小内存估计大量 key 的访问频率。W-TinyLFU 还会加一个小窗口区，让新对象先有短暂机会，再和主缓存候选比较。

所以 TinyLFU 解决的是 LRU 容易被扫描污染、LFU 精确计数太重的问题。它不追求知道每个 key 的精确次数，而是用近似频率帮助回答一个问题：这个新来的对象是否值得挤掉缓存里已有对象？

## 81. TinyLFU 的时间复杂度、空间复杂度和适用场景是什么？

TinyLFU 的访问更新通常是 `O(d)`，`d` 是 sketch 深度，工程上是小常数。准入比较也是常数级：估计新对象频率，估计候选对象频率，再决定是否接纳。空间复杂度主要来自 sketch，通常远小于保存所有 key 精确计数的哈希表。

它适合大规模缓存、访问分布偏斜、存在扫描流量、热点会变化但不希望被瞬时噪声冲掉的场景。Caffeine 这类现代本地缓存采用 W-TinyLFU 思路，就是因为它在很多真实 workload 下比单纯 LRU 或 LFU 更稳。

限制是近似结构会有误差，低频 key 的估计可能被冲突抬高；衰减周期、sketch 大小、窗口比例都会影响效果。TinyLFU 还需要一个底层淘汰结构配合，例如 SLRU、LRU 或其他队列。它是准入策略，不是完整缓存的全部。

## 82. TinyLFU 在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

缓存系统是 TinyLFU 最合适的应用。服务本地缓存、网关缓存、对象缓存、模型元数据缓存，都可能遇到扫描污染：大量只访问一次的 key 把真正热点挤出去。TinyLFU 用准入判断拦住这些低价值对象，让主缓存保留更可能复用的数据。

网关和负载均衡也可以借用 TinyLFU 的思想做热点识别。不是每个刚出现的 key 都立刻进入重保护路径，而是先通过近似频率观察一段时间；只有超过候选阈值的 key 才进入本地缓存、请求合并、热点副本或特殊限流策略。

限流和调度中，TinyLFU 可以辅助识别高频主体，但不要直接把它当精确计数器。它适合做“是否值得投入更多资源”的判断，不适合做收费、审计或安全判定。误差和衰减是设计的一部分，策略层要能接受近似。

## 83. TinyLFU 在并发场景下需要考虑哪些线程安全问题？

TinyLFU 的并发重点在 sketch 更新和准入决策。Count-Min Sketch 的多个计数器需要递增，多个线程同时更新可能丢增量。可以用原子计数器、分片 sketch、本地缓冲后合并，或者接受少量统计误差。由于 TinyLFU 本来就是近似结构，很多实现会优先控制开销，而不是追求每次更新完全精确。

衰减也要同步。周期性把计数减半时，如果和并发增量交错，可能丢失新访问或让某些计数异常。常见办法是分代 sketch、双缓冲、后台维护，或在锁内做批量衰减。衰减不能长时间阻塞请求路径，否则准入策略会反过来拖慢缓存。

准入决策还要和底层缓存淘汰保持一致。线程 A 选中一个候选项准备比较，线程 B 可能已经淘汰或提升了它。实现上通常需要缓存分片锁、版本检查或在同一临界区内完成候选选择和接纳。面试里可以这样总结：TinyLFU 的算法近似不难，难点是把 sketch、窗口缓存、主缓存和并发淘汰连成一个低争用的整体。
## 84. 位图的核心思想是什么？

位图的核心思想是用一个 bit 表示一个状态。假设对象可以映射成非负整数 ID，那么第 `i` 个 bit 就表示 ID 为 `i` 的对象是否存在、是否在线、是否命中、是否具备某个权限。它把一个布尔集合从“每个元素一个对象或一条记录”压缩成“每个元素一个 bit”。

这个结构的优势来自两个地方。第一，空间密度高，8 个布尔状态只占 1 个字节，适合 ID 范围明确、状态只有 0/1 的场景。第二，CPU 能按机器字做批量位运算，`AND`、`OR`、`XOR`、`AND NOT` 一次可以处理 32 位、64 位甚至 SIMD 宽度的数据。两个集合求交、求并、求差时，位图不是逐个元素比较，而是按 word 扫过去。

位图也不是万能集合。它要求元素能映射到相对紧凑的整数空间。如果用户 ID 最大到了几十亿，但实际只有几万个用户，用普通位图会浪费大量空洞空间。它也只能直接表达布尔状态，不能保存对象属性。要表达计数、时间戳或多值状态，就要用多个位图、位段、数组或别的结构配合。

面试里可以这样概括：位图是用 bit offset 代替哈希桶或对象节点，用极低空间和位并行操作来处理大规模布尔集合。适合“范围可控、状态二元、批量集合运算多”的问题，不适合稀疏到极端的 ID 空间和需要保存复杂值的场景。

## 85. 位图的时间复杂度、空间复杂度和适用场景是什么？

单点设置和查询通常是 `O(1)`：先通过 `index / wordSize` 找到机器字，再通过 `index % wordSize` 找到 bit，最后做掩码操作。单个 bit 的设置、清除、翻转、读取都很快。统计一个位图中 1 的数量通常是 `O(m)`，`m` 是机器字数量；现代 CPU 有 popcount 指令，所以常数很小，但它仍然要扫描相关范围。

空间复杂度是 `O(U)` bit，`U` 是可寻址的 ID 范围，而不是实际元素个数 `n`。如果 ID 范围是 1 亿，位图大约需要 1 亿 bit，也就是约 12 MB；如果只有 10 万个真实元素但最大 ID 接近 1 万亿，普通位图就不划算。这也是位图和哈希集合最重要的差别：哈希集合空间跟真实元素数接近线性，普通位图空间跟最大编号范围线性相关。

适用场景包括在线用户标记、签到、权限位、特征开关、人群包、去重标记、已处理 offset、可用资源编号、端口占用、AB 实验命中集合。Redis 的 bitmap 其实是基于 String 的位操作，提供 `SETBIT`、`GETBIT`、`BITCOUNT`、`BITOP` 这类能力，常用于按天签到、活跃用户和布尔状态统计。

边界是稀疏性和维护成本。普通位图适合稠密或上界可控的数据；如果数据稀疏，就考虑 Roaring Bitmap、EWAH、WAH、稀疏集合或哈希集合。还有一个实际问题是迁移和扩容：一旦 ID 映射规则变了，位图 offset 的含义也变了，所以 ID 编码要稳定，不能随便重排。

## 86. 位图在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

在后端系统里，位图很适合做快速资格判断。比如某用户是否参加活动、某账号是否命中灰度、某资源位是否被占用、某任务 shard 是否已经完成，都可以把 ID 映射到 bit。读取路径只需要一次数组访问和一次位运算，适合高 QPS 判断。

在负载均衡和调度里，位图可以表达可用节点集合、故障节点集合、机房集合、标签集合。调度器先用多个位图做交集，例如“健康节点 AND 同机房节点 AND 有 GPU 节点 AND 未满载节点”，再从结果里选择目标。这样比遍历所有节点逐个判断标签更快，尤其是节点规模大、筛选条件多的时候。

在缓存里，位图常用来做存在性辅助和批量失效标记。比如某批 key 是否已经预热、某个对象是否是热对象候选、某个 shard 的数据是否已经加载完。它也可以做非常粗粒度的负缓存：如果 ID 范围固定，某个 ID 的 bit 为 0 就直接判断不存在。但这和布隆过滤器不同，位图没有误判，代价是需要为整个 ID 空间付出空间。

在限流里，位图不适合单独做次数限制，但适合做窗口内去重或状态标记。比如同一用户在一个时间窗口内是否已经领取过令牌、某个 IP 是否已被临时封禁、某个秒级桶里哪些用户出现过。再配合 `BITCOUNT` 可以估算窗口内出现过多少不同 ID。

## 87. 位图在并发场景下需要考虑哪些线程安全问题？

位图并发的核心问题是同一个机器字里包含多个 bit。两个线程看似在设置不同 bit，但如果它们落在同一个 word 上，底层操作通常是读出 word、修改某个 bit、写回 word。没有原子操作或锁保护时，一个线程可能覆盖另一个线程刚设置的 bit，造成丢更新。

解决方式取决于写入模式。低并发可以对整个位图或分段加锁；高并发可以按 word 使用原子 `OR`、原子 `AND`、CAS 循环；写入分散时可以按 shard 拆成多个位图减少争用。只增不删的标记位最容易做，因为设置 bit 可以用原子 OR。清除 bit 更危险，因为它会把某一位变成 0，如果和另一个线程设置同一 word 交错，必须确保不会误清别的位。

批量操作也要考虑一致性。一个线程正在做 `BITCOUNT` 或集合交集，另一个线程同时写入，读到的是某个中间状态。监控统计通常可以接受近似快照；权限判断、资源分配、任务完成确认则不能随便接受不一致。需要强一致时，要在同一把锁、版本号、读写锁或 copy-on-write 快照上完成读写。

还要注意 false sharing。多个高频 bit 落在同一个 cache line 上，不同 CPU 核心反复写，会让缓存行来回失效，吞吐下降。工程上可以通过分片、按主体哈希分散、局部聚合后合并来缓解。位图看起来只是数组，放进高并发路径后，原子粒度和 cache line 粒度才是真正的性能边界。

## 88. Roaring Bitmap 的核心思想是什么？

Roaring Bitmap 的核心思想是压缩位图，但不把所有数据都压成一种格式。它把 32 位整数按高 16 位分块，每个块最多覆盖 65536 个低位值。每个块再根据稀疏程度选择不同容器：稀疏时用有序数组容器，稠密时用普通 bitmap 容器，连续区间多时用 run 容器。

这样做的好处是适应不同数据分布。普通位图在稀疏数据上浪费空间，纯数组集合在密集数据上集合运算慢，RLE 压缩在无长连续区间的数据上也不一定好。Roaring 通过分块和容器切换，把稀疏、稠密、连续三类局部形态分别处理。每个容器内部还能用二分、位运算或区间运算来优化。

Roaring 的另一个关键点是集合运算按容器进行。两个 Roaring Bitmap 求交时，先匹配高 16 位相同的块，再根据容器类型选择最合适的算法：数组和数组可以双指针，bitmap 和 bitmap 可以按 word 做 AND，run 和其他容器可以走区间逻辑。它不是简单地把压缩数据解开再算。

面试里可以这样说：Roaring Bitmap 是“分块索引 + 自适应容器”的压缩位图。它保留了位图适合批量集合运算的优势，又避免普通位图在稀疏大 ID 空间上的空间浪费。数据库索引、搜索倒排、OLAP 标签过滤、人群圈选都常用这种结构。

## 89. Roaring Bitmap 的时间复杂度、空间复杂度和适用场景是什么？

Roaring Bitmap 的单点查询通常先按高 16 位找到容器，再在容器里查询低 16 位。如果顶层容器索引用有序数组，查容器是 `O(log c)`，`c` 是容器数量；容器内数组查询是 `O(log k)`，bitmap 容器查询是 `O(1)`，run 容器按区间数量查询。很多实现会优化顶层索引和容器查找，所以实际常数比较低。

插入和删除的成本也取决于容器类型。数组容器插入可能要移动元素，bitmap 容器设置 bit 是常数级，run 容器要维护区间合并和拆分。容器可能在数组、bitmap、run 之间转换，例如数组元素超过阈值后转成 bitmap，以换取后续操作速度。

空间复杂度和数据分布强相关。稀疏块用数组保存真实低位值，空间接近 `O(n)`；稠密块用 65536 bit，也就是 8 KB 左右；连续数据用 run 容器会更省。相比普通位图，它不会为没有出现过的高位块分配整段空间，所以适合大 ID 空间里局部稀疏、局部密集的数据。

适用场景是需要频繁集合运算的系统：搜索引擎倒排列表、广告人群定向、权限集合、OLAP 多条件过滤、时间序列标签索引、推荐候选过滤。它不适合每次只存几个元素的小集合，也不适合频繁按随机位置做大量细粒度写入且几乎不做集合运算的场景，因为容器维护和对象分配会带来额外成本。

## 90. Roaring Bitmap 在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

后端系统里，Roaring Bitmap 很适合做标签和属性过滤。比如用户画像里有“城市=上海”“近 7 天活跃”“会员等级=金牌”这些集合，每个集合对应一个 bitmap。查询时把多个集合做交集，就能得到候选用户 ID。相比 SQL 一行行扫或哈希集合逐项判断，位运算能把批量过滤做得更紧凑。

缓存系统可以用 Roaring Bitmap 维护 key 分组和失效集合。比如某个租户、某个商品类目、某个活动下有哪些缓存 key，可以映射成 ID 后放入 bitmap；批量失效时先拿到集合，再异步删除。它也适合做预热任务的完成集合、已回源集合和热点 key 候选集合。

调度系统可以把候选资源建成多个 Roaring Bitmap：可用节点、满足标签的节点、有空闲配额的节点、某机房节点。一次调度请求进来，先做集合交集得到候选，再按负载或一致性哈希选具体节点。这个思路适合节点数很大、过滤条件复杂、条件集合变化不太频繁的资源调度。

限流场景中，Roaring Bitmap 可以记录窗口内出现过的主体集合，例如某分钟访问过接口的用户 ID、触发过风控规则的 IP 编号。它更适合“去重后的主体集合”和“批量分析”，不适合直接做精确请求次数，因为次数需要计数器或 sketch 来表达。

## 91. Roaring Bitmap 在并发场景下需要考虑哪些线程安全问题？

Roaring Bitmap 的并发难点比普通位图更复杂，因为它不只是一个 bit 数组，还包含顶层容器索引和可变容器。插入一个值可能导致数组容器扩容、元素移动，甚至转换成 bitmap 容器；删除也可能触发容器缩小或移除。如果多个线程同时修改同一个 bitmap，没有锁或不可变结构保护，很容易破坏容器内部有序性和顶层索引一致性。

读写并发也要特别小心。一个线程正在做交集，另一个线程把某个容器从数组转成 bitmap，读线程如果拿到旧引用或半更新状态，结果可能错。常见做法是把 Roaring Bitmap 当不可变对象使用：构建新版本后通过原子引用发布，读线程只读快照；或者按 bitmap、按容器、按分片加锁，保证集合运算期间结构不变。

批量合并时还要考虑版本一致性。多个 shard 各自维护 bitmap，汇总线程读取时可能看到不同时间点的数据。如果只是监控和画像分析，可以接受最终一致；如果用于权限、配额或任务去重，需要版本号、水位线或事务边界。

另外，Roaring 的容器级操作常有内部临时对象。高并发下频繁构造交集、并集，可能造成内存分配和 GC 压力。工程上会用只读快照、对象池、批量合并、后台构建和前台原子切换来控制开销。面试里要说明：Roaring 的读性能强，但可变压缩结构并不天然线程安全。

## 92. HyperLogLog 的核心思想是什么？

HyperLogLog 解决的是大规模去重计数，也就是估算 distinct count。它不保存每个元素，而是先把元素哈希成均匀随机的二进制串，再观察哈希值里出现“长串前导零”的情况。直觉是：如果你看到了一个前导零很多的哈希值，说明样本规模大概率已经不小，因为这种哈希模式本身很罕见。

单独看一个最大前导零会很不稳定，所以 HyperLogLog 把哈希空间分成很多桶，也叫 registers。哈希值的一部分决定落到哪个 register，剩下部分用来计算前导零长度。每个 register 只记录自己见过的最大前导零长度。估算时把所有 register 的信息做调和平均，再做偏差修正，得到整体基数估计。

它的关键取舍是牺牲精确性换固定空间。比如 Redis 的 HyperLogLog 最大只用十几 KB 级别内存，就能估算非常大的去重规模，误差在工程上可控。它不能告诉你具体有哪些元素，也不能精确判断某元素是否出现过；它只回答“不同元素大约有多少个”。

面试里可以这样答：HyperLogLog 是概率基数估计算法，用哈希随机性和多个 register 的最大前导零统计来估算集合去重规模。适合 UV、独立 IP、去重设备数、唯一请求 ID 等规模统计，不适合精确计费、权限判断或需要列出成员的场景。

## 93. HyperLogLog 的时间复杂度、空间复杂度和适用场景是什么？

单个元素写入通常是 `O(1)`：计算哈希，定位 register，更新最大前导零值。查询估算值需要遍历所有 register，理论上是 `O(m)`，`m` 是 register 数；但很多实现的 `m` 是固定的，所以对用户看起来近似常数。合并多个 HyperLogLog 时，对每个 register 取最大值，成本是 `O(m)` 或 `O(km)`，`k` 是待合并结构数量。

空间复杂度是 `O(m)`，与真实 distinct 数量无关。`m` 越大，误差越小，典型相对标准误差约与 `1 / sqrt(m)` 成正比。也就是说，想把误差降低一半，通常要把 register 数增加约四倍。这个空间和精度的关系，是 HyperLogLog 调参的核心。

适用场景是对“数量级和趋势”敏感、对单次精确值不敏感的系统指标。比如每天独立访客、每个接口的独立调用方、每个租户的活跃用户数、DDoS 期间独立源 IP 估算、搜索词独立用户数。它特别适合分布式统计，因为各节点可以本地维护 HLL，最后通过 register-wise max 合并。

不适合的场景也要说清楚。它不能删除单个元素，除非使用特殊变体或按时间分桶重建；不能判断成员是否存在；不能精确算交集，只能通过并集估算和容斥做近似，而且误差会叠加。需要精确审计、账单、库存、风控处罚时，HLL 只能做旁路指标，不能做最终依据。

## 94. HyperLogLog 在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

后端系统里最常见的是 UV 和去重规模统计。每个服务实例维护本地 HLL，记录请求用户、设备、trace_id、IP 或租户 ID，周期性上报后合并，就能得到全局近似 distinct。相比把所有 ID 打到中心集合里，HLL 的网络和内存成本都低得多。

在负载均衡中，HLL 可以估算每个后端接触到的不同客户端数量，帮助发现负载倾斜。两个节点 QPS 接近，但一个节点独立用户数很低，可能说明它被少数热点 key 打爆；另一个节点独立用户数很高，说明流量更分散。这个指标可以辅助热点识别，而不是直接替代负载均衡算法。

缓存系统可以用 HLL 估算 key、租户或接口的独立访问主体数。比如某个缓存 key 被多少不同用户访问，能帮助判断它是全局热点还是少数用户反复访问。限流里也可以估算窗口内独立 IP 或独立账号数量，辅助识别攻击扩散面。

调度系统中，HLL 可以用作容量规划指标：某任务接触多少不同用户、某批消息覆盖多少不同实体、某个 shard 的 distinct key 数是否异常增长。但它只给近似规模，不给具体成员列表，所以后续处置仍要结合日志、采样或精确集合。

## 95. HyperLogLog 在并发场景下需要考虑哪些线程安全问题？

HyperLogLog 的并发写入看似只是更新一个 register，但更新规则是 `max(old, new)`。如果多个线程同时写同一个 register，必须保证不会把较大的值覆盖成较小的值。可以用原子 CAS 循环、按分片加锁、线程本地 HLL 后台合并，或者利用单线程存储系统提供的命令原子性。

合并也要有一致性边界。一个线程正在把多个 HLL 合成全局视图，另一个线程还在写其中某个 HLL，最终结果可能是混合时间点。监控系统通常可以接受这种近似；如果报表需要固定时间窗口，就要按窗口切分 HLL，在窗口结束后冻结，再合并冻结版本。

稀疏编码和密集编码切换是另一个风险。很多实现为了节省内存，会先用稀疏格式保存少量 register，规模变大后转成密集数组。这个转换必须和读写互斥，或者通过 copy-on-write 发布新结构。否则读线程可能读到格式切换中的半成品。

最后要注意分布式并发的幂等性。HLL 添加同一个元素多次不会影响估算，这点对重试友好；但重复合并同一个已合并结果、窗口归属错误、哈希 seed 不一致，会让统计口径乱掉。并发安全不只是内存竞争，还包括窗口、水位线和哈希配置的一致。

## 96. Count-Min Sketch 的核心思想是什么？

Count-Min Sketch 解决的是流式频率估计。它用多行计数数组和多组哈希函数来记录元素出现次数。一个元素到来时，每一行用对应哈希函数找到一个列位置，并把那个计数器加一。查询某个元素时，也在每一行找到对应计数器，然后取这些计数器的最小值作为估计频次。

为什么取最小值？因为哈希冲突只会把别的元素计数加到当前元素的格子里，使估计值偏大，不会偏小。在多行哈希下，只要有一行冲突少，这一行的计数就更接近真实值。取最小值就是在多次有偏估计里选污染最轻的那个。

它的本质是用固定大小的二维数组近似一个巨大的频率表。你不需要为每个 key 存一条记录，也不需要知道全集有多大。代价是结果有误差，尤其是低频元素容易被高频元素的冲突抬高。Redis 的 Count-Min Sketch 文档也强调它更适合关注高频项，低于误差阈值的结果应当当成噪声看待。

面试里可以这样说：Count-Min Sketch 是用多组哈希和计数器矩阵做近似频率统计的概率结构。它适合流式数据、热点识别、heavy hitter 辅助、缓存准入和异常检测，但它返回的是上界倾向的估计值，不是精确计数。
## 97. Count-Min Sketch 的时间复杂度、空间复杂度和适用场景是什么？

更新一个元素的时间复杂度是 `O(d)`，`d` 是哈希函数数量，也就是 sketch 的深度。查询一个元素也是 `O(d)`，因为要查每一行对应计数器再取最小值。工程上 `d` 通常是小常数，所以常说更新和查询都是常数级。

空间复杂度是 `O(w * d)`，`w` 是每行宽度。宽度主要影响误差大小，深度主要影响误差超过预期的概率。它和元素种类数无直接线性关系，这就是它适合高基数流式数据的原因。你可以用固定内存处理百万、千万甚至更多不同 key，只是误差会受总流量、分布偏斜和参数配置影响。

适用场景包括接口热点统计、广告点击频率、商品销量估计、IP 请求频次、缓存准入、TinyLFU、异常检测和近似 heavy hitter。它尤其适合“只关心高频项”的问题，因为高频项的信号能从噪声里冒出来，低频项则容易被冲突污染。

不适合的场景是必须精确、必须支持任意删除、必须输出完整 key 列表的问题。Count-Min Sketch 本身只会对给定 key 返回估计频率，不知道哪些 key 存在。如果要找 Top-K，还要配候选集合、堆、HeavyKeeper 或 Space-Saving 一类结构。单靠 sketch 不能凭空枚举热点 key。

## 98. Count-Min Sketch 在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

缓存系统里，Count-Min Sketch 常用于估计 key 的访问频率。TinyLFU 就是典型例子：用 sketch 记录近期访问频率，再决定新 key 是否值得进入缓存。这样可以避免扫描流量把真正热点挤出去，又不用为每个 key 维护精确计数。

在网关和负载均衡里，CMS 可以记录 `(client, api)`、`(tenant, route)`、`cache key` 或 `source IP` 的频率，用来发现热点主体。发现某个 key 频率明显升高后，可以触发请求合并、本地缓存、热点副本、降级或单独限流。这里的 sketch 适合作为早期信号，不适合作为唯一处罚依据。

限流中，CMS 可以做近似频控。比如需要对海量用户做低成本频率估计，但无法为每个用户保存精确窗口计数，就可以先用 CMS 判断是否疑似超限，再对疑似主体进入精确计数路径。这样把精确状态集中在少数高频主体上。

调度场景里，CMS 可以估计任务类型、租户或资源 key 的到达频率，帮助识别高频任务和倾斜 shard。它也能辅助负载预测：如果某类任务频率突然升高，就提前扩容或调整队列权重。要注意，CMS 的估计偏大，所以策略要留缓冲，不能把接近阈值的估计直接当事实。

## 99. Count-Min Sketch 在并发场景下需要考虑哪些线程安全问题？

Count-Min Sketch 的并发更新本质是多个计数器递增。多个线程更新同一个格子时，如果不是原子加，就会丢增量。可以用原子整数数组、分片 sketch、线程本地 sketch 后台合并，或者把更新汇聚到单线程事件循环中。具体选法取决于你更看重统计精度还是请求路径延迟。

原子数组虽然简单，但热点 key 会让同一组计数器成为争用点。高频 key 每次都打到固定的 `d` 个位置，多个 CPU 核心同时更新会产生 cache line 抖动。分片 sketch 能缓解这一点：按线程、CPU 或 key hash 拆成多个 sketch，查询时把多个 sketch 的估计合并。代价是读放大和更多内存。

衰减和重置也很关键。很多系统只关心近期频率，会周期性把计数减半或轮换 sketch。衰减期间如果和写入并发，可能丢更新或把新流量衰减掉。常见做法是双缓冲、分代 sketch、后台构建新窗口，再通过原子指针切换。

分布式合并时，还要保证 sketch 参数一致，包括宽度、深度、哈希函数和 seed。不同参数的 sketch 不能直接相加。CMS 是线性结构，同参数下可以按格子相加，但重复合并同一批数据会重复计数。面试里可以总结为：CMS 的近似误差可以接受，竞态造成的系统性丢计数和重复计数不能忽略。

## 100. Reservoir Sampling 的核心思想是什么？

Reservoir Sampling 解决的是从未知长度的数据流中等概率抽样。你不知道流最终有多长，也不可能把所有元素都放进内存，但希望最终保留的 `k` 个样本能代表已经看过的全部元素，并且每个元素被选中的概率相同。

最经典的算法 R 是这样做的：先把前 `k` 个元素放进 reservoir；当第 `i` 个元素到来时，在 `[1, i]` 里随机取一个整数 `j`，如果 `j <= k`，就用新元素替换 reservoir 中第 `j` 个位置，否则丢弃新元素。这样处理到任意时刻，前 `i` 个元素中每个元素留在 reservoir 里的概率都是 `k / i`。

它的漂亮之处在于不需要知道总数，也不需要回看历史数据。每个新元素只做一次随机决策，内存固定为 `O(k)`。这非常适合日志流、请求流、消息流、监控事件和在线实验数据。

边界是它给的是随机样本，不是频率统计，也不是 Top-K。样本能帮助排查问题、估计分布、做人肉审查或训练小样本，但不能保证保留异常事件。低频但重要的错误可能被抽掉，所以生产系统里通常会把 reservoir sampling 和规则采样、错误全采、分层采样结合。

## 101. Reservoir Sampling 的时间复杂度、空间复杂度和适用场景是什么？

基础 Reservoir Sampling 对每个元素处理一次，时间复杂度是 `O(n)`，单个元素更新是 `O(1)`。空间复杂度是 `O(k)`，`k` 是样本大小，与流的总长度无关。对于无法预知长度、无法全量保存的数据流，这个空间特性很重要。

如果 `n` 很大，基础算法每个元素都生成随机数，随机数成本也会明显。Vitter 后续提出过跳跃式算法，用随机跳过一段不可能进入样本的元素，降低随机数生成次数。但面试通常先讲算法 R，再补充大规模下可以用更高效变体。

适用场景包括日志抽样、trace 抽样、在线请求样本、队列消息样本、数据库大表扫描抽样、监控事件样本、训练数据预采样。它适合想保留“无偏样本”的场景，尤其是总量未知或持续流入的数据。

不适合用在必须保留最新数据、必须保留高价值异常、必须按权重抽样而没有权重算法的场景。想偏向新数据，可以用滑动窗口采样或时间衰减采样；想按权重抽样，需要 weighted reservoir sampling；想保留每类都有样本，需要分层 reservoir，而不是一个全局 reservoir。

## 102. Reservoir Sampling 在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

后端系统里，Reservoir Sampling 最常见的用途是低成本保留请求样本。比如每个接口保留最近一段时间的随机请求、响应耗时、错误上下文，用于排查问题和生成诊断报告。相比按固定比例采样，reservoir 可以在不知道总请求数的情况下保持固定内存。

在负载均衡里，可以为每个后端节点保留请求耗时样本，用于估计延迟分布，而不是只看平均值。调度器也可以对任务运行时间、队列等待时间、失败原因做抽样，帮助发现某类任务是否拖慢整体系统。样本不参与每次调度决策时，允许它是近似的。

缓存系统可以抽样记录 miss 请求、回源耗时、被淘汰 key 的访问上下文。这样在缓存命中率下降时，能看到真实请求样本，而不是只有聚合指标。限流系统中，也可以对被拒绝请求做 reservoir，避免高峰期日志爆量，同时保留一批可分析样本。

要注意，抽样不能替代关键路径审计。安全事件、资金操作、权限变更通常不能只采样。更合理的做法是：关键事件全量记录，普通高频事件用 reservoir 保留诊断样本，低价值噪声再丢弃或聚合。

## 103. Reservoir Sampling 在并发场景下需要考虑哪些线程安全问题？

Reservoir Sampling 的并发难点是全局序号和随机替换。算法 R 需要知道当前元素是第几个，也就是递增的 `i`。多个线程同时处理流时，如果序号分配不唯一或乱序，就会破坏每个元素等概率进入样本的证明。全局原子计数器能解决唯一序号，但会成为高并发热点。

替换 reservoir 中的位置也要同步。线程 A 决定替换第 3 个位置，线程 B 同时也替换第 3 个位置，最后哪个样本留下取决于竞态。这个竞态不是简单的“随机一点也没事”，因为它会改变抽样概率。严格实现需要锁、CAS、单线程聚合，或把每个线程维护本地 reservoir 后再做无偏合并。

随机数生成器也要线程安全。共享一个带锁随机源会拖慢请求路径；每个线程独立随机源要保证种子质量，避免多个线程产生相关序列。工程里常用线程本地随机源或高质量快速 PRNG。

分布式场景下，不能简单把每个节点的 reservoir 拼起来，因为节点流量不同。正确合并需要考虑每个分区已处理元素数量，按权重合并样本。否则小流量节点和大流量节点贡献同样多样本，会让全局样本偏斜。

## 104. Top-K 的核心思想是什么？

Top-K 解决的是从大量元素中找出排名最高的 K 个。排名可以是数值大小，比如延迟最高的接口；也可以是频率，比如请求次数最多的 IP；还可以是业务分数，比如最热商品。核心思想是没有必要全量排序，只维护当前最有希望进入前 K 的候选。

如果数据是静态数组，常见方法有最小堆、快速选择和部分排序。用大小为 K 的最小堆时，先放入 K 个元素，后续每来一个元素就和堆顶比较；如果比堆顶大，就替换堆顶并调整堆。这样堆里始终保留当前最大的 K 个元素。

如果数据是流式频率，问题更复杂，因为你既要计数，又要维护候选。可以用哈希表精确计数再配堆，也可以用 Count-Min Sketch、Space-Saving、HeavyKeeper 这类近似 heavy hitter 算法。Redis Top-K 实现就是概率计数结构加最小堆的思路，适合实时识别高频项。

面试里要先问清 Top-K 的定义：是按值 Top-K，还是按频率 Top-K；是离线数组，还是在线流；是否允许近似；是否需要实时更新；是否需要删除。不同条件下，最优结构完全不同。

## 105. Top-K 的时间复杂度、空间复杂度和适用场景是什么？

离线按值 Top-K，如果用大小为 K 的最小堆，时间复杂度是 `O(n log k)`，空间是 `O(k)`。如果用快速选择，平均时间可以做到 `O(n)`，再对前 K 个元素排序是 `O(k log k)`，但最坏情况和实现细节要处理好。全量排序是 `O(n log n)`，只有在同时需要完整排序时才划算。

流式精确频率 Top-K 通常需要哈希表记录所有 key 的计数，空间是 `O(U)`，`U` 是不同 key 数量；再用堆或有序结构维护前 K。更新一个 key 时，计数是 `O(1)`，堆调整通常是 `O(log k)` 或 `O(log U)`，取决于实现是否维护 key 到堆位置的索引。

流式近似 Top-K 的空间可以远小于 `O(U)`。比如 sketch 加候选堆，更新通常是小常数到 `O(log k)`，但结果有误差，低频元素可能被错判。它适合监控、热点识别、推荐候选、异常检测，不适合账单、库存和精确排名。

适用场景包括热 key 发现、访问最多的 IP、错误最多的接口、耗时最高的任务、销量最高的商品、日志中最常见的错误码。K 的大小通常远小于总元素数，这时 Top-K 的意义才明显。如果 K 接近 n，直接排序或分布式排序可能更简单。

## 106. Top-K 在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

缓存系统最需要 Top-K。热 key 会造成单点缓存压力、回源放大和负载倾斜。通过统计访问频率 Top-K，可以识别需要本地缓存、热点副本、请求合并或提前预热的 key。这里常用近似 Top-K，因为 key 空间很大，精确统计所有 key 的成本太高。

负载均衡可以用 Top-K 发现最忙的后端、最热的路由、最重的租户、最常见的失败来源。调度系统可以找出耗时最高的任务类型、排队最多的队列、重试最多的任务。运维上，Top-K 错误码和 Top-K 慢接口是定位故障的基础视图。

限流系统中，Top-K 可以帮助发现高频主体，再给这些主体启用更严格的精确限流。比如先用近似 Top-K 找出请求最多的 IP 或 token，再把它们放入精确窗口计数器。这样避免为所有低频用户维护昂贵状态。

要注意 Top-K 只是识别，不是治理本身。发现热 key 后，还要看它是正常热点还是攻击流量；发现慢任务后，还要看是资源不足、下游慢还是调度策略不合理。Top-K 给的是排序入口，不能替代根因分析。

## 107. Top-K 在并发场景下需要考虑哪些线程安全问题？

精确 Top-K 通常包含计数表和堆，这两个结构必须一致。一个线程更新计数后还没调整堆，另一个线程读取 Top-K，就可能看到过期排名。多个线程同时调整堆，如果没有锁，会破坏堆的结构。常见做法是分片统计，单分片内加锁或单线程维护，查询时合并各分片 Top-K。

全局堆是高争用点。每个请求都更新同一个 Top-K 堆，吞吐会很差。工程上经常把请求路径改成只做轻量计数，后台周期性汇总生成 Top-K；或者每个线程维护本地候选，定期 merge。实时性和开销之间要取舍。

近似 Top-K 也有并发问题。sketch 计数器需要原子更新，候选堆需要同步，元素进出 Top-K 时还要避免重复通知或漏通知。Redis Top-K 这类结构在单线程执行模型里比较容易保证一致；多线程实现则需要额外的锁或分片。

还有一个容易忽略的问题是时间窗口。Top-K 如果不衰减，会被历史热点占住；如果周期性清空，会在窗口边界抖动。并发环境下做窗口切换时，读线程可能混到新旧窗口数据。常见办法是双缓冲窗口、时间分片 Top-K、后台合并和版本化快照。

## 108. 限流计数器的核心思想是什么？

限流计数器的核心思想是为某个主体在某个时间范围内累计请求次数，再和阈值比较。主体可以是 IP、用户、租户、API key、接口、资源 ID。最简单的固定窗口限流就是把当前时间切成固定窗口，例如每秒一个窗口，对 `(主体, 窗口)` 计数，超过阈值就拒绝或降级。

这种结构直观、便宜、容易分布式实现。Redis 官方文档里的 `INCR + EXPIRE` 模式就是典型做法：每个 IP 每秒一个 key，调用时原子递增并设置过期时间，计数超过阈值就限制。它把限流问题转成了“带 TTL 的计数器”。

固定窗口的问题是边界突刺。比如限制每分钟 100 次，用户可以在上一分钟最后一秒打 100 次，又在下一分钟第一秒打 100 次，短时间内实际通过 200 次。滑动窗口计数器、滑动日志、令牌桶、漏桶就是为了解决不同维度的平滑、公平和突发控制。

面试里可以这样答：限流计数器是最基础的频控结构，用时间窗口和主体 key 维护请求次数。它适合简单阈值控制和粗粒度保护，但窗口边界、分布式一致性、热点 key 和原子过期是工程重点。

## 109. 限流计数器的时间复杂度、空间复杂度和适用场景是什么？

固定窗口计数器单次请求通常是 `O(1)`：定位 key、递增、比较阈值。空间复杂度是 `O(S * W)`，`S` 是活跃主体数量，`W` 是需要保留的窗口数量。如果每个窗口结束后 key 自动过期，空间主要跟活跃主体和 TTL 有关。

滑动窗口计数器比固定窗口更平滑。常见做法是保留当前窗口和上一个窗口，用时间比例加权估算当前滑动窗口内的请求量；或者保留多个小桶，把最近 `N` 个小桶求和。单次更新仍可接近 `O(1)`，查询可能是 `O(bucketCount)`，但 bucket 数通常是小常数。

它适合 API 限流、登录尝试限制、短信发送限制、租户配额、后台任务提交限制、Webhook 调用频控。优点是规则直观，容易解释给业务方：一分钟最多多少次，一天最多多少次。

不适合的场景是需要非常平滑的输出速率，或者允许一定突发但要长期平均受控。平滑输出更像漏桶，允许突发更像令牌桶。计数器还容易出现热点主体，例如某攻击 IP 的计数 key 被所有网关同时更新，这时要分片、局部限流或把热点主体提升到本地快速路径。
## 110. 限流计数器在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

在 API 网关里，限流计数器可以按 IP、用户、租户、接口维度做基础保护。例如 `(tenant_id, api, minute)` 作为 key，每次请求递增，超过阈值就返回限流错误。这个做法很适合规则简单、需要可解释的配额控制。

在负载均衡里，计数器可以做本地过载保护。每个实例维护某个路由或下游的当前窗口请求数，当某条路径超过本机承载能力时，优先拒绝低优先级流量，避免把后端打挂。全局限流可以放在 Redis、集中式限流服务或控制面，本地限流则作为快速保护。

缓存场景中，计数器可以保护回源。比如同一个缺失 key 在短时间内被大量请求，缓存层可以对回源次数做计数，超过阈值后只允许少量请求穿透，其余请求等待、降级或返回空值。这样可以缓解缓存击穿和缓存穿透。

调度系统中，计数器可以限制某租户每分钟提交任务数、某队列每秒出队数、某类重试任务的生成速度。它的优势是实现简单，但要配合优先级、队列长度和失败率，否则只看请求数可能误伤慢任务或长任务。

## 111. 限流计数器在并发场景下需要考虑哪些线程安全问题？

限流计数器必须保证“递增、设置过期、比较阈值”这一组动作的原子性。否则两个请求同时读取计数，都认为没有超限，然后一起放行，就会突破阈值。Redis 里常用 `MULTI/EXEC` 或 Lua 脚本把 `INCR` 和 `EXPIRE` 绑在一起，本地实现则要用原子计数器、锁或单线程事件循环。

固定窗口还有 key 泄漏问题。如果第一次递增成功，但设置过期失败，计数 key 可能长期存在，后续主体会一直被限流。这个问题在远程存储和客户端超时场景里很常见，所以 `INCR + EXPIRE` 最好在服务端原子执行。

分布式限流还要面对时钟和副本一致性。多个网关各自本地计数，合计可能超过全局阈值；所有请求都打到中心计数器，又会产生热点和单点延迟。常见取舍是本地预分配额度、分片计数、最终一致汇总，或者对关键接口走强一致限流服务。

窗口切换也要同步。滑动窗口小桶在清零或轮转时，如果和请求更新交错，可能把新请求写进旧桶或把旧桶重复计入。实现上要记录桶的时间戳，更新前确认桶属于当前时间段；不属于就重置桶和时间戳。不能只按数组下标循环复用。

## 112. 时间轮的核心思想是什么？

时间轮的核心思想是用环形数组管理大量定时任务，把时间切成固定 tick。数组中的每个槽代表一个时间刻度或一段时间，定时任务按到期时间映射到某个槽里。时钟每走一个 tick，就处理当前槽中的任务。

单层时间轮适合管理到期时间不太远的任务。如果任务延迟超过一圈，可以记录剩余圈数，每次转到该槽时把圈数减一，减到 0 再执行。层级时间轮则把秒、分钟、小时这类不同粒度分成多层，远期任务先放粗粒度层，时间接近后再下放到细粒度层。

它的优势是插入和推进成本低。相比每个定时器都放进最小堆，时间轮把任务按时间槽分桶，新增任务通常是 `O(1)`，每个 tick 只处理当前槽。Netty 的 HashedWheelTimer 就是面向近似 I/O 超时调度的典型实现，它也明确强调这种定时器不追求严格准时。

时间轮的代价是精度受 tick 限制。tick 越小，精度越高，但轮转越频繁，槽数量和调度开销也会上升；tick 越大，开销低，但任务可能被延后到下一个 tick。面试里可以说：时间轮适合海量、允许近似、到期处理轻量的定时任务，不适合严格实时调度。

## 113. 时间轮的时间复杂度、空间复杂度和适用场景是什么？

新增定时任务通常是 `O(1)`：计算 delay 对应的 tick 数，再定位到环形数组槽位，把任务挂进去。取消任务如果持有任务节点引用，可以做到 `O(1)` 标记取消；如果要从链表里物理删除，可能需要链表操作或延迟删除。每个 tick 的处理成本与当前槽内任务数量有关。

空间复杂度是 `O(slotCount + timerCount)`。槽数组大小固定，任务节点数量和未到期定时器数量线性相关。层级时间轮会有多层槽数组，空间仍然主要由槽数量和任务数量决定。

适用场景包括连接超时、请求超时、重试延迟、心跳检测、缓存过期扫描、会话超时、消息延迟投递。它特别适合定时器数量巨大但精度要求不高的网络系统。比如 I/O 超时通常不需要精确到 1 毫秒，只要能在合理时间内触发即可。

不适合的场景是任务数量不大但精度要求很高，或者定时任务到期时间分布非常稀疏且跨度极大。此时最小堆、红黑树或操作系统定时器可能更简单。时间轮还要求每个槽处理不要阻塞太久，否则后续 tick 会被拖延。

## 114. 时间轮在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

后端服务里，时间轮常用于超时管理。每个 RPC 请求、连接、会话或重试任务注册一个定时器，到期后触发取消、重试或清理。由于这类定时器数量可能很大，最小堆每次 `O(log n)` 的插入成本会比较明显，时间轮的 `O(1)` 插入更适合高吞吐网络路径。

负载均衡里，可以用时间轮做健康检查超时、熔断半开探测、慢启动阶段切换、连接空闲回收。缓存系统里，可以用时间轮做过期 key 扫描、刷新任务调度、回源请求合并的等待超时。限流系统里，可以把临时封禁、令牌桶补充、窗口清理等任务挂到时间轮上。

调度系统中，时间轮适合延迟队列和重试队列。任务失败后按退避时间放入对应槽，到期再重新入队。因为重试任务通常允许几十毫秒甚至秒级误差，时间轮的近似性可以接受。

设计时要避免把重任务直接放在时间轮线程里执行。时间轮线程最好只负责发现到期任务，然后投递到工作队列。如果在 tick 线程里做网络调用、磁盘写入或复杂业务逻辑，一个慢任务就会拖住整个定时系统。

## 115. 时间轮在并发场景下需要考虑哪些线程安全问题？

时间轮通常有一个推进线程和多个业务线程。业务线程负责新增或取消定时器，推进线程负责扫描当前槽并触发到期任务。并发重点是槽链表的修改和扫描不能互相破坏。可以用槽级锁、无锁队列先收集新增任务、单线程批量挂载，或者所有操作都投递到时间轮线程执行。

取消任务最好设计成幂等。业务线程取消时，可以先把任务状态标记为 cancelled，到期扫描时发现取消就跳过。这样避免从槽链表中间物理删除造成锁竞争。缺点是槽里会有一些已取消节点，需要到期时清理。

时间推进还要处理时钟跳变。系统时间回拨或跳跃会让基于 wall clock 的定时器异常，通常应使用单调时钟计算 elapsed time。tick 线程如果被 STW、CPU 抢占或长任务阻塞，恢复后可能要连续推进多个 tick，这时要控制单轮补偿处理量，避免一次性触发过多任务。

内存可见性也不能忽略。任务状态、到期时间、回调引用必须在发布到时间轮后对推进线程可见。用队列、锁、volatile/atomic 或语言运行时的同步原语建立 happens-before 关系。否则看起来已经注册的任务，推进线程可能读到旧状态。

## 116. 最小堆定时器的核心思想是什么？

最小堆定时器把所有定时任务按到期时间排序，堆顶永远是最早到期的任务。调度线程只需要查看堆顶：如果堆顶还没到期，就睡到它的到期时间；如果已经到期，就弹出并执行或投递任务。新增任务时，把任务插入堆并向上调整。

这个结构非常直接。Go 的 `container/heap` 文档也把堆描述为实现优先队列的常用方式，最小元素在根节点。把“优先级”换成“到期时间”，就是最小堆定时器。很多语言运行时、事件循环和任务调度器都会使用堆或堆的变体管理 timer。

与时间轮不同，最小堆定时器没有固定 tick 粒度，定时精度主要取决于系统时钟、睡眠唤醒和调度延迟。它很适合任务数量中等、到期时间分布不规则、需要更精确按 deadline 触发的场景。

代价是插入和删除通常是 `O(log n)`。如果系统里每秒创建和取消海量定时器，堆调整会成为成本。取消任意 timer 还需要知道它在堆里的 index，否则只能延迟删除或线性查找。

## 117. 最小堆定时器的时间复杂度、空间复杂度和适用场景是什么？

查看堆顶是 `O(1)`，新增定时器是 `O(log n)`，弹出到期定时器是 `O(log n)`。如果要修改某个定时器的到期时间，持有 index 时可以用 `fix` 做 `O(log n)` 调整；如果没有 index，需要先查找，可能退化成 `O(n)`。批量建堆可以是 `O(n)`。

空间复杂度是 `O(n)`，每个未到期定时器一个堆节点。节点通常包含 deadline、回调、状态、index、序号等字段。为了处理相同 deadline 的公平性，常用单调递增序号作为 tie-breaker，避免同一时间的任务顺序不稳定。

适用场景包括事件循环定时器、延迟任务、RPC deadline、连接空闲回收、少量到中等规模的重试调度。它比时间轮更容易理解和实现，也更适合 deadline 跨度大、时间分布稀疏的任务。

不适合的场景是超大规模短周期 timer，例如百万连接每个连接频繁刷新超时，堆的 `O(log n)` 调整和锁争用会很明显。此时可能要用时间轮、分片堆、层级队列或把超时检测改成批量扫描。

## 118. 最小堆定时器在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

后端服务里，最小堆定时器适合管理 RPC deadline、重试时间、后台任务启动时间。事件循环只关心最近的 deadline，堆顶能直接告诉它下一次应该睡多久。这个模型清晰，适合单进程内的定时调度。

负载均衡可以用堆管理健康检查计划。每个后端下一次检查时间不同，堆顶就是最近要检查的节点。检查完成后，根据结果和策略计算下一次时间再放回堆。缓存系统可以用堆管理刷新任务、预热任务、软过期刷新。

限流和熔断中，最小堆可以管理临时封禁解除时间、半开探测时间、租户额度恢复时间。调度系统里，延迟任务和重试任务也可以按 `next_run_at` 放进最小堆。

工程上要注意任务执行和堆维护分离。堆线程弹出到期任务后，最好投递给 worker 执行，再继续检查下一个 deadline。如果直接执行回调，慢回调会阻塞后续 timer。堆只负责顺序，不应该承担业务执行。

## 119. 最小堆定时器在并发场景下需要考虑哪些线程安全问题？

最小堆是一个全局有序结构，任何插入、弹出、删除、调整 deadline 都会改变堆数组。多线程同时操作必须加锁或通过单线程事件循环串行化。否则堆不变式很容易被破坏，表现为任务丢失、重复执行或到期顺序错误。

新增更早到期的定时器时，还要唤醒睡眠中的调度线程。调度线程可能正睡到旧堆顶 deadline，如果新 timer 更早，它必须重新计算等待时间。常见做法是条件变量、eventfd、管道、自唤醒 channel 或平台相关唤醒机制。

取消 timer 要设计状态机。业务线程取消时，timer 可能还在堆里、已经被弹出但未执行、正在执行、已经执行完。取消操作要幂等，并明确返回值语义：到底是成功阻止执行，还是任务已经开始。很多 bug 都来自取消和执行之间的竞态。

分片堆可以降低锁争用，但会带来全局最早时间发现问题。每个 shard 有自己的堆，调度线程可以每个 shard 一个，也可以上层再维护一个 shard 堆顶索引。分片后要考虑任务按什么规则落 shard，以及迁移任务时的同步成本。

## 120. 分段锁的核心思想是什么？

分段锁的核心思想是把一个大共享结构拆成多个段，每个段有自己的锁。访问某个 key 时，先根据 key 的哈希值定位到段，只锁这个段，而不是锁整个结构。这样不同段上的操作可以并行，降低锁竞争。

它解决的是粗粒度锁吞吐低的问题。比如一个大 map 如果只有一把互斥锁，所有读写都串行；拆成 64 段后，理论上不同段可以同时更新。分段锁并没有消除锁，只是把冲突范围缩小。

分段锁常和哈希表、计数器、缓存、限流状态表一起出现。早期很多并发 map 的设计都带有这种思想；现代实现可能用更细粒度的桶锁、CAS、读写锁或无锁结构，但“按 key 分散争用”的思路仍然一样。

它的边界是跨段操作。单 key 更新很好做，遍历全表、统计总数、批量迁移、全局清空、按多个 key 原子更新就麻烦了。你可能需要按固定顺序获取多把锁，或者接受弱一致快照。

## 121. 分段锁的时间复杂度、空间复杂度和适用场景是什么？

分段锁本身不改变底层数据结构的渐进复杂度。哈希表查找仍然平均 `O(1)`，树结构查找仍然 `O(log n)`。它改变的是并发下的等待时间：原来所有操作争一把锁，现在只有落在同一段的操作互相等待。

空间复杂度会增加 `O(s)`，`s` 是段数量。每个段通常有一把锁、一小块元数据和自己的容器。段数太少，争用仍然高；段数太多，锁对象和元数据浪费空间，遍历和扩容也更复杂。段数通常按 CPU 数、预期并发度和内存预算选择。

适用场景是高并发、多 key、操作主要集中在单 key 或单段内的状态管理。比如本地缓存、连接表、租户计数器、限流状态表、指标聚合表、任务状态 map。只要 key 分布足够分散，分段锁能明显降低热点锁等待。

不适合的场景是单一热点 key 占大部分流量，或者大部分操作都需要全局一致。热点 key 无论怎么分段都会落在一个段里；全局操作则要扫所有段，甚至锁所有段。此时要考虑热点拆分、专门结构、读写分离或异步聚合。

## 122. 分段锁在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

缓存系统里，分段锁可以保护多个 shard 的 LRU、LFU 或哈希表。每个 key 按 hash 落到一个 shard，读写只锁对应 shard。这样既降低锁争用，也能把淘汰队列拆小，避免一个全局 LRU 队列成为瓶颈。

限流系统中，可以把主体状态表分段。不同用户、IP、租户的计数器落到不同段，更新互不影响。负载均衡器的连接表、后端状态表、会话粘滞表也可以用分段锁保护，避免每次请求都争一把全局锁。

调度系统里，任务队列和任务状态可以按租户、队列名或任务 ID 分段。提交、取消、更新任务状态时只锁相关段。对于多队列调度，可以每个队列独立锁，再由上层调度器做轻量汇总。

应用分段锁时要提前定义跨段操作策略。比如要统计缓存总大小，是逐段累加一个弱一致值，还是锁住所有段得到强一致值？要迁移两个 key，是按段编号升序加锁，还是用事务队列串行处理？这些规则不明确，分段锁很容易引入死锁和偶发不一致。
## 123. 分段锁在并发场景下需要考虑哪些线程安全问题？

分段锁首先要保证 key 到段的映射稳定。扩容、rehash 或 shard 数变化时，如果一个线程按旧规则锁了段 A，另一个线程按新规则锁了段 B，同一个 key 可能被并发修改。实现上要么固定段数，要么在迁移期间用全局迁移锁、版本号或双表切换。

跨段加锁必须有固定顺序。比如一次操作要同时更新两个 key，两个 key 落在不同段。如果线程 1 先锁段 1 再锁段 2，线程 2 先锁段 2 再锁段 1，就可能死锁。解决方法是按段编号升序加锁，或者把跨段操作交给单线程事务队列。

读写锁的使用也要谨慎。读多写少时，每段用读写锁可以提高并发读；但如果读操作里包含升级写锁，或者读锁持有时间很长，会导致写饥饿。很多缓存读操作还会更新访问时间或 LRU 队列，看起来是读，实际是写，不能随便放在读锁里。

全局统计往往是弱一致的。遍历每个段时，其他段可能已经变化。监控指标可以接受这种近似；配额、容量、迁移这类强约束则需要更严格的同步。面试里可以总结：分段锁降低单点争用，但把复杂度转移到了映射稳定性、跨段顺序和全局视图一致性上。

## 124. 分片计数器的核心思想是什么？

分片计数器的核心思想是把一个高争用计数器拆成多个小计数器。更新时，线程、CPU、请求或 key 选择其中一个分片递增；读取总数时，把所有分片求和。这样大量写操作不再争同一个原子变量或同一把锁。

Java 的 LongAdder 就是这种思路的代表：在多线程更新同一个 sum 时，它会用多个变量共同维护总和，以降低竞争；读取时再把这些变量合并。它牺牲的是更高空间和非严格瞬时快照，换取高并发递增吞吐。

分片计数器适合统计指标，而不是强一致状态。比如请求数、错误数、字节数、命中数、队列入队数，这些指标允许读取时有一点时间差。它不适合库存扣减、账户余额、许可证数量这类必须严格线性一致的计数。

面试里可以这样说：分片计数器用多个局部计数分散写热点，再在读时聚合。它是“写快、读稍贵、快照弱一致”的结构，适合高频指标和近似控制，不适合强一致业务事实。

## 125. 分片计数器的时间复杂度、空间复杂度和适用场景是什么？

单次递增通常是 `O(1)`，只更新一个分片。读取总数是 `O(s)`，`s` 是分片数量，因为要把所有分片累加。空间复杂度也是 `O(s)`。分片越多，写争用越低，但读成本和内存越高。

分片选择有几种方式。按线程 ID 或 CPU ID 分片能降低同一线程的写冲突；按 key hash 分片适合多主体统计；随机分片可以简单打散热点，但会让测试和调试不太稳定。实际实现还要做 cache line padding，避免多个分片落在同一个 cache line 上产生 false sharing。

适用场景包括 QPS 计数、错误计数、字节吞吐、缓存命中率、限流近似计数、连接数指标、队列操作数。它特别适合写远多于读的监控指标。比如每个请求都要递增指标，但 Prometheus 每几秒才 scrape 一次，读成本高一点完全可以接受。

不适合的场景是每次写后都要立刻读取精确总数并做强决策。比如“超过 100 就绝不允许第 101 个通过”的限流，分片计数器直接读总和可能已经有并发误差。可以用它做近似快速路径，再用强一致计数器做最终判断。

## 126. 分片计数器在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

后端服务里，分片计数器常用于指标采集。每个 worker 或 CPU 维护局部请求数、错误数、延迟桶计数，监控线程周期性汇总。这样请求路径只做本地递增，不会争全局原子变量。

负载均衡器可以用分片计数器记录每个后端的 in-flight、成功数、失败数和字节数。如果每个后端只有一个原子计数，高流量时会产生争用；按 worker 分片后，选择后端时可以读取近似总量，后台再做更准确汇总。

缓存系统里，命中、miss、淘汰、回源次数都适合分片计数。限流系统中，分片计数器可以做本地近似窗口计数，降低热点主体对单个计数器的争用。对特别敏感的限流规则，再进入集中式精确判断。

调度系统可以用分片计数器维护各队列提交数、完成数、失败数、当前运行数。调度决策如果只需要大致负载，可以读汇总值；如果要严格控制并发上限，就应使用信号量、令牌或强一致状态，而不是只靠分片计数器。

## 127. 分片计数器在并发场景下需要考虑哪些线程安全问题？

每个分片本身仍然要线程安全。如果一个分片可能被多个线程更新，它要用原子加或锁。如果能保证每个线程只写自己的分片，写入可以更轻，但线程退出、分片复用和动态扩容时要处理生命周期。

读取总数不是原子快照。汇总线程读第一个分片后，后面的分片可能已经更新，最终总数对应的是一个时间区间，而不是某一瞬间。监控指标可以接受；控制逻辑要谨慎。Java LongAdder 的文档也提醒，在并发更新时 `sum()` 不是原子快照。

重置操作尤其危险。如果一边读取并清零，一边有线程递增，增量可能丢失。`sumThenReset` 这类操作通常只适合在没有并发更新或能接受竞态的统计场景。更安全的做法是双缓冲计数器：当前窗口写 A，切换后写 B，后台汇总 A。

还要注意分片数量和 CPU 拓扑。分片太少会争用，太多会让读取变慢；分片紧挨着分配可能 false sharing。工程实现里常给分片做 padding，或按 cache line 对齐。并发计数的性能问题经常不在算法复杂度，而在缓存一致性流量。

## 128. 双缓冲的核心思想是什么？

双缓冲的核心思想是准备两个缓冲区：一个给前台读或写，另一个在后台构建、刷新或消费。等后台缓冲区准备好后，通过一次快速切换把它变成前台缓冲区。这样可以避免读写长期互相阻塞。

这个思路在后端里很常见。配置表刷新时，旧配置继续服务请求，新配置在后台完整构建；构建成功后原子替换指针。指标窗口统计时，当前窗口写入一个 buffer，到窗口边界切到另一个 buffer，后台汇总旧 buffer。日志批处理时，业务线程写 active buffer，flush 线程处理 standby buffer。

双缓冲的重点不是“有两个数组”，而是把“构建/消费慢操作”和“前台请求快路径”分开。前台只做追加、读取或引用切换，后台处理耗时工作。切换动作要短，最好是原子指针交换或短锁内交换。

它的边界是只能解决阶段性切换问题。如果读写需要同时修改同一份复杂状态，双缓冲未必够用。它也会增加内存占用，并引入新旧版本并存期间的一致性问题。面试里可以说：双缓冲用空间和版本切换换低阻塞，适合周期性刷新、批量汇总和快照发布。

## 129. 双缓冲的时间复杂度、空间复杂度和适用场景是什么？

单次读写缓冲区通常是 `O(1)`，切换缓冲区也是 `O(1)`，如果只是交换两个引用或下标。后台构建或汇总的复杂度取决于数据量，可能是 `O(n)`。双缓冲的价值在于把这部分 `O(n)` 工作移出请求临界区。

空间复杂度通常是原始缓冲的两倍，即 `O(2n)`，渐进上还是 `O(n)`，但实际内存翻倍要考虑清楚。如果缓冲里是大对象，还要考虑对象引用、GC 和释放时机。

适用场景包括配置热更新、路由表刷新、服务发现快照、指标窗口切换、日志批量刷盘、限流窗口轮转、缓存预热结果发布。只要数据可以按版本整体替换，而不是每次都要原地修改，双缓冲就很自然。

不适合的场景是每个更新都必须立刻对所有读者可见，或者缓冲区太大导致复制成本无法接受。此时可以考虑增量更新、分片双缓冲、RCU、copy-on-write 局部结构，或者普通读写锁。

## 130. 双缓冲在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

负载均衡器可以用双缓冲发布路由表。控制面推送新配置后，后台先解析、校验、构建索引和权重表；构建成功后一次性切换。请求线程始终读一个稳定快照，不需要在每个请求上等待复杂配置更新。

缓存系统可以用双缓冲做预热和失效。后台把新一批热点 key 或索引构建到 standby buffer，完成后切换为 active。限流系统可以用双缓冲做时间窗口：当前窗口写 active，窗口结束时切换，后台汇总或清空旧窗口。

调度系统中，双缓冲适合发布资源视图。比如节点健康状态、资源标签、队列权重、租户配额周期性刷新。调度线程读当前快照，监控线程或控制面构建下一版快照。这样可以减少调度路径上的锁。

要注意切换失败处理。新缓冲构建失败时，不能把半成品发布出去；切换后，旧缓冲也不能马上释放给复用，除非确认没有读线程持有。实际工程里常配合版本号、引用计数、epoch 或 GC 来管理旧快照生命周期。

## 131. 双缓冲在并发场景下需要考虑哪些线程安全问题？

双缓冲最重要的是发布语义。后台线程构建完新缓冲后，前台线程必须看到完整初始化后的内容，而不是半初始化对象。切换引用时要用锁、原子变量、volatile 写或语言提供的同步机制，保证内存可见性。

旧缓冲的生命周期也要处理。读线程可能在切换前拿到了旧缓冲引用，切换后仍在使用。如果后台马上清空或复用旧缓冲，读线程就会读到被修改的数据。解决办法包括读写锁、RCU/epoch、引用计数、延迟回收，或让旧缓冲不可变并交给 GC 回收。

多生产者写 active buffer 时，active 本身还需要并发保护。双缓冲只解决“哪一份数据对外服务”的问题，不自动保证缓冲区内部写入安全。比如指标双缓冲里，当前窗口计数器仍要用原子加或分片计数器。

窗口切换要避免 ABA 问题。线程读到 active=A，切换到 B，又切回 A，如果 A 已经被清空复用，旧引用就不再代表原来的数据。版本号能帮助识别这种情况。面试里可以总结：双缓冲的关键不是交换快，而是完整发布、旧版本安全回收和缓冲区内部同步。

## 132. copy-on-write 的核心思想是什么？

copy-on-write 的核心思想是读共享旧数据，写入时复制一份新数据，在新副本上修改，最后发布新副本。读线程不需要阻塞写线程，也不会看到写到一半的状态。Java 的 CopyOnWriteArrayList 就是典型实现：所有修改操作都会复制底层数组，迭代器读取创建时的快照。

它适合读多写少的场景。读路径只读不可变快照，通常不需要锁；写路径成本高，因为要复制结构。只要写不频繁，这个成本可以接受。配置、路由表、监听器列表、规则表、白名单、插件链都常用这种思路。

copy-on-write 和双缓冲很接近，但粒度可以更灵活。双缓冲通常固定两份缓冲区周期切换；copy-on-write 可以每次写都生成新版本，由旧读者继续使用旧版本。它更强调快照隔离和不可变发布。

边界也明显。数据很大、写很频繁、写入需要就地累积时，copy-on-write 会带来大量复制和内存压力。它也不适合读者必须立刻看到最新写入的强实时场景。读到旧快照是设计的一部分，不是异常。

## 133. copy-on-write 的时间复杂度、空间复杂度和适用场景是什么？

读取通常是 `O(1)` 或按底层结构的普通读复杂度，不需要加锁或只需要一次原子引用读取。写入成本取决于复制范围：数组型结构新增一个元素可能要复制整个数组，时间和空间都是 `O(n)`；树或持久化数据结构可以只复制路径，成本可能是 `O(log n)`。

空间复杂度在写入瞬间会升高，因为新旧版本同时存在。旧版本要等没有读者引用后才能释放。垃圾回收语言里由 GC 处理，但可能造成内存峰值和 GC 压力；手动内存管理语言里要用引用计数、epoch 或 hazard pointer 之类机制。

适用场景是读多写少、读延迟敏感、需要快照一致性的结构。例如服务发现实例列表、路由规则、配置对象、权限规则、拦截器列表、灰度策略、限流规则表。读者拿到一个版本后，可以放心遍历，不怕并发修改。

不适合高频写的数据结构，比如每个请求都更新的缓存访问队列、计数器、任务队列。把这些结构做 copy-on-write 会把写放大得很严重。面试里可以说：COW 是拿写放大和短期内存峰值换读路径无锁和快照稳定。

## 134. copy-on-write 在后端系统、负载均衡、缓存、限流或调度中可以如何应用？

负载均衡里，后端实例列表和权重表可以用 copy-on-write。健康检查或控制面更新时，构建一份新的节点快照，再原子替换；请求线程只读当前快照，选择节点时不需要拿全局锁。这样可以降低请求路径抖动。

配置中心客户端也常用 COW。新配置到达后，先解析成不可变对象，校验通过后发布。业务线程读取配置引用，不需要在每次请求上解析或加锁。限流规则、熔断规则、路由规则、灰度规则都适合这种模式。

缓存系统里，COW 不适合维护高频变化的缓存内容本身，但适合维护缓存策略和索引快照。比如热点 key 白名单、预热 key 列表、租户容量配置。调度系统里，队列权重、资源标签、调度策略也可以通过 COW 发布。

要注意旧版本可观测性。请求 A 用旧规则，配置更新后请求 B 用新规则，在短时间内新旧规则并存。这通常是可接受的，但要在审计和排障里能解释。对于必须全局同时生效的变更，还需要版本屏障、暂停写入或事务化切换。

## 135. copy-on-write 在并发场景下需要考虑哪些线程安全问题？

copy-on-write 的发布必须是原子的。写线程在新副本上完成所有修改后，再用原子引用、volatile 写或锁把新版本发布出去。不能先把半成品放到共享位置再继续修改，否则读线程会看到不完整状态。

新版本发布后不要再修改。COW 的读无锁依赖不可变快照，如果发布后继续原地改，新旧读者都会被影响。工程上要把快照对象设计成不可变，或者至少约定发布后只读。数组、slice、map 这类引用型字段也要深拷贝到足够的层级，不能只拷贝外壳。

多个写线程并发更新时，要避免丢更新。线程 A 基于版本 1 构建版本 2，线程 B 也基于版本 1 构建版本 3；如果两者都直接 set，后发布的会覆盖先发布的。常见做法是写锁串行化，或者 CAS：只有当前版本仍是自己读取的旧版本时才发布，否则重新基于最新版本构建。

旧版本回收也要安全。GC 语言里通常交给 GC，但仍要关注内存峰值；非 GC 语言要确认没有读者持有旧指针。COW 的难点不在读，而在写入复制范围、发布顺序、并发写合并和旧版本生命周期。

## 136. 如何实现一个高性能 LRU Cache？

高性能 LRU Cache 的基本结构是哈希表加双向链表。哈希表负责 `key -> node` 的 `O(1)` 查找，双向链表维护访问顺序：链表头表示最近访问，链表尾表示最久未访问。`Get` 命中后把节点移动到头部，`Put` 新 key 时插入头部；容量超限时从尾部淘汰，再从哈希表删除对应 key。这个组合能把查找、更新访问顺序和淘汰都控制在常数时间。

真正写实现时，节点最好是一个内嵌链表指针的结构，而不是哈希表存 value、链表再存 key 的两份对象。节点里通常包含 `key`、`value`、`prev`、`next`、`cost`、可选的 `expireAt` 和状态位。这样移动节点只改几个指针，淘汰时也能直接拿到 key 去删 map。Go 里可以用 `container/list` 快速实现，但追求低分配时更常见的是自己写侵入式双链表，避免 `Element` 包装和接口装箱。

并发是 LRU 的主要成本来源。因为 `Get` 命中也要移动链表，它不是纯读操作。最简单做法是一把互斥锁保护 map 和 list，正确但高并发下会被热点 key 打穿。更常见的做法是分片：按 key hash 拆成 64 或 256 个 shard，每个 shard 有自己的 map、list、容量和锁。这样不同 key 可以并行访问。缺点是全局容量只能近似公平，某个 shard 热或占用大时需要做容量再平衡，或者按权重给 shard 分配预算。

为了降低请求路径开销，可以把“记录访问”做成近似。比如 `Get` 只更新一个时间戳或把 key 写入访问缓冲，后台批量调整链表顺序；或者只对部分访问提升 recency，减少每次命中都抢锁。很多工业缓存不会追求严格 LRU，而会用采样、分段 LRU、TinyLFU 一类策略降低元数据和锁成本。面试时要说清楚：严格 LRU 语义简单，但在高 QPS 下维护全局访问顺序本身就是负担。

容量也不能只按条目数。真实缓存里 value 大小差异很大，通常要支持按字节、按对象成本或按权重淘汰。`Put` 时先计算 cost，更新总成本；淘汰时循环从尾部删，直到成本回到预算内。还要定义大对象策略：单个对象超过容量时直接拒绝，还是允许它短暂进入再立刻淘汰。否则一个超大 value 会让缓存抖动。

边界条件包括：更新已有 key 时要替换 value 并调整成本；删除时要同时从 map 和 list 移除；淘汰回调不要在持锁时执行，避免用户回调反过来访问缓存造成死锁；缓存关闭或批量清理时要处理回调顺序；如果 value 需要释放资源，淘汰路径必须可靠触发。高性能 LRU 的关键不是把 `O(1)` 背出来，而是把对象分配、锁粒度、容量模型、回调和热点访问这些常数成本处理干净。

## 137. 如何实现一个支持过期时间的缓存？

支持过期时间的缓存至少需要两条索引：一条按 key 查 value，一条按时间找到该清理的 key。最基础的结构是 `map[key]*entry`，entry 里保存 `value`、`expireAt`、可选的 `lastAccessAt` 和版本号。读的时候先从 map 找 entry，再判断当前单调时间是否超过 `expireAt`；过期就当作 miss，并尝试删除。这个 lazy expiration 很便宜，但如果过期 key 很多、一直没人访问，内存会长期占住。

主动清理可以用最小堆、时间轮、跳表或分桶队列。最小堆按 `expireAt` 排序，堆顶就是最早过期项，清理线程循环弹出已过期 entry。问题是更新 TTL 时堆里可能已经有旧节点，常见做法是给 entry 加版本号：每次更新 TTL 递增版本并插入新堆节点，清理时发现堆节点版本不是当前版本就跳过。这样避免在堆中间删除，但会产生一些延迟垃圾。时间轮更适合海量近似过期，按时间槽挂 key，到槽后批量检查；精度由 tick 决定。

TTL 语义要提前定义清楚。固定 TTL 是写入后过一段时间过期；idle TTL 是多久没访问就过期，读命中也会延长时间；refresh TTL 是到期前后台刷新；soft TTL 和 hard TTL 则允许短时间返回旧值，同时触发异步刷新。这些语义对应的实现成本差别很大。idle TTL 会让 `Get` 变成写操作，因为每次读都要更新过期时间索引；soft TTL 要处理单飞刷新，避免大量请求同时回源。

并发实现上，过期判断和删除要用同一个 entry 版本保护。一个线程读到 entry 后准备删除，另一个线程刚刚更新了同一个 key，如果没有版本或指针比较，旧删除可能把新值删掉。常见做法是删除时检查 map 当前指针仍然是自己看到的 entry，或者检查版本一致。分片缓存里，每个 shard 自己管理过期索引和清理任务，避免全局锁。

时间源最好用单调时间计算间隔，避免 wall clock 回拨让对象突然“复活”或提前过期。系统时间可以用于日志和展示，但过期判断应使用运行时提供的 monotonic elapsed time。清理线程也要限制单轮工作量：如果一次发现几十万个 key 过期，不能在一个锁内全部删完，否则正常请求会被长时间阻塞。可以每轮清理固定数量，剩下的下轮继续。

工程上还要考虑内存和回源保护。过期缓存如果大量 key 同时到期，会出现缓存雪崩；可以给 TTL 加随机抖动，让过期时间分散。对热点 key，可以用请求合并、后台预刷新或 stale-while-revalidate，避免一个过期点打爆下游。面试里完整回答可以概括为：map 解决查找，时间索引解决清理，版本号解决并发更新，单调时钟和分批清理解决运行时稳定性。

## 138. 如何实现一个滑动窗口限流器？

滑动窗口限流器要先确定精度。最精确的是滑动日志：每个主体保存最近请求时间戳队列，请求到来时删除窗口外时间戳，再判断队列长度是否超过阈值。它的优点是语义准确，缺点是高 QPS 下每个请求都要写时间戳，内存随窗口内请求数增长。适合低到中等流量、需要精确控制的接口，不适合大规模网关默认限流。

更常见的是时间桶滑动窗口。把窗口切成固定数量的小桶，例如 60 秒窗口切成 60 个 1 秒桶，或者 1 秒窗口切成 20 个 50 毫秒桶。每个主体维护一个环形数组，桶里保存计数和桶对应的时间片编号。请求到来时，根据当前时间计算桶下标；如果桶时间片不是当前片，先重置桶再写入。判断是否放行时，把最近窗口覆盖的桶求和，超过阈值就拒绝。桶越细越平滑，但内存和求和成本越高。

为了让单次请求接近 `O(1)`，可以维护 rolling sum。每次桶被重置时，把旧桶计数从总和里减掉，再把新请求加到当前桶和总和里。这样判断只读总和，不需要每次扫所有桶。这里最容易出错的是桶复用：不能只按数组下标清零，必须校验桶的时间片编号，否则时间跳跃或长时间无请求后，旧桶会被误计入当前窗口。

并发下，每个主体的窗口状态需要同步。按 key 分片加锁是最稳的方案：同一用户、IP 或租户的窗口更新串行化，不同主体并行。高频热点主体会让单个锁很热，可以对热点主体做本地快速拒绝、分片计数加后台合并，或把它提升到专门的限流路径。原子数组也能做一部分优化，但窗口滚动、总和扣减和桶时间戳更新是复合操作，只靠单个原子加法不够。

分布式限流要明确目标是全局严格，还是每个实例近似。严格全局可以把状态放到 Redis，用 Lua 脚本把清理、计数、过期设置和判断放在一次原子操作里；代价是每次请求多一次网络往返，热点 key 会压垮中心存储。近似方案是每个实例本地限流，再按实例数分配配额，或者中心周期性下发租户额度。本地方案延迟低，但节点扩缩容和流量不均时会超发。

返回结果也要设计好。限流器不应只返回 true/false，最好返回剩余额度、建议等待时间、拒绝原因和当前窗口边界。这样上层可以设置 `Retry-After`、做排队或降级。面试里可以说：滑动窗口的实现核心是时间分桶和正确的桶轮转；工程难点在状态膨胀、热点主体、分布式一致性和窗口边界的误差控制。

## 139. 如何实现一个令牌桶限流器？

令牌桶的状态很少：`capacity` 表示桶容量，`tokens` 表示当前令牌数，`rate` 表示补充速率，`lastRefill` 表示上次补充时间。每次请求到来时，先用当前单调时间计算从 `lastRefill` 到现在应该补多少令牌：`tokens = min(capacity, tokens + elapsed * rate)`，再更新 `lastRefill`。如果请求需要的令牌数不超过 `tokens`，就扣掉并放行；否则拒绝或返回需要等待多久。

实现上可以使用浮点 token，也可以用整数定点数。浮点写起来简单，但在长时间运行和高频更新下会有精度细节；整数定点数更稳，例如把 1 个 token 放大成 1e6 个微令牌。补充速率也可以表达成“每隔 fillInterval 增加 fillTokens”，类似很多网关和代理的配置。无论哪种方式，都要用单调时间，避免系统时间调整影响补充速度。

单机并发最直接的方案是每个桶一把锁，锁内完成 refill 和 consume。因为一次操作只改几个字段，锁持有时间很短。高并发、多主体场景下，桶状态通常存在 `map[subject]*bucket` 里，再按 subject 分片加锁。不要为每个请求启动定时器补 token；惰性补充更便宜，只有请求到来时才按时间差计算当前令牌数。后台定时补充适合少量固定桶，不适合海量动态主体。

如果请求允许等待，令牌桶要计算排队时间。缺几个 token，就用 `missing / rate` 算出最早可用时间。等待可以由调用方 sleep，也可以进入队列。进入队列后问题会变复杂：队列长度上限、请求取消、deadline、优先级和公平性都要处理。很多网关宁愿快速拒绝，也不在限流器内部维护长队列，因为排队会把压力转成内存和尾延迟。

分布式令牌桶有几种做法。中心化方案把桶放到 Redis 或控制面，扣减用原子脚本，语义清楚但延迟和热点明显。本地方案给每个实例一部分速率和容量，延迟低但会因为流量不均导致部分实例没令牌、部分实例闲置。折中方案是中心发放租约：实例批量领取一段时间的 token，本地快速扣减，用完再续租。它牺牲一点全局精确性，换取请求路径低延迟。

令牌桶和滑动窗口的差别要讲清。令牌桶控制长期平均速率，同时允许容量范围内的突发；滑动窗口更像最近时间段内的计数上限。实现令牌桶时，核心不是定时塞 token，而是用时间差懒计算当前令牌数。工程重点是时间精度、整数化、并发扣减、等待语义和分布式额度分配。

## 140. 如何实现一个时间轮定时器？

时间轮用一个环形槽数组管理定时任务。假设 tick 是 100 毫秒，槽数是 512，那么一圈覆盖 51.2 秒。新增任务时，根据 `deadline - now` 计算它落在哪个槽；如果延迟超过一圈，就记录剩余圈数 `rounds`。推进线程每过一个 tick 前进一步，取出当前槽里的任务，`rounds` 大于 0 的任务减一后留在槽里，`rounds` 为 0 且到期的任务触发。

任务节点通常包含 `deadline`、回调或任务 ID、槽链表指针、取消标记、版本号和状态。取消最好做成懒取消：业务线程把状态标成 cancelled，推进线程扫到时跳过。直接从槽链表中间删除需要拿槽锁，还要处理推进线程正在遍历的并发问题。懒取消会留下一些无效节点，所以槽处理时要顺手清理。

新增任务的并发路径要尽量轻。常见做法是业务线程把新增任务写入 MPSC 队列，时间轮推进线程每个 tick 批量取出并挂到槽里。这样槽链表只由推进线程修改，锁很少。另一种做法是每个槽有自己的锁，业务线程直接挂槽；实现简单，但高并发注册和当前槽扫描可能冲突。选择哪种方式取决于任务量和延迟要求。

长延迟任务可以用 `rounds`，也可以用层级时间轮。单层时间轮加 rounds 简单，但一个很远的任务会一直挂在某个槽里，每圈检查一次。层级时间轮把近处任务放细粒度轮，远处任务先放粗粒度轮，接近到期时再下放。它更适合跨度很大的定时任务，但实现复杂，需要处理层级推进和任务迁移。

推进线程不能直接执行重任务。它应该只负责发现到期任务，然后投递到 worker 池或回调队列。否则某个回调慢了，后面的 tick 都会延迟。还要限制单槽最多处理数量：如果大量任务集中在同一个 tick 到期，推进线程可能被打满。可以分批投递、记录滞后指标，必要时让调用方知道定时器已经过载。

时间精度由 tick 决定。tick 越小，误差越小，推进频率和锁竞争越高；tick 越大，成本低，但任务可能晚一个 tick 触发。时间轮适合海量、近似、短回调的超时管理，比如连接空闲、RPC timeout、重试退避和临时封禁；如果任务数量不大但要求严格按 deadline 排序，最小堆定时器更简单。面试里要把这个取舍讲出来。

## 141. 如何实现一个 Top-K 热点 key 统计？

Top-K 热点 key 首先要问清是精确还是近似、全历史还是时间窗口、单机还是分布式。如果 key 数量不大，可以用哈希表精确计数，再配一个大小为 K 的最小堆。哈希表记录每个 key 的计数和堆位置；每次 key 计数增加后，如果它已经在堆里就向下或向上调整，如果不在堆里且计数超过堆顶，就替换堆顶。这样更新成本通常是 `O(log K)`，但空间是 `O(U)`，`U` 是不同 key 数量。

如果 key 空间很大，精确计数会吃掉大量内存。近似方案可以用 Count-Min Sketch 估计频率，再配一个候选集合或最小堆维护可能的 Top-K。每次请求更新 sketch 后，得到 key 的估计频率；如果 key 已在候选堆里就调整，否则当估计值超过堆顶时进入候选。要注意 sketch 不能枚举 key，必须有候选结构，否则你只知道某个 key 的估计频率，不知道全局哪些 key 热。

另一类实现是 Space-Saving 或 HeavyKeeper 这类 heavy hitter 算法。它们只保留有限候选，对流式数据持续更新，空间接近 `O(K)` 或 `O(K log K)`。优点是内存稳定，适合网关、缓存和日志流；缺点是结果有误差，低频 key 可能被挤掉，计数也可能偏大或偏小。面试时可以说：业务治理通常接受近似 Top-K，因为热点识别要的是快速发现，而不是计费级精确排名。

窗口化很重要。没有时间衰减的 Top-K 会被历史热点占住，今天已经不热的 key 还在榜上。常见做法是按时间片维护多个 Top-K 或 sketch，例如每 10 秒一个片，查询最近 1 分钟时合并 6 个片；也可以用双缓冲，当前窗口写 active，窗口结束后发布结果并清空旧窗口。滑动窗口越细，结果越平滑，内存和合并成本越高。

并发实现不要让每个请求都抢一个全局堆。请求路径可以只做分片计数或更新本地 sketch，后台周期性合并各 shard 的候选 Top-K。每个 worker 维护本地候选，合并线程把本地 Top-K 做 k 路归并，再用精确计数或 sketch 估计校正。这样实时性略差，但请求路径稳定。对极热 key，还要注意同一个计数器的 cache line 争用，必要时做分片累加。

输出结果也要带上下文：窗口范围、统计口径、估计误差、是否包含被采样流量、key 的脱敏形式和最近更新时间。发现 Top-K 后通常还要接治理动作，比如热点副本、本地缓存、请求合并、单 key 限流或预热。Top-K 统计本身只是观测结构，不能自动判断一个 key 是正常热点还是攻击流量。

## 142. 如何实现一个低内存去重系统？

低内存去重先要确认能不能接受误判。精确去重必须保存所有已见元素或它们的强哈希，内存至少随唯一元素数量线性增长；如果数据量很大，就只能通过外部存储、分片、落盘排序或 LSM 类结构来承接。近似去重可以用 Bloom Filter、Cuckoo Filter、Counting Bloom Filter 或 HyperLogLog 这类结构，但它们的语义不同。Bloom Filter 能回答“可能见过/一定没见过”，HyperLogLog 只能估算 distinct 数，不能判断某个元素是否见过。

最常见的低内存方案是 Bloom Filter。准备一个 bit array 和多个 hash 函数，插入元素时把多个位置置 1，查询时如果任一位置为 0，就一定没见过；如果全为 1，就可能见过。它没有假阴性，但有假阳性。假阳性意味着一个新元素可能被误判为已见过，所以只能用于可以容忍漏处理的场景，例如爬虫 URL 去重、日志预过滤、缓存穿透保护，不能用于订单、权限和资金判断。

内存大小要按目标误判率反推。元素数 `n` 越大、误判率 `p` 越低，需要的 bit 越多，hash 次数也会增加。工程上不能只说“用布隆过滤器省内存”，要给容量规划：预计一天多少唯一 key，允许多少误判，bit array 多大，hash 函数几个。hash 也要稳定且分布均匀，可以用两个 64 位 hash 组合生成多个位置，避免真的计算很多套昂贵 hash。

如果需要删除，普通 Bloom Filter 不够，因为 bit 可能由多个元素共享。Counting Bloom Filter 把 bit 换成小计数器，可以删除，但内存会明显增加，还要处理计数溢出。Cuckoo Filter 支持删除，通常保存短 fingerprint，查询和删除成本也低，但装载率、搬迁失败和扩容策略要处理好。选择结构时要围绕语义，而不是只看名字。

带时间窗口的去重更常见，例如“24 小时内同一个 request_id 只处理一次”。可以按时间分片维护多个 Bloom Filter，当前小时写当前片，查询最近 24 个片；过期时整片丢弃。这样不需要逐个删除，内存上限稳定。缺点是边界粒度受分片大小影响，查询要查多个片。也可以用双 Bloom：当前片和上一片，适合短窗口，但窗口边界会有近似误差。

如果必须精确又要低内存，可以先缩短保存内容：不存原始字符串，只存 64 位或 128 位指纹；再按 hash 分片，把旧分片落盘或做排序归并。64 位指纹碰撞概率很低，但不是零，严肃业务要评估风险或使用 128 位。面试里可以总结：低内存去重要先定误判语义，再选结构；Bloom 类适合近似 membership，HLL 适合基数估计，精确去重最终还是要为每个唯一元素付出线性状态。

## 143. 如何实现一个支持动态节点增删的负载均衡哈希环？

动态哈希环通常用一致性哈希实现。把每个真实节点映射成多个虚拟节点，虚拟节点按 hash 值放到一个有序数组或平衡树里。查找 key 时，先计算 key 的 hash，在有序结构中找第一个大于等于该 hash 的虚拟节点；如果超过末尾就回到第一个节点。这个过程在有序数组中可以用二分查找，复杂度是 `O(log V)`，`V` 是虚拟节点数。

增加节点时，为新节点生成一批虚拟节点 token，插入环中。删除节点时，删除它的所有 token。受影响的 key 主要是新 token 和前一个 token 之间的区间，所以迁移量比普通取模小很多。虚拟节点数量要按节点容量设置：大机器可以有更多 token，小机器更少。token 分布要稳定，通常用节点 ID、序号和 hash 函数生成，避免每次重启 token 都变。

请求路径要读到一致的 ring 快照。最稳的方式是 copy-on-write：控制面或健康检查线程构建一份新的有序 token 数组和元数据，校验通过后用原子引用发布；请求线程只读当前快照，不在请求路径上加全局写锁。更新频繁时，也可以用读写锁，但要注意 ring 重建不能长时间阻塞请求。快照里最好带版本号，便于日志、排障和灰度发布。

节点状态不能只看“存在于环上”。真实负载均衡还要处理健康状态、权重、机房、租户隔离和连接保持。一个节点健康失败后，可以把它从可选环中摘除，也可以降低权重。摘除会导致 key 迁移，频繁抖动会让缓存命中率下降，所以健康检查要有失败阈值、恢复阈值和抖动控制。对有状态连接，还要考虑旧连接继续留在原节点，新连接使用新 ring。

并发增删节点时要避免中间态。不能先删一半 token 就发布，也不能让请求线程读到未排序的 token 数组。构建过程应在私有对象里完成：生成 tokens、排序、合并相同 hash、构建 node 元数据、计算校验信息，全部成功后一次性发布。删除节点也要保证所有 token 和元数据同时消失。多个控制事件同时到达时，按版本串行处理，或基于最新期望状态重建 ring。

还要处理热点 key。一致性哈希只保证 key 映射稳定，不保证负载均匀。少数超级热点 key 仍然会打爆一个节点。工程上可以给热点 key 做多副本选择、请求合并、本地缓存或单独路由；也可以结合 P2C、加权随机和负载反馈，在一致性哈希之外做二次选择。面试答案最好说清：动态哈希环解决的是节点增删时的低迁移，不是完整的负载治理系统。

## 144. 如何实现一个高并发延迟队列？

延迟队列的语义是任务到达指定时间后才可被消费。最直接的数据结构是最小堆，按 `runAt` 排序，堆顶是最早到期任务。生产者插入任务时加锁入堆；消费者查看堆顶，如果未到期就等待到堆顶时间，如果已到期就弹出执行。这个模型简单，适合中小规模任务。高并发下，全局堆和全局条件变量会成为瓶颈。

扩展方案是分片。按任务 ID、租户或随机方式把任务分到多个 shard，每个 shard 有自己的堆、锁和唤醒机制。消费者可以固定绑定 shard，也可以从多个 shard 里抢到期任务。分片降低锁争用，但带来全局最早任务发现问题：如果一个消费者只看某个 shard，其他 shard 的早期任务可能要等自己的消费者唤醒。常见做法是每 shard 一个调度协程，或者上层维护每个 shard 的堆顶索引。

如果任务量非常大且允许时间精度误差，可以用时间轮。生产者把任务按到期时间放到槽里，时间轮推进到对应槽时，把到期任务投递到就绪队列。这样插入通常接近 `O(1)`，比堆的 `O(log n)` 更适合海量短延迟任务。缺点是 tick 粒度带来延迟误差，远期任务需要 rounds 或层级时间轮。很多延迟队列会组合使用：近时间用时间轮，远时间或精确任务用堆。

任务状态要设计完整。一个任务可能处于 waiting、ready、running、done、cancelled、retrying。取消任务时，最好用任务表记录状态，堆或时间轮里保留旧节点，到期弹出时发现 cancelled 就跳过。这样避免从堆或槽链表中间删除。为了支持去重和更新延迟，需要 `map[taskID]*taskState`；插入新版本时递增 version，到期时只有版本匹配才真正投递。

唤醒机制是延迟队列的细节难点。生产者插入一个比当前堆顶更早的任务时，必须唤醒正在睡眠的调度线程，让它重新计算等待时间。否则线程可能睡到旧堆顶，导致新任务延迟执行。可以用条件变量、channel、eventfd 或平台事件通知。消费者等待时要处理虚假唤醒、任务取消、系统暂停和时钟跳跃。等待时间应基于单调时钟计算。

高并发延迟队列还要有背压。队列长度、单租户任务数、最大延迟、最大 payload 大小都要限制；否则延迟队列会变成无限内存池。任务执行不要在调度线程里完成，调度线程只把到期任务投递到 worker 池。需要可靠性时，还要把任务持久化：写入 WAL 或数据库后再确认入队，恢复时重建堆或时间轮。面试里可以按“堆语义、分片降锁、时间轮降复杂度、状态机防竞态、唤醒保证准时、背压保护内存”这条线回答。

## 145. 如何评估一个算法在真实系统中的常数开销？

评估常数开销要从真实路径出发，而不是只看大 O。两个算法同样是 `O(1)`，一个每次只改一个整数，另一个要分配对象、算三次 hash、抢锁、写多条 cache line，系统表现会完全不同。先把算法放到目标调用路径里，列出每次操作实际做了什么：CPU 指令、内存访问、分支、hash、锁、系统调用、网络访问、对象分配和日志埋点。常数开销就是这些东西叠起来的。

第一步通常是微基准，但微基准要贴近生产输入。数据规模、key 分布、命中率、读写比例、对象大小、并发度、热点比例都要设置出来。缓存算法要测命中、未命中、淘汰和更新已有 key；限流器要测冷 key、热 key、窗口轮转；Top-K 要测低基数和高基数；时间轮要测集中到期和均匀到期。只测一个均匀随机 happy path，结论很容易偏。

指标不能只看平均耗时。至少要看 `ns/op`、`B/op`、`allocs/op`、吞吐、P50/P95/P99、锁等待、GC 次数和 CPU profile。Go 里可以用 benchmark 加 `-benchmem` 看分配，用 pprof 看 CPU 和堆，用 trace 看调度和阻塞；Java 里要注意 JIT warmup、逃逸分析和 GC；C/C++ 里还要看 cache miss、branch miss 和 allocator。不同语言工具不同，但关注点一样：请求路径有没有多余分配、锁和缓存抖动。

宏基准和压测用来验证微基准结论。把算法放进真实服务或尽量接近的 harness，接入序列化、网络、日志、指标和下游模拟，观察端到端延迟。很多结构在单线程微基准里很快，一上并发就因为共享状态、false sharing 或全局锁变慢。也有些优化在微基准里很明显，但在真实请求里只占 1% 时间，不值得增加复杂度。

还要看退化场景。哈希表要测冲突和扩容，LRU 要测扫描污染和热点 key，滑动窗口要测窗口切换瞬间，令牌桶要测长时间空闲后突发，时间轮要测单槽堆积，延迟队列要测大量取消任务，Top-K 要测 key 基数暴涨。真实系统的问题经常出现在这些边界，而不是均匀负载。

最后把常数开销转成容量语言。比如一次操作多 80ns，在每秒 200 万次请求上就是 160ms CPU 时间；每次多分配 64B，在 100 万 QPS 下就是每秒 64MB 新对象，会直接影响 GC；一个全局锁在 32 核上让吞吐从线性增长变成排队。面试里可以总结：评估常数开销要用生产分布做基准，用 profile 找真实瓶颈，用并发压测验证尾延迟，再把纳秒、字节和锁等待换算成机器成本和容量边界。
