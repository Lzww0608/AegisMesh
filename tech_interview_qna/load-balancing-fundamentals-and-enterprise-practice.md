## 1. 常见负载均衡有哪些类型？可以按部署位置、网络层级、算法、状态维护方式分别怎么分类？

可以先这样答：

负载均衡不是单一产品名，而是一组“把请求分到多个后端”的机制。面试里如果问“有哪些类型”，最好不要只答 round-robin、least connections 这种算法名，而是按几个正交维度讲：它部署在哪里、工作在第几层、按什么算法分流、运行时维护多少状态。这样回答更完整，也更接近企业真实架构。

先按部署位置分。最靠外的是全局或边缘入口型，比如 DNS 负载均衡、GSLB、CDN 边缘调度、Global Accelerator 这类东西，解决的是“用户先进哪个 Region、哪个边缘点”。再往里是区域入口型，比如云 SLB、四层或七层入口负载均衡、Ingress Controller、硬件 ADC，解决的是“这批公网或内网入口请求先落到哪个接入点”。继续往内是服务间治理型，比如 Service Mesh sidecar、node proxy、L7 proxy。最靠近调用代码的是客户端负载均衡，也就是 gRPC、Finagle、Dubbo 这类 SDK 在调用方进程内自己选实例。AegisMesh 当前就属于这一类。

再按网络层级分。最粗的一层是 DNS 层，它根本不转发真实业务包，只回答“这个域名先解析到哪里”。再下一层是 L4，也就是传输层负载均衡，主要看 IP、端口、协议、连接或流；AWS 的 Network Load Balancer 文档明确把它放在 OSI 第四层。再下一层是 L7，也就是应用层负载均衡，能看到 HTTP host、path、header、method，或者 gRPC method、metadata、status 这类更高层语义；AWS 的 Application Load Balancer 文档就是按第七层来定义它的。比传统 L7 再细一点的，可以叫 RPC-aware 或 application-aware client-side LB，它不是单独 OSI 一层，但在工程实践里很重要，因为它能直接拿到 deadline、attempt、idempotency、local inflight 这些普通网关看不到的信息。

再按算法分。最基础的是静态算法，比如 round-robin、weighted round-robin、random、一致性哈希、源地址哈希。它们主要依赖配置，不怎么依赖实时运行状态。再往上是动态算法，比如 least connections、least requests、P2C、EWMA latency、observed load、ORCA/后端负载反馈、慢启动和自适应权重。Envoy 文档里就把 weighted round robin、least request、ring hash 这些明确分开，而且 least request 默认就是典型的 P2C 风格选择。

最后按状态维护方式分。第一类是近似无状态或弱状态型，典型是简单轮询、随机、基于静态哈希的选择，运行时只需要少量位置指针或哈希映射。第二类是连接或流状态型，比如 least connections、L4 flow hash，它需要知道当前连接数、活跃请求数或连接生命周期。第三类是会话粘滞型，需要维护 cookie、源地址、session affinity 或一致性哈希环，让同一用户尽量落到同一后端。第四类是反馈闭环型，不只维护连接数，还维护健康状态、EWMA、错误率、慢启动、熔断状态、后端负载报告等。AegisMesh 的 adaptive P2C 就属于这一类，因为它会综合本地 EWMA、inflight 和控制面下发的 `slow_score`、`status`。

如果想把这题答得更像做过系统的人，我会补一句：这几个维度不是互斥关系。一个真实系统经常同时是“客户端侧 + L7 aware + 动态 + 反馈闭环型”；另一个系统可能是“入口侧 + L4 + flow-hash + 连接状态型”。关键不是背分类名，而是能说出它在架构里到底解决哪一段分流问题。

如果面试官继续深挖，可以按这条路线走：

1. 先按部署位置问：是 DNS、边缘、入口代理、sidecar，还是客户端进程内选实例。
2. 再按层级问：它看到的是域名、五元组，还是 HTTP/gRPC 语义。
3. 再按算法问：是静态分流，还是实时根据连接、延迟、错误、负载反馈做动态调整。
4. 再按状态问：它是近似无状态，还是要维护连接表、会话粘性、健康状态和权重。
5. 最后落到项目：AegisMesh 为什么属于客户端侧、L7 aware、动态、反馈闭环型负载均衡。

## 2. 静态负载均衡和动态负载均衡的区别是什么？各自适合什么场景？

可以先这样答：

静态和动态的核心区别，不在于算法名字，而在于决策输入会不会随着运行时状态变化。静态负载均衡主要依据预先配置好的规则分流，比如轮询、加权轮询、随机、一致性哈希。它默认认为后端能力差不多，或者至少差异可以用固定权重表达。动态负载均衡则会持续看运行时信号，比如 active requests、连接数、延迟、错误率、CPU、后端自报负载、健康状态，再根据这些信号调整选择。

静态负载均衡的优点是简单、稳定、可预测。调试时很清楚，为什么请求会被分到某个后端，通常一眼就能从配置推出结果。它的代价是对运行时不够敏感。某个实例虽然还在地址列表里，但已经明显变慢，静态策略仍可能继续给它正常流量。对于容量相近、请求成本差异不大、后端非常稳定的场景，这种代价可以接受。

动态负载均衡的优点正好相反。它更适合实例状态波动明显、请求成本差异大、慢故障比宕机更常见的场景。比如一个后端还活着，但 p99 明显变坏、活跃请求堆积上来了，least request、EWMA、observed load 这类策略就能比纯 round-robin 更早地把流量挪开。Envoy 的 least request、client-side weighted round robin，或者 gRPC/ORCA 这类后端负载反馈，本质上都属于这个方向。

但动态也不是天然更高级。它引入了两个新成本。第一是观测成本，你得采集、维护和传播实时状态。第二是反馈控制成本，调得不好会振荡。比如延迟窗口太短、EWMA 太敏感、所有客户端同时看见同一个节点变好又一起冲上去，就会出现 herd 行为或路由抖动。也就是说，动态负载均衡在很多生产系统里更有效，但前提是你愿意为实时状态和稳定性控制付复杂度成本。

适用场景上，我通常这样分。静态负载均衡适合公网入口的基础层、简单 Web 服务、后端差异小的无状态服务、以及你更关心稳定和可解释而不是极致自适应的场景。动态负载均衡适合微服务内部调用、长连接/流式 RPC、实例质量波动明显、慢故障常见、以及你有足够观测基础设施来支持实时调整的场景。

放到 AegisMesh 上，这个对比非常直观。项目里的 round-robin 是静态基线，adaptive P2C 则是动态策略。它不会只看实例列表，而是叠加本地 inflight、EWMA 和控制面下发的 `slow_score`、`status`。所以它更适合处理 fail-slow。代价也很明确：比 round-robin 多了 telemetry、状态传播、评分和本地维护开销。这正是仓库里 no-fault 场景可能比简单 round-robin 稍重，而 fault 场景收益很大的原因。

如果面试官继续深挖，可以按这条路线走：

1. 先问输入：静态策略为什么主要依赖配置，动态策略为什么必须依赖运行时信号。
2. 再问优势：静态为什么更简单稳定，动态为什么更适合慢故障和异构负载。
3. 再问代价：动态为什么更容易引入观测开销、传播延迟和反馈振荡。
4. 再问适用场景：入口层为什么常先用静态或弱动态，服务间治理为什么更偏动态。
5. 最后问项目：AegisMesh 为什么不满足于 round-robin，而要走 adaptive P2C 这条动态路线。

## 3. L4 负载均衡和 L7 负载均衡的核心区别是什么？它们分别能看到哪些信息？

可以先这样答：

L4 和 L7 的核心区别，不是谁“更高级”，而是它们在做分流决策时能看到多少协议语义。L4 工作在传输层，主要根据 IP、端口、协议类型和连接或流状态来选后端。L7 工作在应用层，能理解 HTTP、gRPC、WebSocket 这类上层协议，所以可以按 host、path、header、method、状态码，甚至 RPC 方法名和 metadata 做决策。

AWS 的官方文档把这个边界讲得很清楚。Application Load Balancer 被定义为工作在 OSI 第七层，可以根据请求内容做规则匹配和路由。Network Load Balancer 被定义为工作在第四层，主要根据协议和端口转发，并对 TCP、UDP、QUIC 流维护一致的目标选择。NLB 文档还明确提到 TCP 流量会根据 flow hash 选择目标，而且同一条连接生命周期内会保持到同一个 target。

因此，L4 通常能看到这些信息：源 IP、目的 IP、源端口、目的端口、传输协议、连接建立与关闭、少量 TLS 外层信息，外加自身维护的连接数、活跃连接、流哈希状态。它通常看不到 URI、header、方法名、业务用户、状态码。即便能看到 TLS SNI、ALPN 这类协议信息，也还远没到完整应用语义的程度。

L7 则不同。只要它能终止或解析应用协议，就可以看到 host、path、query、header、cookie、HTTP method、status code、gRPC service/method、metadata，甚至还能做认证、重写、灰度、限流、WAF、缓存、协议转换。代价也很明确：协议解析更重、TLS 终止更复杂、资源消耗更高、隐私和安全边界也更靠前。

面试里还有一个容易被忽略的边界：L7 能不能看到这些信息，取决于它能否拿到明文或协议解析权。如果上层流量端到端加密，而中间层既不终止 TLS 也不理解协议，那它名义上部署在“前面”，实际能力更接近 L4。反过来，像 gRPC 客户端 SDK 这种进程内的负载均衡，虽然不一定是一个“代理盒子”，但它天然就站在应用层，知道每次 RPC 的 method、attempt、deadline 和返回状态。

AegisMesh 就很适合拿来说明这个区别。它不是传统入口 L7 代理，但它是明显的 L7/RPC-aware 负载均衡，因为它工作在 gRPC 客户端里，能看到 resolver 地址、method、interceptor 里的状态码、attempt、本地 inflight 和 EWMA。这些是普通 L4 LB 拿不到的，所以它才有机会做 method-level policy、retry budget 和 fail-slow 自适应路由。

如果面试官继续深挖，可以按这条路线走：

1. 先问核心差异：L4 基于连接和流，L7 基于应用语义。
2. 再问信息面：L4 看五元组和连接状态，L7 看 host、path、header、method、status、RPC method。
3. 再问能力：L7 为什么更适合做灰度、认证、重写、WAF、协议转换和细粒度路由。
4. 再问代价：L7 为什么更重、更复杂，也更依赖 TLS 终止和协议解析。
5. 最后问项目：AegisMesh 为什么虽然不是传统网关，却仍然属于 L7 aware 的负载均衡。

## 4. 企业生产环境通常会把哪些层面的负载均衡组合起来使用？

可以先这样答：

企业生产环境几乎不会只靠一层负载均衡。真实架构里，负载均衡通常是分层叠加的，因为不同层面对的是不同问题。最外层解决“用户先到哪个区域、哪个入口”；中间层解决“这个入口请求该落到哪组服务”；最内层解决“某个服务的这次调用该打到哪个具体实例”。这些问题根本不是一个设备或一个算法能一次性做完的。

典型的公网入口链路可以这样看：最前面是 DNS 或全局流量调度，决定用户先进哪个 Region，或者哪个公网入口地址。再往里是 CDN 或边缘节点，负责就近接入、缓存静态资源、吸收一部分 TLS 和边缘安全压力。进入 Region 以后，通常还有云 SLB、四层 NLB、七层 ALB 或硬件 ADC，负责区域入口接入、跨可用区分流和基础健康检查。再往业务里走，可能是 Ingress、API Gateway 或 BFF 层，处理认证、路由、限流、协议聚合和灰度。到了服务间调用阶段，又会有 Service Mesh 或客户端负载均衡，做实例级别的流量治理。

内网服务间调用的组合也很常见。一个服务先通过服务发现拿到实例列表，然后在客户端 SDK 或 mesh sidecar 上做 least request、EWMA、outlier ejection、retry budget、timeout 这类更细粒度的治理。也就是说，入口负载均衡和服务间负载均衡经常同时存在，只是负责的流量段不同。前者偏 north-south，后者偏 east-west。

从企业实践看，这种分层组合一般有三类常见模式。第一类是“DNS/GSLB + CDN + 区域入口 LB”，适合全球用户访问。第二类是“云 SLB/NLB + Ingress/API Gateway + Mesh”，适合 Kubernetes 或微服务平台。第三类是“服务发现 + 客户端负载均衡”，适合内部 RPC 密集、语言 SDK 能力较强的体系。很多大公司三种都会同时存在，只是不同业务链路上叠的层数不同。

面试时我通常会补一句：不是每一层都在重复做同一件事。DNS 更像把用户送到某个大门口；CDN 更像边缘缓存和接入面；区域 SLB 更像把连接送进某个集群；API Gateway 更像入口业务门卫；Service Mesh 或客户端 LB 才会细到“这次调用具体打哪台实例”。如果把这些层混成一个“负载均衡器”，后面关于故障域、缓存、安全和服务治理的讨论就会变得很乱。

放到 AegisMesh 这条线上，项目当前只覆盖了其中一段，也就是服务间调用的客户端侧治理。它不替代 DNS、CDN、云 SLB 或 API Gateway。更准确地说，它适合被放在企业分层架构的最内层之一，作为 east-west RPC 级别的自适应负载均衡和故障治理组件。

如果面试官继续深挖，可以按这条路线走：

1. 先问公网入口：DNS、CDN、全局加速、区域 LB 分别在哪一层切流。
2. 再问业务入口：为什么入口网关既要路由，也要做认证、限流和灰度。
3. 再问服务间调用：为什么内部 RPC 仍然需要 mesh 或客户端 LB，而不是入口层一次性搞定。
4. 最后问项目：AegisMesh 在整套企业组合里到底占哪一层，不该冒充哪一层。

## 5. 为什么入口流量通常不是只依赖一个负载均衡器？

可以先这样答：

入口流量通常不能只依赖一个负载均衡器，最根本的原因是入口问题不是单维度问题。你同时要处理全球接入、DNS 解析、边缘缓存、DDoS 和 WAF、TLS 终止、跨 Region 或跨 AZ 调度、业务路由、灰度发布、认证限流，以及后端服务健康。这些职责既分布在不同故障域，也分布在不同协议层，硬塞给一个 LB，最后通常只会得到一个既复杂又脆弱的单点。

第一，故障域不同。DNS 是全球控制面，CDN 是边缘 POP，Regional SLB 是单 Region 或单 VPC 入口，API Gateway/Ingress 是业务入口控制点。你不能指望一个区域内的负载均衡器来解决全球用户先连哪个 Region 的问题，也不能指望 DNS 来做每次 HTTP 请求的 header 级路由。

第二，时间尺度不同。DNS 路由变化受 TTL、递归解析器缓存和客户端缓存影响，不适合拿来做秒级流量切换。相反，入口 LB 和网关处理的是实时连接和实时请求，可以按健康状态秒级甚至更快反应。CDN 缓存策略又是另一种时间尺度，它会影响静态资源是否回源、多久失效。一个控制面不可能在所有时间尺度上都同样合适。

第三，协议语义不同。L4 入口 LB 擅长高吞吐接入、跨 AZ 分流、客户端 IP 保留、静态 IP 暴露；L7 Gateway 擅长 host/path/method 路由、认证、限流、canary；WAF 擅长规则拦截；CDN 擅长静态内容边缘缓存。它们不是谁替代谁，而是各自承担不同语义的入口职责。

第四，容量和成本模型不同。把所有事情都压到一个七层大网关上，虽然功能看起来集中，但成本会迅速升高：TLS 终止、WAF、重写、限流、日志、回源策略全在一个点上做，CPU 和内存压力都大，而且变更面也集中。企业更常见的做法是把能够边缘处理的内容尽量边缘处理，把必须到业务入口才能做的决策留到网关，把实例级治理下沉到 mesh 或客户端。

第五，安全和组织边界不同。DNS 或全局接入通常由基础设施团队管理，CDN/WAF 可能是边缘平台团队，API Gateway 常由平台或业务接入团队管理，服务间治理由服务框架或 mesh 团队管理。单个负载均衡器既很难跨越这些组织边界，也很难在职责上保持清晰。

所以面试里如果被问“为什么不就放一个很强的 L7 LB 在最前面”，我会直接说：因为全球流量调度、边缘缓存与防护、业务入口路由、服务间实例选择不是同一个问题。真实系统分层，是为了把不同时间尺度、不同协议语义、不同故障域和不同组织职责拆开。

如果面试官继续深挖，可以按这条路线走：

1. 先问故障域：为什么全球、Region、AZ、集群、实例这几层不能混成一个入口点。
2. 再问时间尺度：为什么 DNS 不适合做秒级业务切流，L7 gateway 又不适合代替全球解析。
3. 再问协议职责：缓存、安全、连接接入、业务路由、实例治理为什么不是同一件事。
4. 最后问组织实践：为什么企业里常常是不同平台团队共同承担入口链路。

## 6. DNS 负载均衡、CDN 负载均衡、云 SLB、API Gateway、Service Mesh、客户端负载均衡之间如何分工？

可以先这样答：

这题最好按请求路径往里走。DNS 负载均衡决定“域名先解析到哪里”；CDN 决定“能不能在边缘就近响应，或者该回哪个源”；云 SLB 决定“进入某个 Region 或某个集群后，连接先落到哪个入口节点”；API Gateway 决定“这个业务请求该进哪条 API 路由、走哪套认证限流和灰度规则”；Service Mesh 决定“服务之间流量怎么治理”；客户端负载均衡决定“这次调用到底选哪个具体实例”。它们是串联关系，不是同义词。

先看 DNS。Route 53 文档里把 weighted、latency、failover、geolocation 这些 routing policy 分得很清楚。它的职责是解析层调度，不直接代理业务请求，也不终止真实连接。它擅长做全局入口选择、主备切换、按地域或延迟把用户导向不同区域，但它的变化速度受 TTL 约束，所以不适合做每个请求的细粒度分流。

再看 CDN。CloudFront 的定义很典型：它把静态和动态内容分发到全球边缘节点，优先由最低延迟的 edge location 响应，未命中才回源。它的核心价值是边缘接入、缓存、回源优化和降低源站压力。CDN 当然也会做一定程度的边缘负载分配，但它主要解决的是“离用户近”和“减少源站回源”，不是替代业务入口网关。

云 SLB 是区域入口层。像 AWS 的 ALB、NLB 或类似的云负载均衡，解决的是把连接和请求稳定送进某个区域、某个 VPC、某个服务池。L4/NLB 更偏连接接入、静态 IP、高吞吐和跨 AZ 分流；L7/ALB 更偏 HTTP/gRPC 语义路由、target group、listener rule、基础七层调度。它是平台入口，不直接承担所有业务认证和 API 生命周期治理。

API Gateway 再往内一层。AWS API Gateway 文档对它的定位很直白，就是应用的 front door。它负责创建、发布、维护、监控和保护 API，并承担 traffic management、authorization、access control、API version management、canary release 等任务。也就是说，API Gateway 更像业务 API 的入口编排和治理层，而不是一个只做后端实例选择的 LB。

Service Mesh 处理的是 east-west 流量。Istio 文档把这件事写得非常清楚：所有 mesh 服务之间的数据面流量通过 Envoy 代理，mesh 根据服务注册信息、流量规则、重试、超时、熔断、流量切分来治理服务间调用。它的关注点是服务到服务，而不是公网用户到系统大门口。mesh 当然也带负载均衡，但它的重点是服务间流量治理和可观测性。

客户端负载均衡是最靠近调用点的一层。gRPC 文档里说得很明确：name resolver 提供服务器地址列表，load balancing policy 维护 subchannel，并在每次 RPC 发送时选择连接。默认 `pick_first` 其实几乎不做真正分流，`round_robin` 才会轮转所有后端。客户端 LB 的优势是它离调用代码最近，知道每次 RPC 的 method、attempt、deadline、本地连接状态和本地延迟。AegisMesh 就属于这一层，只不过它比普通 round-robin 更进一步，叠加了 `slow_score`、EWMA 和状态机信息。

如果只用一句话总结它们的分工，我会这么说：DNS 解决“先去哪”，CDN 解决“能不能边缘就近答”，云 SLB 解决“怎么进这个区域或集群”，API Gateway 解决“这是不是合法请求、该走哪条业务路由”，Service Mesh 解决“服务间流量怎么治理”，客户端 LB 解决“这次调用选哪台实例最合适”。

如果面试官继续深挖，可以按这条路线走：

1. 先问 DNS：为什么它是解析层调度，不直接代理业务流量。
2. 再问 CDN：为什么它首先是边缘缓存和回源优化层，而不是业务 API 治理层。
3. 再问云 SLB：它为什么更偏区域入口接入和基础健康分流。
4. 再问 API Gateway：为什么它天然更关注认证、版本、限流、canary 和 API 生命周期。
5. 再问 Service Mesh：为什么它关注的是 east-west，而不是 north-south 的用户接入。
6. 最后问客户端 LB：为什么只有它最容易拿到本地 RPC 级别的细粒度信号。

## 7. 负载均衡和反向代理是什么关系？二者是否等价？

可以先这样答：

负载均衡和反向代理高度相关，但不等价。更准确地说，反向代理是一种部署形态或角色，站在服务端前面替后端接收请求；负载均衡是一种功能，核心是把请求分配到多个后端。一个反向代理可以带负载均衡能力，但它也可以只代理到单个后端。一个负载均衡器也不一定是典型的应用层反向代理，它可能只在 L4 做连接分发。

NGINX 的官方文档其实把这个关系讲得很直白。它在 reverse proxy 文档里先定义代理服务器如何把请求转给后端，再明确说“反向代理的一个常见用途是提供负载均衡”。也就是说，在 NGINX 视角里，reverse proxy 是更大的概念，load balancing 是其中一种常见用法。它还单独把 HTTP load balancing 和 reverse proxy 拆成两份文档，也正说明两者不是同一个词。

从能力上看，反向代理的典型职责包括：接收客户端请求、隐藏后端、转发请求、改写 header、终止 TLS、缓存、压缩、统一日志、接入认证、做 WAF 或访问控制。负载均衡只关心其中一件事：如果后面有多个可用后端，请求该发给谁。所以“负载均衡”更像策略，“反向代理”更像站位和转发角色。

二者有很大的重叠区，尤其在 L7 产品里。比如 NGINX、Envoy、HAProxy、很多 API Gateway，本身既是反向代理，也带负载均衡、健康检查、重试和观测能力。所以在工程讨论里，很多人会把“前面的反向代理”顺手简称成“负载均衡器”。这个说法不算完全错，但严格一点还是要分开，否则一讨论到缓存、WAF、认证、重写、代理链条，就会把“路由策略”和“代理职责”混成一团。

反过来看，也有大量负载均衡并不具备典型 L7 reverse proxy 语义。最常见的就是 L4 负载均衡，它可能按流哈希把连接打到后端，强调高吞吐、低开销、客户端 IP 保留和连接稳定，但不一定理解 URI、header 或业务协议。AWS NLB 这类产品就更接近“传输层负载分发器”而不是“全功能七层反向代理”。

放到 AegisMesh 上，这个区分也很有用。AegisMesh 当前不是传统反向代理，因为它不站在服务端前面统一接收所有流量；它更像客户端侧负载均衡和服务治理组件。它做了很多传统 LB 关注的事情，比如实例选择、状态过滤、重试预算和故障避让，但它不承担典型反向代理的入口缓存、统一 TLS 终止、WAF 或 API front door 角色。

所以我的结论会很直接：二者不等价。反向代理强调“代谁出面接请求”，负载均衡强调“把请求分给谁”。很多成熟产品两者兼做，但讨论架构职责时最好把这两个概念拆开。

如果面试官继续深挖，可以按这条路线走：

1. 先问定义：反向代理是角色，负载均衡是功能。
2. 再问重叠区：为什么 NGINX、Envoy、HAProxy、API Gateway 常常既做反向代理又做负载均衡。
3. 再问边界：单后端反向代理为什么不是负载均衡，L4 负载均衡为什么又不一定是典型 L7 反向代理。
4. 最后问项目：AegisMesh 为什么更接近客户端 LB，而不是反向代理。

## 8. 负载均衡器是否一定要有状态？无状态负载均衡有什么限制？

可以先这样答：

负载均衡器不一定非得“强状态化”，但真正跑到生产里，完全无状态的负载均衡非常少。因为只要你开始关心健康检查、连接生命周期、会话粘性、长连接复用、实例摘除、优雅下线、动态权重、重试或限流，系统就已经在维护状态了。更准确的说法是：有些负载均衡更接近“弱状态”或“近似无状态”，有些则是明确的“强状态闭环系统”。

最接近无状态的是那些主要靠静态映射做分流的机制。比如 DNS 的加权解析、简单的五元组哈希、ECMP 风格的流量分散、固定权重的随机或轮询。这类方案的优点很明显：实现简单、转发路径短、容易横向扩展、单节点吞吐高，而且节点之间不需要频繁同步运行时数据。对于公网入口、超高吞吐 L4 分流、或者后端差异很小的无状态服务，这种做法很常见。

但它的限制也很直接。第一，它很难对“慢”做出足够快的反应。实例没挂，只是排队变长、锁竞争严重、GC 抖动、磁盘变慢，近似无状态的负载均衡通常看不出来，或者只能等外部健康检查慢慢把它摘掉。第二，它拿不到细粒度运行时负载，所以做不好 `least connections`、`least requests`、基于延迟的动态降权，也做不好慢启动、连接排空、流量回收。第三，它对长连接和多路复用场景不够友好，因为“一次选路，长期复用”会把很多后续请求绑定在早期决策上。第四，它很难处理需要粘性的业务，比如会话、缓存局部性、分片亲和或流式连接恢复。

所以生产里的真实情况通常不是“有状态”和“无状态”二选一，而是分层。最外层可能用比较弱状态的全局分流，追求简单和高吞吐；越往里走，越接近服务实例和真实请求，状态就越重。比如 AWS NLB 在连接建立时按 flow hash 选 target，这比 L7 请求级负载均衡轻得多，但它仍然要维护 target 健康和连接生命周期。AWS ALB、Envoy、gRPC 客户端负载均衡则更进一步，它们已经明显依赖请求级语义和实时状态了。

放到 AegisMesh 里，这个边界就更清楚了。AegisMesh 不是无状态负载均衡。它的 balancer 会读取 resolver 下发的 `status`、`slow_score`，再叠加本地 `inflight`、`EWMA` 和 breaker 状态做选择。这么做的代价是维护成本更高，但换来的是对 fail-slow 的识别和避让能力。如果你把这些状态全部拿掉，只保留一个静态轮询，那它就很难解释项目最核心的收益，也无法支撑对尾延迟的治理。

如果面试官继续深挖，可以按这条路线走：
1. 先问“状态”具体指什么：是连接表、健康状态、权重、会话粘性，还是请求级延迟和错误反馈。
2. 再问为什么近似无状态方案吞吐高、扩展容易，但对慢故障不敏感。
3. 再问长连接、多路复用、会话亲和为什么会逼着负载均衡维护更多状态。
4. 再问动态算法为什么天然依赖状态：没有 `inflight`、延迟、错误率，就做不好 `least request`、EWMA、P2C。
5. 最后落回项目：AegisMesh 为什么必须保留 `slow_score + 本地 EWMA + inflight` 这套状态。

## 9. 负载均衡器本身如何做到高可用？

可以先这样答：

负载均衡器自己也必须被当成一个高可用系统来设计，否则它会成为所有后端之上的新单点。常见思路是三层：先做多副本，再做故障切换，最后把状态和配置的传播做稳。

第一层是多副本部署。云负载均衡通常不是一台设备扛全部入口，而是在多个可用区放多台节点。AWS NLB 文档里明确提到它在每个启用的可用区都放节点，跨可用区转发可选开启；如果某个可用区没有健康 target，对应的 IP 还会从 DNS 返回结果里移除。这个模型的核心就是“入口本身先去单点化”。如果是自建 NGINX/HAProxy，也会至少做双机甚至多机部署，而不是把 VIP 挂在单机上。

第二层是切换机制。最传统的是 active-passive，例如 NGINX 官方高可用方案里常见的 `keepalived + VRRP + 浮动 VIP`。主节点异常时，备节点接管虚拟地址，客户端不用改配置。云厂商更常见的是 active-active，多个入口节点同时承接流量，某个节点挂掉后由 DNS、Anycast 或上游路由自动绕开。active-passive 的优点是实现直观，状态一致性简单；active-active 的优点是利用率更高、切换更平滑，但对配置同步和观测要求更高。

第三层是把“请求路径”和“控制路径”分开。很多成熟系统会尽量让数据面无共享或少共享，让节点能独立转发；而策略、配置、证书、目标列表、健康状态则通过控制面同步。这样即使控制面短时抖动，请求路径也不会立刻全线受影响。对于客户端负载均衡，这一点更明显。gRPC resolver 已经解析出来的地址列表、已有 SubConn、已下发策略，通常都可以在控制面暂时不可达时继续服务。

工程上还要再补几件事。配置发布要支持版本号和回滚，避免多节点看到不同规则；健康状态需要去抖动，防止入口节点频繁做出相反判断；会话粘性、连接表、TLS session 之类如果必须共享，也要明确是强一致、最终一致还是直接不共享；监控上不仅看“活没活着”，还要看连接数、accept backlog、握手失败、CPU、内存、转发延迟和队列长度。

放到 AegisMesh 上，可以顺手把边界讲清楚。AegisMesh 当前不是生产级高可用 mesh，README 和面试材料里都刻意强调它是 SDK-based RPC governance prototype，不该夸大成完整 HA 服务网格。但它也有明显的高可用设计倾向：Controller 不在业务 RPC 数据路径上，resolver 会保留最近一次成功拉取的实例列表，已有 gRPC 连接不会因为控制面一抖就立刻失效。这属于“控制面短时异常不直接打断数据面”的思路。

如果面试官继续深挖，可以按这条路线走：
1. 先问 active-active 和 active-passive 的差别，各自适合什么场景。
2. 再问 DNS、Anycast、VRRP、浮动 VIP 分别解决哪一层切换问题。
3. 再问为什么数据面和控制面最好分离，控制面抖动时怎样保护业务流量。
4. 再问多副本负载均衡里哪些状态必须同步，哪些最好不要共享。
5. 最后落回项目：AegisMesh 现在有哪些“高可用倾向”，又有哪些地方还不能说成生产级 HA。

## 10. 负载均衡器如何避免成为单点瓶颈？

可以先这样答：

避免成为单点瓶颈，核心不是一句“多部署几台”就结束了，而是要同时解决容量、路径和职责三个问题。很多系统不是因为只有一台负载均衡器才出问题，而是因为所有请求都被迫经过同一层、同一种解析、同一种状态表，最后把瓶颈堆在一个位置上。

先说容量层面。L4 和 L7 负载均衡的瓶颈点不一样。L4 更容易卡在连接表、NIC、中断、内核队列、SYN flood 防护、端口耗尽；L7 更容易卡在 TLS 握手、HTTP 解析、头部处理、WAF 规则、压缩、日志、内存分配和长连接管理。所以避免瓶颈的第一步就是把性能热点拆清楚，而不是把“负载均衡器”当成一个抽象黑盒。云负载均衡和成熟代理之所以能扛住量，不只是因为节点多，也因为数据路径尽量简单，很多高级能力是可选叠加的，而不是默认把所有逻辑都塞进每个请求。

再说路径层面。企业入口通常会分层承压：DNS 或 Global Accelerator 先做区域级入口选择，区域内再由 SLB/ALB/NLB 扛连接接入，进入集群后由 Ingress、API Gateway、Service Mesh 或客户端 LB 继续分流。这样每一层只解决自己那一段问题，不会让所有细粒度调度都挤在最外层。客户端负载均衡尤其能明显降低中心瓶颈，因为选实例的动作被分散到每个调用方进程里了。

然后是职责层面。不要让一个负载均衡器同时承担“接公网流量、做认证、做 WAF、做缓存、做 API 编排、做服务间重试、做链路观测、做细粒度实例避让”所有事情。职责越重，路径越长，越容易把 CPU 和内存打成热点，也越难扩容。很多生产事故本质上不是转发本身不够快，而是把太多控制逻辑塞到了请求主路径里。

还有一个容易被忽略的点是连接模型。长连接和 HTTP/2 多路复用会让“连接数看起来不高，但单连接承载的请求很多”，这时如果上游负载均衡按连接平均，下面某个节点仍可能被打热点。反过来，如果每次请求都能在已建立连接池中重新挑选，就更容易把负载铺开。因此“避免入口单点瓶颈”和“避免后端热点”经常是同一件事的两面。

放到 AegisMesh 上，最值得说的一点是：它从架构上就绕开了“中心化数据面瓶颈”。Controller 负责注册、策略和健康状态，不转发真实业务 RPC；真实选路发生在 SDK 本地。也就是说，AegisMesh 的中心组件更像控制面，不是所有业务流量必经的网关。这种设计天然比“所有请求都先过一个中央代理”更不容易形成统一瓶颈。当然，代价是每个客户端都要承担一部分治理逻辑和观测开销。

如果面试官继续深挖，可以按这条路线走：
1. 先问瓶颈到底是 CPU、连接表、TLS、WAF 规则，还是日志和内存分配。
2. 再问为什么要做分层分流，而不是把所有调度都堆在同一个入口。
3. 再问客户端负载均衡为什么能天然缓解中心化数据面瓶颈。
4. 再问职责过重为什么会让负载均衡器变成复杂代理平台，而不是单纯转发层。
5. 最后落回项目：AegisMesh 为什么说 Controller 不是业务流量瓶颈点。

## 11. 负载均衡中的健康检查有哪些类型？主动检查和被动检查有什么区别？

可以先这样答：

健康检查可以按“检查什么”和“怎么拿到证据”两条线来分。按检查对象分，常见有 L3/L4 连通性检查，比如 TCP connect；L7 协议检查，比如 HTTP `/healthz`、HTTPS、gRPC health checking；再往上还有业务级探针，比如真正调用一个轻量查询方法、验证依赖是否可达、检查线程池和队列是否积压。不同层级能证明的东西完全不同，不能混着看。

主动检查是系统自己定时发探针。AWS ALB 的 target group health check 就是典型主动检查：负载均衡节点按间隔、超时、成功码范围和连续成功/失败阈值去判断 target 是否健康。它的优点是即使没有真实业务流量，也能持续拿到健康信号，配置也比较明确，适合做基础存活判断、预热后的接入确认、优雅下线前的摘流。缺点也很明显：它只能证明“这个探针能不能过”，不一定能证明真实流量一定没问题。

被动检查则是观察真实业务流量的结果，不额外发探针。AWS NLB 文档明确说它同时使用 active 和 passive health checks，passive 可以比 active 更早发现不健康；Envoy 也把 active health check 和 passive outlier detection 分开写。被动检查的优点是更接近真实体验，尤其对 fail-slow、局部网络异常、线程池满、数据库偶发抖动这类问题更敏感。缺点是没有流量时它就没有样本，而且它容易把“调用方局部路径异常”误当成“服务端全局异常”，所以需要和调用方维度、最小样本量、连续窗口、熔断状态一起看。

工程上，成熟系统通常不会二选一，而是组合使用。主动检查负责存活、接入、摘除和基础路由安全线；被动检查负责真实请求质量、尾延迟、错误率和异常实例识别。只做主动检查，容易漏掉 fail-slow；只做被动检查，又会在低流量或冷启动阶段看不清状态。两者结合才比较稳。

在 AegisMesh 的语境里，它更偏向“用真实业务 RPC 观测做被动健康判断”。README 里一开始就强调，实例可能还通过健康检查，但 p99 已经在伤害调用方。项目里真正驱动 `slow_score` 和状态机的是 endpoint 级 telemetry，包括延迟、错误、timeout、`inflight` 和网络信号，而不是只看一个 `/healthz`。这正是它和传统存活型健康检查的差别。

如果面试官继续深挖，可以按这条路线走：
1. 先问不同层级的健康检查分别能证明什么，不能证明什么。
2. 再问主动检查为什么适合基础存活判断，但不一定代表真实业务健康。
3. 再问被动检查为什么更贴近真实流量，却依赖样本且容易受局部路径影响。
4. 再问为什么成熟系统常常把 active health check 和 passive outlier detection 组合起来。
5. 最后落回项目：AegisMesh 为什么更强调真实 RPC telemetry，而不是只信 `/healthz`。

## 12. 为什么健康检查通过不代表实例一定适合承载真实流量？

可以先这样答：

因为健康检查通常只验证一个缩小过的问题，而真实流量面对的是完整业务路径。健康检查通过，最多说明“这个探针在这个时刻成功了”；它并不能自动推出“真实请求在真实并发、真实依赖、真实数据规模下也能稳定达标”。

最常见的原因是探针路径太轻。很多健康接口只是返回 200、做一次内存判断，或者最多查一个本地状态位。它不经过真正的数据库热点、锁竞争、下游 RPC、缓存 miss、复杂对象构造，也不承受业务高并发。所以你会看到一个实例 `/healthz` 依然秒回，但真正的下单、推荐、搜索、用户查询已经明显变慢。

第二个原因是健康检查和真实业务的资源池并不完全重合。连接还活着、gRPC keepalive 正常、HTTP/2 会话不断，说明 transport layer 还在；但业务线程池可能已满，数据库连接池可能耗尽，CPU 可能被 throttle，磁盘 IO 或网络重传可能在抖。AegisMesh 的面试材料里专门强调过这一点：连接健康是 transport health，不等于业务健康。

第三个原因是健康检查通常没有真实流量的负载特征。它往往低并发、短报文、固定路径、固定参数，而且采样间隔比较稀。真实流量则可能是突发流量、热点 key、长尾请求、跨 AZ 路径抖动、HTTP/2 多流竞争。这些问题很多只有在真实请求进来后才暴露。

第四个原因是健康检查存在“语义错位”。Envoy 文档就明确提到，一个 host 也许能正常回答 health check URL，但它回答的并不是预期服务类型，或者返回的是退化态。也就是说，“探针成功”不代表“业务语义正确”。这在灰度、错误路由、错配配置、启动阶段误注册时都可能发生。

这也是 AegisMesh README 一开头就强调的问题：实例可以继续通过 health checks，但它的 p99 已经在伤害调用方。项目选择的不是把 health check 做得越来越复杂，而是直接看真实 RPC 的 latency、timeout、error 和 `inflight`，再通过 `slow_score` 和状态机去判断它是不是还适合承载普通流量。这里的关键词不是“活着没”，而是“还能不能稳定承担真实业务请求”。

如果面试官继续深挖，可以按这条路线走：
1. 先问健康检查验证的是轻量探针，还是完整业务链路。
2. 再问 transport health 和 business health 为什么不是一回事。
3. 再问为什么低并发探针很难提前暴露高并发下的队列、锁、依赖和长尾问题。
4. 再问为什么“探针成功”不一定代表服务语义正确或容量充足。
5. 最后落回项目：AegisMesh 为什么把真实 RPC telemetry 放在健康判断核心位置。

## 13. 负载均衡算法如何影响 p99 延迟？

可以先这样答：

p99 延迟本质上是在问：系统怎么处理那批最慢的请求。负载均衡算法如果只关心“平均分配”，往往会把慢节点上的尾延迟继续扩散到整条链路；如果它能更早识别拥塞、排队和异常节点，就有机会在请求进入长尾前把流量挪开。所以算法对 p99 的影响通常比对平均延迟更明显。

最经典的例子是 `round_robin`。它的优点是简单、均匀、可预测，但前提是后端实例质量差不多。一旦某个实例慢下来，轮询仍会按份额持续把请求送过去，于是那个实例上的排队会越来越长，慢请求会不断贡献到系统尾部。对于 fail-stop 它还能配合健康检查工作；但对于 fail-slow，它往往反应太迟。

动态算法更适合处理 p99。像 `least requests`、`least outstanding requests`、P2C、EWMA latency、weighted round robin with observed load，本质上都在利用实时信号减少请求进入拥塞节点的概率。Google 的《The Tail at Scale》讲得很清楚，大规模分布式系统里真正支配体验的是尾延迟，而不是均值。只要算法能更快绕开局部慢点，尾部就会显著改善。

但这也不是说“越动态越好”。动态算法如果太敏感，会引入新的 p99 问题。比如窗口太短、EWMA 太抖、所有客户端同时切流，就可能出现路由振荡、探测流量打爆恢复节点、热点在节点之间来回迁移。此时均值可能还行，p99 反而更差。所以好的动态负载均衡不是只会“快切”，还要会“慢收”，要有滞后、最小样本量、慢启动、probe ratio 和上限保护。

这点在 AegisMesh 的实验里非常直观。项目材料里给出的慢实例场景结果是：adaptive P2C 相比 `round_robin` 把 median p99 从 `348.682 ms` 降到 `32.712 ms`。原因不是它让每个请求都更快，而是它把大量本来会落到慢节点的请求提前绕开了。当然，项目也承认了 no-fault 场景下治理层会有一定 overhead，这也是面试里应该主动承认的 tradeoff。

如果面试官继续深挖，可以按这条路线走：
1. 先问均衡分配为什么不等于尾延迟最优，尤其在实例质量不一致时。
2. 再问 `round_robin`、`least requests`、P2C、EWMA 分别靠什么信号影响 p99。
3. 再问为什么动态算法能降 p99，但也可能因为抖动和 herd behavior 反过来伤害 p99。
4. 再问长连接、多路复用、请求级与连接级决策为什么会放大或削弱算法效果。
5. 最后落回项目：AegisMesh 的 adaptive P2C 为什么能在慢实例实验里明显拉低 p99。

## 14. 负载均衡如何处理慢节点、半死节点和抖动节点？

可以先这样答：

这三类节点最怕用同一种动作粗暴处理。慢节点不是彻底坏了，半死节点通常是间歇性失败或局部失败，抖动节点则可能只是短时波动。如果不区分，系统要么反应过慢，要么误摘除太多节点，最后把自己打成不稳定状态。

处理慢节点，核心是“渐进降权”，不要一上来就当宕机。因为它还可能返回成功，只是延迟明显变差。典型做法是根据请求延迟、错误率、超时、`inflight`、后端自报负载或 outlier score 提高路由 cost，先减少普通流量，再视持续时间和严重程度进入隔离。这样可以优先保护 p99，同时保留少量恢复机会。

处理半死节点，重点在于“尽快识别，但不要只靠主动探针”。这类节点常见表现是偶发超时、RST、短时成功短时失败、局部网络丢包、线程池偶尔打满。主动健康检查可能一会儿过、一会儿不过；单次失败也不适合直接拉闸。所以成熟实现会把 active health check 和 passive outlier detection 结合起来，再用连续失败窗口、熔断、连接排空、ejection time 控制节奏。

处理抖动节点，关键是去抖。不能一看到一个窗口慢就摘，一恢复一个窗口快就立刻全量放回。常见手段包括：EWMA 平滑、最小样本量、连续窗口阈值、hysteresis、slow start、probe ratio、权重变化限速、全局摘除上限。你可以把它理解成：系统既要敏感，也要克制。

这正好就是 AegisMesh 现在的状态机思路。项目里不是只有“健康”和“不健康”两个状态，而是 `HEALTHY -> DEGRADED -> EJECTED -> PROBING` 这样一条恢复路径。慢窗口先推动 `slow_score` 上升，再经由连续窗口进入 `DEGRADED` 或 `EJECTED`；恢复时不会直接回主流量池，而是先进入 `PROBING`，只吃很小比例探测流量。README 里给出的默认 probe share 是 `2%`。这套设计就是为了同时处理慢、半死和抖动三类问题。

如果进一步追问生产化，还可以补一层：全局健康和调用方局部健康最好分开。因为有时候不是实例自己坏了，而是某个 caller 到它的那条网络路径有问题。如果所有调用方的观测都混成一个结论，就可能误伤健康路径。AegisMesh 当前更偏“全局 endpoint health + 本地 EWMA”的混合，继续做下去很自然会走向 caller-aware scoring。

如果面试官继续深挖，可以按这条路线走：
1. 先问慢节点、半死节点、抖动节点三者的症状为什么不同。
2. 再问为什么慢节点更适合渐进降权，半死节点更依赖 active + passive 组合识别。
3. 再问抖动节点为什么必须靠 hysteresis、EWMA、最小样本量和 probe ratio 去抖。
4. 再问为什么恢复阶段不能直接从隔离态回到全量主路径。
5. 最后落回项目：AegisMesh 的 `DEGRADED/EJECTED/PROBING` 分别在解决什么问题。

## 15. 长连接场景下，负载均衡和短连接场景下有什么不同？

可以先这样答：

最大的区别是：短连接里，建立连接这件事本身就是一次很强的负载均衡时机；长连接里，早期选错一次，后面很多请求都会被这个决定绑定住。所以长连接场景下，连接级决策比短连接更重要，请求级重新分配也更难做。

短连接的特点是连接生命周期短，请求完成后很快释放。这样即使算法比较粗，负载也会不断重新洗牌，坏选择不会持续太久。代价是握手、TLS、连接建立和内核资源开销更高。传统 HTTP/1.x、一些简单 TCP 服务、或者对连接成本不太敏感的场景，更容易接受这种模型。

长连接则相反。gRPC 基于 HTTP/2，一个 `SubConn` 上可以复用同一条连接承载很多 RPC。好处是握手少、连接数少、吞吐高；问题是如果你使用 `pick_first` 之类偏连接级的策略，业务可能长期黏在少数连接和少数后端上，负载均衡效果会明显打折。`round_robin` 或 AegisMesh 的 adaptive P2C 之所以更合适，是因为它们在每次 RPC 发出前还会重新 pick，而不是进程启动时选一次就长期复用。

长连接还会带来两个额外问题。第一，stream 或连接一旦建立，中途迁移成本高，很多时候根本不能迁移。比如一个长时间运行的 streaming RPC 选中了某个后端，负载均衡不会在中间把它搬到别的实例。第二，连接健康和业务健康会被混淆。keepalive 正常、TCP 没断、HTTP/2 会话还活着，不代表这个后端适合继续接新流量。AegisMesh 的材料专门拿这一点区分过 transport health 和 business health。

所以长连接场景里，负载均衡要额外关注连接池大小、每连接并发、连接预热、连接排空、优雅下线、stream 数量、HTTP/2 并发上限、局部拥塞和多路复用带来的竞争。短连接更像“每次请求重新开始”；长连接更像“先选一个住处，后面大量活动都围着它展开”。两者不能用同一套直觉去看。

如果面试官继续深挖，可以按这条路线走：
1. 先问为什么短连接容易重新洗牌，长连接却会把早期选路结果放大。
2. 再问 gRPC/HTTP2 的连接复用为什么会让 `pick_first` 这类策略负载不均。
3. 再问长 stream 为什么不能简单中途迁移，优雅下线和连接排空因此变得重要。
4. 再问 keepalive 正常为什么不代表可以继续承载新业务流量。
5. 最后落回项目：AegisMesh 为什么需要在持久连接之上继续做 RPC 级 pick，而不是只做连接级选路。

## 16. HTTP/2 多路复用会给传统负载均衡带来什么问题？

可以先这样答：

HTTP/2 多路复用最大的变化是：连接数不再接近请求负载本身。一条连接上可以并发很多 stream，RFC 9113 也明确把 HTTP/2 定义成“在同一连接上允许多个并发交换”。这会直接冲击很多传统负载均衡的直觉，尤其是那些把“连接数”当成负载近似指标的做法。

第一类问题是负载观测失真。传统连接级负载均衡会觉得“每个客户端连过来的连接数差不多，所以分得挺均匀”。但在 HTTP/2 下，一条连接可能承载成百上千个请求，连接数均匀不代表请求数均匀，更不代表 CPU、内存和队列压力均匀。于是 `least connections` 在多路复用场景下可能变得很误导。

第二类问题是负载重平衡变难。连接一旦建立，很多传统 L4 负载均衡就把整个连接生命周期绑定在一个后端上。HTTP/2 里后续 stream 虽然是“新的请求”，但它们跑在已有连接里，连接级 LB 看不见这些内部 stream，也没法把它们再拆到其他后端。结果就是：表面上用了负载均衡，实际上大量请求可能被同一条长连接长期黏住。

第三类问题是竞争被放大。RFC 9113 在 flow control 部分明确提到，streams 的 multiplexing 会在同一 TCP 连接上引入 contention；它用流控来避免各 stream 互相破坏。但这仍然说明，多路复用不是“彼此完全独立”。同一连接上的窗口、优先级、发送节奏、接收端处理能力，都会让不同 stream 相互影响。

第四类问题是 TCP 层面的队头阻塞仍然存在。HTTP/2 解决了 HTTP/1.1 应用层串行排队的问题，但它通常还是跑在单条 TCP 连接上。只要某个包丢了，后面的字节就不能按序交付给上层，于是同一连接上的多个 stream 都会一起感受到延迟抖动。AegisMesh 在 gRPC 相关面试题里专门把这一点拎出来过，这也是项目里 eBPF TCP retransmit telemetry 有意义的原因。

所以 HTTP/2 多路复用并不是让负载均衡更简单，而是逼着你把决策粒度往请求级、流级、语义级推进。你需要看的不再只是连接数，而是并发 stream、每连接请求量、流控窗口、真实 RPC 延迟、每次 pick 的分布，以及连接是否长期黏在少数后端。对于 gRPC 这类长连接 RPC 系统，这是非常现实的问题。

如果面试官继续深挖，可以按这条路线走：
1. 先问为什么 HTTP/2 下连接数不再是请求负载的可靠代理。
2. 再问连接级 LB 为什么看不见连接内部的 stream，因此很难重平衡。
3. 再问 flow control 和同连接竞争为什么说明多路复用不是“完全互不影响”。
4. 再问 HTTP/2 解决了应用层 HOL，却为什么还会保留 TCP 层 HOL。
5. 最后落回项目：AegisMesh 在 gRPC/HTTP2 场景里为什么更强调 RPC 级观测和选择。

## 17. 连接级负载均衡和请求级负载均衡的区别是什么？

可以先这样答：

两者最核心的区别在于：它们在什么时候做决策，以及一个决策会影响多长时间。连接级负载均衡是在连接建立时选一次后端，之后这个连接上的流量通常都跟着这个选择走；请求级负载均衡则是在每次请求到来时都可以重新决定目标。前者更轻、更适合高吞吐接入，后者更灵活、更适合处理实例状态波动和细粒度策略。

连接级负载均衡典型出现在 L4 场景。AWS NLB 文档就明确写了，TCP 流量会通过 flow hash 选择 target，而且该 TCP connection 生命周期内都保持在同一个 target 上。它的优点是实现简单、转发开销低、连接稳定、适合长连接和高吞吐网络接入，也更容易保留客户端 IP 和传输层语义。缺点是对实例实时状态不够敏感，一旦选到了慢节点，后续这个连接里的很多请求都会一起受影响。

请求级负载均衡更接近 L7 或客户端 LB。AWS ALB 是按请求评估 listener rules 并把请求路由到 target；gRPC 的 `round_robin`、AegisMesh 的 adaptive P2C 则是在每次 RPC 发起前选 `SubConn`。它的优点是能利用 host、path、method、header、gRPC method、实时延迟、`inflight`、错误率、灰度规则、重试预算等信息，做更精细的分配，也更容易优化 p99。缺点是协议解析更重、状态更多、实现更复杂。

但要注意，请求级不等于“可以随时迁移任何东西”。一个普通 unary RPC 可以按请求重新选择，长时间运行的 stream 一旦开始，通常还是绑定在既有连接和既有后端上。所以连接级和请求级不是绝对对立，而是经常叠加。现实系统里经常是：先在连接级建立到若干后端的连接池，再在请求级从这些连接里挑一个最合适的发送目标。

放回 AegisMesh，理解这个区别会很顺。AegisMesh 并没有放弃长连接，它仍然复用 gRPC/HTTP2 的持久连接；但它也没有停留在“连接建好就算负载均衡完成”。真正有价值的地方在于：每次 RPC 发送前还能根据本地和控制面的最新信号重新 pick。也正因为如此，它更接近请求级负载均衡，而不是单纯的连接级分发。

如果面试官继续深挖，可以按这条路线走：
1. 先问决策时机：连接建立时选一次，和每次请求都能再选一次，差别在哪里。
2. 再问为什么连接级更轻、更稳，却更难处理慢节点和尾延迟问题。
3. 再问为什么请求级更适合灰度、重试、方法级策略和实时动态避让。
4. 再问长 stream 为什么会让“请求级”也带有连接绑定色彩。
5. 最后落回项目：AegisMesh 为什么本质上是“持久连接之上的请求级负载均衡”。

## 18. 会话保持的实现方式有哪些？它会带来哪些副作用？

可以先这样答：

会话保持，也常叫 session affinity 或 sticky session，意思是把同一个用户或同一类请求，持续路由到同一个后端。常见实现方式有四类。第一类是 cookie 型。AWS ALB 支持 duration-based 和 application-based stickiness，NGINX Plus 也支持 sticky cookie。它们的共同点是第一次请求先正常选一个后端，再把“以后还回这个后端”的信息放进 cookie。第二类是源地址哈希，比如 NGINX 的 `ip_hash`。它不依赖 cookie，而是直接拿客户端 IP 做哈希，默认把同一来源地址打到同一台机器。第三类是通用哈希或一致性哈希，比如按 `user_id`、`request_uri`、租户、JWT claim 或缓存 key 做 hash。第四类是服务端维护映射表，或者靠长连接天然形成粘性，比如 WebSocket 一旦升级成功，后续消息就都走这条连接。

这些方式看起来都能实现“同一个人回同一个实例”，但适用边界差很多。cookie 型最适合 HTTP/HTTPS 用户会话，因为客户端天然会带 cookie。IP hash 实现简单，但在 NAT、移动网络、企业出口代理后面很容易失真，很多不同用户可能共享一个出口 IP。通用 hash 更适合做缓存局部性、分片亲和或租户隔离，因为 key 可以自己定义，稳定性也比 IP 好。服务端映射表最灵活，但状态最重，要考虑内存、同步和过期。

副作用也很典型。第一，负载会变歪。AWS 文档说得很直接，开启 sticky sessions 后，所选算法只参与第一次目标选择，后续同一客户端请求会绕过算法，直接回到原目标。这样短期看会话连续性好了，长期看很容易把热点用户、重会话用户、慢会话用户黏在少数实例上。第二，扩容和缩容变麻烦。新实例刚加进来时，老会话不会自动迁过去；缩容或下线时，旧会话也不一定愿意立刻离开。第三，故障切换会更复杂。目标实例如果进入 draining、重启、缓存失效，用户会感知到一次“粘性被打断”的跳转。

还有一些更隐蔽的问题。cookie 粘性要求客户端支持 cookie；ALB 还要求开启 cross-zone load balancing，某些 stickiness 类型和 weighted target groups 也不兼容。IP hash 则会把网络拓扑里的偶然性带进业务，比如同一公司办公网里的几千人可能一起被打到一组机器上。长连接粘性的问题是，一旦早期选错目标，后面很长时间都在放大这个错误。

所以工程上通常把会话保持当作一种受约束的能力，而不是默认策略。只有当后端确实保留本地会话状态、缓存命中收益明显、分片亲和价值很高，或者协议本身就是连接型时，才值得打开。能把会话状态外置到 Redis、数据库、共享缓存或对象存储里时，很多系统宁可牺牲一点局部性，也不愿过度依赖粘性路由。

放到 AegisMesh 上，这个问题也能讲出项目边界。AegisMesh 当前主线是 fail-slow 下的 endpoint 级自适应路由，不是浏览器会话保持系统。它更关心“每次 RPC 该不该继续打这个 endpoint”，而不是“同一个用户永远回同一台实例”。如果以后要支持缓存亲和或租户亲和，可以在 resolver/balancer 里引入 hash key，但那会和 slow_score、熔断、灰度策略形成冲突，需要先定义优先级。

如果面试官继续深挖，可以按这条路线走：
1. 先问 cookie、IP hash、一致性 hash、服务端映射表各自适合什么协议和业务。
2. 再问为什么 sticky session 会让负载均衡算法只在首次选择时生效。
3. 再问 NAT、移动网络、共享出口为什么会让 IP hash 失真。
4. 再问为什么会话保持会让扩缩容、故障切换和灰度发布变复杂。
5. 最后落回项目：AegisMesh 如果要支持亲和路由，应该如何和 slow_score、熔断、灰度一起定义优先级。

## 19. 为什么最少连接算法不一定等价于最低负载？

可以先这样答：

最少连接或最少未完成请求，本质上都只是“拿一个容易观测的计数，近似代表当前负载”。这个近似有时有用，但它绝对不等于真实负载。因为真实负载取决于请求成本、连接模型、实例能力、排队情况和资源瓶颈，连接数只是其中一个很粗的影子。

先看请求成本差异。同样是一个活跃连接，背后可能是一个轻量读请求，也可能是一个做复杂 JSON 编解码、数据库 join、远程 RPC 级联、甚至大对象传输的重请求。两个实例各有 100 个活跃连接，不代表 CPU、线程池、内存和下游压力一样。AWS 也明确把 least outstanding requests 说成更适合“请求复杂度不同”或“目标处理能力不同”的场景，这已经是在承认：简单平均并不够，至少要往“未完成请求数”前进一步。但这依然只是前进了一小步。

再看连接模型。如果你用的是 HTTP keep-alive、HTTP/2、gRPC 或 WebSocket，连接数和真实工作量的对应关系会更差。一个 HTTP/2 连接上可能并发很多 stream；一个 WebSocket 连接在选中目标后，后续所有消息都沿着同一连接走。于是“连接少”可能只是因为连接复用做得好，不代表实例空闲；“连接多”也可能只是因为 keepalive 时间长，不代表实例更忙。

第三个问题是连接状态不同。有些连接几乎空闲，只是挂着；有些连接后面有长队列；有些连接在阻塞下游；有些连接已经把线程池打满。最少连接算法看不到这些差别。它也看不到 CPU throttle、GC 抖动、锁竞争、磁盘慢、网络重传这些让实例实际吞吐下降的因素。

第四个问题是实例能力不一样。最少连接只看当前有多少连接，不看这台机器到底能吃多少连接。8 核机器和 2 核机器都各有 50 个活跃连接，后者可能已经在喘了，前者还很轻松。于是“最少连接”不等于“最低负载”，很多时候甚至不等于“最低风险”。

这也是为什么更成熟的策略会把连接数和别的信号叠起来看。Envoy 的 client-side weighted round robin 已经能吃 ORCA 上报的 QPS、EPS 和 utilization。AegisMesh 走得也不是“只看连接数”这条路，它本地看 `inflight` 和 `EWMA`，控制面再叠加 `slow_score` 和 endpoint 状态。逻辑很简单：连接数可以看，但绝对不能只看它。

如果面试官继续深挖，可以按这条路线走：
1. 先问“连接”到底在近似什么，为什么它只是负载代理指标。
2. 再问请求成本不等、长连接、多路复用为什么会让连接数失真。
3. 再问实例异构和资源瓶颈为什么会让相同连接数对应完全不同的真实压力。
4. 再问生产里为什么会把连接数、延迟、QPS、错误率、utilization 一起看。
5. 最后落回项目：AegisMesh 为什么选择 `inflight + EWMA + slow_score`，而不是 `least_conn`。

## 20. 为什么轮询算法在异构实例场景下可能不公平？

可以先这样答：

轮询的公平，实际上是“请求次数公平”，不是“资源消耗公平”，更不是“用户体验公平”。只要后端实例能力不一致，这三种公平就会分开。一个算法把请求数分得很平均，依然可能把弱实例打爆，让整组服务的 p99 变差。

AWS 在 ALB 文档里对 round robin 的适用场景说得很明确：它更适合请求复杂度相近、目标处理能力相近，或者你就是想把请求数量均匀铺开的情况。反过来说，如果请求复杂度不相近，或者目标处理能力不相近，轮询就很容易出问题。

最典型的异构场景有几种。第一，机器规格不同，比如 8 核和 2 核混跑。第二，软件状态不同，比如有的实例缓存刚热起来，有的刚重启。第三，依赖位置不同，比如有的实例离数据库近，有的跨 AZ。第四，运行时状态不同，比如某台机器正在 GC、某个实例线程池已满、某个节点磁盘被别的任务拖慢。轮询对这些差异一律视而不见。

这时所谓“不公平”，不是说算法在数学上错了，而是它优化错了目标。它只保证每台机器收到差不多数量的请求，但系统真正关心的是：每台机器收到的工作量是否和它的能力匹配，用户看到的延迟是否稳定。异构环境里，能力强的实例应该多扛一点，能力弱的实例应该少扛一点，恢复中的实例还应该慢慢升权，这才更接近工程上的公平。

所以成熟系统一般会给轮询加权，或者直接换成动态策略。NGINX 的权重就是最经典的静态修正。Envoy 更进一步，能通过 ORCA 做客户端动态加权。AegisMesh 则是 `base_weight` 作为静态意图，`slow_score` 再把 `effective_weight` 动态拉下来。这个组合比纯轮询更像真实系统会做的事。

如果面试官继续深挖，可以按这条路线走：
1. 先问轮询保证的到底是哪一种公平：请求数、资源占用，还是用户体验。
2. 再问异构实例里，机器规格、缓存冷热、依赖距离和运行时状态为什么会影响“公平”。
3. 再问为什么能力匹配比请求数平均更重要。
4. 再问静态加权和动态加权分别怎样修正轮询的不公平。
5. 最后落回项目：AegisMesh 的 `base_weight` 和 `effective_weight` 分别在修正什么问题。

## 21. 为什么负载均衡需要考虑实例容量？容量可以由哪些指标估算？

可以先这样答：

如果不考虑实例容量，负载均衡默认假设所有实例都一样能扛。这个假设在 demo 里经常成立，在生产里经常不成立。容量一旦估错，最直接的结果就是强实例没吃满，弱实例先崩，系统平均吞吐没上去，p99 还先坏了。

容量可以先按静态维度做一个粗估。比如机器规格、容器限额、vCPU、内存、带宽、磁盘、线程池大小、数据库连接池大小、文件描述符上限、GPU 显存、每实例可开的长连接数。这些指标适合决定“这台实例天花板大概在哪”。如果服务本身就是分层异构，比如大机型、小机型、冷热分层、GPU 型号不同，这些静态指标往往应该先体现在基础权重里。

但真正影响路由的，通常是运行时的有效容量。这个要看更贴近请求处理的信号。常见包括：当前 `inflight`、排队长度、QPS、错误率、timeout、CPU 使用和 CPU steal/throttle、内存压力、GC pause、线程池 active count、连接池占用、下游依赖延迟、网络重传、磁盘 IO 等。Envoy 现在已经支持通过 ORCA 用 QPS、EPS 和 utilization 做客户端动态加权，这就是把“容量”理解成一个实时变化的量，而不是静态常数。

还可以再往前走一步，用服务本身的业务模型估算容量。比如搜索服务可以按每秒可处理 query 数和平均 token cost 估算，数据库代理可以按并发连接和 p95 事务时间估算，LLM 推理服务可以按 KV cache、batch size、token/s 和显存使用估算。越是专业系统，容量越不可能只靠一个 CPU 百分比解释清楚。

放到 AegisMesh，容量意识其实已经在设计里露出来了。SDK 侧有 per-endpoint breaker，默认 `MaxInflightPerEndpoint=128`，本地 Pick 也会把 `inflight` 放进 cost 里。面试材料里还专门提到一个生产化方向：这个上限不该永远写死成同一个数字，而应该按 endpoint capacity 配置，甚至进一步做 adaptive concurrency。也就是说，项目虽然没有把“容量模型”做满，但方向已经很明确了。

如果面试官继续深挖，可以按这条路线走：
1. 先问为什么“所有实例容量相同”在生产里往往不成立。
2. 再问静态容量和运行时有效容量分别适合解决什么问题。
3. 再问为什么 CPU、内存之外，还要看并发、排队、下游依赖和业务特有指标。
4. 再问 ORCA、breaker、adaptive concurrency 这类机制分别是在补哪一层容量信号。
5. 最后落回项目：AegisMesh 现在怎样用 `MaxInflightPerEndpoint` 和 `inflight cost` 间接表达容量约束。

## 22. 负载均衡中的权重应该静态配置还是动态调整？

可以先这样答：

如果非要二选一，我会说都要。静态权重解决的是“长期已知差异”和“人为业务意图”，动态权重解决的是“运行时变化”。把其中一个完全拿掉，系统都会变笨。

静态权重适合几类场景。比如实例规格长期不同，大机器本来就该多吃一点；某个地域更便宜，你故意想多放量；某个灰度版本只想吃 5%；某个机房是备用容量，只打算兜底。这些都不应该等系统自己慢慢学，而应该直接写进配置。NGINX 的 `weight`、Route 53 的 weighted policy、Istio 的 weighted routing，本质上都在表达这种显式意图。

动态权重则更适合处理时变问题。实例虽然规格一样，但某一刻可能因为 GC、缓存 miss、依赖慢、局部网络抖动、线程池打满，实际承载能力已经变了。这时如果还死守静态权重，流量会继续按旧世界分配。AWS ALB 的 Automatic Target Weights、Envoy 的 ORCA 驱动加权、AegisMesh 里 `effective_weight = base_weight / (1 + slow_score)`，都属于“保留基础意图，再让运行时信号来修正”的路线。

真正要避免的是两种极端。第一种是只有静态没有动态，系统对故障和抖动太迟钝。第二种是只有动态没有静态，系统会忘掉容量差异、灰度比例、业务约束，甚至在样本噪声下到处乱摆。动态权重如果没有平滑、上下限、最小样本量和慢启动，很容易出现振荡。

所以工程上比较稳的办法通常是分层：先给每个实例一个 `base_weight`，表达长期能力和业务意图；再乘上或除上一个动态因子，表达当前健康度和即时负载；最后再加安全边界，比如最小健康实例数、最大摘除比例、权重变化速率限制、冷启动 slow start 和紧急回滚。

这套说法放到 AegisMesh 很顺。AegisMesh 已经天然是“静态 + 动态”的组合。`base_weight` 代表基础容量或人工意图，`slow_score`、`inflight` 和 `EWMA` 负责运行时修正。如果以后做 locality、tenant、canary，也应该继续叠在这套模型上，而不是另起一条完全平行的权重系统。

如果面试官继续深挖，可以按这条路线走：
1. 先问静态权重通常承载哪些长期意图：容量、成本、灰度、容灾。
2. 再问动态权重通常响应哪些运行时变化：慢故障、抖动、局部过载。
3. 再问为什么只用静态或只用动态都会出问题。
4. 再问动态权重为什么必须配套 slow start、平滑、上下限和回滚。
5. 最后落回项目：AegisMesh 的 `base_weight` 和 `slow_score` 怎么组合成 `effective_weight`。

## 23. 什么是本地优先、同机房优先、同可用区优先和同地域优先？

可以先这样答：

这几个说法本质上都在讲 locality preference，也就是“先用离我近、故障域也更近的资源”。只是“近”有不同层级。你可以把它理解成一个从小到大的优先级链：本地优先，通常是同进程、同主机、同节点，至少也是最近的网络拓扑；同机房优先，通常指同 IDC、同房间或同交换域；同可用区优先，是云环境里同一个 AZ；同地域优先，则是同一个 Region，跨地域是最后兜底。

这样做首先是为了延迟。越近的链路，一般 RTT 越低，抖动越小。第二是为了成本。跨 AZ、跨 Region 流量通常更贵。第三是为了故障域隔离。正常情况下流量留在本地，某个机房或 AZ 出故障时再往外逃，爆炸半径更小。Istio 对 locality 的定义就是 Region、Zone、Sub-zone 这样一层层往下拆，Envoy 也是先选 priority，再选 locality，再在 locality 内选 endpoint。

但 locality 优先不能写成死规则。因为“近”不等于“健康”。同机房实例如果都在抖、同 AZ 数据库已经慢了、同 Region 某个共享依赖出问题，这时继续死守本地只会把局部故障放大。更稳的思路是把 locality 当作偏好项，而不是绝对约束。平时本地优先，出事时允许跨层 fallback。

这点在 AegisMesh 的扩展思路里已经讲得比较清楚。面试材料里给过一个很直接的 cost function：`locality_penalty + inflight_cost + latency_ewma_cost + slow_score_penalty`。意思就是 locality 影响选路，但它要和健康、容量、延迟一起算。这样正常流量留在近处，局部慢故障时又能及时跳出去。

如果面试官继续深挖，可以按这条路线走：
1. 先问本地、机房、可用区、地域分别对应怎样的网络和故障域层级。
2. 再问 locality 优先为什么同时影响延迟、成本和容灾。
3. 再问为什么 locality 只能是偏好，不能在任何情况下都当硬约束。
4. 再问 Envoy/Istio 的 locality、priority、outlier detection 是怎么配合的。
5. 最后落回项目：AegisMesh 如果加入 locality，为什么应该把它写进 cost function，而不是单独拍脑袋做强制规则。

## 24. 跨地域负载均衡通常如何考虑延迟、成本和容灾？

可以先这样答：

跨地域负载均衡一般不是只问“把流量发到哪个 Region”，而是同时在算三笔账：用户到入口的延迟，Region 之间的数据和流量成本，以及某个 Region 出问题时业务还能不能接住。所以它天然比单地域或单 AZ 的负载均衡更像一个全局调度问题。

在入口层，常见做法有两类。第一类是 DNS 路由，比如 Route 53 的 latency、weighted、failover、geolocation、geoproximity 路由策略。它适合做全局入口分流，简单、通用，但受 DNS 缓存和 TTL 影响。第二类是 Global Accelerator 这种全局流量入口。AWS 文档里讲得很清楚，它会基于健康、客户端位置和配置策略，把流量送到最优的区域端点；同时还能用 traffic dial 控制每个 Region 的新连接流量比例。这类入口对跨地域调度更灵活，反应也更快。

延迟目标通常会推着你做“就近接入”。用户在东亚，就近进东亚 Region；用户在欧洲，就近进欧洲 Region。但如果把所有流量都死绑到最近 Region，又会碰到两个问题。第一，本地 Region 容量可能不足。第二，最近 Region 不一定最健康。所以很多系统会把延迟作为默认偏好，把健康和容量作为强约束。

成本则主要来自跨 Region 复制和跨 Region 流量。active-active 看起来最漂亮，但通常复制成本高、一致性复杂、写路径难设计。active-standby 成本和一致性压力小一些，但平时备用 Region 的资源利用率会偏低。还有很多介于中间的方案，比如读流量多活、写流量单主，或者只在特定租户、特定国家、特定时间段启用跨地域兜底。

容灾上，关键不是“远端能不能收流量”，而是“远端收了以后能不能正确处理”。如果会话状态、缓存、数据库、副本延迟、认证依赖、对象存储和配置分发没有一起考虑，流量切过去也可能只是更快地失败。所以跨地域负载均衡一定要和数据复制策略、故障演练、灰度演练、RTO/RPO 指标一起设计。

放回 AegisMesh，这个项目当前还没走到跨地域控制面和多集群数据面，但面试材料里已经给了一个很合理的方向：Region 内部先由本地 Controller 做本地治理，全球层再下发跨地域 failover 规则和服务目录。本地自治，全球协调。这个方向比“所有流量和状态都穿过一个全球 Controller”现实得多。

如果面试官继续深挖，可以按这条路线走：
1. 先问 DNS 型跨地域路由和全局加速入口各自适合什么层级。
2. 再问为什么延迟通常决定默认路径，但健康和容量应该决定能不能真的走这条路径。
3. 再问 active-active 和 active-standby 在成本、一致性和恢复能力上的取舍。
4. 再问跨地域流量切换为什么必须和数据复制、会话状态和依赖拓扑一起设计。
5. 最后落回项目：AegisMesh 如果以后做多地域，为什么应该是“本地治理 + 全局策略”两层结构。

## 25. 如何衡量一个负载均衡策略是否有效？

可以先这样答：

判断负载均衡策略有没有效，不能只看“平均延迟是不是降了”或者“流量是不是分得更均匀”。真正该看的，是它有没有让系统在目标场景下更稳、更快、更可解释，而且没有把问题偷偷转移到别处。

第一组指标是用户侧结果。吞吐、成功率、错误率、timeout、p95、p99、重试次数，这些都要看。只看均值很危险，因为很多策略正是在均值差不多的时候，把尾延迟拉开了。第二组指标是后端受力情况。每个 endpoint 的 QPS、`inflight`、CPU、队列长度、线程池占用、错误分布、是否出现热点，这能回答“是不是只是把压力从 A 挪到了 B”。第三组指标是策略本身的稳定性。有没有路由振荡、恢复时间多长、PROBING 流量是否受控、误摘除比例高不高、回滚后多久收敛。

再往外一层，还要看成本和副作用。跨 AZ 或跨 Region 流量有没有暴涨，连接数和重建频率有没有上升，会不会因为 stickiness 或长连接让部分机器长期被热点用户绑住，灰度时分流比例有没有真的命中预期。这些问题很多时候不会在“平均延迟”里直接体现出来。

最稳的评估方法通常是先定义 baseline，再定义目标场景，再做对照。比如 no-fault、单慢节点、all-slow、冷启动、单 AZ 故障、灰度发布、长连接重用、HTTP/2 多路复用，这些场景下分别看指标。否则你很容易在一个场景里说策略好，在另一个场景里把坑埋掉。

放到 AegisMesh，这套评估思路几乎就是项目现成的实验框架。README 和 `docs/evaluation.md` 已经把 p99、slow_score、route weight、endpoint state、retry amplification、probe ratio 和 recovery curve 放进去了。它还专门有 verifier 去检查 canary 分流、retry attempt 和 forbidden edge。也就是说，AegisMesh 最像真实工程的地方之一，就是它没有把“效果”缩成一个单一指标。

如果面试官继续深挖，可以按这条路线走：
1. 先问为什么平均延迟和流量均匀度都不足以单独证明策略有效。
2. 再问用户侧指标、后端受力指标、策略稳定性指标分别回答什么问题。
3. 再问为什么一定要做 baseline 对照和多故障场景评估。
4. 再问怎样识别“表面更快，实际只是更快失败了”这种伪优化。
5. 最后落回项目：AegisMesh 为什么把 p99、retry amplification、recovery curve、probe ratio 和 verifier 放在一起看。

## 26. 负载均衡策略上线前应如何压测和灰度？

可以先这样答：

上线前通常要分成两段：先压测，确认它在目标场景里不会把系统带歪；再灰度，确认它在真实生产流量下也没有和纸面假设偏离。两段都不能省。

压测阶段，最怕的是只压“正常流量 + 平均场景”。真正该测的是这几个点：请求复杂度不均匀，实例异构，长连接和 HTTP/2 复用，WebSocket 或 streaming，单慢节点，all-slow，单 AZ 故障，节点冷启动，扩缩容，健康检查通过但真实业务变慢，策略参数配错，重试放大。也就是说，压测要逼策略暴露边界，而不是只帮它证明自己很稳。

灰度阶段，关键是让流量比例、配置修订和观测指标都可验证。Istio 的 traffic shifting 文档就是典型做法，先 50/50，再逐步推到 100/0。AegisMesh 这边虽然不是 Istio，但同样有 policy snapshot、watch 更新和 verifier。README 里 sample trace 的 9/1 canary 检查，就是在证明“配置说 90/10，实际流量分布也真的是 90/10”。这类验证比只看配置文件更有说服力。

实际落地时，我会加几条硬规矩。第一，先做 config validation 和 dry-run，避免明显错误配置直接进生产。第二，灰度推进必须绑门槛，比如 p99、错误率、重试放大、热点偏斜和跨 AZ 流量一旦超线就自动停。第三，灰度窗口里要保留快速回滚路径，不允许一边上线一边临时手改多处配置。第四，长连接场景要单独看，因为“配置已经切了”不代表旧连接马上消失。

放到 AegisMesh 里，这个问题还能多讲一句：项目的优势不只是在“能改策略”，还在“能解释策略有没有生效”。PolicyService、trace verifier、实验脚本和 Prometheus 指标一起用，才构成完整的压测和灰度闭环。

如果面试官继续深挖，可以按这条路线走：
1. 先问压测为什么不能只测 no-fault 和平均请求。
2. 再问灰度为什么必须验证“实际流量分布”，而不是只验证“配置已经发布”。
3. 再问长连接和 HTTP/2 为什么会让灰度收敛变慢。
4. 再问推进门槛应该盯哪些指标，谁来自动停灰度。
5. 最后落回项目：AegisMesh 的 verifier、policy snapshot 和实验脚本为什么适合做上线前验证。

## 27. 负载均衡策略出错时如何快速回滚？

可以先这样答：

想快速回滚，前提不是“出了事以后反应够快”，而是“上线前就把回滚路径设计好了”。如果策略发布没有版本号、没有上一个稳定版本、没有统一入口、没有 kill switch，事故来了以后再快也只是手忙脚乱。

最稳的做法通常有三层。第一层是配置版本化。每次策略发布都产生可追踪的 revision，保留 last-known-good，发布和回滚都走同一条控制面链路。AegisMesh 的 PolicyService 本身就很适合讲这个思路：客户端先 `GetPolicy`，再 `WatchPolicy`，如果新策略出问题，直接回滚到上一个 PolicySnapshot revision。第二层是紧急开关。比如关闭 outlier ejection、把动态权重退回静态、把 locality failover 关掉、把最激进的重试或流控关掉，让系统先回到保守但可用的状态。第三层是流量层面的立即止血，比如把新版本权重打回 0，把旧版本拉到 100。

还要注意一个很现实的问题：回滚配置不等于回滚流量。AWS Global Accelerator 的 traffic dial 文档明确说，traffic dial 变更只影响新连接，不会终止现有连接。sticky session、WebSocket、HTTP/2 长连接、连接池复用，都会让旧决策继续存活一段时间。所以生产里的“快速回滚”通常包含两件事：配置立即回去，已有连接逐步排空。必要时再配合 connection draining、实例摘除和更激进的断连策略。

如果策略错误是“把坏节点误判成好节点”，要回滚策略本身；如果策略错误是“把好节点误判成坏节点”，还要考虑清理状态。AegisMesh 的面试材料里就专门提过两类回滚：一类是回滚 policy revision；另一类是按 service 清空 health state，或者临时 fail-open，避免误摘除把实例全摘光。这个区分很重要，因为不是所有事故都只靠“把 YAML 改回去”就能解决。

再往前走一步，我会把回滚设计成一套预案：什么指标触发自动回滚，回滚是退 revision、退权重、关功能还是切流，是否需要冻结新发布，回滚后要观察多久，谁来确认恢复。这样事故里的动作是机械执行，不是临场讨论。

如果面试官继续深挖，可以按这条路线走：
1. 先问为什么 revision、last-known-good 和统一发布入口是快速回滚的前提。
2. 再问“回滚配置”和“回滚已有连接流量”为什么不是一回事。
3. 再问 sticky session、WebSocket、HTTP/2 长连接为什么会拖慢回滚生效。
4. 再问误配置和误判状态两类事故，回滚动作为什么不同。
5. 最后落回项目：AegisMesh 怎么用 PolicySnapshot revision、fail-open 开关和状态清理来做紧急止血。

## 28. 客户端负载均衡和服务端负载均衡相比，最大的工程复杂度在哪里？

可以先这样答：

如果只让我说一个最大的工程复杂度，我不会答“算法更复杂”，而会答“客户端负载均衡把数据面分散进了每一个调用方进程里，导致状态一致性、版本治理、排障和回滚都被放大了”。服务端负载均衡的复杂度更多集中在少数网关、代理或入口层；客户端负载均衡则把这件事复制到了所有 SDK、所有语言、所有服务、所有版本上。真正难的不是写一个 `round_robin` 或 P2C，而是把它长期稳定地跑在成百上千个调用方里。

先看能力面。gRPC 官方文档对自定义负载均衡讲得很直接：负载均衡策略要接 resolver 给出的地址列表，维护子连接，再在每次 RPC 前 pick 一个连接。也就是说，客户端一旦自己做负载均衡，就不只是“拿到一个 IP 去连一下”，而是要自己处理服务发现、连接生命周期、失败重连、连接池、每次 pick 的局部状态、请求完成后的反馈更新。这些东西如果放在服务端代理里，复杂度是集中式的；一旦放到客户端，它就变成分布式复杂度。

再看治理面。服务端负载均衡升级一次，往往是升级一层代理、一个 Ingress、一批 sidecar，链路上所有调用都会受益。客户端负载均衡不是。你要面临的是多语言 SDK、不同业务组的升级节奏、旧版本残留、配置兼容、灰度顺序、回滚窗口、还有“部分客户端已经切新策略，部分客户端还停在旧策略”的分裂状态。面试里如果讲到这里，面试官一般会认可你真的见过工程落地，而不是只停在概念层。

再往下看观测和排障。服务端负载均衡的决策点集中，日志、指标、trace 也集中，出了问题你大致知道去哪层看。客户端负载均衡的决策发生在调用方本地，每个进程都可能基于自己的本地 inflight、EWMA、连接复用状态做出不同选择。于是你会遇到一种很典型的问题：同一个时刻，A 调用方觉得某个实例很慢，B 调用方却还没感知到；A 已经降权了，B 还在继续打。这个现象不一定是谁错，而是分布式本地视角天然如此。可一旦没有足够好的 trace、per-attempt 指标和版本维度标签，排障会非常痛苦。

客户端负载均衡还有一个容易被低估的成本，是它把“控制面失联时怎么办”变成了 SDK 必须回答的问题。服务端负载均衡大多由平台代理，调用方不需要直接处理控制面中断。客户端负载均衡则必须考虑：服务发现拉不到了怎么办，策略 watch 断了怎么办，最后一份快照还能不能继续用，本地熔断和本地 EWMA 是否足够支撑一段时间的退化运行。这其实是在每个调用方里都实现一套“局部自治”能力。

放回 AegisMesh，这个特征特别明显。项目里的 `sdk/go/aegisgrpc` 不是只写了一个 balancer，而是连 resolver、picker、本地 EWMA、inflight、retry budget、telemetry interception 都一起承担了。`README.md` 和 `docs/project_report.md` 里也写得很清楚：控制面负责给出实例、策略和慢故障状态，真正每次 RPC 前做 pick 的是客户端本地 SDK。`interview/02-rpc-grpc-protocol.md` 还专门解释了 Aegis resolver 会把 `instance_id`、`status`、`slow_score` 写进地址属性里，再交给 adaptive P2C 去决策。这就是客户端负载均衡真正的工程重量所在。

所以更完整的结论是：客户端负载均衡最大的复杂度，不在“选哪个算法”，而在“如何把路由、状态、回退和观测能力安全地分发到所有调用方进程里，并让它们在控制面滞后、实例抖动、版本不齐和长连接复用条件下依然可控”。这也是为什么很多公司会在“客户端能看到更多语义”和“服务端更容易统一治理”之间反复权衡。

如果面试官继续深挖，可以按这条路线走：
1. 先问为什么客户端负载均衡能看到 `deadline`、`attempt`、本地 inflight 这类服务端代理看不到的信息。
2. 再问为什么把决策下沉到每个调用方后，升级、回滚和多语言一致性会变难。
3. 再问同一实例在不同调用方视角里为什么可能呈现出不同健康状态。
4. 再问控制面断连时，客户端负载均衡为什么必须依赖 last-known-good 和本地退化机制继续工作。
5. 最后落回项目：AegisMesh 为什么把 resolver、balancer、retry budget、telemetry 一起放进 SDK，而不是只做一个简单轮询器。

## 29. 负载均衡的控制面和数据面分别负责什么？

可以先这样答：

这道题最容易答空。真正好的回答不是“控制面管配置，数据面管转发”就停了，而是要讲清楚二者分别解决什么问题、彼此怎样解耦、以及为什么控制面最好不要在每个请求路径上。可以把它概括成一句话：控制面决定“应该怎么做”，数据面决定“这一跳现在怎么做”。

控制面的核心职责，是维护一个相对全局、相对慢变、可以被发布和回滚的系统视图。它通常负责服务注册发现、实例元数据、健康状态汇总、权重和 locality 策略、重试与超时策略、慢故障判定、灰度版本、审计记录、配置 revision、分发通道，以及必要时的多租户隔离。它不应该承载每个请求的逐跳决策，但它必须给数据面提供足够新的拓扑和策略边界。

数据面的核心职责，则是站在每次连接或每次请求的现场做动作。它要完成的事包括：从控制面拿到或缓存实例列表，维护连接池或子连接，按当前算法 pick 后端，执行 timeout、retry、circuit breaker、限流、会话保持、连接排空、请求转发，记录本地指标，并把必要的观测结果反馈回去。换句话说，数据面是“实时决策执行层”，它看见的是请求当下的局部真相。

为什么一定要强调解耦？因为控制面和数据面的时延预算根本不是一个数量级。控制面允许有秒级传播、版本化发布、灰度和审计；数据面必须在毫秒甚至微秒级完成 pick 和转发。如果把控制面塞进每个请求路径，整个系统会变成“每次请求都先去问一次大脑”，延迟、可用性和放大故障的风险都会上来。成熟系统一般都追求一个原则：控制面慢一点没关系，但数据面必须能在控制面暂时失联时继续靠最后一份好状态运行。

放到 AegisMesh 上，这个分层非常清晰。`docs/project_report.md` 已经把控制面和数据面拆得很明确：控制面是 `cmd/controller` 以及 `pkg/registry`、`pkg/policy`、`pkg/controller`、`pkg/fault` 这些部分，负责实例注册、TTL lease、YAML policy、`GetPolicy`/`WatchPolicy`、以及收集 endpoint telemetry 来计算慢故障状态。数据面则在 `sdk/go/aegisgrpc`，负责 resolver、adaptive P2C balancer、unary telemetry interception、retry policy enforcement 和 retry-budget admission。

AegisMesh 还有一个很适合面试展开的点：控制面决定的是“哪些实例可见、状态是什么、策略边界是什么”，但真正每次 RPC 要不要发、发给谁、发完后怎么更新本地 EWMA 和 inflight，都是 SDK 本地在做。`README.md` 里写得很具体，balancer 会把 resolver 里的 `status` 和 `slow_score`，跟本地 `inflight`、`latency_ewma` 组合起来算 cost。这正好说明控制面给的是全局背景，数据面做的是现场决策。

再进一步，如果面试官问“控制面挂了会怎样”，好答案通常是：不应该让数据面立刻瘫掉，但会逐渐变钝。因为没有新的实例变化、策略变化和全局慢故障结论进来，数据面只能靠最后一份快照和本地观测继续运行。AegisMesh 当前的设计也符合这个思路：`WatchPolicy` 断了不会立刻让 SDK 失效，resolver 拉取失败也不应该粗暴清空已有地址，而是退化到 last-known-good。

所以最稳的结论是：控制面负责全局视图、策略分发、状态归并和回滚能力；数据面负责低时延执行、本地反馈、请求级决策和故障就地止血。二者不能混成一层，否则不是控制面拖慢数据面，就是数据面把控制面的故障放大成全链路故障。

如果面试官继续深挖，可以按这条路线走：
1. 先问为什么控制面适合处理注册、策略、revision、审计，而不适合落在每个请求路径上。
2. 再问数据面为什么必须保留本地连接状态、本地 inflight 和本地 EWMA，而不能完全依赖中心化状态。
3. 再问控制面延迟和数据面延迟为什么不是同一类问题。
4. 再问控制面短暂不可用时，数据面为什么应该退化运行而不是立即失效。
5. 最后落回项目：AegisMesh 里 Controller 和 `sdk/go/aegisgrpc` 分别承担了哪些职责，为什么这样拆更合理。

## 30. 为什么配置下发延迟会影响负载均衡效果？

可以先这样答：

负载均衡策略最终能不能生效，不只取决于“策略对不对”，还取决于“策略多久才能到数据面”。配置下发延迟本质上就是控制闭环的延迟。控制面已经知道某个实例变慢、某个权重要调整、某个灰度比例要切换，但数据面还没收到，这段时间里所有决策都是基于旧世界做的，效果当然会打折。

最直接的影响，是路由仍然会打在不该继续承载流量的实例上。比如某个实例已经被判定为 `EJECTED`，或者某个冷启动实例本来只该吃少量预热流量，但配置延迟还没传播到客户端，那客户端就可能继续按旧权重发请求。对于负载均衡来说，几秒的滞后有时就足够把一个恢复中的节点重新压垮，或者把一个本该摘掉的节点继续打穿。

第二个影响，是不同客户端会在同一时刻看到不同版本的策略，形成短暂的分裂脑。A 客户端已经收到新权重，B 客户端还没收到；A 已经把某个实例降权，B 还在继续打；A 已经停止对某方法重试，B 还在按旧预算放大请求。这类问题在中心化代理里相对可控，在客户端负载均衡里会更明显，因为决策点多、传播面大。

第三个影响，是灰度和回滚会失真。你以为自己把 10% 流量切到新策略了，但如果一部分客户端还没收新配置，实际生效比例就不一定是 10%。回滚也一样，控制面已经回退 revision，不代表所有客户端立刻停止使用旧策略。长连接、HTTP/2 复用、连接池缓存、stickiness，都可能继续放大旧决策的寿命。所以工程里要分清“配置已经发布”和“流量已经迁移”是两件事。

放回 AegisMesh，这个问题尤其适合结合实现细节回答。项目当前不是所有东西都 push 到客户端。`interview/02-rpc-grpc-protocol.md` 里写得很明确：resolver 现在默认 3 秒轮询 Controller，而不是 server push；`PolicyService` 则提供 `GetPolicy` 和 `WatchPolicy`。这意味着实例列表变化和策略变化的传播路径并不完全一样。控制面已经有了新的状态，不等于客户端立刻就拿到了完整的新视图。

当然，AegisMesh 也不是完全没有缓冲。`README.md` 里 balancer 会结合控制面下发的 `slow_score` 和本地 `latency_ewma`、`inflight` 一起算 cost。也就是说，就算全局配置传播有延迟，客户端本地仍然可以先用局部信号绕开明显变慢的实例。这能缓解一部分问题，但它解决不了拓扑事实的滞后，比如实例已经下线但地址还没更新、灰度权重已经修改但本地还没换、方法级策略 revision 已变而调用方还在旧配置上跑。

所以更高一层的结论是：配置下发延迟影响的不是“能不能配”，而是“控制面判断和数据面行动之间差了多久”。这个差距越大，负载均衡越可能出现流量继续打向坏节点、恢复节点被过早打满、灰度比例不准、回滚不及时，以及不同客户端行为不一致等现象。你可以把它理解成负载均衡领域里的“状态陈旧问题”。

如果面试官继续深挖，可以按这条路线走：
1. 先问为什么负载均衡本质上是一个闭环系统，控制面的判断必须足够快地进入数据面。
2. 再问配置延迟为什么不仅影响坏节点摘除，也影响冷启动预热、灰度分流和回滚止血。
3. 再问客户端负载均衡里为什么更容易出现“不同调用方收到不同版本配置”的分裂状态。
4. 再问本地 EWMA、inflight 这类局部信号为什么只能部分弥补传播延迟，不能替代最新拓扑和最新策略。
5. 最后落回项目：AegisMesh 当前 `ListInstances` 轮询和 `WatchPolicy` 推送并存，会带来哪些传播时延上的真实 tradeoff。

## 31. 什么是冷启动实例？负载均衡如何给冷启动实例预热？

可以先这样答：

冷启动实例，指的不是“进程活着但还没 Ready”那么简单，而是“实例虽然已经可见、甚至健康检查已通过，但内部缓存、连接池、JIT/运行时状态、页缓存、热点数据、下游连接和本地并发窗口都还没进入稳定工作区间”。这类实例从平台角度看像是活的，从业务承载能力看却还处于半热状态。如果负载均衡把它当成熟实例一样立即灌满流量，往往会把它打成新的慢节点。

所以成熟系统不会把“健康检查通过”和“可以立即吃满生产流量”画等号。AWS ALB 的官方文档就提供了 `slow start`，本质上就是让一个刚恢复健康的 target 在一段时间里逐步增加承载比例，而不是瞬间按满权重接流量。NGINX 也有类似的 `slow_start` 思路。它们共同承认的事实是：恢复可达，不等于恢复容量。

预热一般有几种办法。第一种是流量渐进放量，也就是 slow start、渐进加权、probe ratio、分段拉权重。第二种是连接和依赖预热，比如提前建立数据库连接池、TLS 会话、下游 HTTP/gRPC 连接，先把最贵的冷路径做掉。第三种是缓存预热，比如热点配置、热点字典、模型、规则或业务缓存先装入内存。第四种是只让它先承接低风险请求，等观测到延迟和错误率稳定后，再逐步让它接普通流量。

这里面最常见的误区，是只靠主动健康检查。健康检查通常只回答“你活没活着”，它很难回答“你现在适不适合吃 20 倍于刚才的真实业务流量”。真正稳的做法，是健康检查负责把实例从“不可见”推进到“可试”，然后靠 slow start 或 probe 机制把它从“可试”推进到“可承载”。

放回 AegisMesh，这个思路和项目里的 `PROBING` 状态几乎是同一条线。`README.md` 写得很明确：`PROBING` endpoint 不会在还有 `HEALTHY` 或 `DEGRADED` endpoint 时进入主流量池，而是只拿很小一部分探测流量，默认 probe share 是 `2%`。这实际上就是客户端侧的预热和半开探测。它承认恢复中的实例需要先用小流量证明自己，而不是一恢复就回主池。

如果继续往工程上推，还可以再补一层：真正好的冷启动预热不只是“慢慢加流量”，还要和实例身份、版本、镜像启动时间、依赖 readiness 绑定。比如数据库连接池还没建完、sidecar 还没同步好、模型文件还没加载完，业务 readiness 就不该提前变绿。否则负载均衡即使做了 slow start，还是会把探测流量打在没有准备好的路径上。

所以更完整的回答是：冷启动实例本质上是“平台已可见、业务未稳态”的实例；预热机制的目的不是给它一个形式上的健康状态，而是给它一段受控的恢复窗口。slow start、probe、渐进加权、连接预热、缓存预热和 readiness 分层，都是为了解决这个问题。

如果面试官继续深挖，可以按这条路线走：
1. 先问为什么“健康检查通过”不等于“具备稳定承载真实流量的能力”。
2. 再问 slow start、probe ratio、渐进加权分别在防什么风险。
3. 再问只做主动健康检查而不做流量预热，为什么容易把恢复中的实例重新打垮。
4. 再问连接池、缓存、下游依赖 readiness 为什么也是冷启动承载能力的一部分。
5. 最后落回项目：AegisMesh 的 `PROBING` 和默认 `2%` probe share，本质上在解决什么预热问题。

## 32. 什么是负载均衡中的黑洞流量？如何发现？

可以先这样答：

“黑洞流量”不是一个像 TCP 或 HTTP 那样的严格标准术语，更像工程现场的叫法。通常它指的是：流量已经被成功路由到了某条路径、某个地址、某个实例、某个代理，表面上看请求“发出去了”，但实际并没有被正确处理并返回有效业务结果，像掉进了黑洞。它和普通失败的区别在于，问题往往出在路由路径、注册状态、连接状态或转发表状态已经失真，而不是单纯业务代码抛了个错。

黑洞流量常见来源有几类。第一类是服务发现陈旧。实例已经退出、Pod 已经消失、节点已经不可达，但注册信息还没及时删掉，请求继续被发往僵尸地址。第二类是连接层黑洞。长连接表面还在，keepalive 也没断，但后端线程池已经卡死、应用层已不再消费请求，导致流量“连得上、但处理不了”。第三类是路径层黑洞。比如路由规则、ACL、Sidecar、NAT、CNI、draining 状态或防火墙配置不一致，请求走到一半被吞了。第四类是版本和状态错位。比如某个实例还在服务发现里，但它实际处于 draining、冷启动、未完成数据同步或依赖不可用状态。

发现黑洞流量，关键不是只看某一个错误码，而是看“发出”和“完成”之间有没有系统性缺口。最直接的信号包括：连接建立失败上升、超时暴涨、重传和 RST 增多、发出的请求数明显高于成功完成数、某些调用在 trace 里只看到上游 span 看不到下游有效处理、某个实例入口计数很高但应用层业务处理计数很低，或者代理层看到了转发但后端应用几乎没收到等。

如果系统支持多层观测，黑洞会更好抓。比如入口代理的请求计数、客户端 SDK 的 attempt 指标、服务端应用的实际处理计数、内核层的 retransmit/reset 统计、以及 trace 里的 server span 缺失情况，这几层一对就很容易看出“流量是在哪一段掉了”。只看单点指标经常会误判，因为超时既可能是后端真慢，也可能是流量中途被吞。

放回 AegisMesh，可以把它和项目里的几个实现点连起来。`interview/25-scenario-followups.md` 明确提到，生产里最好不是只靠 TTL，而是 `Deregister + TTL + 平台状态 watch` 一起做，避免僵尸实例继续留在 registry 里。SDK 侧还会对连接失败做本地短期隔离，不等 Controller 下一轮状态。再往下，如果 eBPF telemetry 能提供 TCP retransmit 或 connect 信号，就更容易判断问题是在“后端真慢”，还是在“链路已经像黑洞一样丢流量”。

这道题还有一个很好的追问角度：黑洞流量和慢流量不是一回事。慢流量是后端还在处理，只是处理得很慢；黑洞流量往往是请求已经没有希望得到正确处理，但路径上某一层还没有把失败及时、清晰地暴露出来。负载均衡如果只看平均延迟，有时分不清这两种情况；如果能结合超时、重试放大、连接错误和缺失的下游 span，判断会稳很多。

所以更稳的说法是：黑洞流量本质上是“路径看起来还在，业务处理实际上已经掉线”的流量。发现它靠的是多层对账和缺口分析，而不是寄希望于某一个健康检查或某一个状态位自动告诉你答案。

如果面试官继续深挖，可以按这条路线走：
1. 先问为什么黑洞流量更像工程术语，而不是某个协议层的标准定义。
2. 再问僵尸实例、陈旧注册、draining 未生效、长连接假活这几类情况为什么都会制造黑洞。
3. 再问为什么只看错误率或平均延迟，经常分不清慢流量和黑洞流量。
4. 再问入口计数、客户端 attempt、服务端处理计数、trace 缺失 span、内核 retransmit 这些信号怎样组合定位黑洞位置。
5. 最后落回项目：AegisMesh 为什么要同时依赖 registry 生命周期管理、本地短期隔离和网络 telemetry，才能更稳地发现黑洞。

## 33. 什么是流量倾斜？可能由哪些因素导致？

可以先这样答：

流量倾斜，指的是流量没有按照你期望的容量比例或策略比例分散，而是过度集中到一部分实例、连接、机房、可用区或 Region 上。注意，它不等于“完全不均匀”。很多场景本来就允许有偏，比如同地域优先、本地优先、灰度放量、热点 key 粘到少数节点。真正的问题是，这种偏斜已经超出了目标设计，开始让某些实例过载、某些实例闲置，或者让尾延迟和错误率明显恶化。

导致流量倾斜的原因很多，算法只是其中一类。最常见的是长连接和多路复用。HTTP/2 或 gRPC 一旦把大量 RPC 复用到少量连接上，哪怕表面上的连接数看起来均匀，真实请求量也可能非常不均。`pick_first`、连接级哈希、连接建立时机不均匀，都会把早期选路结果长期放大。

第二类原因是粘性和哈希。sticky session、source IP hash、一致性哈希、本地缓存亲和性，本来就是为了命中局部性或减少重映射。但如果用户分布本来就不均、热点 key 特别集中、NAT 后大量用户共享出口 IP，或者某个租户请求量远高于其他租户，这些机制就会把热点稳稳固定在少数实例上。

第三类原因是实例异构和容量误判。轮询算法默认大家能力差不多，可现实里 CPU 型号、机器规格、Pod limit、JVM/Go runtime 状态、是否命中缓存、下游依赖位置、磁盘性能都可能不一样。你看起来“分得一样多”，其实是在用一样的流量压不同容量的实例，结果就会表现成倾斜和局部过载。这也是为什么权重、容量估算和 observed load 会越来越重要。

第四类原因是状态传播滞后。控制面已经知道某个实例该降权了，但一部分客户端还没收到；某个实例刚恢复，大家同时把探测流量打过去；某个实例其实应该摘了，但地址刷新慢了几秒还在列表里。这类倾斜往往不是算法本身设计错了，而是控制闭环延迟让客户端在不同时间点采取了不一致动作。

第五类原因是 locality 和故障转移。你本来故意做同机房优先、同可用区优先，这会让大部分流量优先打在局部池子里；一旦某个局部池子健康度下降，流量会向下一级池子迁移。这种迁移如果没有容量冗余、没有平滑的慢启动和上限控制，就很容易形成新的倾斜，把邻近池子突然打热。

放回 AegisMesh，可以把流量倾斜理解成“全局慢故障状态、本地 EWMA、本地 inflight 和连接复用共同作用后的结果”。项目里的 adaptive P2C 会结合 `slow_score`、`status`、`inflight` 和 `latency_ewma` 去降低慢实例的被选概率，这本身就是在对抗倾斜。但如果控制面更新滞后、地址频繁抖动、长连接早期分布不均，或者所有客户端在相近时间做出同样调整，倾斜还是会发生。

所以不要把“流量倾斜”简单理解成“轮询没轮匀”。它常常是连接模型、哈希策略、热点分布、容量差异、传播延迟、恢复节奏和 locality 共同叠加的结果。真正的治理手段也不会只有一个，而是算法、预热、限流、容量建模、观测和配置传播一起上。

如果面试官继续深挖，可以按这条路线走：
1. 先问为什么“分得不平均”不一定是错误，而“超过设计目标的偏斜”才是问题。
2. 再问 HTTP/2 长连接、多路复用和 `pick_first` 为什么特别容易放大连接早期分布。
3. 再问 sticky session、一致性哈希、热点 key 和 NAT 出口共享为什么会制造稳定倾斜。
4. 再问实例异构、容量误判和权重失真为什么会让“均匀分流”看起来公平、实际上不公平。
5. 最后落回项目：AegisMesh 的 `slow_score + local inflight + EWMA` 是怎样用来缓解倾斜的，它还剩下哪些天然边界。

## 34. 什么是惊群效应？负载均衡如何引发或缓解惊群？

可以先这样答：

惊群效应，或者说 thundering herd，核心不是“流量大”，而是“很多调用方因为同一个触发条件，在差不多同一时间做出同一种动作”。在负载均衡场景里，这种动作可能是同时重试、同时重连、同时切到同一个恢复节点、同时刷新配置、同时把一个节点从坏变好、或者同时把同一批等待中的请求放出去。可怕的地方在于，它会把原本分散的小动作叠成瞬时洪峰。

负载均衡非常容易引发这类问题。最典型的例子，就是某个实例刚恢复，所有客户端都在同一个健康检查窗口里看到它变绿，于是一起把流量打回去。如果没有 slow start、probe ratio 或半开预算，这个“恢复”节点会瞬间重新被打成慢节点。另一类例子是控制面一次性把新权重推给所有客户端，大家同一时间切流；如果策略过于敏感，局部抖动会被集体放大成全局振荡。

重试也经常和负载均衡一起制造惊群。一个实例超时后，所有客户端几乎同时重试到剩余健康实例；如果这些实例本来就只够扛正常流量，叠加的重试洪峰会把它们也打慢。于是你看到的表面现象像是“负载均衡没分好”，但更深层的问题其实是负载均衡、超时、重试、熔断共同形成了放大链。

缓解惊群，第一原则是去同步化。也就是别让所有客户端在同一个时间点、按照同一节奏做同一件事。常见手段包括指数退避加抖动、随机化探测时间、分批应用配置、限制恢复节点的初始权重、把半开探测做成预算而不是无限放行，以及避免所有客户端都共享同一个过于敏感的短窗口判定。

第二原则是限制恢复流量和失败放大。也就是让新恢复节点、冷启动节点、刚从摘除状态返回的节点，只先吃一小部分流量；让重试预算、circuit breaker、并发上限和局部限流先把洪峰切掉，而不是指望负载均衡单靠“换个节点”就把问题抹平。因为如果所有剩余节点都接近满载，单纯换目标不会创造容量。

放回 AegisMesh，这个思路几乎是写进实现里的。`README.md` 里 `PROBING` endpoint 默认只接 `2%` probe share，本质就是防止所有客户端同时把恢复节点重新打爆。每个 endpoint 还有默认 `128` 的本地 in-flight breaker，上层还有 retry budget，这些东西合在一起，就是在限制惊群带来的瞬时请求放大。项目当前如果再往生产化补一层，最值得继续加强的通常会是 watch/reconnect 抖动、轮询错峰和恢复窗口随机化。

这道题的关键不是背定义，而是让面试官听出来你知道：惊群是同步行为问题，不只是吞吐问题；负载均衡既可能制造它，也可能通过随机化、预算、预热和局部保护来缓和它。

如果面试官继续深挖，可以按这条路线走：
1. 先问为什么惊群的本质是“很多调用方因同一信号同时行动”，而不只是“请求很多”。
2. 再问健康恢复、配置切换、重试洪峰为什么都会在负载均衡场景里制造惊群。
3. 再问为什么 slow start、probe ratio、半开预算比“恢复了就全部放回主流量”更稳。
4. 再问指数退避、抖动和分批推配置为什么是在做去同步化。
5. 最后落回项目：AegisMesh 的 `PROBING`、本地 breaker 和 retry budget，各自在缓解哪一类惊群。

## 35. 负载均衡和限流、熔断、降级之间是什么关系？

可以先这样答：

最容易说清楚的一种方式，是把它们看成同一套过载与可用性治理链条里的不同层。负载均衡回答的是“请求应该尽量发给谁”；限流回答的是“这批请求是否应该被放进系统”；熔断回答的是“当前这条依赖路径还能不能继续承受更多调用”；降级回答的是“当正常路径扛不住时，系统要以什么更便宜、更保守的方式继续活着”。它们不是替代关系，而是互相补位。

负载均衡的能力边界要先说清。负载均衡擅长把流量从明显更差的节点挪开，减少局部热点和局部尾延迟；但它不会凭空创造容量。如果所有节点都慢、所有线程池都满、所有下游都在排队，你再怎么换路由目标，也只是把慢请求从 A 搬到 B。所以只靠负载均衡处理系统级过载，通常会失败。

这时候限流就上场了。限流的作用不是“让指标看起来好看”，而是提前阻止系统进入不可恢复的排队区。它可以放在入口、调用方、本地队列、方法级、租户级或依赖级。好的限流能在负载均衡还没来得及把请求打散之前，就先把总入流压在可承载区间里，避免队列无限拉长、超时外溢、重试再放大。

熔断更像是局部保护和故障隔离。它盯的是某个依赖、某个实例、某类请求、某条连接池的并发和失败状态，一旦达到阈值，就快速失败，防止请求继续堆进已经不健康的路径。Envoy 官方把 circuit breaking 定义成 upstream 层面的资源限制，本质上就是给每条上游依赖设上限。AegisMesh 当前的 per-endpoint in-flight breaker 其实就很接近这种思路，它不等慢故障评分慢慢收敛，而是本地先把超额并发卡住。

降级则是再往后一步。它承认“现在不是把请求分好就能解决的阶段了”，需要主动降低功能复杂度、降低一致性要求或降低资源消耗，比如返回缓存、只给摘要、不查重字段、关闭次要依赖、从强一致改读副本、从实时计算改预计算。降级的目标不是完美，而是把单位请求成本降下来，让系统在坏情况下还能提供有界服务。

这四者放在一起时，常见配合是这样的：负载均衡优先绕开局部坏节点；熔断防止某条路径继续被灌；限流控制总体进入量；降级在容量确实不够时降低单位请求成本。再和 timeout、retry、健康检查连起来，才构成完整的保护闭环。Istio 的 traffic management 文档也把路由、超时、重试、circuit breaking 放在同一套治理语境里，说明工业界本来就不是把它们割裂来看。

放回 AegisMesh，这个关系也很清楚。项目当前已经有 adaptive P2C、`slow_score` 状态机、per-endpoint breaker 和 retry budget。它们分别对应“绕开慢节点”“控制恢复节奏”“限制局部并发”和“限制请求放大”。如果未来继续工程化，最自然的下一步往往不是把负载均衡算法再调花，而是补更明确的 caller-side admission control、服务级限流和业务降级钩子。因为当 `all-slow` 真的发生时，项目文档自己也承认，单靠负载均衡是不够的，还需要 load shedding、limit 和 degrade。

所以最稳的结论是：负载均衡解决的是分配问题，限流解决的是总量问题，熔断解决的是局部路径继续放量的问题，降级解决的是资源确实不够时怎么保核心的问题。四者只有一起看，系统才谈得上既快又稳。

## 36. L4 负载均衡为什么通常性能更高？它牺牲了哪些应用层能力？

可以先这样答：

L4 负载均衡通常性能更高，核心原因不是它有某种神奇算法，而是它少做了很多事。它主要看五元组、协议、连接或 flow 状态，选中后端后把包或连接转过去。AWS NLB 文档里把 Network Load Balancer 定位在 OSI 第四层，并说明 TCP 流量按 flow hash 选择 target，同一条 TCP connection 生命周期内会保持在同一个 target 上。这个模型的好处很直接：一次连接只需要做相对粗粒度的选择，不需要每个请求都解析 HTTP、匹配路由规则、构造 header map、执行过滤器链、记录复杂应用日志。

性能优势首先来自数据路径短。L4 可以把逻辑压在内核、DPDK、XDP/eBPF、硬件 ADC 或云厂商高性能转发面里，很多时候不需要把每个请求完整搬到用户态做应用协议解析。即使是在用户态实现，它也常常只处理连接建立、目标选择、NAT 或隧道封装这类传输层动作。对高 QPS、短包、长连接接入、TLS 透传、数据库连接、消息队列连接这类场景，这种简单路径很有价值。

第二个优势是状态更粗。L4 关心的是连接或 UDP flow，而不是每个 HTTP request、每个 gRPC method、每个 header 和每个 response code。状态粒度粗，意味着内存对象少、规则匹配少、指标维度少，热路径上的分配和锁竞争也更容易控制。像 NLB 这类产品能强调“每秒数百万请求”能力，背后就是尽量把每个包上的工作压到最低。

第三个优势是不会因为应用协议复杂度被拖住。HTTP/2 有 stream、HPACK、流控和 GOAWAY；HTTP/3/QUIC 有连接 ID、TLS 1.3、stream 和拥塞控制；gRPC 还有 method、metadata、deadline、status。L7 如果要理解这些，就必须把协议状态机跑起来。L4 不理解这些语义，也就不用为这些语义付 CPU、内存和延迟成本。

但代价也正是在这里。L4 牺牲的是应用层可见性和应用层控制力。它通常不能按 Host、path、Header、Cookie、HTTP method、gRPC service/method、tenant、用户身份、业务错误码来分流。它也很难做 WAF、JWT 校验、细粒度灰度、请求重写、基于状态码的异常检测、按 API 限流、按业务方法熔断、请求级访问日志和 trace 注入。

还有一个很实在的代价：连接级分流不等于请求级分流。一个 HTTP/2 或 gRPC 连接里可能有很多 stream，如果 L4 只在连接建立时选了一次后端，后面的请求都会被这条连接的早期选择绑定住。前面文件里已经讲过，连接级负载均衡可能看起来连接数均匀，但真实请求量不均。L4 在这里不是做错了，而是它根本看不见连接内部的工作量。

TLS 也会限制 L4 的能力。如果 TLS 透传，L4 最多在不解密的情况下利用少量外层信息，比如 SNI 或 ALPN，很多时候连这些也不一定用于路由。URI、Header、状态码、业务身份都在加密层里面。AWS ALB 的 HTTPS listener 文档也把边界讲得很清楚：ALB 终止前端连接并解密后才能把请求发给 target；如果要不解密地传递加密流量，应使用 TCP listener 透传。

放到 AegisMesh 上，这个区别很重要。AegisMesh 当前的核心价值不在 L4 入口转发，而在 gRPC 客户端侧的 L7/RPC-aware 决策。它能在每次 RPC 前看到 method、attempt、本地 inflight、EWMA 和控制面下发的 `slow_score`。如果把它换成一个纯 L4 LB，确实可能得到更轻的数据路径，但也会失去这些 RPC 级信号。对 fail-slow 治理来说，这些信号正是项目想保留的东西。

所以这题的结论可以直接说：L4 快，是因为它少解析、少匹配、少维护细粒度状态，也更容易放进内核或硬件化数据面。它牺牲的是应用层语义、请求级观测、细粒度治理和协议感知能力。面试里不要把 L4 说成“更先进”，它只是把职责压到传输层，换来了更短的热路径。

如果面试官继续深挖，可以按这条路线走：
1. 先问 L4 热路径上到底少做了哪些工作：不解析 HTTP/gRPC，不跑复杂过滤器，不做请求级规则匹配。
2. 再问连接级选择为什么比请求级选择更轻，也为什么会在 HTTP/2 和长连接里失真。
3. 再问 TLS 透传为什么会保留端到端加密，但让中间层看不到应用语义。
4. 再问 L4 牺牲了哪些能力：灰度、WAF、认证、按 Header 路由、按方法限流、请求级日志和 trace。
5. 最后落回项目：AegisMesh 为什么宁愿承担一部分 L7/RPC-aware 成本，也要拿到 fail-slow 治理需要的本地信号。

## 37. L7 负载均衡为什么更灵活？它的 CPU、内存和延迟成本来自哪里？

可以先这样答：

L7 更灵活，是因为它做决策时看见的是应用协议，而不是只有连接外壳。AWS ALB 文档里说得很直接：Application Load Balancer 工作在 OSI 第七层，可以按应用流量内容配置 listener rules，把请求路由到不同 target group。它支持 URL path、Host、HTTP header、method、query parameter 等条件。也就是说，L7 不只是“选一台机器”，它可以理解“这是哪个 API、哪个租户、哪个版本、哪类客户端、走哪条业务路径”。

这种灵活性带来的能力很多。入口网关可以按 path 把 `/api/order` 和 `/api/user` 发到不同服务；按 Header 或 Cookie 做灰度；按 JWT 或 mTLS 身份做认证授权；按 status code、gRPC status、业务错误码做可观测性；按请求体大小或方法名做限流；按协议做 HTTP 到 gRPC 的转换；按 WAF 规则拦截异常请求。L4 做不了这些，不是因为算法差，而是它看不到这些字段。

CPU 成本主要来自协议解析和过滤器执行。L7 代理要解析 HTTP/1.1 文本、HTTP/2 帧、HPACK header、gRPC metadata，可能还要处理 TLS 握手、证书校验、ALPN、SNI、压缩、解压缩、WAF 正则、JWT 签名校验、路由规则匹配、限流判断、日志格式化和 tracing 注入。Envoy 的 TLS 文档也能看到这类复杂性：TLS termination、upstream TLS origination、证书验证、SNI、ALPN、session resumption、OCSP、私钥操作，都是 L7 或边缘代理经常要承担的工作。

内存成本来自连接和请求状态。一个成熟 L7 代理通常同时维护 downstream connection、upstream connection pool、HTTP/2 stream、header map、route match 结果、filter state、buffer、TLS session、访问日志上下文、指标标签和 trace 上下文。只要出现 request buffering、响应缓冲、限速、重试、影子流量、body inspection，内存压力就会更明显。指标维度也会带来内存成本，尤其是按 route、cluster、status、method、tenant 拆得很细时。

延迟成本有几类。第一类是代理多一跳带来的排队和调度成本。第二类是 TLS、协议解析和规则匹配的纯计算成本。第三类是连接池成本，比如 upstream 连接不足时要新建连接，HTTP/2 连接流控或最大并发 stream 限制也可能让请求排队。第四类是过滤器链成本，认证、外部授权、WAF、限流服务、动态配置查询如果走远程调用，延迟会明显上升。

还有一类延迟更隐蔽：L7 代理越聪明，失败模式越多。路由规则写错会 404 或打错后端；证书链或 SNI 配错会握手失败；HTTP/2 stream reset 可能被误判成后端错误；header 太大可能被代理拒绝；WAF 误杀可能看起来像业务失败；访问日志和指标爆量会反过来拖慢代理。L7 的问题定位能力更强，但它自己也成了更复杂的系统。

不过这不代表 L7 一定慢到不可接受。成熟代理会做大量优化，比如连接复用、零拷贝路径、TLS session resumption、规则预编译、异步日志、限流本地缓存、统计采样、热重启和多线程事件循环。真正的工程判断不是“L7 慢不用”，而是“哪些能力必须放在 L7，哪些能力可以留给 L4、客户端 SDK、Service Mesh 或应用自己做”。

放到 AegisMesh 上，也可以这样解释：AegisMesh 是客户端侧 L7/RPC-aware，而不是传统入口 L7 代理。它少了一次独立代理网络跳转，但把一部分 L7 成本放进了调用方进程里，比如 interceptor、resolver、picker、EWMA、retry budget 和 telemetry 上报。好处是能靠近每次 RPC 做决策；代价是 SDK 复杂度、语言一致性和本地状态维护变重。

所以这题最稳的答法是：L7 灵活，是因为它能把负载均衡从“连接分发”提升到“应用语义治理”。它的成本来自 TLS 和协议解析、规则匹配、过滤器链、连接池、请求状态、日志指标和代理跳转。能不能接受这部分成本，要看你到底需要哪些应用层能力。

如果面试官继续深挖，可以按这条路线走：
1. 先问 L7 到底多看到了哪些信息：Host、path、Header、method、Cookie、status、gRPC method、metadata。
2. 再问这些信息带来了哪些能力：灰度、认证、WAF、限流、协议转换、请求级日志和 trace。
3. 再问 CPU 成本来自哪里：TLS、解析、规则匹配、过滤器、压缩、JWT/WAF。
4. 再问内存和延迟成本来自哪里：连接池、stream、header、buffer、指标、队列和额外代理跳。
5. 最后落回项目：AegisMesh 为什么把一部分 L7 成本放在 SDK 内，而不是把所有治理都交给入口代理。

## 38. TLS 终止放在负载均衡层有什么好处和风险？

可以先这样答：

TLS 终止放在负载均衡层，最大的好处是把加密连接的入口处理集中起来。AWS ALB 的 HTTPS listener 文档说得很明确：负载均衡器使用服务器证书终止前端连接，解密客户端请求后再发送给 targets。这意味着证书选择、TLS security policy、SNI、多域名证书、证书轮换、访问日志、WAF、认证、Header 路由都可以在入口层统一处理。

第一个好处是运维简单。证书不用散落在每个后端实例上，轮换、吊销、算法升级、安全策略收敛都更集中。比如从旧 TLS policy 切到更严格的 TLS 1.2/1.3 policy，入口层统一做，比让所有业务服务自己升级 TLS 栈更可控。NLB TLS listener 和 ALB HTTPS listener 都体现了这种模式：证书部署在负载均衡器上，入口先完成安全连接协商。

第二个好处是 L7 能力打开了。TLS 如果不终止，负载均衡器看不到明文 HTTP，也就无法按 path、Header、Cookie、method 做路由，更难做 WAF、认证、细粒度限流、请求日志和 trace 注入。终止之后，入口层能把“这是哪个 API 请求”看清楚，很多企业入口治理能力才有地方落。

第三个好处是可以做集中观测和故障归因。入口层能记录 TLS 协议版本、cipher、SNI、证书选择、握手失败、HTTP 状态码、upstream latency、route name、target group、WAF 命中、认证失败原因。出了问题时，可以更快区分是客户端握手失败、证书过期、路由规则错、后端 5xx，还是 upstream 超时。

风险也很清楚：安全边界前移了。TLS 在负载均衡层被解开之后，从 LB 到后端这段如果是明文，流量就不再是端到端加密。只要 LB 所在网络、节点、内存、日志、调试接口、抓包权限、sidecar 或转发链路出问题，原本只该后端看到的数据就可能被暴露。负载均衡器也成了高价值目标，因为它持有私钥或能调用私钥操作。

第二个风险是身份语义容易丢。客户端证书如果只在入口被验证，后端服务看到的可能只是 LB 的连接，而不是原始客户端的 mTLS 身份。你当然可以把验证后的身份放进 Header，比如某些代理会用 `X-Forwarded-Client-Cert` 表达客户端证书信息；但这类 Header 必须只由可信代理写入，并且要在边界处清理外部伪造值。Envoy 文档对 XFCC 的处理就强调了代理可以 sanitize、append 或 forward，默认不应盲目信任外部带来的身份 Header。

第三个风险是合规和审计边界变复杂。某些业务要求后端服务自己完成客户端认证，或者要求敏感字段在到达具体服务前不被中间层解密。此时入口 TLS 终止可能不符合要求。更稳的做法通常是三选一：完全 TCP/TLS passthrough，牺牲 L7 能力保留端到端 TLS；入口终止后到后端重新加密；入口终止并在内部使用服务网格 mTLS，把后端链路也纳入身份和加密控制。

还有一个工程风险是排障时容易误判。TLS 终止后，客户端到 LB 的连接和 LB 到后端的连接已经是两条连接。客户端看到的证书、协议版本和延迟，不等于后端看到的连接状态。一个 502 可能是 LB 到后端握手失败，也可能是后端关闭连接，还可能是入口规则拒绝。日志要分清 downstream TLS 和 upstream TLS，不要把它们当作同一条端到端连接。

放到 AegisMesh 上，如果未来把 gRPC 流量放到入口 TLS 终止后再进服务，SDK 里看到的 peer 和服务端看到的身份都会变化。AegisMesh 当前更关心服务间 RPC 的实例选择、慢故障和重试预算。如果服务间也要用 mTLS，最好让调用方和被调方之间仍然有明确的 workload identity，而不是只依赖入口层转发来的字符串身份。

所以结论很直接：TLS 终止放在负载均衡层，换来集中证书管理、L7 路由、安全检查和观测能力；代价是明文边界前移、私钥和入口节点变成高价值资产、后端链路需要重新加密或重新认证、客户端身份传递必须谨慎设计。面试里不要只说“方便”，要说清楚它改变了信任边界。

如果面试官继续深挖，可以按这条路线走：
1. 先问为什么 TLS 不终止时，L7 路由、WAF、认证和请求级日志会受限。
2. 再问证书集中管理和安全策略统一为什么是入口终止的主要收益。
3. 再问 LB 到后端如果明文，会带来哪些网络、日志、抓包和合规风险。
4. 再问客户端证书身份终止在 LB 后，后端如何可信地拿到身份，以及为什么不能盲信外部 Header。
5. 最后落回项目：AegisMesh 的服务间治理如果引入 mTLS，应该把 workload identity 放在哪里验证。

## 39. mTLS 在经过多层负载均衡时如何保持端到端身份？

可以先这样答：

这题要先拆开两个概念：端到端“连接加密”和端到端“身份语义”不是同一件事。如果多层负载均衡里每一层都是 L4/TCP passthrough，不终止 TLS，那么客户端证书和服务端证书可以一直到最终工作负载，负载均衡器只是转发连接。这个模式最接近真正的端到端 mTLS，但它也意味着中间层基本拿不到 L7 路由、WAF、Header 观测和请求级治理能力。

如果中间某一层 L7 代理终止了 TLS，原始 mTLS 连接就在那一层结束了。后面再怎么 re-encrypt，也不是同一条 TLS session。此时要保持的是“经过验证的身份语义”，而不是假装原始 TLS 没断。更准确的说法是：每一跳都用 mTLS 重新认证对端身份，同时把上一跳已经验证的客户端或 workload 身份用受信机制传给下一跳。

第一种方案是完全透传。边缘 LB 或中间 LB 只按 SNI、目标端口、源地址或五元组做转发，不解密，不改 Header。最终服务端直接验证客户端证书，客户端也直接验证服务端证书。好处是身份链简单、密码学边界清楚；缺点是中间层的 L7 能力很弱。需要按 path 灰度、按用户限流、WAF 或请求级日志时，这个方案往往不够用。

第二种方案是分段 mTLS。比如 client 到 edge gateway 是一段 mTLS，edge gateway 到 internal gateway 是一段 mTLS，internal gateway 到 sidecar 是一段 mTLS，sidecar 到 workload 或本机进程是本地连接。每一段都验证对端证书，证书里要有稳定的 workload identity、service account、SPIFFE URI 或平台约定的身份字段。Istio 的安全文档就是这个思路：客户端侧 Envoy 和服务端侧 Envoy 建立 mTLS，握手时验证服务端证书中的 service account 是否被授权运行目标服务。

分段 mTLS 的关键，是不要把“Header 里写了谁”当成身份根。Header 只能承载已经验证后的身份结论，不能替代验证。边界代理必须清理外部传入的 `X-Forwarded-Client-Cert`、`X-Forwarded-For`、`X-User` 这类 Header，再由可信代理重新写入或追加。Envoy 文档里也明确说 XFCC 是代理 Header，代理可以选择清理、追加或转发；如果处理策略不严，攻击者就可能自己伪造身份 Header。

第三种方案是把传输层 mTLS 和请求层身份分开。比如外部用户用客户端证书、OIDC 或 JWT 在入口层完成认证；入口把用户身份转换成短期 token 或受保护 Header；内部服务之间仍然用 mesh mTLS 验证 workload identity。这样后端能同时知道“哪个工作负载调用我”和“代表哪个用户调用我”。这不是原始客户端证书的端到端透传，但在企业系统里更常见，因为它把用户身份和服务身份分开治理。

多层负载均衡时还要解决 trust domain 和证书链问题。所有参与 mTLS 的代理和服务必须知道信任哪些 CA、如何轮换根证书、如何处理跨集群或跨云的 trust bundle、如何撤销证书。Istio 文档里提到 CA、证书管理、secure naming、PeerAuthentication 和 AuthorizationPolicy 这些机制，本质就是让“证书里的身份”和“服务发现里的目标服务”能对应起来，而不是只要握手成功就放行。

还有一个容易踩的坑：源 IP 不是稳定身份。经过 SNAT、NAT 网关、Ingress、sidecar、NodePort、企业代理之后，后端看到的源 IP 可能只是上一跳代理。mTLS 的价值就在于把身份从网络位置里拿出来，放到证书和策略里。源 IP 可以作为辅助信号，不能作为多层负载均衡里的主身份。

放到 AegisMesh 上，如果服务间链路未来加 mTLS，比较合理的边界是：SDK 或 sidecar 在每次 RPC 时验证目标服务身份，控制面下发的是“哪些实例和身份允许被调用”，数据面执行的是“这次 RPC 的对端证书是否匹配目标服务”。如果中间再接 L7 网关，就要明确网关是在代表谁发起新 mTLS 连接，后端看到的是原始调用方、网关，还是两者都能在可信上下文里看到。

所以这题的结论是：经过多层 LB 时，真正端到端 mTLS 只能靠 passthrough 保留；一旦 L7 终止 TLS，就要承认连接被分段，然后用每跳 mTLS、可信身份转发、Header 清理、secure naming、统一 CA/trust bundle 和授权策略来保持身份语义。不要把“重新加密”误说成“原始端到端 mTLS 还在”。

如果面试官继续深挖，可以按这条路线走：
1. 先问端到端 TLS session 和端到端身份语义有什么区别。
2. 再问 passthrough 为什么保留原始 mTLS，但牺牲中间层 L7 能力。
3. 再问分段 mTLS 里每一跳应该验证什么证书、什么 service identity、什么 trust bundle。
4. 再问 XFCC、XFF、用户身份 Header 为什么必须由可信代理清理和重写，不能接受外部伪造。
5. 最后落回项目：AegisMesh 如果引入 mTLS，控制面和 SDK 分别应该负责身份映射、策略下发和本地校验的哪一部分。

## 40. L4 直通和 L7 代理在故障定位上有什么差异？

可以先这样答：

L4 直通和 L7 代理的故障定位差异，来自它们能看到的证据不同。L4 直通看到的是连接、包、流和少量传输层状态；L7 代理看到的是请求、路由、Header、状态码、upstream cluster、filter 结果和应用层错误。前者数据路径短，问题面少，但证据也少；后者证据丰富，但自己也变成了一个更复杂的故障来源。

L4 直通下，常见证据是 SYN 是否到达、连接是否建立、RST/FIN 谁发的、是否重传、是否丢包、NAT/conntrack 有没有命中、后端端口是否可达、客户端和后端看到的五元组是否一致。它适合定位“连不连得上”“包有没有走到”“连接为什么断”。如果故障发生在 HTTP path 路由、Header 缺失、gRPC status、后端业务 5xx，L4 基本看不见。

这会导致 L4 场景里经常需要多点抓证据。客户端要看 connect timeout、read timeout、RST；LB 要看连接数、转发表、conntrack、drop、health check；后端要看 accept、应用日志、TLS 握手、业务处理。少一层证据，排障就容易变成猜：请求到底是没到后端，到了但 TLS 失败，还是应用处理了但响应没回来？

L7 代理的优势是能把一次请求拆成更清楚的阶段。它可以告诉你：下游 TLS 握手是否成功，listener rule 命中哪条 route，是否被 WAF 或认证拒绝，转到哪个 upstream cluster，upstream connect 是否失败，后端返回了什么 status，超时发生在 per-try 还是 overall deadline，是否重试过，重试打到哪些节点，最后响应码是谁生成的。Envoy、ALB、NGINX 这类代理的访问日志和统计指标，价值就在这里。

但 L7 代理也会引入新的故障类型。路由规则写错、Header 被重写、body 被缓冲、超时配置太短、TLS 证书不匹配、HTTP/2 stream reset、连接池耗尽、外部授权服务变慢、WAF 误杀、指标和日志阻塞，都可能让问题出在代理层本身。此时 L7 的日志很有用，但也不能默认“代理说后端错了就一定是后端错了”。

还有一个差异是责任边界。L4 passthrough 保留了客户端到后端的 TLS 语义时，后端更容易直接证明自己看到的客户端连接和证书；中间层对业务内容没有解释权。L7 代理终止 TLS 后，客户端到代理、代理到后端是两条连接，故障定位也要按两段看。客户端看到 502，不代表后端真的返回了 502；可能是代理生成的本地错误。

在黑洞流量和慢故障场景里，两者的定位方式也不同。L4 更依赖内核计数、重传、连接状态和后端实际处理计数对账；L7 可以直接看 request count、upstream_rq_timeout、upstream reset、route、cluster、response flags。L7 更容易告诉你“哪类请求慢”，L4 更容易告诉你“哪段连接或路径断”。

放到 AegisMesh 上，比较好的排障姿势是多层对账。SDK 侧有 attempt、deadline、retry budget、选中的 endpoint、本地 EWMA 和 inflight；服务端有实际处理日志；eBPF 或内核层可以补 TCP retransmit、connect、RST 这类信号。只看 L7 SDK 指标，可能漏掉网络黑洞；只看 L4 内核指标，又不知道哪类 RPC 方法受影响。项目本身就是想把这两类证据合起来。

所以这题可以这样收束：L4 直通排障更像网络和连接排障，证据少但路径简单；L7 代理排障更像请求生命周期排障，证据多但代理自身也可能制造故障。成熟系统不会只相信一层日志，而是把客户端、代理、内核和服务端处理计数对起来。

如果面试官继续深挖，可以按这条路线走：
1. 先问 L4 能看到哪些信号：SYN、RST、重传、连接数、五元组、conntrack、健康检查。
2. 再问 L7 能看到哪些信号：route、Header、status、upstream latency、response flag、retry、trace。
3. 再问 L7 终止 TLS 后为什么要把 downstream 和 upstream 两段连接分开看。
4. 再问 L7 代理自身可能制造哪些故障：规则、证书、过滤器、连接池、WAF、日志。
5. 最后落回项目：AegisMesh 为什么需要 SDK 指标、服务端指标和内核网络 telemetry 一起定位 fail-slow 或黑洞。

## 41. DNAT、SNAT、Full NAT、DR 模式、Tunnel 模式分别如何影响流量路径？

可以先这样答：

这几个词本质上都在回答同一个问题：负载均衡器到底改不改包头，回包还要不要经过它，后端看到的客户端是谁。只要把“请求路径”和“响应路径”画清楚，区别就不难。

DNAT 改的是目的地址。典型过程是客户端访问 VIP，负载均衡器把目的 IP 或端口改成某个 real server，然后把包转过去。iptables 的 DNAT 文档也说得很直白：DNAT 会修改 packet 的 destination address，并且这个 connection 后续包也会被相应处理。DNAT 的关键约束是回包最好也回到同一台做 NAT 的设备，否则它没机会把源地址改回客户端期望的 VIP，客户端可能收到一个来自后端真实 IP 的响应，连接语义就乱了。

SNAT 改的是源地址。客户端请求经过负载均衡器后，后端看到的源地址不再是客户端，而是 LB 的地址或某个 SNAT 地址。iptables 的 SNAT 文档说明它会修改 packet 的 source address，并且连接后续包也会被处理。SNAT 的好处是回包天然回到 LB，因为后端以为自己在回复 LB；代价是后端丢失真实客户端 IP，除非额外用 PROXY protocol、`X-Forwarded-For` 或可信 metadata 传过去。

Full NAT 通常指同时做 DNAT 和 SNAT。客户端访问 VIP，LB 把目的改成 real server，也把源改成 LB 地址；后端回复 LB，LB 再改回客户端能理解的 VIP 和端口。它的好处是拓扑最可控，后端不需要知道客户端路由，也不需要把默认网关指回 LB 之外的复杂路径；缺点是所有请求和响应都压在 LB 上，连接状态、端口映射、带宽和 conntrack 压力都会集中到这一层。

DR 模式，也就是 LVS 里的 Direct Routing，更像只改二层下一跳，不改三层目的地址。客户端发给 VIP，LB 选中 real server 后把帧转给后端，后端本机也配置了 VIP，能直接接收这个目的 IP 仍然是 VIP 的包。响应时后端直接把源地址为 VIP 的包发回客户端，不再经过 LB。ipvsadm 手册里 `--gatewaying` 就是 direct routing，也是默认 forwarding method。

DR 的收益是回包绕过 LB，特别适合响应流量远大于请求流量的场景，比如下载、静态内容、大响应 API。代价是网络约束更强：后端要能接收 VIP，通常要处理 ARP 抑制或 lo 绑定 VIP；请求方向一般要求在同一二层或有合适的路由；端口通常不能随意改。ipvsadm 手册也提示，tunneling 和 direct routing 方法下 real server 端口必须等于 service address 的端口。

Tunnel 模式是在三层外再套一层封装。客户端发给 VIP，LB 选中后端后用 IPIP 之类隧道把原始包封装给 real server，后端解封装后看到的仍然是目的 VIP，再直接回复客户端。ipvsadm 的 `--ipip` 对应的就是 tunneling。它比 DR 更容易跨三层网络或跨机房，因为不要求后端和 LB 在同一个二层广播域；代价是后端要支持隧道解封装，MTU、路径、防火墙和隧道可观测性要额外处理。

这些模式对客户端 IP 的影响也不同。DNAT 如果不 SNAT，后端通常还能看到真实客户端 IP，但回程必须设计好。SNAT 和 Full NAT 会隐藏真实客户端 IP，后端需要靠代理协议或可信 Header 恢复。DR 和 Tunnel 一般可以保留真实客户端 IP，且回包直接走后端到客户端，但它们要求后端配置和网络路径更配合。

对观测和排障来说，Full NAT 最容易集中看日志，因为请求和响应都经过 LB；但它也最容易让 LB 成为瓶颈。DR/Tunnel 性能好，回包不经过 LB，可是 LB 只能看到请求方向或部分状态，响应侧问题要去后端和网络路径上查。DNAT/SNAT 介于中间，关键看回程是否对称、是否保留客户端 IP、conntrack 状态是否健康。

放到 AegisMesh 的语境里，这些主要属于入口或内核转发层。AegisMesh 当前更靠近客户端 RPC 负载均衡，不直接实现 LVS DR 或 Tunnel。但理解这些路径很有用，因为线上如果 AegisMesh 看到某个 endpoint 慢，慢可能来自应用，也可能来自底层 NAT、SNAT 端口池、conntrack、隧道 MTU 或非对称路由。

所以这题的记忆方式很简单：DNAT 改目的，SNAT 改来源，Full NAT 两边都改；DR 请求过 LB、响应直回；Tunnel 请求过 LB 并封装到后端、响应通常直回。它们影响的是真实客户端 IP、回程路径、LB 带宽压力、连接状态维护和排障证据。

如果面试官继续深挖，可以按这条路线走：
1. 先问每种模式到底改了源地址、目的地址，还是只改了二层/封装。
2. 再问响应路径是否必须回到负载均衡器。
3. 再问后端是否能看到真实客户端 IP，以及如果看不到要靠什么补。
4. 再问哪几种模式更容易让 LB 成为带宽或 conntrack 瓶颈。
5. 最后落回项目：AegisMesh 定位慢实例时，为什么不能忽略底层 NAT、隧道和回程路径。

## 42. 为什么 NAT 模式可能导致连接跟踪表成为瓶颈？

可以先这样答：

NAT 模式容易让连接跟踪表成为瓶颈，是因为 NAT 不是简单地把一个包改一下就结束。它必须记住“这个连接原来是什么五元组，改成了什么五元组，回包回来时应该怎么改回去”。这个映射要跨请求和响应两个方向保存，直到连接结束或超时。连接越多、连接越短、回包越多、超时越长，conntrack 压力就越大。

Linux kernel 的 nf_conntrack 文档里有几个很关键的变量。`nf_conntrack_count` 表示当前已分配的 flow entries；`nf_conntrack_max` 是允许的最大连接跟踪条目数；文档还提醒，一个连接会在表里加两次：原始方向一次，回复方向一次。也就是说，表项数量、哈希桶、链长和内存占用都不是抽象概念，它们会直接影响查找和更新成本。

第一类瓶颈是容量。连接数接近 `nf_conntrack_max` 时，新连接可能无法建立或被丢弃，表现成客户端 connect timeout、偶发 5xx、SYN 重传、UDP 丢包。很多人只盯应用 QPS，却忘了 NAT 看的是连接和 flow 生命周期。短连接高并发、无连接池、频繁重试、探针过多，都会让 conntrack 条目创建和销毁速度很高。

第二类瓶颈是内存和哈希查找。`nf_conntrack_buckets` 决定哈希表大小，bucket 太少会增加冲突和链长，查找成本上升；条目太多会带来 slab 内存、CPU cache miss 和回收压力。内核文档也提到 buckets 默认按内存计算，并且有上下限。这个参数不是越大越好，因为更大的表也会占更多内存，但太小会让高并发 NAT 的查找变重。

第三类瓶颈是超时。TCP established 默认超时可以很长，内核文档里 `nf_conntrack_tcp_timeout_established` 默认是 432000 秒，也就是 5 天。真实生产里，如果长连接、半开连接、异常关闭、客户端断网、移动网络切换没有被及时清掉，conntrack 表会保留大量已经没有业务价值的条目。UDP 也有自己的 timeout 和 stream timeout，DNS、QUIC、游戏、音视频场景都可能把 UDP flow 数量打上来。

第四类瓶颈是 SNAT 端口空间。SNAT 不只要记录映射，还要给源地址选择可用源端口。单个 SNAT IP 的端口空间有限，如果大量连接都从同一个出口 IP 打到同一个目的 IP/端口，就可能出现端口耗尽或端口复用压力。此时应用看到的是连接失败，底层原因却是 NAT 映射空间不够。

第五类瓶颈是状态同步和故障切换。高可用 NAT 或 LVS director 如果要主备切换不中断连接，就要同步连接状态；不同节点如果没有一致状态，回包到了另一台 LB，就找不到映射。IPVS 的 sysctl 文档里也能看到连接哈希表、连接同步、NAT connection 额外节点这些配置。它还明确提到，如果 IPVS 连接要被 stateful firewall rules 处理才需要维护 conntrack，否则关闭是一种性能优化。这句话很实用：不是所有路径都应该无脑打开 conntrack。

NAT 模式还会影响可观测性。后端看到的源地址可能是 LB，不是真实客户端；客户端看到的是 VIP，不是后端。排障时如果没有把 NAT 前后的五元组、conntrack entry、proxy header、LB access log 对起来，就很容易只看到“后端慢”或“客户端超时”，却看不到真正瓶颈在连接跟踪表、端口映射或非对称回程。

缓解手段要按瓶颈来源选。容量不够，就调大 `nf_conntrack_max`、合理设置 buckets、增加内存和分片；超时太长，就按协议调低不合理的 timeout；短连接太多，就用连接池和 keepalive；SNAT 端口不够，就增加出口 IP、拆分目标、减少同目的连接集中；不需要状态防火墙的高性能转发路径，可以考虑 NOTRACK、DSR/DR、Tunnel、L4 直通或更专门的数据面。不要只会一句“调大 conntrack”，那只是其中一类问题的答案。

放到 AegisMesh 上，如果底层 NAT/conntrack 已经接近满表，SDK 侧可能会看到连接建立变慢、偶发不可达、某些 endpoint 的 EWMA 变差、retry budget 被消耗。此时 adaptive P2C 可能把流量挪开，但它挪开的只是症状上的慢 endpoint；如果所有路径都经过同一个 NAT 瓶颈，单靠负载均衡算法解决不了，要回到底层连接跟踪和出口容量治理。

所以这题最稳的结论是：NAT 模式把“转发”变成了“按连接维护双向映射”。连接跟踪表既吃内存，也吃哈希查找和更新成本，还受 timeout、端口空间、状态同步和回程对称性影响。高连接数、高 churn、长 timeout 和集中 SNAT，都会把它推成瓶颈。

如果面试官继续深挖，可以按这条路线走：
1. 先问 NAT 为什么必须维护双向映射，而不是只改一次包头。
2. 再问 `nf_conntrack_count`、`nf_conntrack_max`、buckets、timeout 分别影响什么。
3. 再问高短连接、长连接、UDP/QUIC、重试洪峰为什么会以不同方式压 conntrack。
4. 再问 SNAT 端口空间和非对称回程为什么会制造看似随机的连接失败。
5. 最后落回项目：AegisMesh 看到 endpoint 变慢时，为什么要把 NAT/conntrack 这类内核层瓶颈纳入排查。

## 43. conntrack 表满了会出现什么现象？如何排查？

可以先这样答：

conntrack 表满，本质上是内核已经没有足够的连接跟踪条目来记录新的 flow。对 NAT、防火墙、Kubernetes Service、NodePort、网关、出口 SNAT 来说，这不是一个边缘问题。只要路径上依赖 netfilter state，内核就要为 TCP、UDP、ICMP 等 flow 保存状态。Linux 内核文档里 `nf_conntrack_count` 表示当前已分配的 flow entries，`nf_conntrack_max` 表示允许的最大条目数。接近或超过上限时，新 flow 可能被丢弃，已有连接也可能因为回包找不到状态而表现异常。

线上现象通常不是一个干净的错误码。客户端可能看到 connect timeout、read timeout、偶发 502/503/504、SYN 重传、TLS 握手超时、gRPC `Unavailable`、DNS 请求随机失败、UDP 丢包。服务端有时完全看不到请求，因为包还没到应用就被内核丢了；有时只能看到很少量请求到达，业务日志和客户端错误量对不上。这个特征很重要：如果应用层 QPS 没有明显上升，但连接 churn 很高，conntrack 仍然可能先被打满。

第一步看内核计数。常用命令是读 `/proc/sys/net/netfilter/nf_conntrack_count` 和 `/proc/sys/net/netfilter/nf_conntrack_max`，也可以用 `conntrack -S`、`conntrack -C` 看统计。如果 `count/max` 长时间在高水位，比如 80% 以上，且故障时接近 100%，基本就要把它纳入主嫌疑。还要看 `dmesg` 或内核日志里是否有 `nf_conntrack: table full, dropping packet` 之类的记录。很多事故里，真正的证据就在这行日志。

第二步看是什么类型的 flow 把表占满。TCP established 太多、TIME_WAIT 类状态过多、SYN_SENT/SYN_RECV 堆积、UDP flow 爆炸，含义都不一样。短连接高并发通常说明连接复用不够；大量 established 可能是长连接太多或超时太长；大量 UDP 可能来自 DNS、QUIC、音视频、游戏、探测流量；SYN 状态异常则要同时排查丢包、防火墙、后端 backlog、半开连接攻击和非对称路由。

第三步看 timeout。内核文档里 `nf_conntrack_tcp_timeout_established` 默认可以是 432000 秒，也就是 5 天。这个默认值对一些传统长连接合理，但对高 churn 服务不一定合适。UDP 也有 `nf_conntrack_udp_timeout` 和 `nf_conntrack_udp_timeout_stream`。如果大量已经没有业务意义的 flow 还被保留，单纯调大 `nf_conntrack_max` 只是把爆炸时间往后推，并没有解决生命周期问题。

第四步看 NAT 和 SNAT 端口空间。conntrack 表满经常和出口 SNAT 端口耗尽一起出现。比如大量 Pod、实例或客户端通过同一个出口 IP 访问同一个目标 IP/端口，五元组可用组合有限，连接映射会非常集中。此时增加 conntrack 上限可能缓解内存表项压力，但如果真实瓶颈是 SNAT IP 和端口池不足，仍然会失败。排查时要看源 IP、目的 IP、目的端口的集中度，而不是只看总连接数。

第五步看路径是否必须经过 conntrack。有些高性能 L4 转发路径可以绕开 stateful firewall 或关闭不必要的 conntrack，比如纯转发、DR、Tunnel、部分 IPVS 场景、XDP/eBPF 数据面。Linux IPVS 文档里也明确区分了是否需要让 IPVS 连接进入 stateful firewall rules。不是所有路径都应该默认打开 conntrack，尤其是入口大流量、UDP 大流量和内部东西向高频短连接。

缓解手段要按原因选。容量不够，可以调大 `nf_conntrack_max`、合理配置 buckets、给节点更多内存。timeout 太长，就按协议调低无意义保留时间。短连接太多，就做 keepalive、连接池、HTTP/2/gRPC 复用。SNAT 集中，就增加出口 IP、拆分 NAT 网关、让流量分散到更多节点。异常流量导致的，就要限流、丢弃、黑名单或把探测频率降下来。排查阶段不要只背一句“调大 conntrack”，面试官一般会继续问为什么满、谁占满、调大以后副作用是什么。

放到 AegisMesh 的语境里，如果底层 conntrack 已经满了，SDK 侧会看到 endpoint 变慢、连接失败、重试增加、EWMA 上升，甚至所有 endpoint 一起变差。adaptive P2C 可以把流量绕开某些变慢实例，但绕不开一个共享的 NAT/conntrack 瓶颈。遇到全局性连接失败时，要把 SDK 指标、服务端日志、节点内核计数和 NAT 网关指标放在一起对账。

所以这题的稳定回答是：conntrack 表满会表现为连接建立失败、随机超时、UDP 丢包、网关 5xx、后端无请求日志和内核 drop 日志。排查要从 `count/max`、内核日志、状态分布、timeout、SNAT 端口、热点五元组、是否必要走 conntrack 这几层查下去。真正的修复不是只有扩表，而是降低 churn、缩短无效生命周期、分散 NAT 压力或减少不必要的 stateful 路径。

如果面试官继续深挖，可以按这条路线走：1. 先解释 conntrack 为什么是双向 flow 状态，不是简单计数器。2. 再说满表后的用户态现象为什么常常是 timeout，而不是明确错误。3. 然后说如何看 `nf_conntrack_count`、`nf_conntrack_max`、内核日志和状态分布。4. 再区分表项容量、timeout、SNAT 端口、UDP flow、非对称路由这些不同原因。5. 最后落到项目：AegisMesh 看到的慢 endpoint 可能只是底层连接跟踪瓶颈的投影。

## 44. 负载均衡器如何处理 client IP 透传？X-Forwarded-For、PROXY protocol 和透明代理有什么区别？

可以先这样答：

client IP 透传要先问一个问题：后端到底需要“看到源 IP”，还是只需要“知道原始客户端是谁”。这两者不一样。看到源 IP 是网络层语义，后端 socket 上的 peer address 就是客户端地址。知道原始客户端是谁可以通过可信 Header、代理协议、metadata、mTLS 身份、JWT 或业务身份来传递。负载均衡链路越多，越不能把这两个概念混在一起。

`X-Forwarded-For` 是最常见的 HTTP 层做法。每经过一个可信 HTTP 代理，就把自己看到的上一跳地址追加到 XFF 列表里。Envoy 文档里也把 XFF 说成 proxy header，并用 `xff_num_trusted_hops` 或 trusted CIDR 来决定哪一个地址能作为 trusted client address。它的优点是简单，应用容易读取，也能和 `X-Forwarded-Proto`、`X-Forwarded-Port` 一起表达外部请求上下文。缺点同样明显：它只适用于能解析 HTTP 的代理和后端；外部客户端可以伪造这个 Header；链路上必须有清理和追加规则。

所以 XFF 的核心不是“拿最左边 IP”。正确做法是先定义可信代理边界。入口代理要清理外部传来的 XFF 或按策略追加，内部代理根据可信跳数或可信 CIDR 取地址。否则攻击者可以自己带一个 `X-Forwarded-For: 1.2.3.4`，让后端日志、限流、风控都被骗。面试里说 XFF 时，一定要补一句：只能信任来自受控代理链的值，不能信任公网客户端直接写进来的值。

PROXY protocol 是传输层前缀。HAProxy 定义它的目的，是让 L4 代理在不解析内部应用协议的情况下，把原始源地址、目的地址、端口等信息放在连接开头发给后端。它既可以服务 HTTP，也可以服务 MySQL、Redis、自定义 TCP、TLS passthrough 后面的协议。后端或下一跳代理必须显式支持 PROXY protocol，否则它会把这段前缀当成业务协议字节，连接直接乱掉。

PROXY protocol 的优势是协议无关，适合 L4 LB、NLB、TLS 透传、TCP 服务。它的风险也在边界上：只有来自可信 LB 的连接才能允许 PROXY protocol。如果后端公网可达，攻击者也能伪造 PROXY header，把自己伪装成任意源地址。因此通常要配合安全组、ACL、监听端口隔离，保证只有上游 LB 能打到这个 listener。

透明代理更接近网络层保真。Linux TPROXY 文档的思路是用策略路由和 `IP_TRANSPARENT` 让代理接收并发起非本机地址的连接，同时不依赖 NAT 改目的地址。这样后端或代理可以保留原始目的地址、源地址语义，适合需要不改包目标、拦截式代理、部分安全网关或复杂四层治理场景。它的代价是运维复杂：需要内核能力、iptables/nftables 规则、policy routing、应用 socket 选项、反向路径和安全边界配合。

三者的差异可以这样记：XFF 是 HTTP Header，语义在应用层，简单但可伪造，必须按可信代理链解析；PROXY protocol 是连接前缀，适合 L4 和非 HTTP，但要求双方都支持，并且只能信任来自 LB 的连接；透明代理是网络路径设计，尽量保留真实地址和原始目的地，但需要内核、路由和应用配合。

还要区分它们对日志、限流和鉴权的影响。XFF 通常用于应用日志、风控和 HTTP 限流；PROXY protocol 常用于让下游代理或 TCP 服务恢复真实 peer 信息；透明代理则可以让应用或代理在 socket 层看到更接近真实的地址。越往下层做，越接近网络真实语义，成本也越高。越往上层做，接入越简单，但越依赖信任边界和清洗规则。

在多层负载均衡里，常见组合是：外层 NLB 用 PROXY protocol 把源地址传给 Envoy 或 NGINX，内层 L7 代理再把可信客户端地址写入 XFF，业务服务只信任内层代理写入后的 Header。也可以选择端到端 TCP passthrough 或 TPROXY，但这通常会牺牲一部分 L7 能力。工程上没有固定答案，关键看后端需要的是审计 IP、风控 IP、网络 peer，还是用户身份。

放到 AegisMesh 上，如果未来要在 SDK、网关和服务端之间传递原始调用方信息，最好不要把 client IP 当成唯一身份。内部 RPC 更适合用 mTLS workload identity、服务名、tenant、trace context 和受控 metadata。IP 可以作为辅助排障字段，但经过 NAT、sidecar、NodePort、Ingress 之后，它经常只是上一跳代理。

所以这题的结论是：client IP 透传不是一个 Header 就能解决的事，而是一套信任边界设计。XFF 解决 HTTP 代理链里的“原始客户端地址记录”；PROXY protocol 解决 L4 转发后的“连接源地址传递”；透明代理解决“尽量不改变网络地址语义”的拦截式转发。它们能不能用，取决于协议层级、后端支持、攻击面和排障需求。

如果面试官继续深挖，可以按这条路线走：1. 先问后端要源 IP 做什么，是日志、限流、审计还是鉴权。2. 再比较 XFF、PROXY protocol、TPROXY 的层级和信任边界。3. 然后说明 XFF 为什么不能直接信最左边，PROXY protocol 为什么不能暴露给公网。4. 再讲多层代理中如何清理、追加和解析。5. 最后落到项目：AegisMesh 内部更应该传服务身份和请求上下文，而不是把 IP 当成稳定身份。
## 45. HTTP keep-alive 会如何影响后端负载分布？

可以先这样答：

HTTP keep-alive 的影响要从连接复用看。HTTP/1.1 默认支持持久连接，一条 TCP 连接可以承载多个顺序请求。这样做能减少 TCP 握手、TLS 握手、慢启动和端口消耗，对延迟和资源使用都有好处。但它会改变负载均衡的观察粒度：如果负载均衡器按连接选后端，而不是按请求选后端，那么后面的很多请求都会跟着早期那次连接选择走。

短连接场景下，每个请求或少量请求会重新建连接，L4 LB 有更多机会重新选择后端。连接数和请求数虽然不完全等价，但偏差不会太大。keep-alive 打开后，少数长寿命连接可能承载大量请求，连接数看起来很均匀，真实请求量却可能不均匀。特别是客户端连接池数量少、请求量大、连接生命周期长时，这个问题会很明显。

一个典型例子是前面有四个后端，客户端连接池只建了四条连接。L4 LB 也许刚好把四条连接分到了四个后端，看起来很公平。但如果其中一条连接来自高流量调用方，另一条连接只是低频探测，后端请求量就不公平。L4 看见的是连接，不是每条连接里的请求成本。最少连接算法也会被误导，因为它数的是连接数量，不是连接内的排队、CPU 和业务耗时。

L7 代理也会受 keep-alive 影响，但它有机会在请求级重新选择 upstream。比如入口代理和客户端之间复用下游连接，同时代理到后端维护 upstream 连接池。只要代理在每个请求到来时重新做路由和负载均衡，它就能把多个下游连接里的请求分散到不同后端。代价是代理要解析 HTTP，并维护更多请求级状态。

后端连接池会进一步放大这个差异。很多 L7 代理为了性能，会对每个 upstream host 保留 keepalive 连接。请求来了以后，不一定新建连接，而是从对应 host 的连接池里取一条。如果某些 upstream 连接池更热、某些连接池因为失败或预热不足很冷，就可能出现局部倾斜。连接池不是错，它只是把“连接建立成本”换成了“池内公平性和生命周期管理”问题。

keep-alive 还会影响扩缩容和权重调整。新实例刚加入时，如果旧连接长期不关闭，旧实例会继续承载大量既有连接上的请求，新实例只能拿到新连接或新请求。对 L4 连接级 LB 来说，新实例预热会比较慢。对 L7 请求级 LB 来说，可以更快把请求引到新实例，但也要小心冷启动，把权重慢慢拉起来。Envoy 的 slow start 就是为这类问题准备的，它会在新 endpoint 加入或恢复健康后逐步提高有效权重。

排查时不能只看 active connections。要同时看 request count、requests per connection、upstream connection reuse、每个后端的 QPS、in-flight、p95/p99、连接年龄和连接池命中率。如果只有连接指标，很容易误判成“负载均衡很均匀”。更可靠的判断是：每个后端的请求数、CPU、队列长度和尾延迟是否也均匀。

缓解方法有几类。第一类是改成请求级负载均衡，让 L7 代理或客户端 SDK 在每个请求或 RPC 前选择。第二类是控制连接生命周期，比如最大请求数、最大连接年龄、空闲超时、连接池大小，让旧连接不要无限期绑定后端。第三类是预热和权重渐进，避免新实例被突然打满，也避免旧实例长时间吃历史连接。第四类是让客户端连接池足够分散，避免少数连接代表大部分流量。

放到 AegisMesh 上，gRPC/HTTP/2 比 HTTP/1.1 keep-alive 更极端，因为它不仅复用连接，还在同一条连接上并发多个 stream。项目选择在客户端 picker 层按 RPC 做选择，就是为了避免“连接一旦建好就把后续工作量固定到某个 endpoint”。如果只在连接建立时选一次后端，fail-slow 信号来得再快，也很难及时改变已经绑定在连接上的请求分布。

所以这题的结论是：keep-alive 降低连接建立成本，但会让连接级负载均衡和请求级真实负载脱钩。它能改善延迟和资源使用，也可能制造流量倾斜、扩容不生效、权重变更滞后和慢节点粘连。回答时不要把 keep-alive 说成纯优化，它是一种用连接生命周期换性能的机制。

如果面试官继续深挖，可以按这条路线走：1. 先解释持久连接减少了握手成本。2. 再说明连接级选择为什么会把后续请求绑定到早期选择。3. 然后比较 L4 连接级和 L7 请求级的差异。4. 再说连接池、扩缩容、权重变更和慢节点如何受影响。5. 最后落到项目：AegisMesh 为什么要在 RPC 级做 picker，而不是只在连接建立时选后端。

## 46. HTTP/2 单连接多 stream 会如何破坏连接级负载均衡的公平性？

可以先这样答：

HTTP/2 的关键变化是把并发从“多条 TCP 连接”搬到“一条连接里的多个 stream”。RFC 9113 明确描述了 stream concurrency，端点可以通过 `SETTINGS_MAX_CONCURRENT_STREAMS` 限制对方同时活跃的 stream 数。也就是说，一条 TCP 连接里可以并发承载很多请求。连接级负载均衡如果只看五元组或连接数，就看不到这些 stream 后面的真实工作量。

这会直接破坏连接数公平。假设 L4 LB 把 100 条连接平均分给 10 个后端，每个后端 10 条，看起来很均匀。但其中一个后端上的连接可能来自高并发客户端，每条连接打开 100 个活跃 stream；另一个后端上的连接可能只是低频调用方，每条连接偶尔一个请求。连接数一样，活跃请求数、CPU、内存、队列和尾延迟完全不一样。

HTTP/2 还有流控和优先级问题。RFC 9113 里强调，multiplexing 会让 stream 之间竞争同一条 TCP 连接的使用，流控既有 stream 级也有 connection 级。某个大响应、慢消费者或流控窗口设置不合理，可能拖住同一条连接上的其他 stream。L4 LB 仍然只看到一条连接是活的，看不到连接内部某些 stream 已经排队或被阻塞。

连接级最少连接算法在这里尤其容易失真。它会把“当前连接数少”的后端当成轻载，但这个后端可能已经有大量 active streams。反过来，一个连接数多的后端也可能很空，因为连接大多 idle。Least connections 在 HTTP/1.1 短连接场景里还有一定直觉，在 HTTP/2/gRPC 场景里必须补上 active request、in-flight stream、EWMA latency、队列长度这类信号。

这也是为什么 gRPC 官方文档强调 load balancing policy 负责维护 subchannels，并在 RPC 发送时 pick 连接。gRPC 的 `pick_first` 只连上第一个地址，基本不做均衡；`round_robin` 会连接所有地址，并在每个 RPC 上轮转 connected backends。这个粒度比“建连接时选一次”更贴近真实负载。

HTTP/2 单连接还会让扩容变慢。如果客户端或代理已经和旧后端建立了长寿命 HTTP/2 连接，新后端加入后，不会自动接到旧连接里的 stream。除非客户端重建连接、L7 代理重新按请求选择 upstream，或控制连接年龄和 draining，否则新实例可能长时间很闲，旧实例继续承载历史连接上的大部分请求。

故障恢复也受影响。某个后端开始 fail-slow，如果连接不断，已有 HTTP/2 连接还会继续向它开新 stream。L4 层只知道连接还活着，不一定会摘除。只有请求级负载均衡、outlier detection、per-RPC deadline、stream reset、GOAWAY、连接 draining 配合起来，才能把新请求逐步迁走。

缓解方案有三种思路。第一，让负载均衡粒度上移到请求或 RPC，L7 代理、客户端 SDK 或 service mesh 根据每个请求选择。第二，给连接设置最大年龄、最大请求数、空闲超时和 GOAWAY 策略，让流量有机会重新分布。第三，收集并使用 active streams、in-flight requests、latency、error rate、backend utilization，而不是只用连接数。

对 AegisMesh 来说，这题正好打到项目核心。项目里的 adaptive P2C、inflight、EWMA、`slow_score` 都是为了让每次 RPC 选择能感知当前 endpoint 状态。如果只在 HTTP/2 连接建立时做一次选择，后续 stream 再多也不会重新决策，慢实例会被长连接粘住，负载均衡看起来“连接公平”，实际上“请求不公平”。

所以这题的结论是：HTTP/2 把多个并发请求压进同一条连接，连接数不再能代表工作量。连接级 LB 只能做到连接分布公平，不能保证 stream、请求成本、队列和尾延迟公平。要处理这个问题，就要在请求级选路、限制连接生命周期，并把 active streams 和后端实时负载纳入决策。

如果面试官继续深挖，可以按这条路线走：1. 先说 HTTP/2 stream concurrency 和 connection flow control。2. 再举连接数均匀但 stream 数不均的例子。3. 然后说明 least connections 为什么失真。4. 再讲扩容、慢节点和连接 draining。5. 最后落到项目：AegisMesh 的 per-RPC picker 为什么比 connection-level picker 更适合 gRPC。

## 47. QUIC/HTTP/3 对传统 L4/L7 负载均衡提出了什么新要求？

可以先这样答：

QUIC/HTTP/3 最大的变化是：应用层 HTTP 语义跑在 QUIC 上，而 QUIC 跑在 UDP 上，同时把 TLS 1.3、连接管理、stream 多路复用、拥塞控制和连接迁移放进传输层。RFC 9114 说明 HTTP/3 依赖 QUIC version 1 作为底层传输；RFC 9000 则说明 QUIC 是基于 UDP 的多路复用安全传输。这对传统按 TCP 连接、五元组和明文 HTTP 做事的 LB 都提出了新要求。

第一个要求是 UDP 不是“无状态就完了”。传统 L4 LB 可能把 UDP 当成短生命周期 flow，用源 IP、源端口、目的 IP、目的端口、协议做 hash。但 QUIC 有 connection ID，客户端还可能发生 NAT rebinding 和 connection migration。RFC 9000 里明确说，zero-length connection ID 在迁移、NAT rebinding、客户端端口复用存在时会失败。负载均衡器如果只看五元组，客户端网络从 Wi-Fi 切到 5G 后，五元组变了，同一个 QUIC connection 可能被打到不同后端，连接就断。

第二个要求是要理解或至少稳定转发 connection ID。QUIC 的 Destination Connection ID 可以帮助后端或 LB 在五元组变化时仍然识别连接。生产级 QUIC LB 往往需要让 connection ID 编码后端 shard、路由信息或可解码 token，或者维护 CID 到后端的映射。否则就只能靠五元组粘性，遇到迁移、NAT 重绑定、多路径和端口复用时稳定性会差。

第三个要求是 L7 可见性下降。HTTP/3 的请求头、stream、状态都在 QUIC/TLS 保护之内。传统 L7 HTTP 代理如果不终止 QUIC，就看不到 path、Header、Cookie、方法、状态码，也不能做 WAF、细粒度灰度和请求级日志。要做真正 L7，就必须终止 HTTP/3/QUIC，理解 QUIC transport、TLS 1.3、QPACK、HTTP/3 frame 和 stream 生命周期。这个成本比只解析 HTTP/1.1 明显更高。

第四个要求是 UDP 网络路径要可靠。很多企业网络、防火墙、NAT 设备、四层代理对 UDP 的超时、放行、MTU、分片、ICMP 处理都比 TCP 更粗糙。RFC 9000 还要求 QUIC 路径至少支持 1200 字节 UDP payload。HTTP/3 部署时要检查 UDP 443 是否通、PMTU 是否合适、NAT UDP timeout 是否太短、conntrack UDP 表是否足够、回程路径是否对称。否则客户端会频繁回退到 TCP 版 HTTP。

第五个要求是健康检查和观测要升级。传统 TCP health check 只能说明端口可连，不能说明 QUIC 握手、TLS ALPN、HTTP/3 SETTINGS、QPACK stream、请求 stream 都正常。L4 UDP check 更弱，可能只能看 ICMP 或自定义探测。要可靠判断 HTTP/3 后端健康，通常需要应用层探测，至少要覆盖 QUIC 握手和一个真实 HTTP/3 请求。

第六个要求是连接排空更复杂。TCP/HTTP/1.1 里可以 close 或 keepalive drain；HTTP/2 有 GOAWAY；HTTP/3 也有自己的 GOAWAY 和 QUIC connection close，但它运行在 QUIC stream 语义上。负载均衡器升级、缩容、摘除后端时，要保证不把同一个 QUIC connection 的后续包突然路由到别的后端，也要让客户端有机会建立新连接。

第七个要求是成本模型变化。HTTP/3 避免了 TCP 层队头阻塞，但不是没有队列和流控。RFC 9114 里提到 HTTP/3 使用 QUIC stream，HTTP/3 的 frame header 和 payload 都受 QUIC stream flow control 影响。LB 如果终止 QUIC，就要处理更多加密、解密、stream、QPACK 和 UDP I/O 成本；如果不终止，就失去很多 L7 能力。这个取舍比 TCP 时代更明显。

工程上常见有三种模式。第一，纯 L4 UDP 转发，依赖 connection ID 或五元组粘性，性能好但 L7 能力弱。第二，边缘终止 QUIC/HTTP/3，再转成 HTTP/2、HTTP/1.1 或 gRPC 到内部，治理能力强但成本高。第三，边缘支持 HTTP/3 接入，内部仍用成熟的 HTTP/2/gRPC/mTLS 服务网格，减少全链路 QUIC 的复杂度。

放到 AegisMesh 上，当前项目主要治理 gRPC/HTTP/2 RPC，不直接实现 QUIC LB。但思路是相通的：如果底层从 TCP 连接变成 QUIC connection 和 stream，负载均衡决策更不能只看五元组。未来如果支持 HTTP/3/gRPC over QUIC，就要把 connection ID、stream 并发、UDP conntrack、路径迁移和 per-RPC 指标一起纳入模型。

所以这题的结论是：QUIC/HTTP/3 让传统 LB 从“TCP 连接和明文 HTTP”进入“UDP、connection ID、加密传输、多 stream、连接迁移”的世界。L4 要会稳定处理 UDP 和 connection ID，L7 要么终止 QUIC 获得应用语义，要么承认自己看不到请求内容。部署时还要补健康检查、观测、draining、UDP timeout 和 MTU 这些工程细节。

如果面试官继续深挖，可以按这条路线走：1. 先说 HTTP/3 运行在 QUIC/UDP 上。2. 再解释为什么五元组粘性遇到 migration 和 NAT rebinding 会失效。3. 然后说 connection ID 对路由稳定性的作用。4. 再比较 L4 passthrough 和 L7 QUIC termination。5. 最后落到项目：AegisMesh 如果扩展到 QUIC，需要从连接级信号转向 connection ID、stream 和 per-RPC 负载信号。
## 48. gRPC 长连接如何做负载均衡？为什么只在连接建立时选择后端通常不够？

可以先这样答：

gRPC 默认跑在 HTTP/2 上，一个 channel 下面可能有一个或多个 subchannel，每个 subchannel 通常对应到某个后端地址的长连接。长连接本身不是问题，它能减少握手成本，也能复用 HTTP/2 stream。问题在于负载均衡的选择粒度：如果只在连接建立时选一个后端，后续很多 RPC 都会被这条连接绑定住，无法及时反映后端负载变化。

gRPC 官方自定义负载均衡文档说得很清楚：load balancing policy 会从 name resolver 得到服务器 IP 列表，维护到服务器的 connections，也就是 subchannels，并在 RPC 发送时 pick 一个 connection。`pick_first` 基本不做负载均衡，连上第一个可用地址后就使用它；`round_robin` 会连接所有地址，并在每个 RPC 上轮转 connected backends。这里的关键是“每个 RPC 选择”，而不是“每条连接选择一次”。

只在连接建立时选择后端，最大问题是连接生命周期和后端负载生命周期不一致。一条 gRPC 连接可能活很久，但后端状态可能几秒内变化：CPU 突增、GC pause、磁盘抖动、下游依赖变慢、限流开启、Pod 被驱逐、新实例加入。连接不重建，选择就不变。流量会继续压在已经变慢的后端上，直到连接断开或上层强行迁移。

第二个问题是连接数不能代表 RPC 数。一个客户端可能只有几条连接，但每条连接上并发很多 RPC。低频客户端和高频客户端在 L4 看起来都是一条连接，实际工作量差几个数量级。gRPC streaming 还会让情况更复杂：一个双向流可能持续很久，占用服务端内存、窗口、goroutine 或线程，但连接级算法只看到连接还活着。

第三个问题是扩容和权重变化不及时。新后端加入后，如果客户端没有建立新的 subchannel，或者 LB policy 不把新 RPC 分配给它，新后端就吃不到流量。权重降低也一样，如果已有连接继续承载大量 RPC，旧权重的影响会拖很久。真正的动态权重要作用在 RPC pick 阶段，并配合连接池、健康状态和 picker rebuild。

第四个问题是重试和 deadline。gRPC 调用通常有 per-RPC deadline、retry、hedging、metadata 和 status。只在连接建立时选后端，会让重试也可能打回同一类坏路径，除非 LB policy 能在每次 attempt 时重新选择，并避开上一次失败的 subchannel。AegisMesh 的 retry budget 和 adaptive picker 就是为了控制这类放大。

好的 gRPC 负载均衡通常分几层。name resolver 负责发现地址；LB policy 维护 subchannel 状态；picker 在每个 RPC 或每次 attempt 前选择；health checking 和 backend metrics 提供可用性、延迟、in-flight、CPU、错误率等信号；控制面可以通过 service config 或 xDS 下发策略。真正的公平性来自这些层合在一起，而不是来自某条 TCP 连接。

算法上，简单场景可以用 round_robin。异构实例、慢节点、fail-slow 场景要用 P2C、least request、EWMA、weighted round robin、ORCA/backend metrics 或自定义成本函数。gRPC 官方文档也提到 backend metrics 可以来自响应内或独立 RPC，标准指标可以包括 CPU、内存，也可以有自定义指标。也就是说，gRPC LB 本来就不该只盯连接。

长 streaming RPC 要单独处理。普通 unary RPC 可以每次 pick；长流一旦建立，中途迁移成本很高。对于长流，可以在建立前按更严格的容量信号选后端，限制每个后端的 active streams，设置最大流生命周期，支持服务端优雅 GOAWAY 或应用层重连。不要用同一套短 RPC 算法粗暴处理所有流式场景。

放到 AegisMesh 上，项目当前的 gRPC 客户端侧 adaptive P2C 比传统 L4 LB 更适合这个问题。它能在 RPC pick 时看本地 inflight、EWMA、控制面 `slow_score` 和 breaker 状态。只在连接建立时选择后端，会把这些信号全部降级成连接生命周期外的旁观指标，无法及时改变新 RPC 的去向。

所以这题的结论是：gRPC 长连接负载均衡要在 subchannel 和 RPC pick 层做，而不是只在 TCP 连接建立时做。连接复用负责降低成本，picker 负责每次调用的分配，健康检查和后端指标负责修正实时状态。只做 connection-time selection，会在慢节点、扩容、权重调整、重试和流式 RPC 场景里失效。

如果面试官继续深挖，可以按这条路线走：1. 先解释 gRPC channel、subchannel 和 HTTP/2 stream。2. 再引用 gRPC policy 在 RPC 发送时 pick connection 的模型。3. 然后说 `pick_first`、`round_robin`、自定义 policy 的差异。4. 再讲长连接为什么让连接数和请求量脱钩。5. 最后落到项目：AegisMesh 为什么要 per-RPC adaptive picker、retry budget 和 slow score。

## 49. 服务实例权重动态变化时，负载均衡器如何避免瞬时流量抖动？

可以先这样答：

服务实例权重动态变化时，最怕的是把“控制面的一次配置变化”直接变成“数据面的一次流量跳变”。比如一个实例权重从 0 调到 100，如果 LB 立刻按完整权重打过去，冷实例可能还没完成 JIT、缓存、连接池、线程池、热点数据加载，就被真实流量压垮。反过来，把一个实例权重突然降到 0，也可能让剩余实例瞬间承接过多请求，造成级联抖动。

第一个手段是权重渐进，也就是 ramp up/ramp down。Envoy slow start 文档说明，新加入或恢复健康的 upstream endpoint 可以在 slow start window 内逐步提高有效权重，而不是立即按完整权重接流量。这个机制本质上是把控制面权重和数据面有效权重分开：配置权重可以先到位，但数据面用时间函数、最小权重、aggression 参数慢慢放量。

第二个手段是平滑调度。普通 weighted round robin 如果实现粗糙，可能出现短时间批量请求集中到高权重实例。更稳的做法是 smooth weighted round robin、EDF、P2C with weight、weighted least request，或者在 pick 时把权重和 active requests 一起算。Envoy 的 weighted least request 会用 `load_balancing_weight / (active_requests + 1)^active_request_bias` 这类有效权重，避免只看静态权重。

第三个手段是抖动和错峰。很多实例同时恢复健康、同时更新权重、同时重新计算 minRTT，都会制造同步振荡。Envoy adaptive concurrency 文档里提到 minRTT recalculation 可以加 jitter，目的就是避免所有 host 同时进入低并发测量窗口。类似地，权重更新、探测、连接重建、预热窗口都可以加随机抖动，减少同频振荡。

第四个手段是滞后和冷却时间。健康检查刚成功，不代表实例立刻能承载满流量；短时间错误率升高，也不一定要马上把权重打到 0。生产系统通常会设置连续成功次数、连续失败次数、最短停留时间、cooldown、outlier ejection base time、恢复观察窗口。这样做会牺牲一点反应速度，但能减少“刚上来又下去、刚下去又上来”的抖动。

第五个手段是把权重变化和连接生命周期一起处理。对 HTTP/1.1 keepalive、HTTP/2/gRPC 长连接来说，权重变化不会自动影响已经绑定的连接或 stream。需要配合连接 draining、最大连接年龄、最大请求数、GOAWAY、连接池重平衡，让新权重能逐步影响新请求，同时不粗暴断掉已有请求。

第六个手段是按容量来源拆分权重。人工配置权重、实例规格权重、实时健康权重、慢故障权重、租户配额权重，不应简单相乘后立即生效。更稳的方式是分别设置上下限、变化速率和优先级。比如实例规格权重变化很慢，健康权重变化较快但有冷却，慢故障分数可以快速降权但恢复要慢，租户配额要有硬隔离。

第七个手段是闭环观测。每次权重变化后，要观察 per-endpoint QPS、in-flight、latency、error rate、shed count、retry count、connection count 和 CPU。没有观测的动态权重很容易变成黑箱控制器。出现振荡时，要能回答：是权重计算太敏感，还是反馈延迟太大，还是实例容量估计错了，还是重试把流量放大了。

算法上可以设置每个周期最大变化幅度，比如权重每 5 秒最多变化 10%；也可以做指数平滑，`effective_weight = alpha * target + (1-alpha) * old`；还可以做 token bucket 式放量，先允许少量真实请求通过，根据结果再提高。关键是不要让瞬时指标直接控制瞬时流量，否则延迟本身会制造反馈振荡。

放到 AegisMesh 上，`slow_score`、EWMA、inflight、breaker 都可以视为动态权重或动态成本的一部分。项目里更稳的做法是：降权可以相对快，恢复要慢；新实例要预热；策略下发要有版本和生效窗口；picker 不能因为一次指标抖动就把流量在 endpoints 之间来回甩。否则 adaptive 算法会变成抖动放大器。

所以这题的结论是：动态权重不能直接等于瞬时流量比例。要用 slow start、平滑权重、变化速率限制、jitter、冷却时间、连接 draining、反馈观测和分层权重模型，把控制面变化变成数据面的渐进变化。负载均衡系统追求的是稳定收敛，不是每个瞬间都追最新指标。

如果面试官继续深挖，可以按这条路线走：1. 先说明权重跳变为什么会导致冷启动和级联抖动。2. 再讲 slow start 和有效权重。3. 然后讲 weighted least request、active request bias 和平滑调度。4. 再讲 jitter、cooldown、连接 draining。5. 最后落到项目：AegisMesh 的慢分数和 EWMA 应该快降慢升，避免把 fail-slow 治理做成振荡器。

## 50. 为什么负载均衡要和排队论一起理解？Little's Law 能解释哪些现象？

可以先这样答：

负载均衡不是简单地把请求平均分给机器。它真正处理的是一个排队系统：请求到达、等待、被服务、离开。后端实例不是只有“可用/不可用”两种状态，它还有服务时间、队列长度、并发上限、CPU 饱和、下游依赖等待、GC pause 和锁竞争。只看请求数量，不看队列，就会把很多尾延迟问题误判成算法问题。

Little's Law 最常用的形式是 `L = lambda * W`。`L` 是系统里的平均请求数，可以理解为在排队和正在服务的请求总量；`lambda` 是有效到达率或吞吐；`W` 是请求在系统里停留的平均时间。它不告诉你每个请求的分布细节，但能建立一个非常有用的直觉：吞吐不变时，系统内请求数越多，平均停留时间越长；停留时间变长时，如果到达率不降，in-flight 就会涨。

这个公式能解释为什么慢节点会吸流量。假设某个后端服务时间变长，单位时间完成的请求变少，但负载均衡器仍按轮询给它发请求。它的 `W` 变大，`L` 就会上升，也就是 in-flight 和队列堆起来。等到你在指标里看到 active requests 很高时，请求已经在里面等了一段时间。最少连接或 P2C 这类算法，本质上就是试图用 `L` 这个信号避开队列更长的实例。

它也能解释为什么接近饱和时 p99 会突然变坏。当到达率接近服务率，系统几乎没有空闲时间吸收波动。哪怕平均 QPS 没超过容量，短时间 burst、服务时间方差、GC 抖动、下游慢调用都会让队列堆积。队列一旦堆起来，请求等待时间进入 `W`，尾延迟就会被放大。用户感受到的不是 CPU 80% 还是 90%，而是排队时间突然变长。

它还能解释为什么重试会制造雪崩。原本下游已经慢了，`W` 上升、`L` 增加；调用方超时后重试，相当于提高到达率 `lambda`。如果重试没有预算和退避，更多请求进入同一个排队系统，`L` 继续涨，`W` 更长，更多请求超时，再触发更多重试。这就是 retry storm 的排队论版本。

Little's Law 也能帮助估算并发上限。假设某个服务稳定处理 1000 RPS，平均响应时间 50ms，那么系统内平均 in-flight 大约是 50。如果 p99 拉到 500ms，且流量仍然是 1000 RPS，那么光从量级上看，系统内请求数就可能涨到几百。这个估算可以反过来指导 breaker、bulkhead、连接池、队列长度和本地限流设置。

负载均衡算法必须理解“请求成本不同”。一个 `/healthz` 和一个复杂查询都算 1 个请求，但服务时间可能差 100 倍。排队论提醒我们，真正影响队列的是服务时间和资源占用，不只是请求计数。因此按 in-flight、latency、CPU、token cost、请求体大小、方法权重做负载均衡，往往比单纯 round_robin 更接近真实系统。

它还解释了为什么限流和负载均衡必须配合。负载均衡解决“把请求发给谁”，限流解决“要不要让请求进入系统”。如果总到达率已经超过总服务率，再聪明的 LB 也只是把队列从一个实例搬到另一个实例。此时必须做 admission control、load shedding、降级或排队上限，主动降低有效 `lambda`，否则 `W` 会继续增长。

排查时可以用这个框架看指标：arrival rate 是多少，completion rate 是多少，in-flight 是否上涨，queue length 是否上涨，latency 是服务时间上涨还是等待时间上涨，retry 是否增加。只看 CPU 很危险，因为很多队列不是 CPU 队列，可能是连接池、线程池、锁、数据库、下游服务、内核 socket buffer 或代理 upstream connection pool。

放到 AegisMesh 上，adaptive P2C 使用 inflight 和 EWMA，就是把排队论信号放进 picker。`inflight` 近似反映 `L`，EWMA latency 近似反映 `W` 的变化，retry budget 控制额外到达率，breaker 控制局部队列上限。项目的价值不是发明一个神秘算法，而是把“慢节点会积队列”这个基本事实工程化到客户端选择里。

所以这题的结论是：负载均衡如果不理解排队，就会误以为平均分配请求就等于平均分配压力。Little's Law 解释了 in-flight、响应时间、吞吐之间的关系，也解释了慢节点积压、尾延迟突增、重试雪崩、并发上限和限流必要性。面试时把公式背出来不够，要能把它落到指标和故障现象上。

如果面试官继续深挖，可以按这条路线走：1. 先把负载均衡描述成到达、排队、服务、离开的系统。2. 再解释 `L = lambda * W` 的工程含义。3. 然后用慢节点、重试、p99、in-flight 估算举例。4. 再说明为什么总过载时 LB 不如 admission control 重要。5. 最后落到项目：AegisMesh 的 inflight、EWMA、breaker、retry budget 分别对应哪些排队信号。
## 51. 如何设计一个支持多租户隔离的负载均衡策略？

可以先这样答：

多租户隔离的负载均衡，不是简单地在请求里多读一个 `tenant_id`。它要保证一个租户的流量、错误、重试、慢查询、热点 key、配额耗尽，不会把其他租户拖垮。设计时要先区分目标：是公平共享、硬隔离、按套餐配额、按租户优先级，还是故障时优先保护高等级租户。目标不同，策略完全不同。

第一层是租户识别。tenant 不能只来自公网可伪造 Header。入口层要通过认证后的 JWT、mTLS 身份、API key、session、网关鉴权结果或内部可信 metadata 得到租户身份，然后清理外部传入的同名 Header。否则攻击者可以伪造租户，把流量打到别人的配额池或高优先级队列里。

第二层是容量切分。最硬的方式是独立集群、独立 node pool、独立 shard、独立连接池、独立队列。这样隔离强，但成本高，利用率低。更常见的是共享集群内做逻辑隔离：每个租户有独立 rate limit、concurrency limit、retry budget、circuit breaker、queue limit 和指标维度。Kubernetes ResourceQuota 是资源配额层面的例子，Envoy 的 rate limit、local rate limit、circuit breaking 则是流量和运行时资源限制的例子。

第三层是调度权重。租户可以有基础权重，比如免费、标准、企业版；也可以有动态权重，比如当前是否超过配额、错误率是否异常、是否处在活动峰值窗口。调度器不能只按租户请求数分配，还要按租户消耗的资源分配。一个租户每秒 100 个大查询，可能比另一个租户每秒 1000 个轻查询更贵。

第四层是队列隔离。不要让所有租户共用一个无界队列。可以做 per-tenant queue、weighted fair queue、priority queue、deficit round robin 或 token bucket。关键是某个租户队列满了，只丢或延迟这个租户的请求，不要把共享 worker、连接池、内存 buffer 全部占住。队列隔离比事后熔断更早，能在系统还没完全坏掉前挡住噪声租户。

第五层是后端选择隔离。某些租户可以绑定到专用 pool 或 shard，某些租户走共享 pool。共享 pool 里也可以做 tenant-aware P2C：先在租户可用的 endpoint 集合里选，再按 endpoint 的 inflight、EWMA、错误率、租户当前占用做成本计算。这样既不会让租户越权访问不该访问的 pool，也能避免一个租户把同一批后端打热。

第六层是重试隔离。重试必须按租户计入预算。否则一个租户下游失败，会通过重试把共享系统的到达率放大，影响其他租户。比较稳的做法是每个租户有独立 retry budget、hedging budget 和失败退避策略；高优先级租户可以有更高预算，但也不能无限重试。

第七层是观测隔离。至少要有 per-tenant request rate、error rate、latency、in-flight、queue length、shed count、retry count、quota usage、top API、top caller。没有这些指标，就无法证明隔离生效。注意 label cardinality，租户数很多时不能把所有租户都无脑打成高基数 Prometheus label，可以对大租户单独标注，小租户聚合或采样。

第八层是故障策略。某个租户超配额，返回 429；某个租户持续打爆后端，降级或排队；某个共享依赖过载，低优先级租户先 shed；某个租户专用 shard 故障，只影响该租户或该租户组。多租户策略必须把“谁被影响”写清楚，否则隔离只是配置项，不是系统性质。

放到 AegisMesh 上，可以设计成 policy 里带 tenant 维度：每个 tenant 有 endpoint subset、权重、并发上限、retry budget、慢分数阈值和降级策略。SDK picker 在每次 RPC 前根据 metadata 识别租户，再在该租户允许的 endpoint 集合内做 adaptive P2C。服务端和控制面则持续回传 per-tenant 成本和错误信号。这样隔离发生在调用前，而不是等到共享后端已经被打爆。

所以这题的结论是：多租户负载均衡要同时做身份可信、容量切分、队列隔离、配额限流、租户级重试预算、租户感知后端选择和可观测性。只按 `tenant_id` hash 到后端不够，只按全局 QPS 限流也不够。真正的目标是一个租户出问题时，影响范围能被关在它自己的预算和队列里。

如果面试官继续深挖，可以按这条路线走：1. 先问隔离目标是硬隔离还是公平共享。2. 再讲租户身份必须来自可信认证结果。3. 然后讲 per-tenant quota、queue、breaker、retry budget。4. 再讲共享池和专用池如何选择。5. 最后落到项目：AegisMesh policy 可以把 tenant 维度放进 picker、breaker 和 telemetry。

## 52. 如何设计一个按请求成本而不是请求数量分配流量的算法？

可以先这样答：

按请求数量分配流量的隐含假设是：每个请求成本差不多。真实系统里这个假设经常不成立。一个健康检查、一个缓存命中查询、一个跨库聚合、一个大文件上传、一个长流式 RPC、一个会触发下游 fan-out 的请求，成本完全不同。如果 LB 仍然把它们都当成 1，低成本请求多的实例看起来很忙，高成本请求少的实例反而可能被压垮。

第一步是定义成本。成本可以来自静态规则，也可以来自动态观测。静态规则包括 API method 权重、请求体大小、租户等级、是否写请求、是否需要强一致、fan-out 估计、历史平均耗时。动态观测包括 CPU time、wall time、内存分配、下游调用次数、DB rows scanned、response size、in-flight duration、错误率和队列时间。不要一开始就追求完美成本模型，先选 2 到 4 个最稳定、最难伪造、和瓶颈最相关的信号。

第二步是把成本转成 token 或 work units。比如轻请求 cost=1，普通查询 cost=5，复杂报表 cost=50，流式 RPC 按持续时间持续扣 token。每个 endpoint 有一个 capacity budget，调度时看的是已占用成本，而不是已占用请求数。这样一个高成本请求会占更多额度，防止算法继续往同一个实例塞重活。

第三步是在线估计请求成本。请求到来时只能知道预测成本，完成后才知道真实成本。因此需要一个预测模型和一个校正模型。预测可以按 method、tenant、payload size、历史 EWMA 估算；完成后用真实 latency、CPU、bytes、downstream calls 更新该类别的成本。成本估计要平滑，不能因为一次离群请求把整个类别权重打坏。

第四步是设计 pick 函数。一个简单可用的形式是 `score = endpoint_load / endpoint_capacity + predicted_cost_penalty + latency_penalty + error_penalty`，然后用 P2C 抽两个候选，选 score 低的。`endpoint_load` 不再是请求数，而是当前 outstanding cost。`capacity` 可以来自实例规格、历史吞吐、控制面权重或后端上报。这样算法的复杂度仍然低，但比按请求数公平更接近按工作量公平。

第五步是完成后释放成本。普通 unary 请求完成就释放 predicted cost，并用真实成本修正模型。长流请求不能只在开始时扣一次，否则长流会被低估；可以按时间片扣 token，或者根据 active stream duration、发送字节、接收字节持续计费。上传下载类请求也要考虑 bytes，而不是只看 request count。

第六步是防止客户端伪造和策略逃逸。如果成本来自 Header，比如客户端声明 `x-request-cost`，只能作为提示，不能直接信任。可信成本要来自网关分类、服务端历史、控制面配置或后端上报。否则调用方会把自己所有请求都标成 cost=1。对租户计费、限流和负载均衡共用成本模型时，这一点尤其重要。

第七步是处理未知请求和冷启动。新 API 没有历史成本时，可以给保守默认值；新实例没有历史容量时，要 slow start；某个类别成本方差很大时，要按高分位数估计，而不是平均值。成本算法如果太乐观，会把重请求集中到看起来空的实例；如果太悲观，会降低利用率。上线时一般先 shadow 计算成本，不直接影响路由，再逐步放量。

第八步是和队列、限流配合。按成本分配只能决定发给谁，不能让总成本超过总容量。如果所有 endpoint 的 outstanding cost 都高，调度器应该触发 admission control、排队上限、租户限流或降级，而不是继续找一个“相对最不坏”的实例硬塞。成本模型要能给限流器提供同一套 work units，这样入口控制和后端选择才一致。

Envoy 的一些机制可以作为参考。weighted least request 会把权重和 active requests 结合起来；client-side weighted round robin 可以使用 ORCA 负载报告，把 QPS、EPS、utilization 纳入权重。它们不等于完整的请求成本模型，但方向一致：不要只按请求个数看负载，要让后端实时负载和利用率参与决策。

放到 AegisMesh 上，可以这样落地：在 policy 中给 gRPC method 配基础 cost；SDK picker 维护 per-endpoint outstanding cost，而不是只有 inflight count；Done 回调里根据 latency、status、response size 或服务端 trailer 上报的 cost 更新 EWMA；控制面把慢分数、实例容量和租户权重一起下发。这样 AegisMesh 的 P2C 就从“两个 endpoint 谁 in-flight 少”升级成“两个 endpoint 谁剩余成本容量更高”。

所以这题的结论是：按请求成本分配流量，要先定义成本单位，再用预测成本做 pick，用完成后的真实成本修正模型，用 outstanding cost 表示当前负载，并和容量、限流、租户、慢故障信号一起工作。它的难点不在公式，而在成本信号是否可信、是否稳定、是否能解释真实瓶颈。

如果面试官继续深挖，可以按这条路线走：1. 先说明 request count 为什么不等于 work。2. 再定义成本来源：method、payload、历史耗时、CPU、下游 fan-out、bytes。3. 然后讲 predicted cost、actual cost 和 EWMA 校正。4. 再讲 P2C score 如何从 inflight 扩展到 outstanding cost。5. 最后落到项目：AegisMesh 可以把 per-RPC cost 接进 picker、retry budget 和 telemetry。
## 53. 如何避免新实例刚上线时被瞬间打满？

可以先这样答：
新实例刚上线被瞬间打满，本质上是“服务发现已经把它暴露出去了，但它的真实可服务能力还没有达到稳定态”。这类问题很常见：Pod 已经 Ready，连接已经能建，健康检查也通过了，但进程里的缓存、JIT、连接池、线程池、数据库连接、TLS 会话、热点对象、限流桶、CPU 调度状态、GC 形态都还没有稳定。负载均衡器如果立刻按正常权重分配流量，新实例会在最脆弱的时候承担和老实例一样的压力，结果就是刚上线就超时、熔断、被踢出，再重新加入，形成抖动。

第一层要先把“启动成功”和“可以接真实流量”拆开。Kubernetes 里 `startupProbe`、`readinessProbe`、`livenessProbe` 的语义不同：启动探针适合保护慢启动进程，避免 liveness 过早杀掉它；readiness 才是决定这个 Pod 是否进入 Service endpoints 的信号。比较稳的做法是：进程初始化完成不等于 Ready，至少要等关键依赖可达、基础缓存加载、连接池有最低水位、核心接口的轻量自检通过，再让 readiness 放行。这样可以减少“容器启动了，但业务还没热”的窗口。

第二层是在负载均衡器里做 slow start，也就是新 endpoint 进入可选集合后，不直接给满权重，而是在一个窗口内逐步提升有效权重。Envoy 的 slow start mode 就是这个思路：在 slow start window 内根据端点加入集群后的时间计算有效权重，配合最小权重、增长曲线和负载均衡算法，把新端点从小流量逐步推到正常流量。这里要注意，slow start 不是健康检查的替代品，它只能降低流量爬升速度，不能证明实例真的可服务。

第三层是用请求级或连接级的“暖身预算”。对于 HTTP/1.1 短连接或普通 HTTP 请求，按有效权重少分一点请求就有效；但对 HTTP/2、gRPC、长连接来说，只在连接建立时选一次后端不够，因为一条连接可能承载大量 stream 或 RPC。更合理的是每个 RPC 或每个 stream 都看到新实例的 warmup 权重，或者至少让连接池、客户端侧 picker、服务网格在子流量层面感知 endpoint 的年龄和当前负载。

第四层要保护并发，而不只是保护 QPS。新实例最怕的是瞬间 in-flight 堆高，因为缓存 miss、连接建立和依赖预热会让每个请求更慢，慢又会带来更多并发占用。可以给新实例设置较小的初始并发上限，比如只允许正常容量的 5% 到 20%，根据成功率、延迟和错误率逐步放大。这个上限最好和实际反馈挂钩：连续成功、延迟接近集群均值、没有大量 5xx 或超时，才继续升；一旦失败，快速降权，恢复时再慢慢升。

第五层要处理连接池和客户端重连。发布、扩容、滚动重启、网关重载时，大量客户端可能同时发现新地址或同时重建连接。如果所有客户端都在同一秒刷新服务发现、同一秒重连、同一秒把新实例纳入候选集合，就会把“新实例打满”放大成“全局重连风暴”。因此客户端侧服务发现刷新、连接重建、max connection age、HTTP/2 GOAWAY、draining、重试退避都应该加 jitter，让流量自然摊开。

第六层是预热业务路径，但不要把预热伪装成真实容量。可以在实例 Ready 前做缓存加载、模型加载、配置拉取、连接池预建、核心 SQL prepare、热点 key 预取，也可以用少量内部探针走关键路径。边界是：预热流量不能把下游打爆，也不能因为几次 synthetic request 成功就宣布实例能吃满生产流量。预热只能降低冷启动成本，最终是否放量仍然要看生产流量下的延迟、错误率和并发。

第七层是把发布系统和负载均衡系统连起来。很多事故不是单个实例冷，而是一次发布里同时出现太多新实例。滚动发布要限制 `maxSurge`、`maxUnavailable`，扩容要限制每轮加入的 endpoint 数，服务网格或 SDK 要能识别“新加入实例”并自动降权。容量紧张时，不能一边旧实例在 drain，一边新实例还没热，就把两边都推到极限。

第八层是监控要按实例年龄看。只看全局 p99 或平均错误率，容易把新实例的问题藏在集群均值里。更有用的是按 endpoint age 分桶：0 到 30 秒、30 到 120 秒、2 到 5 分钟、稳定态，分别看 QPS、in-flight、p95/p99、5xx、连接数、重试数、被熔断次数。如果新实例只在前两分钟表现差，说明 warmup 策略有价值；如果稳定后也差，可能是镜像、配置、资源规格或依赖本身有问题。

放到 AegisMesh 上，可以把新实例的状态下发成策略字段，例如 `warmup_until`、初始权重、最大并发、慢启动窗口和降权恢复曲线。SDK picker 在做 P2C 或加权选择时，把 endpoint 的年龄、成功率、EWMA 延迟、in-flight 和熔断状态一起算进去。这样新实例不是一上线就和老实例平权，而是通过“时间增长 + 成功反馈”逐步获得流量。这里的核心不是让新实例永远少吃流量，而是让它用可控的小流量证明自己已经进入稳定态。

所以这题的结论是：避免新实例刚上线被打满，要同时做 readiness 分层、慢启动权重、并发上限、连接重建抖动、业务预热、发布节奏控制和按实例年龄观测。只靠健康检查不够，只靠扩容也不够；真正稳的做法是让新实例先小流量进入系统，用真实反馈逐步增加权重，失败时快速保护，恢复时慢慢放量。

如果面试官继续深挖，可以按这条路线走：先解释 Ready 不等于 warm，再讲 Kubernetes readiness/startupProbe 的边界，再讲 Envoy slow start 的权重爬升，再补充 HTTP/2/gRPC 长连接下要做请求级感知，最后落到项目里说明 AegisMesh 可以把 endpoint age、warmup 权重和并发预算放进 picker。

## 54. 如何让负载均衡策略对突发流量更稳健？

可以先这样答：
突发流量下，负载均衡最容易犯的错误是把系统当成平稳流量来调度。真实突发可能来自秒杀、缓存同时失效、定时任务、客户端批量重连、发布后的连接迁移、重试风暴、上游超时设置过短，或者某个热点租户突然放量。此时问题不是“平均 QPS 能不能承受”，而是短时间到达率、队列长度、in-flight、下游 fan-out 和重试放大是否会一起失控。

第一步是做 admission control，不要让所有请求无条件进入后端。负载均衡决定请求发给谁，准入控制决定请求该不该进系统。突发到来时，如果总到达率已经超过总服务率，继续把请求均匀分给所有实例，只会让所有实例一起排队。更稳的做法是在入口、租户、方法、调用方几个维度设置 token bucket、concurrency limit、队列上限和超时预算，超过预算时尽早返回 429、503 或降级结果。

第二步是用自适应并发，而不是只看静态权重。静态权重只能表达“正常情况下谁更强”，但突发时某个实例可能因为 GC、下游慢、局部热点、连接池耗尽而突然变慢。Envoy 的 adaptive concurrency filter 通过采样延迟、估计 minRTT 和调整 outstanding request limit 来控制并发，本质上就是让系统根据延迟反馈收缩或放开入口。AegisMesh 这类 SDK 负载均衡也可以用类似思想，把 EWMA latency、in-flight、错误率纳入 pick score。

第三步是限制队列，而不是让队列无限吸收突发。队列可以削峰，但无限队列会把过载伪装成“还在处理中”，最后表现为 p99 爆炸和大面积超时。比较稳的队列策略是：每个实例、每个租户、每个优先级都有有界队列；请求带 deadline；排队超过剩余预算就直接失败；低优先级请求先被 shed；关键路径请求保留少量独立容量。这样突发来了以后，系统退化得可控，而不是所有请求一起变慢。

第四步是控制重试。突发流量经常和重试风暴连在一起：后端变慢，调用方超时，调用方重试，到达率进一步上升，后端更慢。Google SRE 文档反复强调 retry budget 的原因就在这里。重试要有全局预算、每调用方预算、指数退避、jitter、幂等判断和超时继承。一次请求已经在上游等了很久，下游重试不应该重新拿一份完整超时预算；否则系统会把一个真实请求放大成多个并发请求。

第五步是让所有周期性行为带随机性。很多突发不是业务自然产生的，而是系统自己同步出来的，比如客户端同一时间刷新 DNS、同一时间拉配置、同一时间重建连接、同一时间执行 cron、同一时间探活、同一时间做 minRTT 测量。对这些动作加 jitter，可以把尖峰变成斜坡。Envoy adaptive concurrency 的文档里也提到 minRTT 采样要避免所有 host 同时测量，这就是同一个原则。

第六步是让负载均衡状态变化有阻尼。突发期间，如果算法对短期指标过度敏感，可能出现“所有流量追逐看起来最空的实例”的摆动。比如某个实例刚好延迟低一点，瞬间被大量请求选中，随后变慢，又被所有客户端抛弃，流量再冲向下一个实例。可以用 EWMA、最小样本数、权重变化斜率限制、冷却时间、随机化候选集、P2C 而不是全局最小值，降低这种同步振荡。

第七步是准备过载模式。Envoy overload manager 可以基于资源压力触发动作，例如停止接收新连接、缩短空闲连接、禁用 keep-alive 或重置部分流。业务系统也应该有自己的过载策略：低优先级功能降级，非关键查询走缓存或返回旧值，批量任务暂停，报表类接口排队或拒绝，写请求保护核心链路。突发稳健性不是永远不失败，而是失败时先保护核心容量。

第八步是区分“扩容能解决”和“扩容来不及解决”。Kubernetes HPA 会周期性读取指标并调整副本数，但从指标采集、控制器决策、调度、拉镜像、启动、预热到真正接流量，中间有明显滞后。对可预测的突发，比如活动、批处理窗口、考试报名、定时推送，应该提前扩容和预热；对不可预测突发，则依赖入口限流、队列上限、降级和负载均衡的快速避让。不能把 HPA 当成毫秒级过载保护。

第九步是监控要能解释突发过程。只看平均 QPS 没用，要看 peak RPS、token 耗尽次数、shed rate、队列长度、in-flight、连接数、重试数、超时来源、各优先级成功率、各租户消耗、实例间负载方差、HPA scale-up latency。突发事故复盘时，要能回答：第一批请求在哪里排队，什么时候开始重试，哪个保护动作先触发，是否有某个实例或租户被流量集中打穿。

放到 AegisMesh 上，可以把策略做成组合拳：客户端侧 P2C 用 in-flight 和 EWMA 避开局部慢实例；每个 endpoint 有 breaker 和最大 outstanding cost；每个调用方有 retry budget 和 jittered backoff；控制面下发租户、方法、优先级的限流和降级策略；服务端上报延迟、错误、shed、队列等反馈。这样突发到来时，系统不是只靠“选一个更空的后端”，而是先控制进入系统的流量，再把可接受的流量分配到当前最能处理的位置。

所以这题的结论是：对突发流量稳健的负载均衡，不是单个算法，而是一组机制，包括准入控制、自适应并发、有界队列、重试预算、随机化、状态阻尼、过载降级、预扩容和可观测性。负载均衡器要避免把突发均匀扩散成全局故障，也要避免所有客户端同步追逐同一个“看起来最好”的实例。

如果面试官继续深挖，可以按这条路线走：先说明突发会把排队、重试和下游 fan-out 放大；再讲 admission control 和 bounded queue；再讲 adaptive concurrency、EWMA 和 P2C 如何减少局部拥塞；然后讲 retry budget 和 jitter；最后落到项目里说明 AegisMesh 怎么把 picker、breaker、retry budget 和策略下发结合起来。

## 55. 为什么负载均衡不能代替容量规划？

可以先这样答：
负载均衡解决的是“已有容量如何分配”，容量规划解决的是“总容量是否足够、容量在哪里、什么时候需要、失效时还剩多少”。这两个问题不能互相替代。如果集群总服务率小于总到达率，负载均衡器再聪明，也只能把队列从一个实例挪到另一个实例，不能凭空创造 CPU、内存、IO、网络、数据库连接、下游配额和人工设置的限流额度。

从排队论看也很直观。假设总到达率 `lambda` 接近或超过总服务率 `mu`，排队等待时间会急剧上升；超过服务率后，队列会持续增长，直到超时、拒绝、崩溃或人为限流发生。负载均衡能做的是让不同实例的负载更均匀，减少某些实例提前排队；但当所有实例都接近饱和时，均衡本身不能降低总排队时间。此时必须增加容量、降低请求成本、减少到达率、削峰、降级或拒绝部分请求。

容量规划也不能只看 QPS。Google SRE 的过载处理材料里提到，QPS 不是容量的好抽象，因为请求成本差异很大。一个健康检查、一个缓存命中查询、一个复杂报表、一个需要下游 fan-out 的写请求、一个大响应下载，对 CPU、内存、锁、连接池、数据库、网络的占用完全不同。容量规划必须按请求类型、租户、payload、下游调用、峰值分布和尾延迟目标来估算，而不是只问“每秒能抗多少请求”。

负载均衡还会掩盖容量不足。系统刚开始容量不够时，LB 可能把热点从一个实例摊到多个实例，让平均延迟暂时好看；但这不代表容量充足，只是瓶颈被平铺了。随着流量继续上升，所有实例都会进入高利用率区间，p99 先变差，重试开始增加，熔断开始触发，健康检查开始抖动，最后可用实例变少，剩余实例更忙。没有容量规划，LB 会让故障从“一个点过热”演化成“全体慢性过载”。

容量规划要覆盖失效场景，而不只是正常场景。比如正常情况下 10 个实例够用，不代表一个可用区故障、一个机房断网、一个下游限流、一次发布同时替换 20% 实例时还够用。生产系统通常要问 N+1、N+2、单 AZ 丢失、单依赖变慢、热点租户突增时是否还能满足 SLO。负载均衡可以在失效时把流量转移走，但转移后的剩余容量必须提前规划出来。

自动扩缩容也不能代替容量规划。HPA、Cluster Autoscaler、云厂商自动扩容都有采样周期、决策周期、调度时间、镜像拉取时间、启动时间和预热时间。突发在一分钟内打过来，而扩容可能几分钟后才真正接流量。容量规划要给这段滞后留 headroom，也要对已知峰值提前预扩容。否则系统在扩容生效前已经进入超时和重试循环。

容量规划还要看不可被 LB 平衡的资源。比如数据库主库写入、全局锁、单分区热点、消息队列分区、对象存储限额、第三方 API 配额、内核 conntrack、端口数、TLS 握手 CPU、日志系统吞吐、限流器自身容量。这些资源可能不是每个服务实例各自独立拥有的，LB 把请求分散到更多实例，并不会增加这些共享瓶颈的容量，反而可能制造更多连接和更多下游并发。

一个靠谱的容量模型至少要包含几类输入：稳态流量和峰值流量、请求类型占比、每类请求资源成本、目标延迟和错误率、实例规格、单实例稳定吞吐、依赖容量、连接数上限、重试预算、发布和故障时的冗余比例、扩容冷启动时间。然后用压测和线上观测校准模型，而不是一次压测后永久相信某个 QPS 数字。

负载均衡在容量规划里仍然很重要，但它是执行层和保护层。它可以让容量利用更均匀，可以把慢实例摘掉，可以在区域之间转移流量，可以用权重表达不同实例规格，可以用 breaker 防止局部过载，可以用 slow start 保护新实例，可以用成本感知调度提高有效吞吐。但这些能力的前提是“可用容量总体存在”。如果总容量不够，LB 应该尽早配合限流、降级和告警，而不是继续把请求硬塞给后端。

放到 AegisMesh 上，adaptive picker、EWMA、in-flight、breaker、retry budget 都是在尽量用好已有容量，减少局部慢节点和重试放大。容量规划则要回答另一组问题：当前服务实例数是否支撑目标 SLO；单实例在不同方法 mix 下的稳定容量是多少；控制面下发的权重是否匹配真实规格；某个 AZ 丢失后剩余实例是否够；扩容后 warmup 需要多久；依赖瓶颈是否比应用实例更早到顶。这些问题不在 picker 的局部决策里解决。

所以这题的结论是：负载均衡不能代替容量规划，因为它只能分配和保护已有容量，不能创造总容量，也不能消除共享瓶颈、扩容滞后和失效冗余需求。容量规划给系统确定边界，负载均衡在边界内提高利用率和稳定性；一旦超过边界，正确动作是扩容、降级、限流、削峰或减少请求成本，而不是期待更复杂的 LB 算法救场。

如果面试官继续深挖，可以按这条路线走：先区分“容量总量”和“容量分配”；再用排队论解释超过服务率后队列必然增长；再说明 QPS 不等于成本；然后讲 HPA 和新实例 warmup 的滞后；最后落到项目里说明 AegisMesh 的负载均衡策略是保护已有容量，而容量规划要由压测、SLO、依赖预算和故障冗余共同决定。
